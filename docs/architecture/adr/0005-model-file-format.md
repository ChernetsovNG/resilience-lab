# ADR 0005. Файлы модели в JSON по JSON Schema

Дата: 2026-10-27  
Статус: принято  
Связано: [целевая архитектура](../2026-10-27-target-architecture.md), решение A1; [исследование формата файлов](../../research/2026-10-27-model-file-format.md) (#47); [ADR 0001](0001-block-type-catalog.md), [ADR 0002](0002-model-pipeline.md), [ADR 0003](0003-workspace.md).

## Контекст

Модели, раскладка, эксперименты и библиотека блоков хранятся как файлы, удобные для git (драйвер D3). Основной писатель файлов — UI через рабочую область на backend (ADR 0003); файлы также правят вручную люди и агенты. Исследование #47 сравнило JSON и YAML на примере `retry-storm.json`, настоящих диффах и прототипах на JVM и в браузере.

YAML компактнее и сохраняет комментарии, но только при точечной правке дерева документа: обычная запись из объекта их теряет. Каждая команда редактора тогда должна работать с исходным деревом. JSON записывается из типизированных данных без такой модели, напрямую проверяется JSON Schema и в измерениях разбирается в десятки раз быстрее.

## Решение

1. Модели, раскладка, эксперименты и библиотечные блоки хранятся в JSON (RFC 8259) и проверяются по JSON Schema Draft 2020-12.
2. Это отдельные документы с явными суффиксами: `*.model.json`, `*.layout.json`, `*.experiment.json`, `*.block.json`. Суффикс позволяет редакторам и CLI сопоставлять файл со схемой.
3. Ссылки между документами — относительные пути (`modelRef`, `layoutRef`, `libraryRef`), которые разрешает компилятор модели (ADR 0002). URL и выход за пределы рабочей области запрещены.
4. Запись детерминированная и выполняется одним писателем в ядре, общим для backend и CLI: UTF-8, LF, отступ два пробела, перевод строки в конце файла, фиксированный порядок полей; порядок массивов сохраняется.
5. Пояснения хранятся в полях `description` и `notes` документов и блоков; UI показывает их в инспекторе и подсказках.
6. Величины записываются строками с единицами (`"60ms"`, `"120/s"`) по ADR 0001; варианты эксперимента — переопределения по путям по ADR 0002, а не копии модели.
7. Загрузчик до проверки схемы отвергает повторяющиеся ключи и неконечные числа.
8. Структурная схема генерируется из сериализуемых типов файлов через kotlinx-schema и дополняется метаданными каталога типов (ADR 0001): единицами, диапазонами, значениями по умолчанию и описаниями. Версии схем хранятся в репозитории; CI проверяет, что повторная генерация не даёт диффа. JVM и браузер проверяют один набор допустимых и недопустимых файлов.
9. Необязательное поле, допускающее null, объявляется со значением по умолчанию `null`; обязательное передаётся явно. Настройки кодека и генератора схемы согласованы общими примерами.
10. `seed` — целое от 0 до 2⁵³−1. Ядро разворачивает seed в начальное состояние генератора KSL, где больше 32 бит на компонент не используется, поэтому большой диапазон не нужен; в этом диапазоне seed читается без потерь и в Kotlin, и в браузере.

## Последствия

- Формат сценария MVP (один JSON на эксперимент) заменяется без миграции; новые документы начинают нумерацию версий схемы с `schemaVersion: 1` ([дизайн этапа 1](../../superpowers/specs/2026-10-27-stage-1-design.md), §1). Миграции между версиями нового формата — решение A11.
- Пропадает различие форматирования между backend и web: пишет только ядро.
- Импорт многовариантного `examples/retry-storm.json`, который сейчас отвергает web, решается новым форматом эксперимента; это касается демо-сценариев (#19).
- Комментарии прямо рядом с параметром в файле невозможны; пояснения живут в данных.
- Хеш модели для манифеста результата (решение A7) требует отдельно определённой нормализации без раскладки.

## Рассмотренные варианты

- **YAML с сохранением комментариев.** Компактнее и удобнее для ручной правки, но каждая команда редактора должна точечно менять дерево документа, а запись из объекта теряет комментарии; разбор заметно медленнее.
- **TOML, KDL, JSONC.** Не дают преимуществ для требований задачи и требуют отдельных парсеров или нового отображения типов.
