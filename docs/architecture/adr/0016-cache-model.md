# ADR 0016. Модель кэша: внешний блок, точная модель по ключам, cache-aside

Дата: 2026-11-01\
Статус: принято\
Связано: [дизайн третьего среза этапа 2](../../superpowers/specs/2026-11-01-stage-2-slice-3-design.md), §3.1, §3.2, §5; [ADR 0006](0006-random-streams-by-block-path.md); [ADR 0011](0011-type-outputs.md); [ADR 0013](0013-slot-pools.md); [ADR 0015](0015-resilience-policies.md); [продуктовое видение](../../product/2026-10-27-product-vision.md), §6 и §7

## Контекст

Продолжение сквозного кейса — сервис, время ответа которого определяет кэш. Пользователь спрашивает, что будет при холодном старте, одновременном истечении TTL, лавине промахов на популярный ключ и недоступности кэша, и что из защит поможет. Ответы зависят от динамики: какие именно ключи в кэше, когда они истекают, кто одновременно идёт за одним ключом в источник. Кэши в реальных системах бывают локальными (в процессе сервиса) и внешними (Redis, Memcached), читаются по схеме cache-aside (сервис сам идёт в источник при промахе) или read-through (кэш сам загружает значение).

## Решение

1. **Внешний кэш — отдельный блок `cache`.** У него набор слотов (ADR 0013) для обработки операций, своя сеть, свои отказы и выходы. Сервис обращается к нему по обычной связи `call`, на которой действуют таймауты, повторы, пул и политики (ADR 0015).
2. **Точная модель по ключам.** Хранилище кэша содержит записи с временем истечения и порядком обращений; ёмкость ограничена числом записей, вытеснение — LRU. Ключи берутся из пространств ключей кэша: число ключей и перекос популярности по Зипфу. Попадание определяется по наличию и сроку записи в момент обработки операции.
3. **Cache-aside в сценарии сервиса.** Шаг «чтение через кэш» делает GET; при промахе выполняет вложенные шаги и затем SET. При ошибке кэша по умолчанию выполняются вложенные шаги без SET. Обычный шаг вызова к кэшу не допускается: у операции кэша всегда есть ключ.
4. **Объединение промахов — состояние вызывающего экземпляра сервиса**, по правилу ADR 0015 п. 2: так устроены библиотеки single-flight в процессе. Ожидающие получают результат загрузки или её причину отказа.
5. **Разброс TTL и начальное наполнение** — параметры кэша; сброс содержимого — отказ эксперимента в момент времени.
6. **Случайные числа** — ключ шага по пути шага, разброс TTL по пути кэша (ADR 0006). Состояние хранилища сбрасывается в начале каждого повторения; артефакт побайтно повторяется при любом числе потоков.

## Последствия

- Память прогона пропорциональна числу записей кэша; оценка стоимости и линтер учитывают `capacity` и число ключей.
- Локальный кэш, read-through, кластер с распределением ключей, отдача устаревшего значения, пакетное чтение и запись с инвалидацией добавляются новыми параметрами и шагами поверх того же хранилища, без пересмотра этого решения.
- Кэш в срезе — один экземпляр; группа реплик кэша без модели распределения ключей была бы неверной, поэтому компилятор её отвергает.

## Рассмотренные варианты

- **Аналитическая доля попаданий** (приближение Че по Зипфу, TTL и ёмкости). Дёшево, но теряет динамику: одновременное истечение, лавину промахов на конкретный ключ и объединение промахов моделировать не на чем.
- **Гибрид:** точно для горячих ключей, формулой для хвоста. Подходит для очень больших пространств ключей; сложнее и пока не нужен — оставлен точкой расширения.
- **Локальный кэш как параметр вызова** вместо блока. Проще, но не моделирует недоступность кэша и нагрузку на него — два из главных вопросов кейса.
- **Read-through как основная схема.** Короче сценарий сервиса, но редок для Redis-кэшей и скрывает, что при падении кэша вся нагрузка идёт в источник из сервиса.
