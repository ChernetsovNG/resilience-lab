# ADR 0010. Контракт API — REST по сгенерированной OpenAPI

Дата: 2026-10-27  
Статус: принято  
Связано: [целевая архитектура](../2026-10-27-target-architecture.md), решение A8; [дизайн этапа 1](../../superpowers/specs/2026-10-27-stage-1-design.md), §5.2; [ADR 0003](0003-workspace.md), [ADR 0009](0009-execution.md).

## Контекст

Нынешние типы API продублированы вручную в `web/src/api/types.ts`. Этап 1 заменяет API целиком: каталог, документы рабочей области, проверка, задания, прогоны. Сервер и web разрабатывают разные исполнители параллельно, и им нужен общий проверяемый контракт.

## Решение

1. API — REST с базовым путём `/api/v1`; новое API заменяет нынешнее, старые ручки удаляются.
2. Спецификация OpenAPI генерируется из кода сервера и хранится в репозитории; CI проверяет, что повторная генерация не даёт диффа.
3. TypeScript-типы web генерируются из этой спецификации; ручное дублирование типов API уходит.
4. Ход заданий UI получает опросом `GET /jobs/{id}`; потоковая передача (SSE, #23) — отдельное решение позже.
5. Ошибки имеют единый формат с кодом и диагностикой (дизайн этапа 1, §4.1); конфликт версий документа — 409 при несовпадении `If-Match`.
6. Инструменты генерации выбираются в плане реализации с проверкой совместимости со Spring Boot и TypeScript проекта.

## Последствия

- Изменение API — это изменение кода сервера и закоммиченной спецификации в одном PR; web видит его через сгенерированные типы.
- Исполнитель web может начинать работу по спецификации до готовности реализации ручек.

## Рассмотренные варианты

- **Спецификация пишется вручную раньше кода.** Контракт появляется раньше, но вручную поддерживаемый документ расходится с кодом без отдельной проверки.
- **Ручные типы в web, как сейчас.** Без генерации контракт держится только на дисциплине исполнителей.
