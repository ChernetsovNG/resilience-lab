# ADR 0013. Набор слотов — общая модель ограниченного ресурса

Дата: 2026-10-30\
Статус: принято\
Связано: [дизайн первого среза этапа 2](../../superpowers/specs/2026-10-30-stage-2-slice-1-design.md), §5; [ADR 0007](0007-simulation-engine-ksl.md); [ADR 0011](0011-type-outputs.md); [ADR 0012](0012-call-graph-and-replica-groups.md); [исследование возможностей KSL](../../research/2026-10-27-ksl-capabilities.md); [продуктовое видение](../../product/2026-10-27-product-vision.md), §5.6

## Контекст

В этапе 1 ограниченный ресурс один — обработчики сервиса с FIFO-очередью (`FifoResourceWithQ`, `BoundedRequestQ`). Сквозной кейс этапа 2 добавляет ещё несколько: пул соединений в сервисе (Hikari), клиентские подключения и серверный пул внешнего пулера (pgbouncer), предел соединений БД. В жизни они стоят одновременно, и задача модели — показать, где именно копится ожидание. Видение (§5.6) описывает ресурсы, удерживаемые на фазах запроса, как основу неблокирующих сервисов и шаблонов стеков.

## Решение

1. **Одна деталь движка — набор слотов.** Параметры: ёмкость, вместимость очереди ожидания (0 — без очереди), предел ожидания (без предела — ждать сколько угодно). Порядок очереди — FIFO.
2. **Исходы занятия слота:** занят сразу; занят после ожидания; отвергнут, потому что очередь полна; отвергнут, потому что ожидание превысило предел. Отказы по двум причинам считаются раздельно.
3. **Удержание и освобождение** задаёт владелец: обработчик держится весь сценарий сервиса, соединение пула на связи — на время попытки до ответа или таймаута, серверное соединение пулера — на время запроса в БД.
4. **Изменяемая ёмкость.** Ёмкость может меняться во время прогона (отказ «потеря ёмкости»): занятые слоты сверх новой ёмкости доделывают работу, новые занятия видят меньшую ёмкость, возврат ёмкости обслуживает очередь.
5. **Одинаковые метрики** у всех наборов: интеграл занятости, интеграл длины очереди, ёмкость по времени, число и суммарное время ожиданий, отказы по причинам. Выходы описываются в каталоге по ADR 0011 одинаково для всех мест использования.
6. **Насыщение набора** — обработчики заняты и есть очередь (как в этапе 1) или пул исчерпан: все слоты заняты и есть ожидающие. Правило вывода одно для всех наборов.
7. **Места использования в срезе:** обработчики сервиса и БД (`maxConnections`), пул на связи, клиентские подключения пулера (без очереди) и серверный пул пулера (с пределом ожидания).
8. **Реализация** — поверх ресурсов и очередей KSL (ADR 0007): существующие `FifoResourceWithQ` и `BoundedRequestQ` обобщаются; предел ожидания — событие таймаута, которое снимает запрос из очереди, если его ещё не обслужили. При одновременном освобождении слота и истечении ожидания приоритет у обслуживания, как у ответа перед таймаутом в этапе 1.

## Последствия

- Обработчики сервиса этапа 1 становятся частным случаем набора; поведение и сводка на примерах этапа 1 сохраняются (проверка ADR 0012).
- Новые ограниченные ресурсы — лимит одновременных запросов, пул потоков неблокирующего сервиса, CPU — добавляются как новые места использования набора, без новой логики очереди.
- Модель «фазы и ресурсы» видения §5.6 строится как шаги сценария, удерживающие наборы слотов; это не требует пересмотра этого решения.
- Приоритеты, вытеснение и очереди не по FIFO этим решением не вводятся.

## Рассмотренные варианты

- **Отдельная реализация для каждого вида пула.** Проще начать, но логика очереди, ожидания и метрик расходится между местами, а вывод о насыщении приходится писать для каждого вида.
- **Пул только как свойство связи.** Покрывает Hikari, но не внешний пулер и не общий пул на несколько вызовов.
- **Сразу общий язык «фазы и ресурсы» для всех блоков.** Максимально общо, но требует проектирования языка до появления реальных шаблонов стеков; набор слотов — его будущий строительный блок.
