# ADR 0017. Fan-out: повтор и параллельные ветки в сценарии сервиса

Дата: 2026-11-01\
Статус: принято\
Связано: [дизайн третьего среза этапа 2](../../superpowers/specs/2026-11-01-stage-2-slice-3-design.md), §3.3, §5; [ADR 0012](0012-call-graph-and-replica-groups.md); [ADR 0016](0016-cache-model.md); [исследование S1](../../research/2026-10-27-ksl-capabilities.md)

## Контекст

Сценарий сервиса (ADR 0012) — упорядоченный список шагов «обработка» и «вызов», которые выполняются строго друг за другом. Реальные сервисы делают много вызовов на запрос двумя способами: в цикле по элементам (N+1) и одновременно — к одной зависимости N раз или к нескольким разным зависимостям, ожидая все ответы. Хвост задержки такого запроса определяется худшей из параллельных веток. KSL поддерживает ожидание всех дочерних процессов (S1). Чтобы сравнивать число параллельных обращений в вариантах и сеткой, кратность должна быть параметром, а не только структурой.

## Решение

1. **Повтор у любого шага:** `repeat: { count, mode }`, `sequential` — цикл, `parallel` — N одновременных копий шага с ожиданием всех.
2. **Шаг `parallel`** — ветки, каждая — список шагов; ветки запускаются одновременно, шаг ждёт все.
3. **Синхронность сохраняется:** обработчик сервиса удерживается до конца шага; таймауты, повторы и политики действуют на каждый вызов внутри ветки; дедлайн запроса общий.
4. **Исход:** если хотя бы одна ветка или копия неуспешна, шаг неуспешен с причиной первой неуспешной ветки в порядке веток (для повтора — в порядке копий). Остальные ветки дорабатывают, их работа учитывается в метриках.
5. **Адресация шагов.** У шага может быть `id`, уникальный в сценарии сервиса. `repeat.count` шага с `id` — параметр: вариант может его переопределить, сетка — перебрать. Остальная структура сценария на странице варианта только для просмотра (дизайн этапа 1, §6).
6. **Вид в интерфейсе** — компактная структура шагов со сворачиванием и sequence-диаграмма с фрагментами `par`, `loop`, `alt`, `opt` (дизайн среза 3, §7); формат глубину вложенности не ограничивает.

## Последствия

- Обход путей, оценка стоимости и линтер учитывают кратность повторов и вложенные шаги.
- Hedged requests, ожидание первых k из N, отмена оставшихся веток при первом отказе, пакетное чтение добавляются новыми полями шага `parallel` или `repeat` без пересмотра этого решения.
- Шаги с `id` становятся адресуемыми и для будущих параметров шага (например, своего таймаута ветки).

## Рассмотренные варианты

- **Только шаг `parallel` с явными ветками.** Для 20 одинаковых чтений пришлось бы рисовать 20 веток; кратность нельзя перебирать.
- **Отмена оставшихся веток при первом отказе (fail-fast).** Встречается, но чаще код ждёт все результаты; отмена меняет учёт брошенной работы и оставлена точкой расширения.
- **Кратность как структура без `id`.** Проще формат, но сравнение N в вариантах и сеткой невозможно — а это главный вопрос про хвост fan-out.
