# ADR 0003. Рабочая область на backend за абстракцией хранилища

Дата: 2026-10-27  
Статус: принято  
Связано: [целевая архитектура](../2026-10-27-target-architecture.md), решение A6, драйверы D1, D3, D6.

## Контекст

Сейчас UI импортирует и экспортирует отдельные JSON-файлы через браузер. Видение требует нескольких документов со ссылками: модели, библиотечные блоки, раскладка, эксперименты, результаты. Продукт работает локально, общий сервис команды появится позже (D1); локально модели и результаты хранятся как файлы, удобные для git (D3).

Решение человека (2026-10-27): рабочая область живёт на backend, причём хранилище не обязательно файловое — возможны база данных или другое хранилище.

## Решение

1. UI работает с рабочей областью — моделями, библиотечными блоками, экспериментами и результатами — через backend; CLI обращается к ней через ядро напрямую.
2. Ядро обращается к хранению через абстракцию рабочей области: перечислить, прочитать, записать и удалить документ по относительному пути, узнать о внешних изменениях. API и UI не знают, где лежат данные, и не видят абсолютных путей.
3. Первая реализация — каталог файлов, обычно git-репозиторий (D3). Локальный сервер открывает каталог, указанный при запуске (в Docker — подключённый каталог), отслеживает внешние изменения и предлагает UI перечитать документ; автоматического слияния нет.
4. Другие реализации — база данных, объектное хранилище, git-сервер — добавляются для общего сервиса команды (D1) без изменения API и UI.
5. Результаты прогонов — артефакты в той же рабочей области; в файловой реализации — каталог `.results/`, по умолчанию в `.gitignore`.
6. Встроенная библиотека шаблонов поставляется с приложением и версионируется вместе с ним (D6); собственные библиотеки лежат в рабочей области.
7. Импорт и экспорт через браузер остаются для обмена отдельными документами.

## Последствия

- Docker Compose подключает каталог рабочей области; README и `AGENTS.md` описывают запуск с каталогом.
- Нужны отслеживание внешних изменений и обработка конфликта «несохранённая правка в UI + изменение на диске».
- Раскладка каталога — имена и расширения файлов — зависит от формата (решение A1, исследование #47).
- Общему сервису понадобятся авторизация и изоляция рабочих областей; это вне текущего объёма.

## Рассмотренные варианты

- **File System Access API в браузере.** Backend остаётся только вычислителем, но работает лишь в Chromium, а CLI всё равно читает файлы отдельно.
- **Только импорт и экспорт, как в MVP.** Проще всего, но с несколькими документами и библиотекой неудобно, а работа с git остаётся ручной.
