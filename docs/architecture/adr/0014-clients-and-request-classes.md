# ADR 0014. Несколько клиентов и классы запросов

Дата: 2026-10-31\
Статус: принято\
Связано: [дизайн второго среза этапа 2](../../superpowers/specs/2026-10-31-stage-2-slice-2-design.md), §3.1, §3.2, §5, §6; [ADR 0006](0006-random-streams-by-block-path.md); [ADR 0011](0011-type-outputs.md); [ADR 0012](0012-call-graph-and-replica-groups.md); [продуктовое видение](../../product/2026-10-27-product-vision.md), §7

## Контекст

В этапе 1 и первом срезе этапа 2 в модели ровно один клиент: компилятор требует один блок `client` и одну связь `request`, IR хранит одиночные клиента и вход, движок создаёт один генератор прибытий, а сводка держит метрики входа полями верхнего уровня. Запрос несёт только время прибытия, дедлайн и признак когорты измерения. Реальные системы принимают трафик с нескольких входов, а в одном сервисе разные виды запросов идут разными путями: чтение и запись, статус заказа и оформление. Нагрузка видов меняется во времени независимо: пик оформлений при ровных запросах статуса.

## Решение

1. **Несколько клиентов.** В модели один или несколько блоков `client`. У каждого клиента ровно одна связь `request` к своему входу; несколько клиентов могут ходить в один вход. Вход не получает вызовов `call`; каждый блок достижим хотя бы из одного входа.
2. **Атрибуты запроса.** Исходный запрос несёт клиента, класс, время прибытия и дедлайн своего клиента. Все попытки и вложенные вызовы наследуют клиента и класс.
3. **Класс и его нагрузка.** Клиент задаёт либо один профиль `load`, либо список классов `classes`, у каждого — свой кусочно-линейный профиль того же формата. Нагрузка клиента — сумма профилей его классов. Клиент без `classes` шлёт запросы класса `default`. Идентификатор класса общий для модели: разные клиенты могут слать один класс.
4. **Прибытия.** Генератор прибытий — на каждый класс каждого клиента. Поток случайных чисел генератора определяется путём клиента и идентификатором класса (ADR 0006): добавление клиента или класса не меняет прибытия остальных.
5. **Пути по классам.** Шаг сценария и маршрут `route` могут ограничиться множеством классов; без ограничения действуют для всех. Если для класса запроса у маршрутизатора нет допустимого маршрута, компилятор отвергает модель, если это видно из графа; иначе попытка получает отказ «нет маршрута».
6. **Когорта и знаменатели.** Когорта измерения — исходные запросы всех клиентов, пришедшие в измеряемом интервале. Знаменатель усиления у связей — исходные запросы всех клиентов.
7. **Метрики входа** считаются по каждому клиенту, по каждому классу и в сумме. Сумма совпадает с прежними метриками входа одиночного клиента; на моделях с одним клиентом без классов числа сводки не меняются.

## Последствия

- Меняются форматы модели и артефакта: новые версии схем, документы и прогоны прежних версий отвергаются понятной ошибкой о версии.
- IR, обход путей, оценка стоимости и линтер работают от множества входов; дедлайн проверяется для каждого клиента.
- Ключи запросов для кэша (срез 3), дедлайн и приоритет по классу, ограничения по клиенту или классу добавляются как новые атрибуты запроса и параметры классов без пересмотра этого решения.
- Перебор нагрузки множителем (#311) должен определить, к чему применяется множитель: ко всей модели, клиенту или классу.

## Рассмотренные варианты

- **Доли классов при общем профиле клиента.** Проще задать, но смесь постоянна во времени: пик одного вида запросов без роста другого не описать.
- **Только несколько клиентов, без классов.** Разные входы описываются, но путь внутри общего сервиса не может зависеть от вида запроса: нужен атрибут, который запрос несёт через граф.
- **Класс задаёт входной сервис, а не клиент.** Отрывает нагрузку от источника и не даёт двум клиентам слать один вид запросов с разными профилями.
