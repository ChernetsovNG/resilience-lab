# ADR 0009. Исполнение: задания, задачи и общий пул

Дата: 2026-10-27  
Статус: принято  
Связано: [целевая архитектура](../2026-10-27-target-architecture.md), решение A5, драйверы D1, D2, D5; [ADR 0006](0006-random-streams-by-block-path.md), [ADR 0007](0007-simulation-engine-ksl.md), [ADR 0008](0008-run-results.md).

## Контекст

В MVP сервер выполняет каждый эксперимент целиком в одном потоке пула размером с число ядер (`SimulationExecutorConfig`), повторения внутри идут последовательно; параллельны только разные эксперименты. Задания живут в памяти процесса. CLI считает в своём процессе отдельным кодом. Исследование KSL (#46) показало, что независимые повторения в отдельных моделях хорошо параллелятся: восемь потоков дали ускорение 3,2×.

## Термины

- **Задание** — один запуск, начатый кнопкой «Запустить» в UI или командой CLI: сравнение вариантов, серия, 2D-карта.
- **Задача** — единица расчёта внутри задания: вариант × точка сетки × повторение; каждая задача — свежая модель KSL.

## Решение

1. Исполнение — модуль ядра, общий для backend и CLI (D5): одинаковые разбиение на задачи, проверка бюджетов, артефакты и коды результата.
2. Локально расчёт идёт в процессе backend; CLI вызывает тот же модуль в своём процессе. Отдельный рабочий процесс JVM добавляется, если сервер начнёт падать от нехватки памяти в расчёте, или для общего сервиса.
3. Все задания делят один пул потоков; по умолчанию — число ядер минус один, значение настраивается. Планировщик чередует задачи разных заданий, поэтому короткий прогон не ждёт длинную сетку. Число одновременных заданий не ограничено; ограничены число потоков и бюджет памяти — сколько моделей KSL одновременно помещается в памяти по оценке до запуска.
4. Результат не зависит от числа потоков и порядка выполнения задач (ADR 0006).
5. Готовая задача сразу пишет свою часть артефакта (ADR 0008). API отдаёт ход выполнения — число готовых задач из общего числа; позже — потоком через SSE (#23).
6. Жизненный цикл задания: в очереди → выполняется → завершено, ошибка или отменено. Отмена кооперативная: начатые задачи останавливаются в ближайшей точке проверки, артефакт помечается незаконченным. Лимит реального времени на задачу (`maxRealTimeSeconds`) сохраняется.
7. Незаконченное задание можно досчитать: при той же версии приложения и тех же хешах модели и эксперимента пересчитываются только задачи, чьих частей нет или чьи контрольные суммы не совпадают. Иначе задание считается заново.
8. Перед запуском показывается оценка стоимости — формула из исследования #46 и объём из исследования #48; для крупной модели — по короткому пробному прогону.
9. Модуль исполнения скрыт за интерфейсом очереди заданий; для общего сервиса (D1) его можно заменить распределёнными воркерами без изменения API.

## Последствия

- `ExperimentJobManager` и пул сервера переходят на модуль ядра; CLI — на тот же модуль.
- Повторения перестают идти последовательно внутри одной модели KSL: каждая задача создаёт свою модель, а потоки задаются по ADR 0006 и исследованию S4 (#55).
- Нужны планировщик с чередованием задач, учёт бюджета памяти и проверка полноты артефакта при досчёте.
- Нехватка памяти внутри расчёта может уронить сервер; до перехода на отдельный процесс защита — оценка до запуска и бюджеты.

## Рассмотренные варианты

- **Отдельный процесс JVM на задание.** Изоляция памяти и свой `-Xmx`, но запуск процесса и обмен с ним усложняют локальную версию без подтверждённой необходимости.
- **Одно активное задание, остальные в очереди.** Проще, но короткий прогон ждёт долгую сетку.
- **Только перезапуск незаконченного задания целиком.** Проще, но долгие сетки теряют уже посчитанную работу, хотя расчёт детерминирован.
