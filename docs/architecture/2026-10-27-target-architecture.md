# Resilience Lab — целевая архитектура

Дата: 2026-10-27  
Статус: черновик — драйверы согласованы, решения в работе  
Связанные документы: [продуктовое видение](../product/2026-10-27-product-vision.md), [проектный дизайн MVP](../superpowers/specs/2026-10-25-resilience-lab-design.md).

Документ фиксирует архитектурные драйверы и решения под всё продуктовое видение — этапы 1–5. Проектный дизайн MVP остаётся источником модельной семантики линейной цепочки; часть решений, которые он оставил реализующему разработчику (§7, §12), принимается здесь. Дизайн каждого этапа пишется внутри этой архитектуры.

## 1. Драйверы

### 1.1. Решения человека (2026-10-27)

| № | Драйвер | Следствие для архитектуры |
|---|---|---|
| D1 | Продукт работает локально у одного инженера; общий сервис команды — позже, и архитектура не должна его запрещать | Сейчас без учётных записей и общей БД; API и хранение не завязаны на абсолютные локальные пути и единственного пользователя |
| D2 | Размер модели заранее не ограничен: большие системы собираются из шаблонных составных блоков | UI рисует текущий уровень иерархии; результаты агрегируются по уровням и подгружаются по запросу; стоимость расчёта известна из измеренной модели производительности, и пользователь видит её до запуска |
| D3 | Модели, библиотека блоков и результаты — файлы, удобные для git | Модель как код: читаемый формат, стабильный порядок, малошумные диффы; результаты — артефакты прогона |
| D4 | Новые примитивы добавляет только ядро | Примитив — код на Kotlin с тестами; пользователи собирают своё из примитивов и составных блоков; API плагинов нет |
| D5 | CLI умеет всё, что UI | Расчёт, эксперименты и проверка требований доступны из CLI, с кодом возврата для CI системы пользователя |
| D6 | Воспроизводимость в пределах версии — точная | Те же версия, модель и seed дают те же числа; результат фиксирует версии приложения и движка и хеш модели; старые сценарии мигрируют автоматически |

Стоимость расчёта растёт примерно как интенсивность × длительность × средняя длина пути запроса × число попыток × число повторений × число точек сетки. Предел размера задаёт не формат, а производительность движка, поэтому её нужно измерить (исследование S1).

### 1.2. Из продуктового видения

- Статистическая честность: независимые повторения и неопределённость в результатах (проектный дизайн §4, §9).
- Доверие и объяснимость: допущения рядом с результатом, вывод с причиной, калибровка, воспроизведение инцидентов (видение §4, §5.3).
- Интерактивность: каркас UI без прокрутки, результаты на схеме, воспроизведение прогона (видение §5.5).
- Расширяемость предметной модели: фазы и ресурсы, иерархия, асинхронность и брокеры добавляются без замены ядра (видение §5.6, §5.7, §7).
- Разработка агентами-исполнителями: модули с явными контрактами, чтобы задачи шли параллельно и не пересекались.

## 2. Карта архитектурных решений

«Гипотеза» — предложение для обсуждения; «открыто» — нужны варианты или исследование; «решено» — согласовано и оформлено в ADR в `docs/architecture/adr/`.

| № | Решение | Гипотеза | Статус |
|---|---|---|---|
| A1 | Формат модели в файлах | YAML или JSON по JSON Schema. Модель, раскладка и эксперимент — разные файлы, чтобы перемещение блоков не шумело в диффе семантики. Библиотека — каталог файлов составных блоков | открыто |
| A2 | Система типов блоков | Каталог примитивов в ядре: параметры с типами, единицами, диапазонами, значениями по умолчанию и описанием. Из каталога строятся JSON Schema, формы UI, валидация и справка CLI | гипотеза |
| A3 | Конвейер модели | Разбор файлов → разрешение библиотечных ссылок → применение масок → валидация → разворачивание иерархии → исполняемый граф → адаптер движка. Один «компилятор модели» в ядре для CLI и сервера | гипотеза |
| A4 | Движок | KSL остаётся, если покрывает ресурсы на фазах, fan-out с ожиданием ответов, трассу событий и нужную производительность | открыто, S1 |
| A5 | Исполнение | Локальный backend и CLI вызывают одно ядро; независимые повторения и точки сетки считаются параллельно; задания живут в памяти процесса, результаты пишутся в каталог артефактов | гипотеза |
| A6 | Рабочая область | Backend открывает каталог — обычно git-репозиторий — и читает и пишет файлы модели напрямую; импорт и экспорт через браузер остаются | открыто |
| A7 | Модель результатов | Артефакт прогона — каталог: манифест (версии, seed, хеш модели), сводка, временные ряды по узлам в компактном формате, выборочная трасса событий. UI грузит сводку сразу, ряды — по уровню и по запросу | гипотеза, S3 |
| A8 | Контракт API | REST по OpenAPI с генерацией TypeScript-клиента; прогресс и потоковые данные — SSE (#23) | гипотеза |
| A9 | Фронтенд | Документ модели — единственный источник состояния; правки — команды с undo/redo; навигация по уровням; формы из каталога типов; библиотека холста — по итогам #4 | гипотеза |
| A10 | Требования и проверки в CI | Требования, например «p99 < 300 ms при отказе реплики», — часть файла эксперимента; CLI возвращает ненулевой код при нарушении с учётом доверительных интервалов | открыто |
| A11 | Версии и миграции | Версия схемы в каждом файле, цепочка миграций в ядре, команда CLI для миграции рабочей области | гипотеза |
| A12 | Интеграции | Импортёры — отдельные команды, которые пишут файлы модели и наблюдений нейтрального формата; приватные адаптеры живут вне репозитория | гипотеза |
| A13 | Поставка | Локально — Docker Compose и CLI; рассмотреть один процесс, в котором Spring Boot отдаёт и API, и собранный UI | открыто |

## 3. Исследования

| № | Вопрос | Результат |
|---|---|---|
| S1 | Покрывает ли KSL ресурсы, удерживаемые на фазах запроса, fan-out с ожиданием ответов, неблокирующую модель и запись трассы событий. Сколько событий в секунду и памяти уходит на модели из 50, 500 и 5000 листовых блоков; как ускоряют расчёт параллельные повторения | Документ с прототипом и цифрами; решение A4 |
| S2 | YAML или JSON при записи из UI: стабильный порядок, комментарии, шум в диффах; генерация JSON Schema из типов Kotlin | Решение A1 |
| S3 | Объём временных рядов и трасс для больших моделей; формат хранения и скорость чтения в браузере | Решение A7 |

## 4. Порядок работы

1. Обсудить и оформить в ADR решения A1, A2, A3 и A6 — они задают формат и границы модулей; затем остальные.
2. Параллельно отдать исполнителям S1: от него зависит A4.
3. После решений A1–A7 написать дизайн этапа 1 (#5) внутри этой архитектуры и уточнить issues этапа 1.
