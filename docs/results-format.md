# Формат артефакта прогона

Манифест и сводка используют `schemaVersion: 16`. Индекс и части рядов используют версию 7, итоги повторения — версию 6. Версия модели — 6, эксперимента — 2, раскладки — 1. Старые артефакты не мигрируются: их нужно получить новым запуском. Каталог прогонов пропускает неподдерживаемые версии; явное чтение через API возвращает HTTP 400 с кодом `RUN_VERSION_UNSUPPORTED`.

Основания: [дизайн этапа 1](superpowers/specs/2026-10-27-stage-1-design.md), [дизайн второго среза этапа 2](superpowers/specs/2026-10-31-stage-2-slice-2-design.md), [ADR 0014](architecture/adr/0014-clients-and-request-classes.md), [ADR 0015](architecture/adr/0015-resilience-policies.md), [ADR 0008](architecture/adr/0008-run-results.md), [ADR 0009](architecture/adr/0009-execution.md), [профиль S5](research/2026-10-28-latency-sketch.md).

## Удаление прогонов

`DELETE /api/v1/runs/{id}` удаляет каталог прогона со всеми файлами и вложенными каталогами; успех — 204, отсутствующий или уже удалённый прогон — 404 `RUN_NOT_FOUND`. Удаление не зависит от версии манифеста. Задание Run или Resume в очереди либо в работе блокирует удаление своего прогона и прогонов того же эксперимента: 409 `RUN_ACTIVE` с идентификатором задания и путём эксперимента. Запрошенная отмена сохраняет блокировку до остановки расчёта и записи файлов.

`GET /api/v1/runs` перечисляет читаемые прогоны и их `sizeBytes`. `GET /api/v1/runs/obsolete` перечисляет каталоги с неподдерживаемым, повреждённым или отсутствующим манифестом, включая пустые каталоги; активные прогоны исключаются. Каждая запись содержит `id`, `directory` относительно рабочей области, `sizeBytes` и `experiment`, если это поле удалось прочитать из манифеста, иначе `null`. Размер — сумма размеров обычных файлов, без перехода по символьным ссылкам.

`DELETE /api/v1/runs?directory=.results/<эксперимент>/<прогон>` позволяет удалить конкретный каталог, в том числе без читаемого манифеста. Допустим только полный путь каталога прогона внутри `.results/`: корень, группа эксперимента и пути с `..` отклоняются с 400 `RUN_PATH`. Каталоги, указанные через символьные ссылки, не удаляются; ссылки внутри удаляемого каталога удаляются без перехода к их целям.

Команды удаления модели и эксперимента в UI сначала удаляют прогоны, затем документы. Принадлежность определяется полным путём `experiment` в манифесте. Разные эксперименты, в том числе с одинаковым именем файла в разных каталогах, получают отдельные группы в `.results/`. Устаревшие прогоны с читаемым полем `experiment` также входят в удаление. Каталоги без этого поля доступны отдельной командой «Очистить устаревшие прогоны…».

В списках прогонов и заданий пути экспериментов приводятся к пути внутри физической рабочей области: `.` и `..`, а также существующие внутренние символьные ссылки обозначают тот же эксперимент. Исходные манифесты сохраняются без изменений. Перед первым удалением прогона UI сверяет версии всех подтверждённых документов; при изменении документа требуется новое подтверждение.

## Файлы

Группа эксперимента — SHA-256 UTF-8-байтов его канонического пути относительно рабочей области, 64 строчные шестнадцатеричные цифры. Путь содержит имя файла вместе с `.experiment.json`; разделители — `/`. Перед вычислением хеша разрешаются `.` и `..` и внутренние символьные ссылки. Имя документа может содержать кириллицу, пробелы и другие символы, допустимые в рабочей области: в каталог результатов попадает только хеш. Идентификатор прогона остаётся одним сегментом по шаблону `[A-Za-z0-9][A-Za-z0-9._-]*`.

Это правило действует начиная с формата артефакта 15. Прогоны прежних версий не мигрируются и требуют нового запуска.

Пример структуры каталога:

```text
.results/<хеш пути эксперимента>/<прогон>/
  manifest.json
  summary.json
  series/<вариант>/<точка>/rep-0/
    replication.json.gz
    index.json
    part-0.json.gz
    part-1.json.gz
```

Итоги повторения и части рядов хранятся в JSON+gzip без меток времени в заголовке gzip. При тех же данных байты совпадают при любом числе потоков. `manifest.json`, `summary.json` и `index.json` остаются несжатым JSON. Сжатие итогов не меняет их JSON-содержимое и версию внутренней схемы.

Нумерация повторений, окон и частей начинается с нуля. Точки нумеруются как `p0`, `p1` и далее: первая ось `grid` внешняя, вторая меняется быстрее. Без сетки есть одна точка `p0` с пустыми координатами. Отсутствующий `grid` и пустой список означают отсутствие сетки.

`manifest.json` перечисляет относительные пути всех файлов артефакта и SHA-256 их сохранённых байтов. Для gzip это хеш сжатых байтов. Сам манифест в список не входит; он записывается последним. В нём также находятся версии приложения и KSL, версия назначения потоков, seed, варианты, число повторений и метаданные рядов `series`: интервалы в миллисекундах, шаг окна, профиль скетча, версия библиотеки, единица времени, способы учёта событий. Поле `series.points` содержит упорядоченный список `{ id, coordinates }`, где `coordinates` сопоставляет пути параметров их значениям в исходных единицах документа. Хеш модели для артефакта вычисляется после упорядочивания связей: сначала `request`, затем вызовы в топологическом порядке IR. Перестановка связей в документе не меняет манифест; версии исходных файлов для проверки перед запуском остаются строгими. Порядок сериализации строк рядов по id сохранён для побайтной совместимости с артефактами этапа 1.

Манифест и сводка содержат верхнеуровневое поле `grid`: список осей `{ path, values }` в порядке документа. Порядок `values`, повторы и исходные единицы сохраняются. Канонический писатель сортирует ключи словаря `coordinates`, поэтому порядок осей нужно брать из `grid`, а не из ключей координат. Без сетки `grid` равен `[]`. Оси доступны сразу после загрузки сводки, до чтения манифеста и рядов.

Поле `documents` содержит SHA-256 канонической записи модели и эксперимента: ключи объектов упорядочены кодеком документов. Поэтому перестановка блоков и форматирование JSON не меняют артефакт. Проверка принятых в очередь документов по `expectedVersions` и HTTP `If-Match` по-прежнему использует хеш исходных байтов документа.

`complete: true` означает, что все задачи и сводка записаны. При ошибке или отмене сохраняются готовые файлы задач, сводка не создаётся, манифест получает `complete: false`. У незаконченной задачи могут остаться части без индекса или итогов повторения. Такие файлы перечислены в неполном манифесте. Исключение отмены остаётся `CancellationException`. Вызов с уже установленным признаком отмены не создаёт артефакт.

Начатая запись файла части завершается в отдельном потоке, который отмена не прерывает. Исполнитель ждёт завершения активных задач перед публикацией неполного манифеста. Незаписанный буфер текущей части незавершённой задачи может быть потерян при отмене; готовые каталоги задач сохраняются целиком. После последней проверки отмены окончательная запись сводки и манифеста завершается целиком; прерывание вызывающего потока восстанавливается после записи.

`Lab.resume` повторно использует задачу только при совпадении SHA-256 `replication.json.gz`, `index.json` и всех gzip-частей с манифестом, а также SHA-256 частей с индексом. Форматы итогов и индекса проверяются. Если файл отсутствует, повреждён или в каталоге задачи есть лишний файл, вся задача пересчитывается с исходным номером повторения. Посторонние файлы прогона и прежняя сводка удаляются перед расчётом. Новая сводка собирается из сохранённых и пересчитанных итогов; манифест атомарно заменяется и не включает собственный хеш в `parts`. При тех же версиях и документах итоговые байты совпадают с непрерывным прогоном.

## Окна и статистики

Выходы, показанные в Timeline, инспекторе и наложении, описаны в каталоге типов по [ADR 0011](architecture/adr/0011-type-outputs.md). Их вычисления ссылаются на поля этого формата: например, интенсивность отправленных попыток использует `sentAttempts` и `durationMs`, загрузка — `slotPools.handlers.busyIntegralMs` и `slotPools.handlers.capacityIntegralMs`. Идентификатор производного выхода задаётся отдельно от имён исходных полей. Каталог не меняет сохранённые ряды и сводку, их версии, когорты и правила слияния статистик.

`execution.window` задаётся длительностью с единицами, например `"100ms"`. По умолчанию шаг равен `measurement / 100`. Окна покрывают `[0, warmup + measurement)` от нуля; последнее может быть короче. Поля `startMs` и `durationMs` каждого окна задают его фактический интервал. Событие на границе попадает в следующее окно; событие в конце интервала и последующий run-out в ряды не входят.

Каждое окно каждой строки в `nodes`, `classes` и `connections` содержит `clientOriginalArrivals`, включая строки групп, экземпляров и копий связей. Это сумма исходных запросов всех клиентов, пришедших в тот же интервал `[startMs, startMs + durationMs)`. Поле использует время события: учитывает прогрев и не включает run-out, как остальные ряды. Для одного окна во всех строках записано одно и то же число, в том числе ноль при отсутствии прибытий. Число относится ко всем клиентам, даже в строке отдельного клиента или класса.

`clientOriginalArrivals` служит знаменателем усиления прямо в загруженной части. Для его получения не требуются дополнительные части `INSTANCE` со строками клиентов. Это сохраняет загрузку экземпляров только после выбора пользователя, предусмотренную T4.4 (#290).

Ряды учитывают события по времени их возникновения, включая прогрев. Для каждого клиента сохраняется строка в `nodes` с его идентификатором из модели. Фиксированного идентификатора `client` больше нет. Массив `classes` содержит строки `{ id, windows }` по классам запросов; один класс объединяет запросы всех клиентов с этим классом. Клиент без `classes` использует класс `default`.

В окнах клиента и класса сохраняются `originalArrivals`, `successes`, `degraded`, `failures`, `failuresByReason` и `latency`. Завершение, причина отказа и задержка относятся к окну завершения запроса. `degraded` входит в `successes`. Карты `failuresByReason` есть также в окнах сервисов и связей; они используют общий список кодов ниже.

Для сервиса сохраняются:

- `offeredAttempts` — попытки, дошедшие до сервиса после сетевой задержки запроса;
- `admittedAttempts` — попытки, принятые в очередь или сразу занявшие обработчик;
- `successes` и `failures` — успешные и неуспешные завершения принятой работы до сетевой задержки ответа;
- `timeouts` и `retries` — таймауты ожидания downstream-вызова и повторы, отнесённые к вызывающему сервису;
- `slotPools.handlers` — статистики набора обработчиков;
- `latency` — время пребывания принятой попытки в сервисе: очередь и удержание обработчика. Отказы очереди увеличивают `slotPools.handlers.queueFullCount` и не входят в скетч задержки сервиса. Нулевая задержка принятой попытки остаётся допустимым наблюдением.

Все владельцы ограниченных ресурсов записывают `slotPools: Map<String, SlotPoolMetrics>` в строках рядов, итогах повторения и `totals` сводки. Сервис и БД владеют набором `handlers`; связь с пулом — набором `pool`; пулер — наборами `clientConnections` и `serverConnections`. У клиента, маршрутизатора и связи без пула наборов нет: карта пуста. Несуществующий набор не добавляется с нулевыми значениями.

Каждый существующий набор всегда содержит семь полей, включая нулевые:

| Поле | Тип | Смысл и единица |
|---|---|---|
| `busyIntegralMs` | Double | Интеграл числа занятых слотов, слот × ms |
| `queueIntegralMs` | Double | Интеграл числа ожидающих, запрос × ms |
| `capacityIntegralMs` | Double | Интеграл фактической доступной ёмкости, слот × ms |
| `waitCount` | Long | Число завершённых ожиданий, включая истечение предела |
| `totalWaitMs` | Double | Суммарная полная длительность завершённых ожиданий, ms |
| `queueFullCount` | Long | Число отказов из-за полной очереди |
| `waitLimitCount` | Long | Число отказов по пределу ожидания |

Немедленное занятие слота и отказ по полной очереди не дают наблюдения ожидания. В окнах счётчики и полные длительности ожиданий относятся к моменту завершения ожидания. В итогах повторения они относятся к когорте запросов измерения, включая завершения во время run-out. Интегралы окон покрывают фактический интервал окна; интегралы итогов — фиксированный интервал измерения, включая присутствующую работу прогрева и исключая run-out. Потеря и возврат ёмкости учитываются в `capacityIntegralMs`, в том числе при нулевой ёмкости и занятости выше уменьшенной ёмкости. Сводка суммирует каждое из семи полей по повторениям.

Загрузка набора — `busyIntegralMs / capacityIntegralMs`, средняя очередь — `queueIntegralMs / durationMs` в окне и `/ measurementMs` в итогах. Среднее ожидание — `totalWaitMs / waitCount`. Неположительный знаменатель означает отсутствие значения. Общий построитель выходов каталога задаёт эти вычисления и отказы по обеим причинам через операции ADR 0011; идентификаторы существующих выходов сохраняются.

Блок `database` записывается в строки узлов и словари `services` итогов. Его `handlers` в карте `slotPools` — соединения БД с исходной ёмкостью `maxConnections`. `offeredAttempts` — поступившие запросы, `admittedAttempts` — принятые в очередь или на выполнение. Оконные `successes` и `failures` считают результаты выполненных запросов; `latency` включает ожидание и выполнение, а отклонённые запросы в скетч не входят. Поля `timeouts` и `retries` БД равны нулю: ожиданием и повторами управляет вызывающий сервис. В итогах `failures` считает ошибки выполнения запросов. Когорта, учёт run-out и правило насыщения обработчиков сохраняются.

Для каждой связи `call` сохраняются собственные окна. Связь `request` рядов не имеет. Идентификатор связи берётся из модели; он не заменяется парой узлов. Поля окна:

- `sentAttempts` — отправленные попытки, включая повторы; событие относится к окну отправки до сетевой задержки запроса;
- `retries` — повторные попытки из `sentAttempts`, в том же окне отправки;
- `succeeded` и `failed` — ответы, полученные вызывающим до срабатывания timeout, в окне получения. Неуспешный ответ включает отказ очереди, локальный отказ и исчерпание deadline ниже по цепочке;
- `timeouts` — попытки, ожидание которых прервано по timeout, в окне обрыва. Сюда входит timeout, укороченный оставшимся общим deadline;
- `orphaned` — из прерванных попыток те, чей вызываемый процесс ещё не завершился в момент обрыва, в том же окне;
- `inFlightIntegralMs` — интеграл числа отправленных попыток, для которых вызывающий ещё ждёт ответ и timeout не сработал;
- `orphanedIntegralMs` — интеграл числа брошенных попыток от timeout до завершения вызываемого процесса, включая обратную сетевую задержку;
- `backoffIntegralMs` — интеграл числа вызывающих, ожидающих backoff. В это время обработчик вызывающего остаётся занят;
- `latency` — длительность попытки от отправки до получения ответа, включая обе сетевые задержки. Скетч содержит только попытки из `succeeded` и `failed`, поэтому его `count` равен их сумме.

Средние числа ожидаемых, брошенных попыток и вызывающих в backoff вычисляются делением соответствующего интеграла на `durationMs`. Состояние переносится через границы окон; событие завершения на границе прекращает интеграл в предыдущем окне и относится к следующему.

Попытки, брошенные по timeout, в `latency` не входят: они учтены в `timeouts`, а их длительность ожидания задана сработавшим timeout. Поэтому среднее и квантили `latency` описывают только попытки с полученным ответом, а не все отправленные попытки. Профиль скетча, `count` и `sumMs` такие же, как у узлов.

Каждое поле `latency` содержит `count`, `sumMs` и `sketch`. Среднее — `sumMs / count`, пустая выборка не имеет среднего. Сумма копится в порядке событий; значения из представителей корзин для среднего не используются.

Связь `call` с параметром `pool` записывает семь общих полей в `slotPools.pool`. У связи без пула, включая `route`, карта пуста. `slotPools.pool.waitLimitCount` считает отказы по `acquireTimeout`; завершение ожидания по общему дедлайну увеличивает `waitCount` и `totalWaitMs`, но не этот счётчик.

Ожидание пула предшествует отправке: отказ получения не увеличивает `sentAttempts`, `failed` или `timeouts` и не создаёт наблюдения `latency`. Он расходует попытку и подчиняется политике повторов; `retries` связи по-прежнему считает только отправленные повторные попытки. `latency` связи отсчитывается от отправки, без ожидания пула. Соединение освобождается при ответе или таймауте попытки; последующая работа без ожидающего ответа не удерживает соединение.

У выходов маршрутизатора `route` сохраняются строки связей того же формата. `sentAttempts` считает выборы этого выхода, включая повторы входящего вызова. В окнах это события отправки до сетевой задержки; в `replication.json.gz` и `summary.json` — попытки когорты измерения, включая run-out. Поля исходов и занятости следуют жизненному циклу входящего `call` до выбранного сервиса; вложенные маршрутизаторы получают по одной записи на каждом выбранном выходе. Собственного backoff у `route` нет. Каталог выхода `route.sentAttempts` показывает число попыток в окне, а в сводке — среднее число на повторение (`totals.sentAttempts / replications`). У `router` нет очереди, обработчиков и отдельной строки узла: распределение видно по его выходам. Структура артефакта и её версия сохраняются.

Группа реплик записывает строки экземпляров `<сервис>#1…#N`, копий исходящих вызовов `<связь>#1…#N` и выходов маршрутизатора `<сервис>#lb#1…#N`. При `replicas = 1` строк групп нет, имена остаются прежними. Для входной группы выход `route` учитывает исходный запрос и его исход до полного завершения работы, включая работу после дедлайна.

## Группы реплик

Сервис с `replicas > 1` и каждая скопированная исходящая связь получают строку группы с идентификатором исходного элемента документа, например `order-service` и `order-to-db`. Выходы сгенерированного маршрутизатора остаются отдельными связями. `groups` в индексе рядов, итогах повторения и агрегате сводки перечисляет состав: `{ id, kind, instances }`, где `kind` — `NODE` или `CONNECTION`, а каждый элемент `instances` содержит `id` и целый номер `replica`. Группы упорядочены по виду и идентификатору, экземпляры — по номеру.

В строке группы `clientOriginalArrivals` равен тому же общему числу прибытий за окно, что у каждого экземпляра и копии связи. При свёртке реплик значение копируется в строку группы один раз и не суммируется по экземплярам. Число реплик не увеличивает знаменатель.

В каждом окне остальные счётчики и интегралы группы равны суммам по экземплярам. `latency` получается слиянием их скетчей. `startMs`, `durationMs` и `measurementMs` относятся к общему интервалу: число реплик не увеличивает его длительность. Загрузка группы — суммарный интеграл занятости, делённый на суммарный интеграл ёмкости; средняя очередь — суммарный интеграл очереди, делённый на длительность одного интервала.

Каждый набор слотов группы дополнительно содержит `replicaExtrema`:

- `minUtilization` и `maxUtilization` — минимум и максимум загрузки экземпляров от их собственной ёмкости;
- `maxUtilizationReplica` — номер экземпляра с максимальной загрузкой;
- `minMeanQueueLength` и `maxMeanQueueLength` — минимум и максимум средней очереди экземпляров;
- `maxMeanQueueLengthReplica` — номер экземпляра с максимальной средней очередью.

При равных максимумах выбирается меньший номер. Экземпляр с нулевым интегралом ёмкости не участвует в сравнении загрузки; если ни у одного экземпляра нет положительного интеграла ёмкости, значения загрузки и номер худшего по загрузке не определены. Очередь при этом учитывается. В обычных строках `replicaExtrema` отсутствует.

В итогах повторения группы находятся рядом с экземплярами в `services` и `connections`. `ServiceMetrics.latency` теперь содержит время пребывания принятых попыток измеряемой когорты, включая завершение работы после измерения; отказы очереди в него не входят. Оно собирается и у отдельных сервисов, чтобы получить слитый скетч группы. `queueDurationsMs` группы пуст: гистограммы отдельных очередей не задают распределение их суммы во времени.

В сводке группы и экземпляры используют те же словари. У группы узлов и каждого её экземпляра `pooledLatency` объединяет наблюдения всех повторений; группа дополнительно объединяет наблюдения всех экземпляров. p99 берётся из соответствующего объединённого скетча. У группы `meanLatencyMs` описывает средние задержки по независимым повторениям. `slotPoolSummaries` содержит для каждого набора `MetricSummary` полей `utilization`, `meanQueueLength` и `meanWaitMs`; повторения без знаменателя или наблюдений не участвуют в соответствующей статистике. Число наблюдений и доверительные границы сохраняют общий смысл `MetricSummary`. Экстремумы в `totals.slotPools` пересчитываются по полным интегралам каждого экземпляра за все повторения. Максимумы отдельных окон для этого не используются.

Выходы каталога описывают сводные значения группы, p99 слитого скетча и минимальные и максимальные значения экземпляров операциями ADR 0011. Схема показывает сводное значение группы и худшую реплику, инспектор — сортируемую таблицу реплик. В Ответе и Map реплики раскрываются внутри группы; выбор реплики не меняет документы и историю Undo. Timeline показывает сводную линию группы и полосу min–max загрузки или средней очереди из `replicaExtrema` того же окна. Отдельные реплики добавляются по выбору и используют показатели своей группы; до выбора их части `INSTANCE` не загружаются. Правило насыщения читает только строки экземпляров; строки групп в нём не участвуют.

## Строка пулера

У `pooler` собственная строка в `nodes`, с идентификатором блока. Общие поля `offeredAttempts`, `admittedAttempts`, `successes`, `failures` и `latency` описывают поступившие и принятые попытки, ответы и время пребывания принятой попытки. Отказы по пределу клиентских подключений не входят в `admittedAttempts`, `failures` и скетч. Принятая попытка, не дождавшаяся серверного соединения, входит в `failures` и скетч. Время пребывания заканчивается при освобождении клиентского подключения после ответа, включая обратную сетевую задержку входящего `call`.

Ресурсы записываются в `slotPools.clientConnections` и `slotPools.serverConnections` с одинаковыми семью полями. У клиентских подключений нет очереди: её интеграл, число ожиданий и отказы по пределу ожидания равны нулю; немедленный отказ учитывается в `clientConnections.queueFullCount`. Серверное ожидание и его истечение записываются в `serverConnections`. Общие `timeouts` и `retries` окон учитывают исходящий вызов пулера, как у сервиса. Насыщение остаётся только для набора `handlers`; распространение правила на наборы пулера относится к T3.3.

В итогах повторения `result.poolers` сопоставляет идентификатору `PoolerMetrics`; строки пулера в `result.services` нет. `measurementMs` задаёт длительность измерения. В сводке `aggregate.poolers` содержит `pooledLatency` и `totals`: счётчики, каждое поле наборов слотов и `measurementMs` суммируются по повторениям. Скетчи времени пребывания объединяются до вычисления квантилей; среднее берётся из общей суммы и числа наблюдений. Пустой словарь пулеров в файлах итогов и сводки может быть опущен; API выдаёт `{}`.

Из формата удалены прежние поля наборов и объект `WindowMetrics.pooler`. Таблица задаёт соответствие полей; для итогов сводки пути начинаются с `totals.`:

| Прежнее поле | Поле внутри `slotPools` |
|---|---|
| `busyHandlerTimeMs`, `queueLengthIntegralMs`, `queueRejections` | `handlers.busyIntegralMs`, `handlers.queueIntegralMs`, `handlers.queueFullCount` |
| `handlers`, `handlerCapacityTimeMs` | `handlers.capacityIntegralMs` интегрирует фактическую ёмкость; число слотов задаётся снимком модели |
| `poolBusyTimeMs`, `poolCapacityTimeMs`, `poolQueueIntegralMs` | `pool.busyIntegralMs`, `pool.capacityIntegralMs`, `pool.queueIntegralMs` |
| `poolWaitCount`, `poolWaitTimeMs`, `poolAcquireTimeouts` | `pool.waitCount`, `pool.totalWaitMs`, `pool.waitLimitCount` |
| `busyClientConnectionTimeMs`, `clientConnectionCapacityTimeMs`, `clientConnectionRejections` | `clientConnections.busyIntegralMs`, `clientConnections.capacityIntegralMs`, `clientConnections.queueFullCount` |
| `busyServerConnectionTimeMs`, `serverConnectionCapacityTimeMs`, `serverQueueLengthIntegralMs` | `serverConnections.busyIntegralMs`, `serverConnections.capacityIntegralMs`, `serverConnections.queueIntegralMs` |
| `serverWaitCount`, `serverWaitTimeMs`, `waitTimeouts` | `serverConnections.waitCount`, `serverConnections.totalWaitMs`, `serverConnections.waitLimitCount` |

Прежние `maxClientConnections` и `poolSize` остаются параметрами снимка модели. При постоянной ёмкости новый интеграл равен числу слотов, умноженному на длительность окна или измерения; при потере ёмкости используется её фактическая история. Счётчики попыток, исходов, таймаутов, повторов, скетчи задержек и `queueDurationsMs` итогов сервиса сохраняются.

## Части и индекс

`part-<k>.json.gz` содержит сжатый UTF-8 JSON `SeriesPart`: `schemaVersion: 7`, `kind`, `profile`, полуоткрытый диапазон индексов `fromWindow`/`untilWindow` и массивы `nodes`, `connections` и `classes`. Элемент каждого массива содержит `id` и `windows` в порядке времени. Массивы могут быть пустыми; у частей `GROUP` строк классов нет. `kind: INSTANCE` содержит строки отдельных элементов, `kind: GROUP` — строки групп. Они не смешиваются в одной части; правило нарезки применяется к каждому виду независимо.

Последовательные полные окна накапливаются в текущей части, пока добавление следующего окна не превысит общий лимит узлов, связей и классов. Тогда часть записывается, а новое окно начинает следующую. Узлы, связи и классы упорядочены лексикографически внутри своего массива. Если одно окно всех элементов не помещается, оно делится на группы: сначала узлы, затем связи и классы. Каждая такая группа покрывает одно окно; возможна часть только со связями или классами. Каждая пара «элемент × окно», включая пустые окна, присутствует ровно один раз в своём массиве. Узел, связь и класс с одинаковым `id` остаются разными элементами. Для исходного `retry-storm` все 100 окон повторения помещаются в одну часть.

Лимит части до сжатия — 4 МиБ, то есть 4 194 304 байта. Писатель считает фактически закодированные байты всех трёх массивов вместе с заголовком и разделителями. Если не помещается один узел, одна связь или один класс в одном окне, расчёт завершается ошибкой с видом элемента, его идентификатором, окном и лимитом. Данные не обрезаются. Gzip не содержит времени запуска, поэтому одинаковые данные дают одинаковые байты.

`index.json` содержит `schemaVersion: 7`, `endMs`, `windowMs`, список `parts` и состав групп `groups`. Для каждой части указаны `file`, `kind`, списки идентификаторов `nodes`, `connections` и `classes`, `fromWindow`, `untilWindow`, `uncompressedBytes` и `sha256`. Пустые списки `connections` и `classes` в ссылке могут быть опущены и читаются как `[]`. Временного ряда знаменателя в индексе нет: `clientOriginalArrivals` хранится в `windows` каждой строки части. Индекс записывается после всех окон задачи.

Сборщик передаёт закрытое окно писателю и освобождает его объекты. Для каждого вида строк писатель хранит одну текущую часть с уже закодированными окнами; её байты освобождаются после записи. В памяти остаются текущее окно, текущие части, статистики повторения и метаданные индекса; все оконные скетчи прогона одновременно не хранятся.

## Скетч задержки

Профиль `ddsketch-bitwise6-rational-v1` использует `sketches-java:0.8.3`: `BitwiseLinearlyInterpolatedMapping(6)` с представителем `lowerBound * 129/128`. Оконные накопители используют `SparseStore`, итоги и слияние — `UnboundedSizeDenseStore`.

Поле `sketch` — массив `[zeroCount, index, count, ...]`. Индексы строго возрастают, ненулевые counts положительны, целые записываются десятичными числами без экспоненты. Пустое распределение — `[0]`. Профиль указан один раз на часть или файл итогов. Ноль хранится точно.

До изменения скетча проверяются конечность и диапазон значения, будущие count и диапазон корзин. Разрешены ноль и положительные значения в `[2^-1021, 2^1023)` ms; общий count не больше `9 007 199 254 740 990`, занятый диапазон — не больше 2048 адресов корзин. Ошибка оставляет принимающий скетч неизменным. Сливаются только одинаковые профиль и единица. Целые counts дают одинаковые корзины при любом допустимом порядке слияния.

Квантили сохраняют соглашение KSL: позиция `p * (n + 1)`, крайние позиции ограничены первым и последним представителем, между соседними порядковыми статистиками применяется `a + fraction * (b - a)`. Пустой скетч возвращает `null`. Относительная погрешность квантилей для проверенного диапазона задержек `0.001–60000 ms`, включая точные нули, не больше 0,78125 % с учётом округления binary64. Для крайне малых результатов интерполяции относительная гарантия не заявляется; ограничение описано в S5.

## Причины отказов и поля политик

`failuresByReason` использует общий список кодов для входа, сервисов и связей:

| Код | Причина |
|---|---|
| `error` | Ошибка обработки: `failureRate` шага или блока либо отказ вида «ошибки» |
| `unavailable` | Быстрый отказ до приёма работы или передачи |
| `timeout` | Истёк таймаут попытки вызова |
| `deadline` | Истёк общий дедлайн исходного запроса |
| `queueFull` | Полна очередь обработчиков, соединений БД или клиентских подключений пулера |
| `waitLimit` | Превышен предел ожидания слота пула на связи или серверного соединения пулера |
| `circuitOpen` | Разомкнут circuit breaker; заполняется в T2.1 |
| `rateLimited` | Запрос отклонён ограничением интенсивности; заполняется в T2.2 |
| `noRoute` | У маршрутизатора нет маршрута для класса запроса |
| `noReadyTarget` | Нет готовых экземпляров по health-check; заполняется в T2.2 |

В итогах сервисов и связей `failuresByReason` считает причины неуспешных попыток. Карта сервиса включает завершившиеся попытки и отказы до приёма работы; карта связи — также таймауты и истечение ожидания пула до отправки. Существующие `ServiceTotals.failures`, оконное `failures` сервиса и `failed` связи сохраняют свои определения, поэтому их значения не обязаны совпадать с суммой этой карты.

Вызов, исчерпавший попытки, сохраняет причину последней выполненной попытки. Неуспешный шаг передаёт исходную причину через вызывающие сервисы до входа. Отдельной причины «ошибка ниже по цепочке» нет. Если истёк дедлайн клиента, вход получает `deadline`. Отказ бюджета повторов не заменяет причину последней попытки: он учитывается отдельным счётчиком `retriesDenied`. Заглушка в T2.1 превратит неуспешный вызов в успешный, увеличит `fallbacks` связи и отметит успешный исходный запрос в `degraded`.

В итогах повторения и окнах рядов заранее присутствуют поля политик. В T3.1 они записываются нулями; задачи T2 заполняют их без новой смены версий артефакта и рядов:

| Где | Поля |
|---|---|
| Связь `call` | `circuitOpenMs`, `circuitRejections`, `retriesDenied`, `fallbacks` |
| Вход: клиент, класс, итог | `degraded` |
| Сервис и экземпляр | `rateLimited`, `probes`, `probeFailures`, `notReadyMs` |
| Экземпляр — цель маршрутизатора | `ejections`, `ejectedMs` |

`circuitOpenMs` — сумма времени в открытом состоянии по вызывающим экземплярам; `notReadyMs` — время неготовности; `ejectedMs` — время вывода экземпляра всеми ведущими на него маршрутизаторами. Длительности заданы в миллисекундах, остальные поля — счётчики. Отдельные выходы каталога по причинам отказа не добавляются: потребители читают `failuresByReason`.

## Итоги повторения и сводка

`replication.json.gz` содержит `schemaVersion: 6`, `profile`, `unit` и `result`. В `result` находятся `entries` и словари `services`, `connections` и `poolers` с итогами сервисов, связей и пулеров. Списков отдельных задержек или времён поступления в файле нет.

`result.entries` содержит три поля:

- `total` — метрики всех исходных запросов;
- `clients` — словарь «идентификатор клиента → метрики его исходных запросов»;
- `classes` — словарь «идентификатор класса → метрики запросов этого класса от всех клиентов».

Каждый элемент имеет одну структуру `EntryMetrics`: `originalArrivals`, `successes`, `degraded`, `failures`, `failuresByReason`, `allLatency`, `successfulLatency` и `failedLatency`. Поле `degraded` считает успешные запросы, на пути которых сработала хотя бы одна заглушка; оно входит в `successes`. Карта `failuresByReason` содержит ненулевые числа отказов по причинам, их сумма равна `failures`. Пустая карта означает отсутствие отказов. Счётчики `total` равны сумме клиентов и сумме классов; скетчи задержек `total` получаются слиянием соответствующих скетчей.

Поля входа верхнего уровня `result.originalArrivals`, `successes`, `failures`, `allLatency`, `successfulLatency` и `failedLatency` заменены на `result.entries.total.*`. Знаменатель усиления — `entries.total.originalArrivals`, то есть исходные запросы всех клиентов. Выходы каталога отдельного клиента используют его `entries.clients.<id>`.

В `aggregate.entries` сводки та же структура `total` / `clients` / `classes`. Каждый элемент `AggregateEntryMetrics` содержит `pooledLatency`, `successRate`, `p95LatencyMs`, `p99LatencyMs`, `degradedRate` и `failuresByReason`. Прежние четыре поля входа верхнего уровня `AggregateMetrics` перенесены в `entries.total`. `pooledLatency` объединяет задержки соответствующих исходных запросов. Остальные поля — статистики независимых повторений: `successRate` и `degradedRate` описывают доли `successes / originalArrivals` и `degraded / originalArrivals`, `failuresByReason` сопоставляет причине `MetricSummary` доли отказов от исходных запросов этого элемента. Причина, встречавшаяся хотя бы в одном повторении, получает нулевое наблюдение в других повторениях с исходными запросами. Повторения без исходных запросов не участвуют в статистиках долей; без определённых наблюдений метрика равна `null`.

Когорта итогов состоит из запросов, пришедших за измеряемый интервал `[warmup, warmup + measurement)`. Их исходы, задержки и вызванные ими попытки учитываются и во время run-out. Занятость и очередь сервисов интегрируются только по измеряемому интервалу, включая работу, которая поступила во время прогрева. В итогах сервисов `failures` сохраняет прежний смысл локальных отказов; оконное поле `failures` считает все неуспешные завершения принятой работы. Счётчики и задержки связей используют ту же когорту с run-out. Интегралы связей, как занятость и очередь сервисов, охватывают только `[warmup, warmup + measurement)` и учитывают всю присутствующую работу, включая поступившую при прогреве.

В `AggregateMetrics.connections` каждой связи соответствует `AggregateConnectionMetrics`. Поле `totals` содержит суммы `sentAttempts`, `retries`, `succeeded`, `failed`, `timeouts`, `orphaned`, трёх интегралов, `measurementMs` и шести полей пула по повторениям. `pooledLatency` строится слиянием скетчей ответов; среднее вычисляется из общей суммы и числа ответов. При отсутствии ответов оно равно `null`. Поле `timeoutRate` — `MetricSummary` доли `timeouts / sentAttempts` по повторениям с отправленными попытками; без таких повторений оно равно `null`. Поле `meanInFlight` — `MetricSummary` средних `inFlightIntegralMs / measurementMs` по повторениям. Это средние по независимым повторениям, а не отношения объединённых сумм; их 95 % доверительные интервалы Стьюдента не обрезаются. При одном наблюдении границы интервала равны `null`.

На полностью завершённом повторении сумма `succeeded + failed + timeouts` равна `sentAttempts`; отправленные попытки связи равны `offeredAttempts` вызываемого. В линейной цепочке без пула `timeouts` и `retries` связи совпадают с одноимёнными полями вызывающего узла; прежний смысл полей узлов сохранён. `orphaned` не превышает `timeouts`. К концу run-out все попытки и orphaned work завершены.

`summary.json` собирается в порядке «вариант, точка, повторение»: метрики — только из записанных `replication.json.gz`, вывод насыщения — из `index.json` и перечисленных в нём gzip-частей тех же задач. У варианта находятся `id`, `label`, `replications` и список `points`; каждая точка содержит `id`, `coordinates`, `aggregate`, `saturation` и `headroom`. Прежнее поле `aggregate` варианта удалено. Summary в web показывает строку на каждую пару «вариант, точка».

CLI `run`, `resume` и `summary` печатают `вариант/точка [путь=значение, ...]: entry total: success ...`, сохраняя единицы; без координат квадратные скобки отсутствуют. Если клиентов больше одного, следуют строки `entry client <id>`; если классов больше одного — строки `entry class <id>`. Клиенты и классы упорядочены по идентификатору. В каждой строке входа показаны доля успешных, p95, p99 и до трёх причин отказа: по убыванию средней доли от исходных запросов этой строки, при равенстве — по коду причины. При отсутствии отказов список причин опущен. Вывод о насыщении, запас по ёмкости и строки сервисов и групп сохраняют прежний смысл; `--replicas` раскрывает экземпляры групп.

Пул задержек строится слиянием скетчей, его среднее — из counts и сумм; в `LatencyDistribution.statistics` сохраняются достаточные статистики. `AggregateServiceMetrics.totals` содержит числители, знаменатели и интегралы сервисов.

В `saturation.rule` записаны `minimumDurationMs` (100 ms), `utilizationThreshold` (0,95), `meanQueueLengthThreshold` (0,5) и `rejectionsThreshold` (0). Правило применяется отдельно к каждому набору слотов каждого экземпляра узла и связи. Строки групп в проверке не участвуют.

Ветка очереди требует непрерывного интервала не короче `minimumDurationMs`, в каждом окне которого загрузка набора не ниже порога, а средняя очередь больше порога. Загрузка равна `busyIntegralMs / capacityIntegralMs`, средняя очередь — `queueIntegralMs / durationMs`; нулевой знаменатель не подтверждает эту ветку. Укороченное последнее окно учитывается по фактической длительности. Набор `clientConnections` пулера не имеет очереди и проверяется только по отказам.

Ветка переполнения использует сумму `queueFullCount + waitLimitCount`. Она требует серии подряд окон, в каждом из которых число отказов больше порога, а от начала первого до начала последнего прошло не меньше `minimumDurationMs`. Длительность последнего окна не добавляется: одно окно с отказами не подтверждает насыщение при любом шаге рядов. Ветки проверяются независимо; начало относится к первому окну той подтверждённой серии, которая началась раньше.

Список `replications` упорядочен по номеру повторения. Его элемент содержит `replication` и `degradationPath`; каждая запись пути содержит `node` (идентификатор узла или связи), `slotPool`, `startMs` и `label`. Путь упорядочен по моменту начала, затем от вызываемого к вызывающему по топологическому порядку графа. Пул связи расположен между вызывающим и вызываемым; пулы связей с одним источником имеют одинаковую позицию. При одинаковой позиции используются идентификатор элемента и имя набора. Пустой путь означает отсутствие насыщения; такое повторение учитывается только в `withoutSaturation`.

Для каждой пары «элемент и набор», бывшей первой, `firstNodes` содержит `node`, `slotPool`, `label`, `replicationCount`, `medianStartMs`, `minStartMs` и `maxStartMs`. Медиана чётного числа моментов — среднее двух центральных, min/max задают разброс. Записи упорядочены по убыванию `replicationCount`, затем по идентификатору элемента и имени набора. Повторения без насыщения не участвуют в статистике моментов.

`label` содержит `code`, `message` и `args` из контракта `CoreMessage`. Web переводит название при показе, CLI использует английский `message`. Название различает обработчики сервиса, соединения БД, пул соединений на связи, клиентские подключения и серверные соединения пулера. Для пула связи аргументы содержат `from` и `to`, для остальных наборов — `element`.

`headroom` содержит два независимых максимума по объединённым данным точки: `utilization` и `meanQueueLength`. Каждый максимум содержит `node`, `slotPool`, `value` и `label`. Ядро сравнивает наборы всех экземпляров сервисов, БД, пулеров и связей; строки групп исключаются. Для загрузки используется отношение сумм интегралов занятости и ёмкости, для средней очереди — отношение суммы интегралов очереди к сумме длительностей измерения. При равенстве значений выбирается меньший идентификатор элемента, затем имя набора. Если определённых значений нет, максимум равен `null`. Web и CLI показывают сохранённые значения без повторного поиска максимумов; Findings показывает запас, когда насыщения не было ни в одном повторении.

Статистики независимых повторений остаются отдельными: `MetricSummary` для success rate, p95/p99 и amplification. Обязательное поле `count` содержит число наблюдений, по которым рассчитаны `mean`, `stdDev` и доверительный интервал. Это число повторений с определённым значением метрики: например, `timeoutRate` исключает повторения без отправленных попыток. При отсутствии наблюдений сама метрика равна `null`; при `count: 1` поля `stdDev`, `ci95Low` и `ci95High` равны `null`. Поля `mean`, `min` и `max` описывают наблюдаемые значения метрики; границы `ci95Low`/`ci95High` могут выходить за `[0,1]`, в том числе для `successRate`. Их доверительные границы Стьюдента не обрезаются до физического диапазона. Погрешность скетча и неопределённость между повторениями имеют разный смысл; pooled p99 не вычисляется усреднением p99 повторений.
