# Формат артефакта прогона

Манифест и сводка используют `schemaVersion: 9`. Индекс и части рядов используют версию 4, итоги повторения — версию 3. Версия модели — 5; версии эксперимента и раскладки — 1. Старые артефакты не мигрируются: их нужно получить новым запуском. Каталог прогонов пропускает неподдерживаемые версии; явное чтение через API возвращает HTTP 400 с кодом `RUN_VERSION_UNSUPPORTED`.

Основания: [дизайн этапа 1](superpowers/specs/2026-10-27-stage-1-design.md), [ADR 0008](architecture/adr/0008-run-results.md), [ADR 0009](architecture/adr/0009-execution.md), [профиль S5](research/2026-10-28-latency-sketch.md).

## Файлы

Пример структуры каталога:

```text
.results/<эксперимент>/<прогон>/
  manifest.json
  summary.json
  series/<вариант>/<точка>/rep-0/
    replication.json
    index.json
    part-0.json.gz
    part-1.json.gz
```

Нумерация повторений, окон и частей начинается с нуля. Точки нумеруются как `p0`, `p1` и далее: первая ось `grid` внешняя, вторая меняется быстрее. Без сетки есть одна точка `p0` с пустыми координатами. Отсутствующий `grid` и пустой список означают отсутствие сетки.

`manifest.json` перечисляет относительные пути всех файлов артефакта и SHA-256 их сохранённых байтов. Для gzip это хеш сжатых байтов. Сам манифест в список не входит; он записывается последним. В нём также находятся версии приложения и KSL, версия назначения потоков, seed, варианты, число повторений и метаданные рядов `series`: интервалы в миллисекундах, шаг окна, профиль скетча, версия библиотеки, единица времени, способы учёта событий. Поле `series.points` содержит упорядоченный список `{ id, coordinates }`, где `coordinates` сопоставляет пути параметров их значениям в исходных единицах документа. Хеш модели для артефакта вычисляется после упорядочивания связей: сначала `request`, затем вызовы в топологическом порядке IR. Перестановка связей в документе не меняет манифест; версии исходных файлов для проверки перед запуском остаются строгими. Порядок сериализации строк рядов по id сохранён для побайтной совместимости с артефактами этапа 1.

Манифест и сводка содержат верхнеуровневое поле `grid`: список осей `{ path, values }` в порядке документа. Порядок `values`, повторы и исходные единицы сохраняются. Канонический писатель сортирует ключи словаря `coordinates`, поэтому порядок осей нужно брать из `grid`, а не из ключей координат. Без сетки `grid` равен `[]`. Оси доступны сразу после загрузки сводки, до чтения манифеста и рядов.

Поле `documents` содержит SHA-256 канонической записи модели и эксперимента: ключи объектов упорядочены кодеком документов. Поэтому перестановка блоков и форматирование JSON не меняют артефакт. Проверка принятых в очередь документов по `expectedVersions` и HTTP `If-Match` по-прежнему использует хеш исходных байтов документа.

`complete: true` означает, что все задачи и сводка записаны. При ошибке или отмене сохраняются готовые файлы задач, сводка не создаётся, манифест получает `complete: false`. У незаконченной задачи могут остаться части без индекса или итогов повторения. Такие файлы перечислены в неполном манифесте. Исключение отмены остаётся `CancellationException`. Вызов с уже установленным признаком отмены не создаёт артефакт.

Начатая запись файла части завершается в отдельном потоке, который отмена не прерывает. Исполнитель ждёт завершения активных задач перед публикацией неполного манифеста. Незаписанный буфер текущей части незавершённой задачи может быть потерян при отмене; готовые каталоги задач сохраняются целиком. После последней проверки отмены окончательная запись сводки и манифеста завершается целиком; прерывание вызывающего потока восстанавливается после записи.

`Lab.resume` повторно использует задачу только при совпадении SHA-256 `replication.json`, `index.json` и всех gzip-частей с манифестом, а также SHA-256 частей с индексом. Форматы итогов и индекса проверяются. Если файл отсутствует, повреждён или в каталоге задачи есть лишний файл, вся задача пересчитывается с исходным номером повторения. Посторонние файлы прогона и прежняя сводка удаляются перед расчётом. Новая сводка собирается из сохранённых и пересчитанных итогов; манифест атомарно заменяется и не включает собственный хеш в `parts`. При тех же версиях и документах итоговые байты совпадают с непрерывным прогоном.

## Окна и статистики

Выходы, показанные в Timeline, инспекторе и наложении, описаны в каталоге типов по [ADR 0011](architecture/adr/0011-type-outputs.md). Их вычисления ссылаются на поля этого формата: например, интенсивность отправленных попыток использует `sentAttempts` и `durationMs`, загрузка — `busyHandlerTimeMs`, `handlers` и `durationMs`. Идентификатор производного выхода задаётся отдельно от имён исходных полей. Каталог не меняет сохранённые ряды и сводку, их версии, когорты и правила слияния статистик.

`execution.window` задаётся длительностью с единицами, например `"100ms"`. По умолчанию шаг равен `measurement / 100`. Окна покрывают `[0, warmup + measurement)` от нуля; последнее может быть короче. Поля `startMs` и `durationMs` каждого окна задают его фактический интервал. Событие на границе попадает в следующее окно; событие в конце интервала и последующий run-out в ряды не входят.

Ряды учитывают события по времени их возникновения, включая прогрев. Для клиента сохраняются `originalArrivals`, `successes`, `failures` и `latency`; завершение и задержка относятся к окну завершения запроса.

Для сервиса сохраняются:

- `offeredAttempts` — попытки, дошедшие до сервиса после сетевой задержки запроса;
- `admittedAttempts` — попытки, принятые в очередь или сразу занявшие обработчик;
- `queueRejections` — отказы при переполнении очереди;
- `successes` и `failures` — успешные и неуспешные завершения принятой работы до сетевой задержки ответа;
- `timeouts` и `retries` — таймауты ожидания downstream-вызова и повторы, отнесённые к вызывающему сервису;
- `busyHandlerTimeMs` и `handlers` — сумма времени занятости и число обработчиков;
- `queueLengthIntegralMs` — интеграл длины очереди по времени;
- `latency` — время пребывания принятой попытки в сервисе: очередь и удержание обработчика. Отказы очереди увеличивают `queueRejections` и не входят в скетч задержки сервиса. Нулевая задержка принятой попытки остаётся допустимым наблюдением.

Загрузка окна вычисляется как `busyHandlerTimeMs / (handlers * durationMs)`, средняя очередь — как `queueLengthIntegralMs / durationMs`. Число обработчиков клиента равно нулю; эти формулы применяются к сервисам.

Блок `database` записывается в те же строки узлов и словари `services` итогов. Для БД `offeredAttempts` — поступившие запросы, `admittedAttempts` — запросы, принятые в очередь или на выполнение, `queueRejections` — отказы, когда все соединения заняты и очередь заполнена. `handlers` равен `maxConnections`, `busyHandlerTimeMs` — суммарное время занятости соединений, `queueLengthIntegralMs` — интеграл числа ожидающих запросов. Оконные `successes` и `failures` считают результаты выполненных запросов, `latency` включает ожидание и выполнение; отклонённые запросы в скетч не входят. Поля `timeouts` и `retries` БД равны нулю: ожиданием и повторами управляет вызывающий сервис. В итогах `failures` считает ошибки выполнения запросов. Формулы загрузки и очереди, когорта итогов, учёт run-out и правило насыщения сервисов применяются к БД без изменений. Новых полей и версии артефакта для БД нет.

Для каждой связи `call` сохраняются собственные окна. Связь `request` рядов не имеет. Идентификатор связи берётся из модели; он не заменяется парой узлов. Поля окна:

- `sentAttempts` — отправленные попытки, включая повторы; событие относится к окну отправки до сетевой задержки запроса;
- `retries` — повторные попытки из `sentAttempts`, в том же окне отправки;
- `succeeded` и `failed` — ответы, полученные вызывающим до срабатывания timeout, в окне получения. Неуспешный ответ включает отказ очереди, локальный отказ и исчерпание deadline ниже по цепочке;
- `timeouts` — попытки, ожидание которых прервано по timeout, в окне обрыва. Сюда входит timeout, укороченный оставшимся общим deadline;
- `orphaned` — из прерванных попыток те, чей вызываемый процесс ещё не завершился в момент обрыва, в том же окне;
- `inFlightIntegralMs` — интеграл числа отправленных попыток, для которых вызывающий ещё ждёт ответ и timeout не сработал;
- `orphanedIntegralMs` — интеграл числа брошенных попыток от timeout до завершения вызываемого процесса, включая обратную сетевую задержку;
- `backoffIntegralMs` — интеграл числа вызывающих, ожидающих backoff. В это время обработчик вызывающего остаётся занят;
- `latency` — длительность попытки от отправки до получения ответа, включая обе сетевые задержки. Скетч содержит только попытки из `succeeded` и `failed`, поэтому его `count` равен их сумме.

Средние числа ожидаемых, брошенных попыток и вызывающих в backoff вычисляются делением соответствующего интеграла на `durationMs`. Состояние переносится через границы окон; событие завершения на границе прекращает интеграл в предыдущем окне и относится к следующему.

Попытки, брошенные по timeout, в `latency` не входят: они учтены в `timeouts`, а их длительность ожидания задана сработавшим timeout. Поэтому среднее и квантили `latency` описывают только попытки с полученным ответом, а не все отправленные попытки. Профиль скетча, `count` и `sumMs` такие же, как у узлов.

Каждое поле `latency` содержит `count`, `sumMs` и `sketch`. Среднее — `sumMs / count`, пустая выборка не имеет среднего. Сумма копится в порядке событий; значения из представителей корзин для среднего не используются.

Связь `call` с параметром `pool` дополнительно записывает:

- `poolBusyTimeMs` — интеграл числа занятых соединений;
- `poolCapacityTimeMs` — интеграл ёмкости пула: при постоянном размере это `size × durationMs` в окне и `size × measurementMs` в итогах повторения;
- `poolQueueIntegralMs` — интеграл числа ожидающих соединение;
- `poolWaitCount` — число завершившихся ожиданий, включая отказы; немедленное получение свободного соединения не учитывается;
- `poolWaitTimeMs` — суммарную длительность этих ожиданий;
- `poolAcquireTimeouts` — число отказов по `acquireTimeout`; ожидание, завершившееся по общему дедлайну, сюда не входит.

В окне интегралы ограничены его интервалом, а число и длительность ожиданий относятся к окну завершения ожидания. В итогах повторения интегралы покрывают только измеряемый интервал, включая работу запросов прогрева. Число и длительность ожиданий относятся к когорте запросов измерения, включая завершение после измеряемого интервала. В `summary.json` все шесть полей суммируются по повторениям. Без `pool`, в том числе у `route`, эти поля равны нулю; канонический писатель итогов может опускать нулевые значения по умолчанию. Загрузка пула — `poolBusyTimeMs / poolCapacityTimeMs`, средняя очередь — `poolQueueIntegralMs / durationMs` в окне и `/ measurementMs` в итогах. При нулевой ёмкости загрузка не определена.

Ожидание пула предшествует отправке: отказ получения не увеличивает `sentAttempts`, `failed` или `timeouts` и не создаёт наблюдения `latency`. Он расходует попытку и подчиняется политике повторов; `retries` связи по-прежнему считает только отправленные повторные попытки. `latency` связи отсчитывается от отправки, без ожидания пула. Соединение освобождается при ответе или таймауте попытки; последующая работа без ожидающего ответа не удерживает соединение.

У выходов маршрутизатора `route` сохраняются строки связей того же формата. `sentAttempts` считает выборы этого выхода, включая повторы входящего вызова. В окнах это события отправки до сетевой задержки; в `replication.json` и `summary.json` — попытки когорты измерения, включая run-out. Поля исходов и занятости следуют жизненному циклу входящего `call` до выбранного сервиса; вложенные маршрутизаторы получают по одной записи на каждом выбранном выходе. Собственного backoff у `route` нет. Каталог выхода `route.sentAttempts` показывает число попыток в окне, а в сводке — среднее число на повторение (`totals.sentAttempts / replications`). У `router` нет очереди, обработчиков и отдельной строки узла: распределение видно по его выходам. Структура артефакта и её версия сохраняются.

Группа реплик записывает строки экземпляров `<сервис>#1…#N`, копий исходящих вызовов `<связь>#1…#N` и выходов маршрутизатора `<сервис>#lb#1…#N`. При `replicas = 1` имена остаются прежними. Строки сводной группы и худшей реплики добавляются в T3; текущая структура артефакта не меняется. Для входной группы выход `route` учитывает исходный запрос и его исход до полного завершения работы, включая работу после дедлайна.

## Строка пулера

У `pooler` собственная строка в `nodes`, с идентификатором блока. Общие поля `offeredAttempts`, `admittedAttempts`, `successes`, `failures` и `latency` описывают поступившие и принятые попытки, ответы и время пребывания принятой попытки. Отказы по пределу клиентских подключений не входят в `admittedAttempts`, `failures` и скетч. Принятая попытка, не дождавшаяся серверного соединения, входит в `failures` и скетч. Время пребывания заканчивается при освобождении клиентского подключения после ответа, включая обратную сетевую задержку входящего `call`.

Поле `pooler` содержит:

- `maxClientConnections` и `poolSize` — ёмкости клиентского и серверного наборов;
- `clientConnectionRejections` — немедленные отказы из-за занятых клиентских подключений;
- `waitTimeouts` — отказы по пределу ожидания серверного соединения;
- `busyClientConnectionTimeMs` и `busyServerConnectionTimeMs` — интегралы числа занятых подключений и соединений;
- `serverQueueLengthIntegralMs` — интеграл числа ожидающих серверного соединения;
- `serverWaitCount` и `serverWaitTimeMs` — число и суммарная длительность завершённых ожиданий, включая истечение предела. Занятие без ожидания не входит в эти поля; событие относится к окну окончания ожидания.

Для остальных типов `pooler` равен `null` в частях рядов. У пулера общие поля `handlers`, `busyHandlerTimeMs`, `queueLengthIntegralMs` и `queueRejections` нулевые: его ресурсы и причины отказа описаны отдельными полями. Общие `timeouts` и `retries` учитывают исходящий вызов пулера, как у сервиса. Правило насыщения пулера относится к дорожке T3.

В итогах повторения `result.poolers` сопоставляет идентификатору `PoolerMetrics`; строки пулера в `result.services` нет. Счётчики, завершённые ожидания и скетч используют когорту измерения, включая run-out. Три интеграла охватывают только измеряемый интервал и включают присутствующую работу прогрева. `measurementMs`, `maxClientConnections` и `poolSize` задают знаменатели загрузки. Пустой словарь пулеров в файлах итогов и сводки может быть опущен; API выдаёт `{}`.

В сводке `aggregate.poolers` содержит `pooledLatency` и `totals`. Счётчики, время ожиданий, интегралы и `measurementMs` суммируются по повторениям. `clientConnectionCapacityTimeMs` — сумма `maxClientConnections × measurementMs`, `serverConnectionCapacityTimeMs` — сумма `poolSize × measurementMs`. Загрузки вычисляются делением соответствующего интеграла занятости на время ёмкости, среднее число ожидающих — делением интеграла очереди на `measurementMs`, среднее ожидание — делением `serverWaitTimeMs` на `serverWaitCount`. Скетчи времени пребывания объединяются до вычисления квантилей; среднее берётся из общей суммы и числа наблюдений.

## Части и индекс

`part-<k>.json.gz` содержит сжатый UTF-8 JSON `SeriesPart`: `schemaVersion: 4`, `profile`, полуоткрытый диапазон индексов `fromWindow`/`untilWindow` и массивы `nodes` и `connections`. Элемент каждого массива содержит `id` и `windows` в порядке времени. Оба массива присутствуют; один из них может быть пустым.

Последовательные полные окна накапливаются в текущей части, пока добавление следующего окна не превысит общий лимит узлов и связей. Тогда часть записывается, а новое окно начинает следующую. Узлы и связи упорядочены лексикографически внутри своего массива. Если одно окно всех элементов не помещается, оно делится на группы: сначала узлы, затем связи. Каждая такая группа покрывает одно окно; возможна часть только со связями. Каждая пара «узел × окно» и «связь × окно», включая пустые окна, присутствует ровно один раз. Узел и связь с одинаковым `id` остаются разными элементами. Для исходного `retry-storm` все 100 окон повторения помещаются в одну часть.

Лимит части до сжатия — 4 МиБ, то есть 4 194 304 байта. Писатель считает фактически закодированные байты обоих массивов вместе с заголовком и разделителями. Если не помещается один узел или одна связь в одном окне, расчёт завершается ошибкой с видом элемента, его идентификатором, окном и лимитом. Данные не обрезаются. Gzip не содержит времени запуска, поэтому одинаковые данные дают одинаковые байты.

`index.json` содержит `schemaVersion: 4`, `endMs`, `windowMs` и список `parts`. Для каждой части указаны `file`, списки идентификаторов `nodes` и `connections`, `fromWindow`, `untilWindow`, `uncompressedBytes` и `sha256`. Пустой список `connections` в ссылке может быть опущен и читается как `[]`. Индекс записывается после всех окон задачи.

Сборщик передаёт закрытое окно писателю и освобождает его объекты. Текущая часть хранит уже закодированные окна; их байты освобождаются после записи части. В памяти остаются текущее окно, текущая часть, статистики повторения и метаданные индекса; все оконные скетчи прогона одновременно не хранятся.

## Скетч задержки

Профиль `ddsketch-bitwise6-rational-v1` использует `sketches-java:0.8.3`: `BitwiseLinearlyInterpolatedMapping(6)` с представителем `lowerBound * 129/128`. Оконные накопители используют `SparseStore`, итоги и слияние — `UnboundedSizeDenseStore`.

Поле `sketch` — массив `[zeroCount, index, count, ...]`. Индексы строго возрастают, ненулевые counts положительны, целые записываются десятичными числами без экспоненты. Пустое распределение — `[0]`. Профиль указан один раз на часть или файл итогов. Ноль хранится точно.

До изменения скетча проверяются конечность и диапазон значения, будущие count и диапазон корзин. Разрешены ноль и положительные значения в `[2^-1021, 2^1023)` ms; общий count не больше `9 007 199 254 740 990`, занятый диапазон — не больше 2048 адресов корзин. Ошибка оставляет принимающий скетч неизменным. Сливаются только одинаковые профиль и единица. Целые counts дают одинаковые корзины при любом допустимом порядке слияния.

Квантили сохраняют соглашение KSL: позиция `p * (n + 1)`, крайние позиции ограничены первым и последним представителем, между соседними порядковыми статистиками применяется `a + fraction * (b - a)`. Пустой скетч возвращает `null`. Относительная погрешность квантилей для проверенного диапазона задержек `0.001–60000 ms`, включая точные нули, не больше 0,78125 % с учётом округления binary64. Для крайне малых результатов интерполяции относительная гарантия не заявляется; ограничение описано в S5.

## Итоги повторения и сводка

`replication.json` содержит `schemaVersion`, `profile`, `unit` и `result`. В `result` находятся счётчики исходных запросов, `allLatency`, `successfulLatency`, `failedLatency` и словари `services`, `connections` и `poolers` с итогами сервисов, связей и пулеров. Списков отдельных задержек или времён поступления в файле нет.

Когорта итогов состоит из запросов, пришедших за измеряемый интервал `[warmup, warmup + measurement)`. Их исходы, задержки и вызванные ими попытки учитываются и во время run-out. Занятость и очередь сервисов интегрируются только по измеряемому интервалу, включая работу, которая поступила во время прогрева. В итогах сервисов `failures` сохраняет прежний смысл локальных отказов; оконное поле `failures` считает все неуспешные завершения принятой работы. Счётчики и задержки связей используют ту же когорту с run-out. Интегралы связей, как занятость и очередь сервисов, охватывают только `[warmup, warmup + measurement)` и учитывают всю присутствующую работу, включая поступившую при прогреве.

В `AggregateMetrics.connections` каждой связи соответствует `AggregateConnectionMetrics`. Поле `totals` содержит суммы `sentAttempts`, `retries`, `succeeded`, `failed`, `timeouts`, `orphaned`, трёх интегралов, `measurementMs` и шести полей пула по повторениям. `pooledLatency` строится слиянием скетчей ответов; среднее вычисляется из общей суммы и числа ответов. При отсутствии ответов оно равно `null`. Поле `timeoutRate` — `MetricSummary` доли `timeouts / sentAttempts` по повторениям с отправленными попытками; без таких повторений оно равно `null`. Поле `meanInFlight` — `MetricSummary` средних `inFlightIntegralMs / measurementMs` по повторениям. Это средние по независимым повторениям, а не отношения объединённых сумм; их 95 % доверительные интервалы Стьюдента не обрезаются. При одном наблюдении границы интервала равны `null`.

На полностью завершённом повторении сумма `succeeded + failed + timeouts` равна `sentAttempts`; отправленные попытки связи равны `offeredAttempts` вызываемого. В линейной цепочке без пула `timeouts` и `retries` связи совпадают с одноимёнными полями вызывающего узла; прежний смысл полей узлов сохранён. `orphaned` не превышает `timeouts`. К концу run-out все попытки и orphaned work завершены.

`summary.json` собирается в порядке «вариант, точка, повторение»: метрики — только из записанных `replication.json`, вывод насыщения — из `index.json` и перечисленных в нём gzip-частей тех же задач. У варианта находятся `id`, `label`, `replications` и список `points`; каждая точка содержит `id`, `coordinates`, `aggregate` и `saturation`. Прежнее поле `aggregate` варианта удалено. Summary в web показывает строку на каждую пару «вариант, точка». CLI `run` печатает `вариант/точка [путь=значение, ...]: success ...`, сохраняя единицы; без координат квадратные скобки отсутствуют. Пул задержек строится слиянием скетчей, его среднее — из counts и сумм; в `LatencyDistribution.statistics` сохраняются достаточные статистики. `AggregateServiceMetrics.totals` содержит числители, знаменатели и интегралы сервисов.

В `saturation.rule` записаны `minimumDurationMs` (100 ms), `handlerUtilizationThreshold` (0,95), `meanQueueLengthThreshold` (0,5) и `queueRejectionsThreshold` (0). Ветка очереди требует непрерывного интервала не короче `minimumDurationMs`, в каждом окне которого загрузка не ниже порога и средняя очередь больше порога; укороченное последнее окно учитывается по фактической длительности. Ветка переполнения требует серии подряд окон с числом отклонений больше порога, от начала первого до начала последнего из которых прошло не меньше `minimumDurationMs`. Длительность последнего окна в этой ветке не добавляется: одно окно с отклонениями не подтверждает насыщение при любом шаге рядов. Ветки проверяются независимо, начало относится к первому окну той подтверждённой серии, которая началась раньше. Параметр `consecutiveWindows` удалён. Список `replications` упорядочен по номеру повторения; его элемент содержит `replication` и `degradationPath` с парами `{ node, startMs }` в порядке начала насыщения, при равенстве — в обратном топологическом порядке графа, от вызываемого к вызывающему. Для узлов вне переданного порядка используется id. Пустой путь явно означает отсутствие насыщения; такие повторения учитываются только в `withoutSaturation`. Для каждого узла, бывшего первым, `firstNodes` содержит `node`, `replicationCount`, `medianStartMs`, `minStartMs` и `maxStartMs`. Медиана чётного числа моментов — среднее двух центральных, min/max задают разброс. Первые узлы упорядочены по убыванию `replicationCount`, затем по id. Повторения без насыщения не участвуют в статистике моментов.

Статистики независимых повторений остаются отдельными: `MetricSummary` для success rate, p95/p99 и amplification. Поля `mean`, `min` и `max` описывают наблюдаемые значения метрики; границы `ci95Low`/`ci95High` могут выходить за `[0,1]`, в том числе для `successRate`. Их доверительные границы Стьюдента не обрезаются до физического диапазона. Погрешность скетча и неопределённость между повторениями имеют разный смысл; pooled p99 не вычисляется усреднением p99 повторений.
