# Дорожка T1 этапа 2, срез 1: граф и движок на общих деталях — план-контракт

**Цель.** Перевести ядро с линейной цепочки на граф вызовов: `GraphIr` вместо `ChainIr`, движок из общих деталей (набор слотов, исполнитель сценария, попытка вызова, маршрутизатор), сценарий сервиса с несколькими вызовами, маршрутизатор и группы реплик. Примеры этапа 1 при этом дают прежнюю сводку.

**Как читать.** Это план-контракт, а не пошаговый рецепт. Для каждой задачи он фиксирует границы, контракты для соседних задач и дорожек, инварианты и приёмку. Структуру классов, реализацию и тесты исполнитель выбирает сам, по правилам `AGENTS.md`. Расхождение с ADR или дизайном обсуждается в issue до реализации.

**Источники.** [Дизайн первого среза этапа 2](../specs/2026-10-30-stage-2-slice-1-design.md): §3–§6, §8. ADR [0002](../../architecture/adr/0002-model-pipeline.md), [0006](../../architecture/adr/0006-random-streams-by-block-path.md), [0007](../../architecture/adr/0007-simulation-engine-ksl.md), [0008](../../architecture/adr/0008-run-results.md), [0011](../../architecture/adr/0011-type-outputs.md), [0012](../../architecture/adr/0012-call-graph-and-replica-groups.md), [0013](../../architecture/adr/0013-slot-pools.md). Исследование [S1, возможности KSL](../../research/2026-10-27-ksl-capabilities.md): идиомы фаз, ресурсов и таймаутов.

## Общие инварианты

1. **Равенство на примерах этапа 1.** После каждой задачи `examples/retry-storm/` и `examples/checkout/` дают ту же сводку, что на `main` до задачи. Цель — побайтное равенство `summary.json` и рядов. Если задача меняет порядок одновременных событий и побайтное равенство недостижимо, это доказывается в PR: что именно изменилось в порядке, почему иначе нельзя, и все метрики сводки лежат в пределах доверительных интервалов прежней. Тогда эталоны (`WebSeriesGoldenTest` и др.) пересоздаются в той же задаче с объяснением.
2. **Детерминизм.** При тех же версии, документах и seed артефакт побайтно одинаков при любом числе потоков, порядке задач и порядке блоков и связей в документах (ADR 0006, драйвер D6).
3. **Пути и случайные числа.** Пути элементов и экземпляров — ключи потоков по ADR 0006 и ADR 0012. Добавление элемента или реплики не меняет потоки остальных; тест подтверждает это для каждой новой роли потока.
4. **Документы этапа 1 читаются без правки.** Если структура документа меняется, растёт его `schemaVersion`, а ядро мигрирует старую версию при чтении и пишет новую. Миграция покрыта тестом на `examples/**`. JSON-схемы и OpenAPI пересоздаются (`UPDATE_SCHEMAS=1`, `UPDATE_OPENAPI=1`), типы web — `npm run api:generate`.
5. **Сообщения.** Новые диагностики выдаются через контракты `CoreMessage` с аргументами (#193); ключи `messages.<CODE>` добавляются в `en.json` и `ru.json` в той же задаче.
6. **Web не теряет данные.** Интерфейс новых структур — дорожка T4, но web уже сейчас сохраняет поля блоков и связей, которые не редактирует: открыть и сохранить модель с новыми полями — значит не изменить их. Новые типы каталога не ломают палитру и инспектор; если web не умеет показать параметр, он показывает его только для чтения.
7. **Новые зависимости** — только с обоснованием в issue (`AGENTS.md`).

## T1.1 `GraphIr` и компилятор

**Входит.** `GraphIr` вместо `ChainIr` для существующих типов (`client`, `service`, `request`, `call`); проверка топологии графа; сценарий сервиса по умолчанию; детерминированный порядок; перевод всех потребителей IR — компилятора, линтера, оценки стоимости, исполнителя, адаптера движка.

**Не входит.** Новый движок (T1.2): адаптер может временно продолжать работать на нынешнем `ReliabilityModel`, если умеет исполнять граф-цепочку. Сценарий в документах (T1.3), маршрутизатор и группы (T1.4, T1.5).

**Контракт.**
- `GraphIr`: клиент, узлы-экземпляры, рёбра-вызовы, отказы, параметры прогона. У экземпляра сервиса — сценарий шагов `process` и `call`; без явного сценария он строится как в этапе 1: обработка, затем вызов по единственной исходящей связи. Каждый элемент хранит путь (список сегментов по ADR 0012) и происхождение.
- Порядок узлов и рёбер — топологический от клиента, при равенстве — по пути. Он используется везде, где этап 1 опирался на порядок цепочки, включая порядок записи артефакта и правило равенства в пути деградации: при одинаковом моменте первым идёт элемент дальше от клиента.
- Проверка топологии заменяет правила цепочки (`TOPOLOGY_CHAIN.*`):
  - ровно один клиент и одна связь `request` от него;
  - граф вызовов без циклов — ошибка называет элементы цикла;
  - все узлы достижимы от клиента;
  - входной сервис не получает вызовов.
  Ограничение «не больше одного исходящего и входящего вызова» снимается на уровне проверки; пока нет сценариев (T1.3), сервис с несколькими исходящими вызовами — ошибка «нет сценария для нескольких вызовов».
- Линтер работает на `GraphIr`. Правила этапа 1 вычисляются вдоль путей от клиента и на графе-цепочке дают прежние предупреждения с прежними текстами и указателями. Обобщённая семантика для ветвлений и маршрутизаторов — задачи milestone «Линтер».
- Оценка стоимости (`CostEstimator`) считает по `GraphIr`: средняя длина пути запроса — сумма по шагам сценария вдоль графа; на цепочке оценка не меняется.

**Приёмка.**
- Инвариант 1 побайтно: движок не менялся, меняется только IR.
- Тесты проверки: цикл, недостижимый узел, два клиента, вызов во входной сервис — по ошибке на каждый, с указателем в документ.
- Перестановка блоков и связей в документе не меняет `GraphIr` и артефакт.
- В `core` не осталось `ChainIr`.

## T1.2 Движок на общих деталях

**Входит.** Перестройка `ReliabilityModel` под `GraphIr` по ADR 0013 и дизайну §5: набор слотов, исполнитель сценария, попытка вызова; обработчики сервиса — набор слотов; сбор рядов и итогов по узлам и рёбрам графа.

**Не входит.** Маршрутизатор (T1.4), пулер, БД, пул на связи, новые виды отказов и профили (T2), сводные строки групп и насыщение пулов (T3).

**Контракт.**
- **Набор слотов** (ADR 0013): ёмкость, FIFO-очередь с вместимостью (0 — без очереди), предел ожидания (без предела — по умолчанию). Исходы: занят сразу, после ожидания, отказ «очередь полна», отказ «предел ожидания». Ёмкость меняется во время прогона через явный метод: занятые сверх новой ёмкости доделывают работу, новые занятия видят новую ёмкость, рост ёмкости обслуживает очередь. Метрики: интеграл занятости, интеграл длины очереди, ёмкость по времени, число и суммарное время ожиданий, отказы по причинам. Одновременные освобождение слота и истечение ожидания: приоритет у обслуживания.
- **Исполнитель сценария**: попытка занимает обработчик экземпляра и проходит шаги по порядку; обработчик удерживается до конца сценария. `process` — задержка и возможная ошибка; `call` — попытка вызова. Окончательная неудача вызова прерывает сценарий ошибкой.
- **Попытка вызова** сохраняет семантику этапа 1: таймаут на попытку, продолжение работы ниже по графу после таймаута, общий дедлайн, backoff и jitter. Деталь принимает цель вызова извне, чтобы T1.4 подключил маршрутизатор без её изменения.
- Сбор рядов и итогов идёт по узлам и рёбрам графа; поля формата этапа 1 сохраняются. Поля набора слотов, которых нет в формате этапа 1, в этой задаче в артефакт не пишутся (T3).
- Правило насыщения применяется к набору слотов обработчиков, как в этапе 1.

**Приёмка.**
- Инвариант 1 — главная приёмка задачи.
- Детерминированные тесты набора слотов: исходы занятия, предел ожидания, приоритет обслуживания при совпадении моментов, уменьшение и рост ёмкости с очередью и без.
- Детерминированные тесты сценария на графе, построенном в тесте: два вызова подряд, повторный вызов одной связи, неудача второго вызова прерывает сценарий, обработчик держится до конца.
- Инвариант 2 на графе с ветвлением, построенном в тесте.
- Время прогона `retry-storm` и `checkout` не хуже прежнего более чем на 10 %; замер в PR.

## T1.3 Сценарий сервиса в документах

**Входит.** Поле сценария у блока сервиса в модели; несколько исходящих вызовов из сервиса; проверка и линтер сценария; миграция документов.

**Не входит.** Редактор сценария в интерфейсе (T4). Переопределение параметров отдельных шагов в вариантах и сетке.

**Контракт.**
- Сценарий — поле блока `scenario` рядом с `params`, а не параметр каталога: это структура, она не переопределяется в вариантах. Шаг — объект с видом `process` или `call`. Шаг `process` может задать своё время обработки и долю ошибок; без них используются параметры сервиса `processing` и `failureRate`. Шаг `call` ссылается на идентификатор исходящей связи сервиса; одну связь можно вызвать несколько раз. Точная запись в JSON — решение задачи; она описывается в JSON-схеме и в §3 дизайна этапа 1 (раздел документов).
- Без поля `scenario` сценарий строится по умолчанию: обработка, затем исходящие вызовы в порядке их идентификаторов. Модели этапа 1 не меняются.
- Ошибки: шаг `call` на связь, которая не исходит из этого сервиса; пустой сценарий; сервис с несколькими исходящими вызовами без сценария. Предупреждение: исходящая связь не используется в сценарии.
- `schemaVersion` модели растёт, если это нужно для записи поля; миграция по инварианту 4.

**Приёмка.**
- Модель с сервисом, который вызывает `db`, затем `payment`, затем снова `db`, проходит проверку и считается; число попыток по связям в итогах соответствует сценарию.
- Ошибки и предупреждение из контракта — по тесту на каждое, с указателем на шаг.
- Web открывает и сохраняет модель со сценарием без изменения поля (инвариант 6) — unit-тест web.

## T1.4 Маршрутизатор

**Входит.** Тип блока `router`, тип связи `route`, политики выбора выхода, параметр вызова «не на ту же цель», роль потока `routing`.

**Не входит.** Группы реплик (T1.5), повторы внутри балансировщика и outlier detection (точки расширения дизайна, §9).

**Контракт.**
- `router`: один вход от вызова, параметр `policy` — `roundRobin`, `random`, `leastInFlight`. Своей очереди и задержки нет. Выходы — связи `route` к сервисам или другим маршрутизаторам; у `route` параметр `weight` (по умолчанию 1), используется политикой `random`.
- Вызов, ведущий в маршрутизатор, выбирает цель для каждой попытки: таймаут, повторы и дедлайн относятся ко всему пути до выбранной цели. Цель выбирается в момент отправки попытки.
- `roundRobin` — свой счётчик маршрутизатора; `random` — веса и поток роли `routing` по пути маршрутизатора; `leastInFlight` — наименьшее текущее число попыток в работе у выхода, при равенстве — первый по порядку выходов.
- Параметр вызова `retryTarget` — `any` (по умолчанию) или `other`. При `other` попытка выбирает среди выходов, которые она ещё не пробовала; если таких нет — среди всех. Это выбор из существующего вида `CHOICE`, без нового вида параметра.
- Проверка: у маршрутизатора есть хотя бы один выход; связь `route` исходит только из маршрутизатора; цикл через маршрутизаторы — ошибка по T1.1.
- Ряды и итоги маршрутизатора: число попыток в каждый выход. Формат описывается в документе формата артефакта; версия формата растёт, если меняется структура.

**Приёмка.**
- Детерминированные тесты каждой политики: распределение попыток по выходам, веса `random` в пределах статистической погрешности, `leastInFlight` обходит выход с долгой обработкой.
- `retryTarget: other`: повтор не попадает на выход предыдущей неудачной попытки, пока есть другие; с одним выходом идёт на него же.
- Инвариант 3 для роли `routing`: добавление выхода не меняет потоки остальных элементов.
- Модель «gateway → router → три сервиса» проходит проверку и считается; web открывает её, палитра показывает `router`, сохранение не теряет данные.

## T1.5 Группы реплик

**Входит.** Параметр сервиса `replicas`, поле блока `replicaOverrides`, разворачивание группы в маршрутизатор и экземпляры по ADR 0012, пути экземпляров, адресация реплики в отказах.

**Не входит.** Сводные строки групп, худшая реплика и полоса min–max (T3), отображение групп в интерфейсе (T4), новые виды отказов (T2).

**Контракт.**
- `replicas` — целый параметр сервиса, не меньше 1, по умолчанию 1, переопределяется в вариантах и перебирается сеткой. При `replicas = 1` разворачивания нет: модель этапа 1 не меняется.
- Политика балансировки группы — параметр входящего вызова, ведущего в группу (`balancing` с теми же значениями, что `router.policy`); у вызова в сервис без реплик параметр игнорируется с предупреждением линтера.
- Разворачивание: маршрутизатор с путём `<сервис>`, `#lb` и экземпляры `<сервис>`, `#1…#N`. Исходящие связи группы копируются для каждого экземпляра; путь копии — путь связи и сегмент номера источника. Связь в группу из другой группы ведёт в маршрутизатор целевой группы.
- `replicaOverrides` — поле блока, словарь «номер реплики → частичный набор параметров». Номер больше `replicas` — ошибка; параметры проверяются как параметры сервиса.
- Отказы: цель `<сервис>` действует на все экземпляры группы, цель `<сервис>#<k>` — только на экземпляр k; цель на связь группы — на все её копии. Существующие виды отказов этапа 1 работают на экземплярах; новые — в T2.
- Диагностика экземпляра указывает на блок группы в документе и называет номер реплики.
- Ряды и итоги пишутся по экземплярам и копиям связей; сводные строки группы — T3.

**Приёмка.**
- Группа с `replicas: 3` и явная схема «router + три одинаковых сервиса с теми же путями экземпляров» дают побайтно одинаковый артефакт.
- Инвариант 3: рост `replicas` с 3 до 5 не меняет адреса потоков экземпляров 1–3 и остальных элементов; проверяется сравнением плана адресов потоков.
- `replicaOverrides` с другим числом обработчиков у реплики 2 меняет только её; отказ на `<сервис>#2` замедляет только её.
- Перебор сеткой `replicas = 2, 3, 4` проходит; оценка стоимости растёт с числом реплик.
