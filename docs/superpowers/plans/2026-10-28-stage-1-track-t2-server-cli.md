# Дорожка T2 этапа 1: сервер и CLI — план-контракт

**Цель.** Довести сервер и CLI до дизайна этапа 1 после сквозного среза и T1: ручки рядов, параллельные задания с отменой, досчёт и оценка, удаление документов и отслеживание внешних изменений, команды CLI `catalog`, `schema`, `estimate`, `resume`, Compose с рабочей областью на хосте.

**Как читать.** Это план-контракт, а не пошаговый рецепт. Для каждой задачи он фиксирует границы, контракты API и CLI, инварианты и приёмку. Структуру кода и тесты исполнитель выбирает сам, по правилам `AGENTS.md`. Расхождение с ADR или дизайном этапа 1 обсуждается в issue до реализации.

**Источники.** [Дизайн этапа 1](../specs/2026-10-27-stage-1-design.md): §5, §7.2. ADR [0003](../../architecture/adr/0003-workspace.md) (рабочая область), [0008](../../architecture/adr/0008-run-results.md) (артефакт и бюджеты), [0009](../../architecture/adr/0009-execution.md) (исполнение), [0010](../../architecture/adr/0010-api-contract.md) (API). [Формат артефакта](../../results-format.md). План T1: [T1.3, T1.4, T1.7](2026-10-28-stage-1-track-t1-core.md).

## Общие инварианты

1. **API аддитивно.** Существующие ручки и поля не меняют смысла; новые поля и ручки описаны в `apps/server/openapi.json`, ответы проверяет `OpenApiConformance`, TS-типы web пересоздаются (ADR 0010).
2. **Паритет API и CLI** (драйвер D5): обе стороны вызывают одни и те же методы `Lab` и выдают одинаковую диагностику с теми же кодами.
3. **Ошибки — `ApiProblem`** со стабильным кодом; новые коды перечислены в KDoc обработчика и в описании PR.
4. **Пути и идентификаторы проверяются.** Параметры пути не позволяют выйти за рабочую область или каталог прогона; неизвестный объект — 404, а не 500.
5. **Задания живут в памяти процесса, прогоны — в `.results/`.** Всё, что должно пережить перезапуск, опирается на прогон, а не на задание.
6. **Новые зависимости** — только с обоснованием в issue (`AGENTS.md`).

## T2.1 Ручки рядов

**Входит.** Дизайн §5.2: индекс частей задачи и сами части рядов из артефакта T1.4.

**Не входит.** Чтение рядов в web (T4), ряды незаконченных прогонов в списке (T2.3).

**Контракт.**
- `GET /api/v1/runs/{id}/series/{variant}/{cell}/{rep}` — содержимое `index.json` задачи как типизированный JSON. `cell` — идентификатор точки (`p0`, `p<k>`), `rep` — номер повторения с нуля.
- `GET /api/v1/runs/{id}/series/{variant}/{cell}/{rep}/{part}` — байты `part-<part>.json.gz` как есть: `Content-Type: application/json`, `Content-Encoding: gzip`, сильный `ETag` из SHA-256 индекса, `Cache-Control` с долгим сроком и `immutable` — файлы прогона не меняются.
- Схемы `SeriesIndex` и `SeriesPart` описаны в OpenAPI, чтобы web получил их TS-типы; в описании ручки части сказано, что тело передаётся в gzip.
- Неизвестные прогон, вариант, точка, повторение или часть — 404 `SERIES_NOT_FOUND`; параметры, не подходящие под формат идентификаторов, — 400.

**Приёмка.**
- После прогона `examples/retry-storm/` индекс и часть каждой задачи читаются; распакованная часть совпадает побайтно с файлом в `.results/`, контрольная сумма совпадает с индексом.
- Ответы сверяются с OpenAPI; попытка выхода из каталога прогона через параметры — 400 или 404.
- Запрос через Vite proxy и Nginx в Compose возвращает тело, которое браузер распаковывает сам.

## T2.2 Параллельные задания и отмена

**Входит.** ADR 0009, п. 3 и 6 на уровне сервера: несколько заданий выполняются одновременно, ядро чередует их задачи (T1.3); отмена задания через API и прерывание `run` в CLI.

**Не входит.** Кнопка отмены в UI (T4), досчёт отменённого прогона (T2.3).

**Контракт.**
- Сервер не ограничивает число одновременных вызовов `Lab.run` одним: задания стартуют сразу, чередование задач обеспечивает общий пул ядра. Ожидание вызывающих потоков не занимает потоки расчёта.
- `POST /api/v1/jobs/{id}/cancel` — 202 с `JobView`. Задание в очереди сразу становится `CANCELLED`; выполняющееся помечается `cancelRequested: true` и переходит в `CANCELLED`, когда ядро остановило расчёт. Повторная отмена — тот же ответ; отмена завершённого задания — 409 `JOB_FINISHED`; неизвестного — 404.
- `JobStatus` получает `CANCELLED`, `JobView` — поле `cancelRequested`. Каталог отменённого прогона остаётся с `complete: false` (T1.3, T1.4).
- CLI `run`: Ctrl+C или SIGTERM передаёт отмену в `Lab.run`, ждёт остановки, сообщает в stderr путь незаконченного артефакта и завершается кодом 130.

**Приёмка.**
- Через API: длинное задание и поданное позже короткое — короткое завершается раньше.
- Отмена задания в очереди и выполняющегося; после отмены следующие задания идут, ответы сверяются с OpenAPI.
- CLI: прерывание `run` оставляет каталог с `complete: false` и даёт код 130.

## T2.3 Досчёт и оценка в API и CLI

**Входит.** Методы досчёта и оценки `Lab` из T1.7 (#70) в API и CLI; незаконченные прогоны в списке.

**Не входит.** Кнопка «Оценить» в UI (#6), кнопка досчёта в UI (T4).

**Контракт.**
- `POST /api/v1/estimate` — тело как у `POST /validate` (эксперимент и необязательные черновики); ответ — оценка `Lab` в типизированной форме: число задач, событий, время при текущем числе потоков, размеры и предупреждения о бюджетах ADR 0008.
- Досчёт привязан к прогону, а не к заданию, потому что задания не переживают перезапуск сервера (инвариант 5): `POST /api/v1/runs/{id}/resume` создаёт задание и возвращает 202 с `JobView`. Законченный прогон — 409 `RUN_COMPLETE`; изменённые документы — 400 с диагностикой ядра; неизвестный прогон — 404.
- `GET /api/v1/runs` перечисляет и незаконченные прогоны; `RunEntry` получает поле `complete`. Сводка незаконченного прогона — 404 `RUN_INCOMPLETE`; ряды готовых задач незаконченного прогона доступны через ручки T2.1.
- CLI `estimate <experiment>` печатает оценку; `resume <run>` принимает идентификатор прогона или путь к его каталогу, пишет ход выполнения в stderr, а итог — в stdout так же, как `run`, и использует те же коды выхода.
- В дизайне этапа 1 (§5.2) ручка досчёта записана как `POST /runs/{id}/resume`.

**Приёмка.**
- Отменённый через API прогон досчитывается через API и CLI, итоговый артефакт побайтно равен непрерывному.
- Оценка через API и CLI совпадает с оценкой `Lab` на тех же документах.
- Список прогонов отличает законченные от незаконченных.

## T2.4 Удаление документа и внешние изменения

**Входит.** Дизайн §5.1–5.2: `DELETE` документа и отслеживание внешних изменений рабочей области.

**Не входит.** Реакция web на внешние изменения (T3, отдельная задача).

**Контракт.**
- `DELETE /api/v1/workspace/document?path=` требует `If-Match`: без него — 428 `VERSION_REQUIRED`, при несовпадении — 409, отсутствующий документ — 404, успех — 204. Ядро удаляет документ под той же блокировкой рабочей области, что и запись.
- Ядро следит за документами рабочей области (`*.model.json`, `*.layout.json`, `*.experiment.json`, без скрытых каталогов и `.results/`) и ведёт журнал изменений с монотонным курсором. Механизм выбирает исполнитель: `WatchService` с запасным сканированием, если платформа не даёт событий.
- `GET /api/v1/workspace/changes?since=<cursor>` возвращает новый курсор и изменения после `since`: путь, вид документа, версия или `null` для удалённого. Записи через API тоже попадают в журнал — клиент отличает свои сохранения по версии. Журнал ограничен; если `since` старше сохранённого, ответ содержит признак сброса, и клиент перечитывает список документов. Без `since` — текущий курсор и пустой список.
- Изменение файла снаружи видно в журнале не позже чем через 5 секунд.

**Приёмка.**
- Удаление с правильной и устаревшей версией, без `If-Match` и для отсутствующего документа.
- Изменение, создание и удаление файла снаружи сервера появляются в журнале; записи через API — тоже; сброс при устаревшем курсоре.
- Ответы сверяются с OpenAPI.

## T2.5 Команды CLI `catalog` и `schema`

**Входит.** Дизайн §5.3: справка по каталогу и JSON-схемы документов из CLI.

**Контракт.**
- `catalog` печатает в stdout тот же JSON, что `GET /api/v1/catalog`.
- `schema <model|layout|experiment>` печатает в stdout JSON-схему документа из того же генератора, что `schemas/*.schema.json` (T1.1).
- Неизвестный аргумент — сообщение в stderr и код 2; справка `USAGE` перечисляет новые команды.

**Приёмка.**
- Вывод `catalog` совпадает с ответом API; вывод `schema` совпадает с закоммиченными файлами `schemas/` побайтно.

## T2.6 Compose с рабочей областью на хосте

**Входит.** Дизайн §5.1: Docker Compose подключает каталог рабочей области с хоста.

**Контракт.**
- Compose монтирует каталог хоста в `/workspace` контейнера на запись; по умолчанию `./examples`, другой каталог задаётся переменной окружения. Изменения документов и `.results/` появляются на хосте.
- Пользователь контейнера может писать в смонтированный каталог без root; способ сопоставления пользователя описан в `AGENTS.md`.
- Блокировка рабочей области (`.workspace.lock`) работает на смонтированном каталоге Docker Desktop и Linux; если нет — задача останавливается и описывает это в issue.
- Внешние правки файлов на хосте видны через ручку изменений T2.4.
- Порты по-прежнему только на `127.0.0.1`.

**Приёмка.**
- `docker compose up --build -d`, правка документа через UI сохраняется в каталоге хоста, прогон пишет `.results/` на хосте, правка файла на хосте видна в журнале изменений; `docker compose down`.
- Если Docker недоступен в окружении исполнителя, это написано в PR, а проверку повторяет координатор.
