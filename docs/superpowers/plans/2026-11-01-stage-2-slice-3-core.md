# Этап 2, срез 3: ядро — кэш и fan-out — план-контракт

**Цель.** Дать ядру всё, что нужно третьему срезу: блок внешнего кэша с точной моделью по ключам, шаг «чтение через кэш», повтор и параллельные ветки в сценарии, отказ «сброс кэша», результаты кэша, линтер и оценку стоимости. Форматы должны быть такими, чтобы интерфейс (T4) и пример (T5) взяли их без изменений.

**Как читать.** Это план-контракт, а не пошаговый рецепт. Для каждой задачи он фиксирует границы, общие форматы, инварианты и приёмку. Внутреннее устройство и тесты исполнитель выбирает сам, по правилам `AGENTS.md`. Расхождение с ADR или дизайном обсуждается в issue до реализации. **Форматы из раздела «Общие форматы» обязательны для всех задач:** задача не меняет их молча. Если формат не подходит, это обсуждается в issue и правится в этом плане до реализации.

## Исходное состояние

- **Сценарий сервиса — плоский список.** В документе это поле блока `scenario` из `ScenarioStep` с полями `type` (`process` или `call`), `processing`, `failureRate`, `connection` и `classes` (`core/.../document/Documents.kt`). В IR — `ServiceStep.Process` и `ServiceStep.Call` (`core/.../ir/GraphIr.kt`). Движок выполняет шаги по порядку в одном процессе KSL, пока вызывающий держит обработчик (`executeScenario` в `core/.../engine/ksl/ReliabilityModel.kt`); первый неуспешный шаг завершает сценарий.
- **Состояние запроса** (`originalOutcome`, `degraded`, дедлайн, когорта) живёт в процессе запроса. Дочерних процессов внутри обработки сервиса нет.
- **Блоки:** `client`, `service`, `router`, `database`, `pooler`. Кэша нет.
- **Отказы:** `slowdown`, `errors`, `unavailable`, `blackhole`, `capacityLoss`, у каждого `from` и `to` (`FaultKind` в `GraphIr.kt`).
- **Пути переопределений и сетки** — `<элемент>.<параметр>[.<поле>]`. Сценарий — структура: вариант его не переопределяет.
- **Линтер** считает нагрузку общей функцией `serviceLoad` (`core/.../compiler/ModelLinter.kt`); оценка стоимости — `core/.../execution/CostEstimator.kt`.
- **Версии:** модель 6, эксперимент 3, раскладка 2; артефакт (манифест и сводка) 19, ряды 7, итоги повторения 7; каталог 7.

## Общие инварианты

1. **Равенство чисел на прежних примерах.** `examples/retry-storm/`, `examples/checkout/`, `examples/checkout-replicas/` и `examples/checkout-policies/` не используют новых шагов и кэша. Они дают те же числа сводки и рядов, что до среза; меняются только версии. Перестройка исполнителя сценария под дерево шагов не должна менять порядок выборки случайных чисел у плоского сценария. Если число всё же изменилось, PR объясняет причину и показывает, что новое значение лежит внутри прежнего доверительного интервала.
2. **Детерминизм.** Артефакт побайтно повторяется при 1, 2, 4 и 8 потоках и не зависит от порядка задач.
3. **Пути и случайные числа** (ADR 0006, 0016). Новые потоки:
   - ключи шага `cacheRead` — по пути экземпляра вызывающего сервиса и `id` шага; копии повтора берут ключи из одного потока по порядку копий в момент запуска шага;
   - разброс TTL — по пути блока кэша.

   Других новых потоков нет. Добавление шага, пространства ключей или ветки не меняет ключи остальных шагов.
4. **Версии без совместимости.** Каждая смена формата повышает `schemaVersion`, переписывает `examples/**` и фикстуры. Документ или прогон прежней версии получает понятную ошибку о версии (`SCHEMA_VERSION`, `RUN_VERSION_UNSUPPORTED`). Схемы пересоздаются через `UPDATE_SCHEMAS=1`, OpenAPI — через `UPDATE_OPENAPI=1`, типы web — через `npm run api:generate`, эталон рядов — через `UPDATE_SERIES_GOLDEN=1` (команды в `AGENTS.md`).
5. **Сообщения** — `CoreMessage` с аргументами и ключи `messages.<CODE>` в `web/src/i18n/en.json` и `ru.json`.
6. **Web не теряет данные.** До T4 интерфейс не правит новые поля, но открывает и сохраняет документы версий 7 и 4 без потерь. Нынешний редактор сценария показывает шаги `cacheRead` и `parallel`, а также поля `repeat`, `id` и `title`, только для чтения и сохраняет их без изменений. Каждая задача, меняющая формат, проходит `npm test -- --run` и затронутые E2E.
7. **Без новых конструкций — прежнее поведение.** Сценарий без `repeat`, `parallel` и `cacheRead` и модель без кэша выполняются так же, как до среза (инвариант 1).
8. **Новые зависимости** — только с обоснованием в issue.

## Общие форматы

### Модель, версия 7

**Блок `cache`.** Узел с набором слотов `handlers` (ADR 0013), без сценария и без `replicas`:

```json
"redis": { "type": "cache", "title": "Кэш товаров", "params": {
  "handlers": 1, "queue": 1000, "processing": { "kind": "fixed", "mean": "0.2ms" },
  "capacity": 50000, "ttl": "60s", "ttlJitter": "0%",
  "keySpaces": [ { "id": "product", "keys": 100000, "zipf": 1.0, "ttl": "30s" } ],
  "prefill": { "kind": "hot", "keys": 5000 } } }
```

| Параметр | Вид, начальное значение |
|---|---|
| `handlers` | целое ≥ 1, `1` |
| `queue` | целое ≥ 0, как у сервиса |
| `processing` | распределение, `fixed 0.2ms`; одинаково для GET и SET |
| `capacity` | целое ≥ 1, `10000` — число записей |
| `ttl` | длительность > 0, `60s` |
| `ttlJitter` | доля 0–100 %, `0%`; фактический TTL `ttl × (1 + ttlJitter × u)`, `u` равномерно на [−1, 1] |
| `keySpaces` | непустой массив `{ id, keys, zipf, ttl? }`: `keys` — целое ≥ 1, `zipf` — число ≥ 0 (0 — равномерно), `ttl` — своя длительность пространства; `id` — по правилу идентификаторов, уникален в кэше |
| `prefill` | `{ "kind": "none" }` (начальное) или `{ "kind": "hot", "keys": N }` — N самых популярных ключей **каждого** пространства |

- Ключ — номер `1..keys` в порядке убывания популярности, вероятность пропорциональна `1 / k^zipf`. Ключи разных пространств различны.
- `prefill` — записи в момент 0 повторения с TTL своего пространства (или кэша) и разбросом. Порядок LRU: самый популярный ключ — самый свежий. Проверки: `keys` прогрева не больше `keys` каждого пространства; сумма прогрева по пространствам не больше `capacity`.
- `keySpaces` и `prefill` вариант переопределяет целиком, как `load` и `classes`; сеткой они не перебираются. Числовые параметры (`capacity`, `ttl`, `ttlJitter`, `handlers`, `queue`) перебираются.
- Связь к кэшу — обычная `call` с таймаутом, повторами, пулом и политиками (ADR 0015). Поле `classes` у такой связи не нужно: фильтр задаёт шаг.

**Шаги сценария.** Общие необязательные поля любого шага: `id`, `classes`, `repeat`.

```json
"scenario": [
  { "type": "process" },
  { "type": "parallel", "branches": [
    [ { "type": "cacheRead", "id": "product-read", "connection": "catalog-to-redis", "keySpace": "product",
        "singleFlight": false, "onCacheError": "source",
        "repeat": { "count": 20, "mode": "parallel" },
        "onMiss": [ { "type": "call", "connection": "catalog-to-products-db" } ] } ],
    [ { "type": "call", "connection": "catalog-to-price" } ],
    [ { "type": "call", "connection": "catalog-to-stock" } ]
  ] }
]
```

- `id` — по правилу идентификаторов блоков, уникален во всём сценарии сервиса, включая вложенные шаги. **У `cacheRead` поле `id` обязательно:** по нему задаются поток ключей (инвариант 3) и строки результатов шага. Это уточнение дизайна §3.2 и §3.3, где `id` необязателен у всех шагов.
- `repeat` — `{ count, mode }`: `count` — целое ≥ 1, `mode` — `sequential` или `parallel`.
- `parallel` — `branches`: непустой список веток, каждая ветка — непустой список шагов.
- `cacheRead`:
  - `connection` — связь `call` этого сервиса к блоку `cache`;
  - `keySpace` — пространство этого кэша;
  - `onMiss` — список шагов, может быть пустым;
  - `singleFlight` — логическое, `false`;
  - `onCacheError` — `source` (начальное) или `fail`.
- Шаг `call` по связи к кэшу отвергается: у него нет ключа. `classes` действует на любом уровне вложенности: шаг не своего класса пропускается вместе с вложенными.
- Глубина вложенности форматом не ограничивается.

**Отображаемое имя.** У любого блока — необязательное поле `title` рядом с `type`: непустая строка не длиннее 80 знаков, любые буквы, уникальность не требуется. Это решение по UX-ревью 2026-11-01 ([#486](https://github.com/ChernetsovNG/resilience-lab/issues/486)). Ядро только хранит и отдаёт его; сообщения и пути используют идентификатор.

### Эксперимент, версия 4

- **Путь к кратности повтора:** `<сервис>.steps.<id шага>.repeat.count`. Он допустим в `overrides` и `grid`, значения — целые ≥ 1. Шаг с этим `id` должен существовать и иметь `repeat` в модели: путь меняет только `count`, а `mode` остаётся из модели. У группы реплик путь действует на сценарий группы. Остальная структура сценария, как и раньше, не переопределяется.
- **Отказ `flush`:** `{ "target": "redis", "kind": "flush", "at": "20s" }` — только у блока `cache`; `at` лежит между началом разогрева и концом измерения. Остальные виды отказов у кэша действуют на обработку операций, как у сервиса.

### Семантика движка

- **Повтор.** `sequential` — `count` выполнений подряд; `parallel` — `count` одновременных копий, ожидание всех. Неуспех: при `sequential` — первая неуспешная копия завершает шаг; при `parallel` — причина первой неуспешной копии в порядке копий, остальные дорабатывают.
- **`parallel`.** Ветки запускаются одновременно, шаг ждёт все. Причина неуспеха — первой неуспешной ветки в порядке веток. Остальные ветки дорабатывают, их работа учитывается в метриках (ADR 0017).
- **Синхронность.** Обработчик сервиса удерживается до конца шага. Таймауты, повторы и политики действуют на каждый вызов внутри ветки; дедлайн общий. Заглушка в любой ветке отмечает исходный запрос `degraded` по прежнему правилу. Брошенная работа сервиса (вызывающий уже не ждёт) продолжает все свои ветки.
- **`cacheRead`.**
  1. Ключ выбирается в момент запуска шага.
  2. GET по связи. Попадание определяется в момент обработки в кэше, после очереди:
     - запись есть и не истекла — попадание, позиция LRU обновляется;
     - запись истекла — промах «истёк», запись удаляется;
     - записи нет — промах «нет в кэше».
  3. При промахе выполняется `onMiss`. Если он непуст и успешен, затем SET по той же связи. Вызывающий ждёт ответа SET; неуспех SET не делает шаг неуспешным.
  4. Пустой `onMiss` — промах завершает шаг успешно, без SET.
  5. Неуспех `onMiss` — шаг неуспешен с его причиной, без SET.
- **Ошибка кэша** — GET неуспешен после всех попыток вызова (причина из списка причин второго среза: `timeout`, `unavailable`, `circuitOpen`, …). При `source` выполняется `onMiss`, SET пропускается. При `fail` шаг неуспешен с причиной вызова. Заглушка (`call.fallback`) на связи к кэшу применяется к итогу GET по прежнему правилу и считается попаданием без значения: `onMiss` не выполняется.
- **SET** записывает ключ в момент обработки с TTL пространства (или кэша) и разбросом. При переполнении вытесняется запись с самым давним обращением.
- **Объединение промахов** (ADR 0016, п. 4). Группа — экземпляр вызывающего сервиса, кэш, пространство и ключ; участвуют только шаги с `singleFlight: true`. Первое выполнение с промахом (или ошибкой кэша при `source`) загружает ключ, остальные ждут его исхода. Успех — ожидающие завершают шаг успешно без своего SET; неуспех — ту же причину. Ожидание не занимает соединения пула, не делает вызовов и ограничено только дедлайном запроса.
- **Сброс** очищает хранилище в момент `at`. Идущие загрузки завершаются как обычно и записывают свои ключи.
- Состояние хранилища и групп объединения сбрасывается в начале каждого повторения.

### Результаты, артефакт версии 20

Вводит T3.1; до неё задачи T2 собирают счётчики кэша в коллекторе и проверяют их тестами движка, не записывая в артефакт.

- **Строка кэша** — в `nodes` рядов и в словаре `services` итогов, по идентификатору блока, как у `database`. Общие поля (`offeredAttempts`, `admittedAttempts`, `successes`, `failures`, `latency`, `slotPools.handlers`) описывают операции GET и SET. `timeouts` и `retries` у кэша равны нулю. Дополнительно — объект `cache`:

  | Поле | Смысл |
  |---|---|
  | `gets`, `hits`, `missesAbsent`, `missesExpired`, `sets`, `evictions`, `flushes` | счётчики операций и событий хранилища; `gets = hits + missesAbsent + missesExpired` по обработанным GET |
  | `entries` | в окне — число записей в конце окна; в итогах — `entriesIntegralMs` (интеграл числа записей по измерению) |
  | `keySpaces` | `{ <id>: { gets, hits, missesAbsent, missesExpired } }` |

- **Шаги `cacheRead` вызывающего** — у строки сервиса и экземпляра объект `cacheReads`: `{ <id шага>: { reads, hits, misses, cacheErrors, sourceLoads, singleFlightWaits } }`.
  - `reads = hits + misses + cacheErrors`;
  - `sourceLoads` — выполнения `onMiss`;
  - `singleFlightWaits` — выполнения, дождавшиеся чужой загрузки;
  - `sourceLoads + singleFlightWaits ≤ misses + cacheErrors`.

  У группы реплик значения суммируются по экземплярам.
- **Версии:** артефакт 20, ряды 8, итоги повторения 8. Пустые `cache` и `cacheReads` опускаются в файлах, API выдаёт их явно, как пулеры.
- **Сводка** — `aggregate.services.<кэш>.cache.hitRate`: `MetricSummary` доли `hits / gets` по повторениям; объединённые счётчики `cache` в `totals`.
- **Выходы каталога** (ADR 0011):
  - кэш — `operationsPerSecond`, `hitRate`, `missesAbsentPerSecond`, `missesExpiredPerSecond`, `evictionsPerSecond`, `entries`, а также общая загрузка обработчиков, как у сервиса;
  - сервис — `cacheSourceLoadsPerSecond` (сумма по шагам).

  Отдельных выходов по пространствам ключей и шагам нет: интерфейс и CLI читают `keySpaces` и `cacheReads` напрямую.
- Вывод о насыщении не меняется: обработчики кэша — обычный набор слотов.

## T1 Модель 7 и эксперимент 4: документ, компилятор, IR

**Не входит:** движок (T2), результаты (T3.1), линтер и оценка стоимости (T3.2), интерфейс правки (T4).

**Контракт.**
- Форматы — по разделу «Общие форматы». Каталог описывает тип `cache` и его параметры с подсказками; версия каталога растёт.
- **Проверки** (новые коды `CoreMessage` с аргументами и переводами):
  - `connection` шага `cacheRead` ведёт к блоку `cache`; `keySpace` объявлено в этом кэше;
  - обычный `call` к кэшу запрещён;
  - ветки `parallel` непусты; `count ≥ 1`; `id` уникальны в сценарии; у `cacheRead` есть `id`;
  - у кэша нет `scenario` и `replicas`;
  - прогрев помещается в `capacity` и в число ключей;
  - путь `repeat.count` ведёт к существующему шагу с `repeat`;
  - `flush` — только у кэша, `at` — в пределах прогона.
- **IR:** узел кэша с параметрами хранилища и пространствами; `ServiceStep` — дерево (`CacheRead` с `onMiss`, `Parallel` с ветками, `repeat` у любого шага). Обход путей и достижимость учитывают вложенные шаги.
- **Движок до T2.** Запуск модели с кэшем, `repeat` или `parallel` отвергается понятной ошибкой с новым кодом. Ни один пример эти конструкции пока не использует. T2.1 и T2.2 снимают ограничение для своих конструкций.

**Приёмка.**
- Unit: каждая проверка — валидный и невалидный документ; IR вложенного сценария (три уровня); путь `repeat.count` в варианте и сетке; `title` сохраняется и возвращается без изменений.
- Прежние примеры переписаны под версии 7 и 4 без изменений смысла; модель 6 и эксперимент 3 — `SCHEMA_VERSION`. Инвариант 1 — числа сводки прежних примеров не меняются.
- `./gradlew clean build`; web — `npm run api:generate`, `npm test -- --run`, затронутые E2E (инвариант 6: в редакторе сценария модель с вложенными шагами открывается, сохраняется без потерь, новые шаги — только для чтения).

## T2.1 Движок: повтор и параллельные ветки

**Входит:** выполнение дерева шагов, `repeat` в обоих режимах, `parallel`; снятие ограничения T1 для этих конструкций.

**Не входит:** кэш (T2.2).

**Контракт.**
- Семантика — по разделу «Семантика движка». Ветки и параллельные копии — отдельные сущности KSL с ожиданием всех (S1: `activate`, `blockUntilAllCompleted`).
- **Общее состояние запроса** (клиент, вид запроса, дедлайн, когорта, `degraded`) ветки разделяют с родителем, а не копируют. Признак `degraded` из любой ветки доходит до исходного запроса.
- Новых потоков случайных чисел нет: шаги внутри веток берут числа из тех же потоков, что и раньше. Порядок выборки детерминирован порядком событий (инвариант 2).

**Приёмка.**
- Unit:
  - последовательный повтор — задержка шага около `count ×` одного выполнения;
  - параллельный повтор и `parallel` — ожидание самой медленной копии или ветки;
  - причина первой неуспешной ветки и копии в их порядке;
  - остальные ветки дорабатывают и учитываются в метриках связей;
  - обработчик удерживается до конца шага;
  - дедлайн, истекший внутри ветки, даёт `deadline`;
  - заглушка в ветке даёт `degraded`.
- **Хвост fan-out** (критерий дизайна §2, п. 5) на укороченной модели с экспоненциальным временем у зависимости: при `count` 1 и 20 в режиме `parallel` p99 входа заметно растёт, а средняя задержка вызова почти не меняется. Числа — в PR.
- Инварианты 1, 2 и 7.

## T2.2 Движок: хранилище кэша, чтение через кэш, сброс

**Входит:** узел кэша в движке (обработка операций, отказы), хранилище с LRU и TTL, разброс, прогрев, `cacheRead`, `onCacheError`, объединение промахов, отказ `flush`, счётчики кэша в коллекторе; снятие ограничения T1 для кэша.

**Не входит:** запись счётчиков в артефакт и ряды, выходы каталога, CLI (T3.1).

**Контракт.**
- Семантика — по разделу «Семантика движка», ADR 0016. Хранилище — точная модель по ключам. Память пропорциональна числу записей, а не `keys`; таблица выборки Зипфа допустима, если её размер в PR оценён для `keys = 10⁶`.
- Потоки — по инварианту 3.
- Счётчики собираются в тех же точках и с тем же правилом когорты, что поля «Результаты, артефакт версии 20»: T3.1 только записывает их.

**Приёмка.**
- Unit, детерминированные сценарии хранилища: попадание; промах «нет в кэше»; промах «истёк» с удалением; вытеснение LRU; разброс TTL в заданных пределах; прогрев и одновременное истечение; сброс; загрузка, идущая во время сброса, записывает ключ.
- Объединение промахов: ожидающие получают результат загрузки без своего SET; неуспех загрузки передаётся ожидающим; разные экземпляры загружают независимо; шаг без `singleFlight` не ждёт чужих загрузок.
- Ошибка кэша: `source` — `onMiss` без SET; `fail` — шаг неуспешен с причиной вызова; пустой `onMiss` при промахе — успех без SET.
- Выбор ключей: частоты сходятся с Зипфом в пределах статистической погрешности; добавление шага или пространства не меняет ключи остальных шагов.
- Качественно, на укороченных моделях (числа — в PR):
  - холодный кэш — доля попаданий растёт от нуля;
  - прогрев без разброса — всплеск промахов в момент истечения, с разбросом 20 % — пик ниже;
  - сброс при перекошенной популярности — пик обращений к источнику ниже с объединением промахов, чем без него.
- Инварианты 1, 2 и 7.

## T3.2 Линтер и оценка стоимости

**Входит:** обход дерева шагов и кратности повторов в линтере и оценке стоимости; предупреждение о размере кэша.

**Не входит:** правило «источник не выдержит нагрузки без кэша». Это возможное расширение; если оно нужно, его заводят отдельной задачей.

**Контракт.**
- **Нагрузка** (`serviceLoad` и правила, которые её используют) учитывает кратность `repeat` и вложенные шаги. Для `cacheRead` берётся путь попадания: GET без `onMiss` и SET. Сообщение правила, которое затрагивает такой шаг, говорит, что нагрузка источника при промахах не учтена.
- **Время ответа** для правил таймаута: последовательный повтор — `count ×`, параллельный повтор и `parallel` — максимум по копиям и веткам, `cacheRead` — путь попадания.
- **Оценка стоимости:** события на запрос умножаются на кратности; память прогона учитывает записи кэшей (`capacity` или сумма `keys`, если она меньше).
- **Новое предупреждение:** `capacity` или сумма `keys` пространств кэша больше порога. Порог выбери по замеру памяти одного прогона и опиши его в PR.

**Приёмка.**
- Unit: нагрузка с последовательным и параллельным повтором и с `parallel`; таймаут против максимума веток; оценка стоимости растёт с `count`; предупреждение о размере есть выше порога и нет ниже.
- Предупреждения прежних примеров не меняются.
