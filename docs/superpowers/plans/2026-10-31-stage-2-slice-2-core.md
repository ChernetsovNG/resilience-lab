# Этап 2, срез 2: ядро — клиенты, классы запросов и политики отказоустойчивости — план-контракт

**Цель.** Дать ядру всё, что нужно второму срезу: несколько клиентов, классы запросов со своими профилями нагрузки, причины отказов в результатах и пять политик отказоустойчивости — с форматами, которые интерфейс (T4) и пример (T5) возьмут без изменений.

**Как читать.** Это план-контракт, а не пошаговый рецепт. Для каждой задачи он фиксирует границы, общие форматы, инварианты и приёмку. Внутреннее устройство и тесты исполнитель выбирает сам, по правилам `AGENTS.md`. Расхождение с ADR или дизайном обсуждается в issue до реализации. **Форматы из раздела «Общие форматы» обязательны для всех задач:** задача не меняет их молча; если формат не подходит, это обсуждается в issue и правится в этом плане до реализации.

## Исходное состояние

- **Один клиент.** Компилятор требует ровно один `client` и одну связь `request` (`TOPOLOGY_CLIENT`, `TOPOLOGY_GRAPH`); `GraphIr` хранит одиночные `client` и `entry`; движок создаёт один генератор прибытий; строка клиента в рядах имеет фиксированный идентификатор `client`; линтер и оценка стоимости берут нагрузку и дедлайн единственного клиента.
- **Метрики входа** — поля верхнего уровня: в `ReplicationResult` — `allLatency`, `successfulLatency`, `failedLatency`, `originalArrivals`, `successes`, `failures`; в `AggregateMetrics` — `pooledLatency`, `successRate`, `p95LatencyMs`, `p99LatencyMs`. Знаменатель усиления — `client.originalArrivals`.
- **Причины отказов не сохраняются.** Движок различает исходы попытки (`AttemptOutcome`: `LOCAL_FAILURE`, `DOWNSTREAM_FAILURE`, `TIMED_OUT`, `ACQUIRE_TIMED_OUT`, `QUEUE_REJECTED`, `DEADLINE_EXCEEDED`), но в сводку и ряды попадают только счётчики `failures`, `timeouts` и косвенно `queueFullCount`, `waitLimitCount` наборов слотов.
- **Атрибутов запроса** кроме времени прибытия, дедлайна и когорты нет.
- **Политик нет.** Точки встраивания: `ServiceInvocation.executeCall` (до попытки и после исхода), `RouterRuntime.select`/`complete`, приём у сервиса перед занятием обработчика.
- **Версии:** модель 5, эксперимент 2, раскладка 1; артефакт (манифест и сводка) 15, ряды 6, итоги повторения 5; каталог 4.

## Общие инварианты

1. **Равенство чисел на прежних примерах.** `examples/retry-storm/`, `examples/checkout/` и `examples/checkout-replicas/` (один клиент, без классов, политики выключены) дают те же числа сводки и рядов, что до среза: значения метрик входа переезжают в `entries.total` без изменения; меняется только раскладка полей и версия. Для этого класс `default` клиента без `classes` использует **тот же** поток случайных чисел, что прежний единственный клиент. Если число всё же изменилось, PR объясняет причину и показывает, что новое значение внутри прежнего доверительного интервала.
2. **Детерминизм.** Артефакт побайтно повторяется при 1, 2, 4 и 8 потоках и не зависит от порядка задач.
3. **Пути и случайные числа** (ADR 0006, 0012). Новые потоки: прибытия класса — по пути клиента и идентификатору класса. Политикам потоки не нужны.
4. **Версии без совместимости.** Каждая смена формата повышает `schemaVersion`, переписывает `examples/**` и фикстуры; документ или прогон прежней версии получает понятную ошибку о версии (`SCHEMA_VERSION`, `RUN_VERSION_UNSUPPORTED`). Схемы — `UPDATE_SCHEMAS=1`, OpenAPI — `UPDATE_OPENAPI=1`, типы web — `npm run api:generate`, эталон рядов — `UPDATE_SERIES_GOLDEN=1` (команды в `AGENTS.md`).
5. **Сообщения** — `CoreMessage` с аргументами и ключи `messages.<CODE>` в `web/src/i18n/en.json` и `ru.json`.
6. **Web не теряет данные.** До T4 интерфейс не правит новые поля, но открывает и сохраняет документы версии 6 без потерь; неизвестные параметры показываются только для чтения. Каждая задача, меняющая формат, проходит `npm test -- --run` и затронутые E2E.
7. **Выключенная политика не меняет ни поведения, ни чисел** (ADR 0015).
8. **Новые зависимости** — только с обоснованием в issue.

## Общие форматы

### Модель, версия 6

Клиент — либо `load`, либо `classes`:

```json
"mobile-app": { "type": "client", "params": {
  "deadline": "2s",
  "classes": [
    { "id": "status",   "load": { "points": [ { "time": "0s", "rate": "80/s" } ] } },
    { "id": "checkout", "load": { "points": [ { "time": "0s", "rate": "20/s" }, { "time": "30s", "rate": "60/s" } ] } }
  ] } }
```

- `client.params.classes` — параметр-массив объектов `{ id, load }`; `load` того же формата, что `client.params.load`. Вариант переопределяет `classes` клиента целиком, как `load` (срез 1). Перебор сеткой запрещён, как у `load`.
- Идентификатор класса — по правилу идентификаторов блоков; `default` зарезервирован за клиентом без `classes`.
- Шаг сценария: необязательное поле `classes` — массив идентификаторов, рядом с `type`:
  `{ "type": "call", "connection": "order-to-payment", "classes": ["checkout"] }`.
- Связь `route`: необязательное поле `classes` на уровне связи, рядом с `params`, а не параметр: это структура, вариант её не переопределяет.
- Параметры политик (имена фиксированы; все — необязательные объекты, отсутствие — политика выключена):

| Параметр | Поля (вид, начальное значение) |
|---|---|
| `call.circuitBreaker` | `failureRate` (доля, `50%`), `minimumCalls` (целое, 10), `window` (целое, число попыток, 20), `openDuration` (длительность, `5s`), `halfOpenCalls` (целое, 3) |
| `call.retryBudget` | `ratio` (доля, `20%`), `minPerSecond` (интенсивность, `10/s`), `window` (длительность, `10s`) |
| `call.fallback` | `on` (массив кодов причин, `["circuitOpen"]`; допустимы `error`, `unavailable`, `timeout`, `queueFull`, `waitLimit`, `circuitOpen`, `rateLimited`, `noRoute`, `noReadyTarget`, но не `deadline`), `processing` (длительность, `1ms`) |
| `call.outlierDetection`, `router.outlierDetection` | `consecutiveFailures` (целое, 5), `baseEjection` (длительность, `30s`), `maxEjected` (доля, `50%`) |
| `service.rateLimit` | `rate` (интенсивность, `100/s`), `burst` (целое, 10) |
| `service.healthCheck` | `interval` (длительность, `10s`), `timeout` (длительность, `1s`), `unhealthyThreshold` (целое, 3), `healthyThreshold` (целое, 1), `processing` (длительность, `1ms`) |

  `call.outlierDetection` допустим только у вызова в группу реплик; `service.rateLimit` и `service.healthCheck` применяются к каждому экземпляру группы и переопределяются в `replicaOverrides`. Числовые поля политик перебираются сеткой.
- Параметры политик — содержимое каталога, а не новый формат документа: их добавляют задачи T2, версия модели остаётся 6, схема `schemas/model.schema.json` пересоздаётся.

### Причины отказа

Единый список кодов (строки в JSON, `camelCase`), общий для попыток, вызовов и входа:

| Код | Когда |
|---|---|
| `error` | ошибка обработки: `failureRate` шага или блока, отказ «ошибки» |
| `unavailable` | отказ «быстрый отказ» (до приёма работы или передачи) |
| `timeout` | таймаут попытки вызова |
| `deadline` | истёк дедлайн исходного запроса |
| `queueFull` | очередь набора слотов полна (обработчики, соединения БД, клиентские подключения пулера) |
| `waitLimit` | ожидание слота превысило предел (пул на связи, серверный пул пулера) |
| `circuitOpen` | breaker открыт (T2.1) |
| `rateLimited` | отклонено ограничением интенсивности (T2.2) |
| `noRoute` | у маршрутизатора нет маршрута для класса запроса (T1.2) |
| `noReadyTarget` | нет готовых экземпляров по health-check (T2.2) |

**Причина неуспеха вызова и входа — исходная.** Вызов, исчерпавший попытки, получает причину своей последней попытки. Неуспешный шаг сценария передаёт причину вызывающему: сервис, у которого не удался вызов, завершает свою работу с причиной этого вызова, а не «ошибка вниз по цепочке». Запрос на входе неуспешен с исходной причиной из глубины пути, кроме `deadline` — она ставится на входе, когда истёк дедлайн клиента. Отклонённый бюджетом повтор — не причина: вызов завершается причиной последней выполненной попытки, а счётчик `retriesDenied` растёт.

**Заглушка.** Если итоговая причина неуспешного вызова (после всех попыток) входит в `call.fallback.on`, вызов через `processing` считается успешным, его причина не передаётся вверх, а счётчик `fallbacks` связи растёт. Исходный запрос, на пути которого сработала хотя бы одна заглушка, успешен и дополнительно учитывается в `degraded`.

### Результаты, артефакт версии 16

- **Итоги повторения.** Поля входа верхнего уровня `ReplicationResult` заменяются объектом `entries`:

  ```json
  "entries": {
    "total":   { "originalArrivals": 7140, "successes": 7050, "degraded": 120, "failures": 90,
                 "failuresByReason": { "timeout": 60, "deadline": 30 },
                 "allLatency": { … }, "successfulLatency": { … }, "failedLatency": { … } },
    "clients": { "mobile-app": { … }, "partner-api": { … } },
    "classes": { "status": { … }, "checkout": { … } }
  }
  ```

  Каждый элемент — одна структура метрик входа; `degraded` — успешные с заглушкой, входят в `successes`; `failuresByReason` содержит только ненулевые причины; сумма по причинам равна `failures`. `total` равен сумме клиентов и сумме классов.
- **Сводка.** Поля входа верхнего уровня `AggregateMetrics` (`pooledLatency`, `successRate`, `p95LatencyMs`, `p99LatencyMs`) заменяются `entries` с той же тройкой `total` / `clients` / `classes`; в каждом элементе — прежние четыре поля, `degradedRate` (`MetricSummary` доли успешных с заглушкой от исходных запросов) и `failuresByReason`: причина → `MetricSummary` доли от исходных запросов этого элемента по повторениям.
- **Попытки по причинам.** У сервиса (`ServiceTotals`) и связи — `failuresByReason`: причина → число неуспешных попыток за измерение.
- **Знаменатель усиления** — `entries.total.originalArrivals`; путь выхода `client.originalArrivals` в описаниях каталога заменяется на `entries.total.originalArrivals` (ADR 0011).
- **Ряды, версия 7.** Строка каждого клиента в `nodes` — по его идентификатору (а не `client`). Новый массив `classes` в части рядов: `{ id, windows }` с теми же полями окна, что у клиента. В окна клиента, класса, сервиса и связи добавляется `failuresByReason`. `clientOriginalArrivals` в строках групп — сумма исходных запросов всех клиентов за окно.
- **Поля политик** в итогах повторения и окнах рядов. Их вводит T3.1 вместе с версиями 16 и 7 и пишет нулями; задачи T2 только заполняют их, поэтому артефакт и ряды больше не меняют версию в этом срезе:

| Где | Поля |
|---|---|
| связь `call` | `circuitOpenMs` (время в открытом состоянии, сумма по вызывающим экземплярам), `circuitRejections`, `retriesDenied`, `fallbacks` |
| вход (клиент, класс, итог) | `degraded` |
| сервис / экземпляр | `rateLimited`, `probes`, `probeFailures`, `notReadyMs` |
| экземпляр — цель маршрутизатора | `ejections`, `ejectedMs` (по всем маршрутизаторам, которые на него ведут) |

- **Выходы каталога политик** (ADR 0011): связь — `circuitOpenShare`, `circuitRejectionsPerSecond`, `retriesDeniedPerSecond`, `fallbacksPerSecond`; клиент — `degradedPerSecond`; сервис — `rateLimitedPerSecond`, `rateLimitedRate`, `probeFailuresPerSecond`, `notReadyShare`; сервис и экземпляр группы — `ejectionsCount`, `ejectedShare`. Отдельных выходов по каждой причине отказа нет: интерфейс и CLI читают `failuresByReason` напрямую.

## T1.1 Модель v6: клиенты и классы — документ, компилятор, IR

**Входит.** Формат модели версии 6 для клиентов и классов (без параметров политик); проверки компилятора; `GraphIr` с несколькими клиентами; линтер и оценка стоимости от всех входов.

**Не входит.** Движок (T1.2), результаты (T3.1), политики (T2).

**Контракт.**
- `client.params.classes`, поле `classes` у шага сценария и у связи `route` — по разделу «Общие форматы». Каталог описывает `classes` клиента с подсказкой; версия типа `client` растёт.
- Проверки: несколько клиентов; у каждого ровно одна `request`; клиент задаёт либо `load`, либо `classes`; идентификаторы классов клиента уникальны и не `default` при явном списке; класс в шаге или маршруте объявлен хотя бы у одного клиента; для каждого класса, который может дойти до маршрутизатора, есть маршрут. Новые коды `CoreMessage` с аргументами и переводами.
- `GraphIr` — список клиентов, у каждого вход, дедлайн и профили классов; множество классов модели; классы у шагов и маршрутов. Обход путей, достижимость, линтер (дедлайн каждого клиента против его пути) и оценка стоимости (сумма средних нагрузок классов) — от всех входов.

**Приёмка.**
- Unit: каждая проверка — валидный и невалидный документ; IR для двух клиентов с общим входом и для классов с фильтрами.
- Прежние примеры переписаны под версию 6 без изменений смысла; модель версии 5 — `SCHEMA_VERSION`.
- `./gradlew clean build`; web — `npm run api:generate`, `npm test -- --run`, затронутые E2E (инвариант 6).

## T1.2 Движок: прибытия по классам, атрибуты, пути по классам

**Входит.** Генераторы прибытий на каждый класс каждого клиента; атрибуты запроса; фильтры шагов и маршрутов; исход «нет маршрута».

**Не входит.** Запись метрик по клиентам и классам и причин в артефакт (T3.1): задача может временно агрегировать вход как сейчас.

**Контракт.**
- Запрос несёт клиента, класс, время прибытия и дедлайн своего клиента; попытки и вложенные вызовы наследуют клиента и класс.

**Приёмка.**

## T3.1 Результаты входа по клиентам и классам, причины отказов

**Входит.** `entries` в итогах повторения и сводке; `failuresByReason` входа, сервисов и связей; исходная причина по цепочке; ряды версии 7 со строками клиентов и классов; поля политик, записанные нулями; артефакт версии 16; CLI.

**Не входит.** Заполнение полей политик и их выходы каталога (T2); интерфейс (T4).

**Контракт.**
- Структуры и коды — по разделу «Общие форматы». Внутренние исходы движка отображаются в коды причин один к одному; `DOWNSTREAM_FAILURE` заменяется передачей исходной причины.
- Выходы каталога, читающие поля входа верхнего уровня и `client.originalArrivals`, переходят на `entries.total.*`; у выходов клиента — значения своего элемента `entries.clients.<id>`.
- Вывод о насыщении и запас по ёмкости не меняются.
- CLI `run` и `summary` печатают строку входа `total` и, если клиентов или классов больше одного, по строке на каждого; в строке — доля успешных, p95, p99 и до трёх главных причин отказа.
- Обновить `docs/results-format.md`.

**Приёмка.**
- Unit: исходная причина через два уровня вызовов и через повторы; сумма по причинам равна `failures`; `total` равен сумме клиентов и сумме классов.
- Инвариант 1: значения `entries.total` на прежних примерах совпадают с прежними полями верхнего уровня.
- Прогон прежней версии — `RUN_VERSION_UNSUPPORTED`; эталон рядов пересоздан; `WebSeriesGoldenTest` проходит.
- Web: `npm run api:generate`, `npm test -- --run`, затронутые E2E; интерфейс показывает `entries.total` там, где показывал поля верхнего уровня (переименование источника, без новых экранов).

## T2.1 Circuit breaker, бюджет повторов и заглушка

**Входит.** `call.circuitBreaker`, `call.retryBudget`, `call.fallback`: каталог, проверки, движок, поля в итогах и рядах, выходы каталога.

**Не входит.** Интерфейс правки (T4).

**Контракт.**
- Поведение — по дизайну (§3.3) и ADR 0015: breaker — окно по числу попыток, состояние у вызывающего экземпляра, отказ `circuitOpen` без пула, сети и работы у цели, такие отказы в окно не засчитываются; полуоткрытое состояние пропускает `halfOpenCalls` пробных попыток. Бюджет — повторов не больше `ratio` от первых попыток за `window` плюс `minPerSecond × window`; отклонённый повтор увеличивает `retriesDenied`. Заглушка — по разделу «Общие форматы»: применяется к итогу вызова, не к отдельной попытке.
- Поля и выходы — по разделу «Общие форматы».

**Приёмка.**
- Unit: размыкание по порогу и минимуму, время открытого состояния, переходы полуоткрытого состояния; исчерпание и восстановление бюджета; детерминированные сценарии.
- Заглушка: вызов с итоговой причиной из `on` успешен через `processing`, причина не уходит вверх, `fallbacks` и `degraded` растут; причина не из `on` — вызов неуспешен, как без заглушки.
- Бюджет на `retry-storm`: вариант с бюджетом даёт усиление не выше `1 + ratio` плюс вклад минимума; выключенная политика — инвариант 7.

## T2.2 Ограничение интенсивности и health-check

**Входит.** `service.rateLimit`, `service.healthCheck`: каталог, проверки, движок, готовность в выборе цели, поля и выходы.

**Контракт.**
- Корзина токенов на экземпляр перед очередью; отказ `rateLimited` без занятия обработчика.
- Проверка — по ADR 0015: процесс на экземпляр, проходит очередь и занимает обработчик на `processing`; таймаут `timeout`; пороги неуспешных и успешных подряд; неготовый экземпляр исключается из выбора всеми маршрутизаторами; без готовых — `noReadyTarget` сразу. Проверки не входят в когорту.
- Поля и выходы — по разделу «Общие форматы».

**Приёмка.**
- Unit: корзина токенов (интенсивность, всплеск); провал проверок при перегрузке и восстановление; `noReadyTarget`; проверки не меняют метрики входа.
- Детерминированный сценарий каскада: агрессивные пороги при всплеске выводят экземпляры один за другим.

## T2.3 Outlier detection

**Входит.** `router.outlierDetection`, `call.outlierDetection` для вызова в группу: каталог, проверки, движок, поля и выходы.

**Контракт.**
- Состояние у маршрутизатора (в том числе сгенерированного балансировщика группы), общее для вызывающих (ADR 0015). Неуспехом считается неуспех, вызванный выбранным экземпляром. Вывод на `baseEjection × номер вывода`; `maxEjected` ограничивает долю выведенных.
- Выведенные исключаются в `select` вместе с неготовыми и опробованными.
- У группы один сгенерированный балансировщик на все вызовы в неё, поэтому `call.outlierDetection` всех вызовов в одну группу должен совпадать; иначе — ошибка компилятора с новым кодом. Для явного маршрутизатора параметр один — `router.outlierDetection`.
- Поля и выходы — по разделу «Общие форматы».

**Приёмка.**
- Unit: вывод после `consecutiveFailures` подряд, возврат, рост времени вывода, предел доли.
- На `checkout-replicas`: вариант `leastInFlight` с outlier detection уменьшает долю ошибок на входе относительно `leastInFlight` без неё (проверка T5 первого среза показала, что `leastInFlight` притягивает трафик к быстро отказывающей реплике); числа и интервалы — в PR.
