# Дорожка T1 этапа 1: ядро — план-контракт

**Цель.** Довести ядро до дизайна этапа 1 после сквозного среза: JSON-схемы документов, линтер, исполнение с чередованием, отменой и досчётом, ряды по окнам со скетчем задержек, вывод v1, сетка параметров и оценка стоимости.

**Как читать.** Это план-контракт, а не пошаговый рецепт. Для каждой задачи он фиксирует границы, контракты для соседних задач и дорожек, инварианты и приёмку. Структуру классов, реализацию и тесты исполнитель выбирает сам, по правилам `AGENTS.md`. Расхождение с ADR или дизайном этапа 1 обсуждается в issue до реализации.

**Источники.** [Дизайн этапа 1](../specs/2026-10-27-stage-1-design.md): §3.2–3.4, §4, §5.3, §7.2. ADR [0002](../../architecture/adr/0002-model-pipeline.md), [0005](../../architecture/adr/0005-model-file-format.md), [0006](../../architecture/adr/0006-random-streams-by-block-path.md), [0007](../../architecture/adr/0007-simulation-engine-ksl.md), [0008](../../architecture/adr/0008-run-results.md), [0009](../../architecture/adr/0009-execution.md). Исследования: [S1, KSL](../../research/2026-10-27-ksl-capabilities.md) (оценка стоимости), [S3, объём результатов](../../research/2026-10-27-results-volume.md) (бюджеты), S5 — скетч задержек (#67, документ появится в `docs/research/`).

## Общие инварианты

1. **Детерминизм.** При тех же версии, документах и seed артефакт побайтно одинаков при любом числе потоков, порядке задач и порядке блоков в документах (ADR 0006, драйвер D6). Каждая задача, которая трогает исполнение или артефакт, доказывает это тестом.
2. **Сводка — только из частей.** Каждая задача «вариант × точка × повторение» пишет свою часть; сводка считается только из записанных частей, а не из памяти процесса (ADR 0009, п. 5 и 7). Иначе досчёт невозможен.
3. **Достаточные статистики.** В частях и сводке хранятся числители, знаменатели, занятое время, интегралы и сливаемые скетчи, а не готовые доли и квантили. Усреднять квантили нельзя (ADR 0008, п. 4).
4. **Неполнота видна.** Незаконченный, отменённый или упёршийся в бюджет артефакт помечен в манифесте и не выглядит готовым (ADR 0008, п. 2).
5. **Точки сетки.** Точка — сочетание значений осей `grid` в порядке «первая ось внешняя». Идентификатор — `p<k>`, где `k` — индекс с нуля. Без сетки у эксперимента одна точка `p0` без координат. T1.4 пишет части по этому правилу сразу, до T1.6.
6. **Новые зависимости** — только с исследованием или явным согласованием в issue (`AGENTS.md`).
7. **Версии форматов.** Меняется структура манифеста или сводки — растёт их `schemaVersion`. Старые артефакты `.results/` не мигрируются; сервер и CLI сообщают о неподдерживаемой версии понятной диагностикой, а не падением.

## T1.1 JSON-схемы документов

**Входит.** Генерация JSON Schema 2020-12 для `*.model.json`, `*.layout.json` и `*.experiment.json` из классов документов и каталога (дизайн §3.4, ADR 0001, п. 3). Схемы закоммичены; тест или шаг CI проверяет, что повторная генерация не даёт диффа, по образцу `OpenApiSpecTest` (`UPDATE_…=1` пересоздаёт файлы).

**Не входит.** Команда CLI `schema` (T2), подсказки в редакторах кода, `$schema` внутри документов (строгий разбор отвергает неизвестные ключи).

**Контракт.**
- Файлы: `schemas/model.schema.json`, `schemas/layout.schema.json`, `schemas/experiment.schema.json` в корне репозитория.
- Схема модели описывает параметры блока по его типу из каталога: обязательность, тип значения, величины с единицами из `ParamDescriptor.units`, диапазоны, варианты выбора, вложенные поля.
- Схема не строже ядра: всё, что принимают разбор и проверка отдельных полей, проходит схему. Межэлементные правила — ссылки, топология, пути переопределений — остаются компилятору.
- Значения `overrides` и `grid` по путям схема описывает как «любой JSON»: тип зависит от пути.

**Приёмка.**
- Примеры `examples/**` проходят схемы валидатором Draft 2020-12.
- Набор заведомо неверных документов отвергается: неизвестный тип блока, величина без единиц или с чужими единицами, значение вне диапазона, лишнее поле.
- Повторная генерация без изменений даёт пустой дифф; изменение каталога без пересоздания схем роняет проверку.
- Валидатор JSON Schema, если нужен в тестах, — тестовая зависимость с обоснованием в PR.

## T1.2 Линтер

**Входит.** Предупреждения на IR по четырём правилам дизайна (§3.4). Выдача — через `Lab.validate`, то есть в `POST /validate` и CLI `validate`, без изменения формы API.

**Не входит.** Значки на схеме и вкладка Problems (T3.4).

**Контракт.**
- Правила, коды и пороги:

| Код | Условие предупреждения | Порог по умолчанию |
|---|---|---|
| `LINT_TIMEOUT_BUDGET` | timeout вызова меньше, чем нужно downstream-части: попытки следующего вызова × его timeout плюс сумма максимальных задержек backoff | — |
| `LINT_RETRY_AMPLIFICATION` | произведение числа попыток по слоям цепочки больше порога | 10 |
| `LINT_HANDLERS_LITTLE` | обработчиков сервиса меньше λ·W: λ — интенсивность клиента, W — среднее время удержания обработчика (своя обработка плюс ожидаемое время downstream-вызова без отказов и повторов) | — |
| `LINT_DEADLINE_BUDGET` | общий deadline клиента меньше суммы timeout цепочки с учётом попыток | — |

- Каждое предупреждение — `Diagnostic` с `severity = WARNING`, указателем на элемент модели (`document`, `pointer`, `path`) и текстом, в котором названы фактические числа и порог.
- Линтер проверяет IR каждого варианта. Предупреждение, одинаковое во всех вариантах, выдаётся один раз; различающееся называет варианты в тексте.
- Предупреждения не блокируют запуск: `ValidationReport.valid` зависит только от ошибок.
- Формулы, включая учёт сетевых задержек запроса и ответа, записаны в KDoc правил и совпадают с семантикой движка.

**Приёмка.**
- На каждое правило — тест «срабатывает» и «не срабатывает на границе».
- На `examples/retry-storm/` нет ложных срабатываний, а если предупреждение там по существу верно, это обосновано в PR.
- CLI `validate` печатает предупреждения и завершается с кодом 0.

## T1.3 Чередование заданий и отмена

**Входит.** ADR 0009, п. 3 и 6: задачи разных заданий в общем пуле чередуются, короткий прогон не ждёт длинный; кооперативная отмена задания.

**Не входит.** Ручка `POST /jobs/{id}/cancel` и статус `CANCELLED` в API (T2); бюджет памяти (T1.7 даёт оценку, ограничение — по её итогам); досчёт (T1.7).

**Контракт.**
- Исполнитель выдаёт задачи по кругу между активными заданиями; внутри задания — в порядке «вариант, точка, повторение».
- `Lab.run` принимает признак отмены от вызывающего кода; форму признака выбирает исполнитель. После отмены новые задачи задания не стартуют, начатые останавливаются в ближайшей точке проверки модели или доходят до конца за ограниченное время. Вызов завершается исключением отмены, отличимым от ошибки расчёта.
- Отменённое задание не пишет сводку. Пока нет T1.4, оно не оставляет файлов; после T1.4 части готовых задач остаются, а манифест помечает артефакт незаконченным.
- Лимит реального времени на задачу сохраняется.

**Приёмка.**
- Два задания в пуле из одного потока — длинное и короткое, поданное позже: короткое завершается раньше длинного.
- Отмена во время расчёта освобождает потоки в пределах заданного в тесте времени; следующие задания идут.
- Результат неотменённого задания не зависит от параллельных заданий и отмен (инвариант 1).

## T1.4 Ряды по окнам и части артефакта

**Входит.** Дизайн §4.3 и §4.6, ADR 0008: свой сборщик рядов, скетч задержек по итогам S5, части `series/…`, сводка из частей, поле `execution.window`.

**Не входит.** Ручка рядов в API (T2), Timeline и воспроизведение (T4), выборочная трасса (`traces/`, после этапа 1).

**Контракт.**
- `execution.window` — величина длительности, по умолчанию измеряемый интервал / 100. Окна покрывают `[0, warmup + measurement)` от нуля, последнее может быть короче — его длина записана. События после конца измерения (run-out) в ряды не попадают.
- Семантика рядов — по времени события: значение окна описывает то, что произошло в окне. Это отличается от когорты сводки, где учитываются исходы запросов, пришедших за измеряемый интервал, включая их run-out. Разница описана в KDoc и в документации формата.
- Для каждого сервиса и окна: поступило попыток, принято, отклонено по переполнению, успешно, отказов, таймаутов вызывающей стороны, повторов; занятое время обработчиков и их число; интеграл длины очереди. Для клиента и окна: исходные запросы, успехи, неудачи, скетч задержек, отнесённых к окну по моменту завершения. Скетч задержек по сервисам — если S5 покажет, что это укладывается в бюджеты.
- Часть одной задачи — `series/<вариант>/<точка>/rep-<n>.json.gz`, где `n` с нуля. Внутри — описание окон, ряды по узлам и итоги повторения, нужные сводке (инвариант 2). Формат части описан в манифесте (`format`, единицы и смысл метрик); точная JSON-структура — по итогам S5 и описывается в KDoc и в `docs/` вместе с задачей.
- Части пишет готовая задача сразу (ADR 0009, п. 5). Манифест перечисляет части с контрольными суммами и пишется последним; поле полноты отличает готовый артефакт.
- Сводка: метрики считаются из итогов повторений в частях. Квантили задержек повторения считаются из скетча; изменение точности против нынешних точных квантилей отражено в `AGENTS.md` и KDoc `MetricSummary`.
- Бюджеты ADR 0008 (часть до 64 МиБ) проверяются до записи. При превышении — явная ошибка с понятным текстом, а не обрезание.

**Приёмка.**
- Ряды одного повторения сходятся с итогами: сумма успехов по окнам клиента равна успехам по времени событий за `[0, warmup + measurement)`.
- Загрузка обработчиков по окну в `[0, 1]`; при постоянной нагрузке M/M/1 (тест `ExperimentExecutorTest`) средняя по окнам совпадает с нынешней `handlerUtilization` в пределах погрешности теста.
- Артефакт побайтно одинаков при 1 и 3 потоках и при перестановке блоков (инвариант 1).
- Сводка, собранная заново только из частей, совпадает с записанной побайтно.
- Размер части `examples/retry-storm/` указан в PR; при числе узлов и окон из S3 часть укладывается в бюджет или задача объясняет, как это обеспечено.

## T1.5 Вывод v1

**Входит.** Правило насыщения и агрегирование по повторениям (§4.4); данные вывода в сводке.

**Не входит.** Текст вывода в UI (T4), отметка первого насытившегося узла на схеме (T4, #15).

**Контракт.**
- Насыщение узла начинается в первом из трёх окон подряд, где загрузка обработчиков не ниже 95 % и средняя длина очереди больше нуля, либо в окне первого отклонения по переполнению — что раньше. Пороги (3 окна, 95 %, «очередь больше нуля») — параметры правила; они записаны в сводке рядом с выводом.
- Для повторения: узел с самым ранним началом и порядок остальных — путь деградации. Без насыщения — явное «нет».
- По точке варианта: сколько повторений назвали каждый узел первым, медиана и разброс момента начала. Повторения без насыщения учитываются отдельно.
- Вывод — поле сводки на уровне точки варианта. Имена полей выбирает исполнитель, KDoc описывает смысл; форма одинакова для API и CLI.

**Приёмка.**
- Тесты правила на синтетических рядах: три окна подряд, разрыв серии, отклонение раньше трёх окон, одновременное начало у двух узлов с детерминированным порядком, отсутствие насыщения.
- На `examples/retry-storm/` вывод называет узел и момент; если пример не насыщается, это видно в выводе и отмечено в PR.

## T1.6 Сетка параметров

**Входит.** Поле `grid` эксперимента (§3.2): одна или две оси по путям параметров; задачи «вариант × точка × повторение»; части и сводка по точкам.

**Не входит.** Вкладка Map (T4), выбор точки в UI (T4).

**Контракт.**
- Ось — `{ "path": "<id>.<param>[.<field>]", "values": [...] }`, значения в формате документа (величины строками с единицами). Пути и значения проверяет компилятор, ошибки указывают на `/grid/<i>/…`.
- Значение точки применяется поверх переопределений варианта: модель → переопределения варианта → значения точки.
- Порядок точек и идентификаторы — по инварианту 5.
- Сводка: у каждого варианта список точек с координатами (путь → значение) и метриками, включая вывод (T1.5). Без сетки — одна точка `p0`. Поле `aggregate` верхнего уровня варианта заменяется точками, `schemaVersion` сводки растёт; таблица Summary в web и вывод CLI `run` в той же задаче переходят на точки, чтобы `main` не потерял работающую сводку.
- Потоки случайных чисел зависят от пути блока, а не от точки, поэтому точки сравниваются на согласованных числах.

**Приёмка.**
- Сетка 2×3 даёт 6 точек в описанном порядке; ошибки пути и значения указывают на ось.
- Точка, совпадающая с исходной моделью, даёт те же метрики, что прогон без сетки.
- Инвариант 1 при сетке.

## T1.7 Досчёт и оценка стоимости

**Входит.** ADR 0009, п. 7 и 8: досчёт незаконченного артефакта и оценка стоимости до запуска.

**Не входит.** Ручки `POST /estimate`, `POST /jobs/{id}/resume`, команды CLI `estimate` и `resume` (T2); кнопка «Оценить» (#6).

**Контракт.**
- Досчёт: при совпадении версии приложения и хешей модели и эксперимента из манифеста пересчитываются только задачи без части или с неверной контрольной суммой, затем пишутся сводка и манифест. Иначе — отказ с диагностикой и предложением запустить заново.
- Досчитанный артефакт побайтно равен артефакту непрерывного прогона.
- Оценка: число задач; ожидаемое число событий и время расчёта при заданном числе потоков по формуле S1; ожидаемый размер частей по формату T1.4 и S3; сравнение с бюджетами ADR 0008 с понятными предупреждениями. Оценка не запускает модель, кроме короткого пробного прогона, если формула S1 этого требует.
- Обе операции — методы `Lab`; форму результата выбирает исполнитель, она пригодна для API и CLI без перевода.

**Приёмка.**
- Прерванный (отменённый) прогон после досчёта равен непрерывному побайтно; часть с испорченной контрольной суммой пересчитывается.
- Изменение модели после прерывания делает досчёт невозможным с понятной диагностикой.
- Оценка для `examples/retry-storm/` отличается от фактического времени не более чем в заданное в PR число раз, и это число обосновано.
