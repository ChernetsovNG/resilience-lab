# Этап 2, срез 3 — дизайн: кэш и fan-out

Дата: 2026-11-01\
Статус: согласовано\
Связано: [продуктовое видение](../../product/2026-10-27-product-vision.md), §6 (продолжение сквозного кейса «кэш доминирует во времени ответа») и §7 (порядок срезов этапа 2); [дизайн среза 2](2026-10-31-stage-2-slice-2-design.md); [дизайн среза 1](2026-10-30-stage-2-slice-1-design.md); [дизайн этапа 1](2026-10-27-stage-1-design.md); [формат артефакта](../../results-format.md); [исследование S1](../../research/2026-10-27-ksl-capabilities.md) (fan-out в KSL); ADR [0006](../../architecture/adr/0006-random-streams-by-block-path.md), [0011](../../architecture/adr/0011-type-outputs.md), [0012](../../architecture/adr/0012-call-graph-and-replica-groups.md), [0013](../../architecture/adr/0013-slot-pools.md), [0015](../../architecture/adr/0015-resilience-policies.md), [0016](../../architecture/adr/0016-cache-model.md), [0017](../../architecture/adr/0017-fan-out-steps.md)

Срезы 1 и 2 показали отказ медленной реплики и то, как политики его лечат. Следующее продолжение сквозного кейса — сервис, у которого время ответа определяет кэш: на один запрос он делает много чтений кэша и, при промахах, базы данных, часто параллельно. Здесь проблемы другие — холодный кэш после перезапуска, одновременное истечение TTL, лавина промахов на популярный ключ, недоступность кэша, хвост задержки при fan-out — и интуиция в них подводит так же, как в gray failure одной реплики.

## 1. Цель и границы

Цель — собрать на схеме сервис, который читает данные через внешний кэш и параллельно опрашивает зависимости, и увидеть, как ведут себя доля попаданий, нагрузка на БД и p99 при холодном старте, одновременном истечении TTL, сбросе и недоступности кэша, и как с этим справляются разброс TTL и объединение промахов.

Входит:

- блок `cache` — внешний кэш в духе Redis: ёмкость, вытеснение LRU, TTL с разбросом, пространства ключей с популярностью по Зипфу, начальное наполнение;
- шаг сценария «чтение через кэш» (cache-aside): обращение к кэшу, при промахе — вложенные шаги и запись в кэш; объединение промахов (single-flight);
- повтор любого шага N раз подряд или одновременно; шаг «параллельно» с ветками;
- отказ «сброс кэша»;
- результаты кэша и шагов, ряды по окнам, линтер и оценка стоимости;
- API, CLI, интерфейс; пример «каталог товаров» и E2E.

Не входит (точки расширения, §9): локальный кэш в процессе сервиса, кэш как прокси с чтением из источника (read-through), кластер кэша с распределением ключей, отдача устаревшего значения (stale-while-revalidate), hedged requests, пакетное чтение (MGET), гибридная модель ключей.

## 2. Критерии готовности

1. Пример `examples/catalog/` (§8.1) собирается и запускается через интерфейс без правки файлов вручную.
2. Результат качественно воспроизводит ожидаемое поведение:
   - **холодный старт:** доля попаданий растёт от нуля; первые секунды нагрузка на БД и p99 входа выше, чем у прогретого кэша;
   - **одновременное истечение:** после прогрева без разброса TTL — всплеск обращений к БД в момент истечения; с разбросом TTL пик заметно ниже;
   - **лавина промахов:** после сброса кэша при перекошенной популярности объединение промахов снижает пик обращений к БД;
   - **недоступность кэша:** уход всех чтений в БД насыщает её пул и поднимает p99; вариант с breaker на вызове кэша сокращает ожидание таймаутов кэша;
   - **хвост fan-out:** p99 запроса растёт с числом параллельных чтений при почти неизменной средней задержке.
3. Примеры этапа 1 и срезов 1–2 дают те же числа сводки, что до среза; меняется только версия формата.
4. Артефакт побайтно повторяется при любом числе потоков.

## 3. Модель и документы

### 3.1. Блок кэша

Блок `cache` по устройству — узел с набором слотов (ADR 0013), как сервис без сценария:

- `handlers`, `queue`, `processing` — обработка одной операции; у Redis обычно один обработчик;
- `capacity` — число записей; при переполнении вытесняется запись, к которой дольше всего не обращались (LRU);
- `ttl` — время жизни записи по умолчанию; `ttlJitter` — доля разброса, по умолчанию 0: фактический TTL равен `ttl × (1 + ttlJitter × u)`, `u` равномерно на [−1, 1];
- `keySpaces` — пространства ключей: `{ id, keys, zipf, ttl? }`, где `keys` — число различных ключей, `zipf` — показатель перекоса популярности (0 — равномерно), `ttl` — собственный TTL пространства. Ключ — номер в порядке популярности; ключи разных пространств различны;
- `prefill` — начальное наполнение: `none` (холодный кэш) или `{ hot: N }` — N самых популярных ключей каждого пространства записаны в момент 0 с TTL пространства. Прогрев с одинаковым временем записи и создаёт одновременное истечение.

Кэш в срезе — один экземпляр, `replicas` для него не допускается (§9).

### 3.2. Шаг «чтение через кэш»

Шаг `cacheRead` в сценарии сервиса:

- `connection` — связь `call` сервиса к блоку `cache`;
- `keySpace` — пространство ключей этого кэша;
- `onMiss` — вложенные шаги, выполняемые при промахе: любые шаги сценария — вызов БД или другого сервиса, обработка, «параллельно». Список может быть пустым: тогда промах завершает шаг успешно, без обращения к источнику и без SET — так описываются необязательные данные (персональные рекомендации, флаги) и кэш, который наполняет кто-то другой;
- `singleFlight` — объединение промахов, по умолчанию выключено;
- `onCacheError` — `source` (по умолчанию: при ошибке кэша выполнить `onMiss`) или `fail` (шаг неуспешен с причиной ошибки кэша).

Ход шага: операция GET по связи → попадание — шаг окончен; промах — `onMiss`, затем операция SET по той же связи (если `onMiss` не пуст). GET и SET — части шага, а не отдельные шаги сценария. Подробности — §5.

### 3.3. Повтор и параллельность

- У любого шага — необязательный `repeat: { count, mode }`, `mode` — `sequential` или `parallel`. Последовательный повтор — цикл (типичный N+1), параллельный — N одновременных копий шага с ожиданием всех. Каждое повторение `cacheRead` берёт свой ключ.
- Шаг `parallel` — `branches`: список веток, каждая — непустой список шагов. Ветки запускаются одновременно, шаг ждёт все.
- У шага может быть `id` — уникальный в сценарии сервиса идентификатор. `repeat.count` шага с `id` — параметр: его можно переопределить в варианте и перебирать сеткой (путь вида `<сервис>.steps.<id>.repeat.count`, точная форма — в плане-контракте). Остальная структура сценария, как и раньше, правится только на странице модели.
- Фильтр видов запросов (`classes`) работает для всех шагов, включая вложенные.

### 3.4. Отказ «сброс кэша»

Новый вид отказа `flush` у блока `cache`: в момент `at` все записи удаляются. Другие отказы (замедление, ошибки, недоступность, «чёрная дыра», потеря ёмкости обработчиков) действуют на операции кэша, как на обработку сервиса.

### 3.5. Документы и версии

Модель — версия 7 (блок `cache`, новые шаги, `repeat`, `id` шагов), эксперимент — версия 4 (отказ `flush`, пути к `repeat.count`). Прежние версии отвергаются понятной ошибкой о версии, примеры и фикстуры переписываются (`AGENTS.md`, «Устойчивые решения»).

## 4. IR и компилятор

- IR получает узел кэша с параметрами хранилища и пространствами ключей; шаги сценария — дерево: `cacheRead` с вложенными `onMiss`, `parallel` с ветками, `repeat` у любого шага.
- Проверки: `connection` шага `cacheRead` ведёт к блоку `cache`; `keySpace` объявлено в этом кэше; ветки `parallel` непусты; `count ≥ 1`; `id` уникальны; у кэша нет сценария и `replicas`; вызов кэша — только из `cacheRead` (обычный шаг `call` к кэшу отвергается: у него нет ключа).
- Обход путей, оценка стоимости и линтер учитывают вложенные шаги и кратность повторов; ожидание параллельных веток удерживает обработчик сервиса.

## 5. Движок

- **Выбор ключа.** Каждое выполнение `cacheRead` берёт номер ключа из Зипфа своего пространства. Поток случайных чисел привязан к пути шага (ADR 0006): добавление шага или пространства не меняет ключи остальных.
- **GET.** Попадание определяется в момент обработки операции в кэше, после очереди. Запись есть и не истекла — попадание, позиция LRU обновляется; запись истекла — промах «истёк», запись удаляется; записи нет — промах «нет в кэше».
- **SET.** Записывает ключ в момент обработки с TTL пространства (или кэша) и разбросом; поток разброса привязан к пути кэша. При переполнении вытесняется запись с самым давним обращением.
- **Объединение промахов** — состояние вызывающего экземпляра сервиса (ADR 0015, п. 2): первый промах по ключу загружает его, остальные выполнения `cacheRead` этого экземпляра с тем же ключом ждут результата. Успех — ожидавшие получают значение без своего SET; неуспех — ту же причину отказа. Ожидание не занимает соединения пула и не делает вызовов.
- **Ошибка кэша.** При `onCacheError: source` выполняется `onMiss`, а SET после ошибки кэша пропускается — запись в упавший кэш не делается. При `fail` шаг неуспешен с причиной ошибки кэша.
- **Fan-out.** Ветки и параллельные повторы — отдельные процессы, как в S1; родитель ждёт все. Обработчик сервиса удерживается до конца шага. Таймауты, повторы и политики действуют на каждый вызов внутри ветки; дедлайн общий. Если ветка неуспешна, шаг неуспешен с причиной первой неуспешной ветки в порядке веток; остальные ветки дорабатывают, их работа учитывается.
- **Сброс** очищает хранилище в момент `at`; идущие загрузки single-flight завершаются как обычно и записывают свои ключи.
- **Детерминизм.** Состояние хранилища сбрасывается в начале каждого повторения; порядок событий фиксирован; артефакт побайтно повторяется при любом числе потоков. Хранилище — точная модель по ключам (ADR 0016); память пропорциональна числу записей, линтер предупреждает о больших `capacity` и `keys`.

## 6. Результаты и вывод

- **Кэш** (выходы ADR 0011, ряды по окнам): операции в секунду, загрузка обработчиков, доля попаданий, промахи «нет в кэше» и «истёк», вытеснения, число записей во времени, сбросы.
- **Пространство ключей** — доля попаданий и промахи по пространству.
- **Шаг `cacheRead`** по вызывающему сервису — обращения к источнику на промах, ожидания single-flight (промахи, не дошедшие до источника), ошибки кэша с уходом в источник.
- **Fan-out** отдельных выходов не получает: хвост виден в p99 вызовов и входа.
- Вывод о насыщении не меняется: обработчики кэша — обычный набор слотов. События кэша в выводе — точка расширения.
- Формат артефакта повышается; ряды получают поля кэша.

## 7. API, CLI и интерфейс

API и CLI меняют содержимое по ADR 0010: каталог с блоком `cache`, документы новых версий, выходы и ряды кэша. CLI `summary` печатает строки кэшей с долей попаданий.

Интерфейс:

- **Палитра** — блок «Кэш». На узле — объём и TTL, после прогона — доля попаданий.
- **Инспектор кэша** — параметры и таблица пространств ключей: имя, число ключей, перекос, свой TTL; начальное наполнение.
- **Редактор сценария** — шаги «Чтение через кэш» (связь, пространство, «при промахе» — вложенные шаги, объединение промахов, поведение при ошибке кэша) и «Параллельно» (ветки); у любого шага — «Повторить: N раз, подряд или одновременно» и необязательное имя шага. Вложенность — отступами.
- **Связи** — при повторе подпись показывает кратность «×N»; у связи к кэшу после прогона — доля попаданий.
- **Отказы** — вид «сброс кэша» с моментом времени у блока кэша.
- **Timeline** — попадания и промахи, число записей, вытеснения, отметки сбросов.

*Сцена:* пользователь добавляет блок «Кэш» и протягивает связь от `catalog-service`. В сценарии сервиса вставляет «Чтение через кэш» по пространству `product` с вызовом БД при промахе и ставит «Повторить 20 раз одновременно». Запускает эксперимент со сбросом кэша на 20-й секунде: на Timeline доля попаданий падает до нуля, обращения к БД резко растут. Он включает объединение промахов — пик ниже. *Неудобный случай:* три уровня вложенности («параллельно» → «чтение через кэш» → «при промахе» → вызов) читаются в инспекторе без горизонтальной прокрутки; глубже трёх уровней редактор не даёт вложить.

## 8. Порядок работ и проверка

### 8.1. Пример

`examples/catalog/`:

```
web ──→ api-gateway ──→ catalog-service ×3 ─┬→ redis
                                             ├→ (пул 10) → products-db
                                             ├→ price-service
                                             └→ stock-service
```

Сценарий `catalog-service`: обработка; «параллельно» — ветка 1: «чтение через кэш» `product` × 20 одновременно, при промахе — вызов `products-db`; ветка 2: вызов `price-service`; ветка 3: вызов `stock-service`.

Эксперименты: «холодный старт» (пустой кэш и прогретый), «одновременное истечение» (прогрев, TTL 30 s без разброса и с разбросом 20 %), «лавина промахов» (перекошенная популярность, сброс, single-flight выключен и включён), «падение Redis» (недоступность кэша; вариант с breaker на вызове кэша), «хвост fan-out» (сетка по числу параллельных чтений). Источники чисел и допущения — в `notes`.

### 8.4. Тесты

- Детерминированные сценарии хранилища: попадание, промах «нет», промах «истёк», вытеснение LRU, разброс TTL, прогрев и одновременное истечение, сброс.
- Single-flight: ожидающие получают результат загрузки; неуспех загрузки передаётся ожидающим; разные экземпляры сервиса загружают независимо.
- Fan-out: ожидание всех веток, причина первой неуспешной ветки, удержание обработчика, дедлайн внутри веток; последовательный и параллельный повтор.
- Выбор ключей: частоты сходятся с Зипфом в пределах погрешности; добавление шага не меняет ключи остальных.
- Равенство чисел на прежних примерах (§2, п. 3); побайтная воспроизводимость при 1, 2, 4 и 8 потоках на укороченных копиях.
- E2E: сборка кэша и шагов через интерфейс, прогон, результаты кэша на Timeline.

## 9. Точки расширения

Формат, IR и движок не должны запрещать:

- **локальный кэш в процессе сервиса** — та же модель ключей как параметр вызова;
- **read-through** — кэш как прокси со своей связью к источнику;
- **кластер кэша** — несколько экземпляров с распределением ключей и отказом одного узла;
- **stale-while-revalidate** — отдача истёкшего значения с фоновым обновлением;
- **hedged requests** — дубль медленной ветки fan-out, первый ответ;
- **пакетное чтение (MGET)** — N ключей одной операцией;
- **гибридная модель ключей** — точная для горячих ключей, аналитическая для хвоста;
- **запись и инвалидация** — шаги, удаляющие или обновляющие ключи;
- **события кэша в выводе** — сброс и лавина промахов как причины насыщения.

## 10. Открытые вопросы

- Время операции кэша по умолчанию и учёт размера значения: в срезе размер значения не моделируется, время операции одинаково для GET и SET.
- Нужно ли ожидание single-flight ограничить таймаутом вызывающего отдельно от дедлайна; в срезе ожидание ограничено только дедлайном запроса.
- Как показывать в интерфейсе шаги глубже трёх уровней, если пример реального сервиса их потребует.
