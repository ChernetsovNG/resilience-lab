# Этап 2, срез 2 — дизайн: несколько клиентов, классы запросов и политики отказоустойчивости

Дата: 2026-10-31\
Статус: согласовано\
Связано: [продуктовое видение](../../product/2026-10-27-product-vision.md), §3, §6 и §7 (порядок срезов этапа 2, решение 2026-10-31); [дизайн среза 1](2026-10-30-stage-2-slice-1-design.md); [дизайн этапа 1](2026-10-27-stage-1-design.md); [формат артефакта](../../results-format.md); [ADR 0006](../../architecture/adr/0006-random-streams-by-block-path.md), [ADR 0011](../../architecture/adr/0011-type-outputs.md), [ADR 0012](../../architecture/adr/0012-call-graph-and-replica-groups.md), [ADR 0013](../../architecture/adr/0013-slot-pools.md)

Срез 1 показал на сквозном кейсе проблему: путь одной реплики медленный, p99 и ошибки на входе растут, первым насыщается пул этой реплики. Срез 2 отвечает на следующий вопрос пользователя — что поможет и что навредит. Для этого в модель входят политики отказоустойчивости, а чтобы модель была похожа на реальную систему — несколько входов и разные виды запросов.

## 1. Цель и границы

Цель — сравнивать на сквозном кейсе варианты «с политикой и без», видеть, кому из клиентов и какому виду запросов стало лучше или хуже, и воспроизвести продолжение кейса из видения: health-check выводит перегруженные реплики из трафика, оставшиеся перегружаются, начинается каскад.

Входит:

- несколько блоков `client` в одной модели, у каждого свои нагрузка и дедлайн;
- классы запросов: у каждого класса клиента свой профиль нагрузки, шаги сценария и маршруты только для своих классов;
- результаты на входе по клиентам и по классам;
- circuit breaker и бюджет повторов на связи `call`;
- ограничение интенсивности на сервисе;
- outlier detection на маршрутизаторе и на связи в группу реплик;
- health-check сервиса с выводом экземпляра из трафика;
- API, CLI и интерфейс для всего перечисленного; пример и E2E.

Bulkhead отдельной политикой не вводится: его роль уже выполняет пул соединений на связи (срез 1).

Не входит — точки расширения (§9): outlier detection отдельно у каждого вызывающего, статистика успешности вместо подряд идущих ошибок, дедлайн и приоритет по классу, ограничение интенсивности по клиенту или классу, адаптивное ограничение параллельности, hedged requests (с fan-out в срезе 3), ключи запросов (кэш, срез 3), очереди и брокеры (срез 4).

## 2. Критерии готовности

1. Пример `examples/checkout-policies/` (§8.1) собирается и запускается через интерфейс без правки файлов вручную.
2. Результат качественно воспроизводит ожидаемое поведение:
   - outlier detection выводит медленную реплику #2: p99 на входе после вывода близок к уровню без отказа, без политики — остаётся высоким;
   - circuit breaker на вызове оплаты при «чёрной дыре» PSP быстро отказывает и освобождает обработчики `order-service`: запросы класса, который не вызывает оплату, сохраняют успешность; без breaker они деградируют из-за общих обработчиков;
   - бюджет повторов ограничивает усиление на `retry-storm` этапа 1 примерно долей бюджета; без бюджета усиление растёт до числа попыток;
   - агрессивный health-check при всплеске нагрузки выводит перегруженные реплики, и начинается каскад; умеренные пороги каскада не дают;
   - ограничение интенсивности на входном сервисе отклоняет избыток сразу, p99 принятых запросов остаётся стабильным;
   - всплеск одного клиента повышает p99 другого клиента, и это видно в результатах по клиентам.
3. Примеры этапа 1 и среза 1 (политики выключены, один клиент, один класс) дают те же числа сводки, что до среза; меняется только раскладка полей результата.
4. Артефакт побайтно повторяется при любом числе потоков.

## 3. Модель и документы

### 3.1. Несколько клиентов

В модели один или несколько блоков `client`. У каждого клиента своя нагрузка — один профиль `load` или профили классов (§3.2), свой дедлайн и ровно одна связь `request` к своему входу. Несколько клиентов могут ходить в один вход. Правила топологии этапа 1 и среза 1 сохраняются для каждого входа: вход не получает вызовов `call`, граф без циклов; каждый блок достижим хотя бы из одного входа.

Потоки случайных чисел прибытий уже связаны с путём клиента (ADR 0006), поэтому добавление клиента не меняет прибытия остальных.

Когорта измерения — исходные запросы всех клиентов, пришедшие в измеряемом интервале. Каждый исходный запрос помнит своего клиента. Знаменатель усиления у связей — исходные запросы всех клиентов.

### 3.2. Классы запросов

Класс запроса — строковый идентификатор вида (`status`, `checkout`, `read`, `write`), который запрос несёт от входа до конца пути, включая все попытки и вложенные вызовы.

- **Где задаётся.** У клиента необязательный параметр `classes` — список `{ id, load }`: у каждого класса свой кусочно-линейный профиль нагрузки того же формата, что `client.load` (срез 1, §3.4). Нагрузка клиента — сумма профилей его классов. Так описываются и постоянная смесь (профили одной формы), и неравномерная: пик оформлений заказов при ровных запросах статуса. Клиент задаёт либо `load`, либо `classes`, но не оба; без `classes` у запросов клиента один класс `default` с профилем `load`. Идентификатор класса общий для модели: разные клиенты могут слать один и тот же класс.
- **Шаг сценария.** У шага необязательное поле `classes` — список классов, для которых шаг выполняется. Остальные классы шаг пропускают. Без поля шаг выполняется для всех.
- **Маршрут.** У связи `route` необязательное поле `classes`: маршрут доступен только запросам этих классов. Если для класса запроса у маршрутизатора нет доступного маршрута, попытка получает отказ «нет маршрута».
- **Проверки компилятора.** Идентификаторы классов клиента не повторяются; профиль каждого класса проверяется, как `client.load`. Класс в шаге или маршруте должен объявляться хотя бы у одного клиента. Для каждого класса, который может дойти до маршрутизатора, должен быть хотя бы один маршрут; иначе — ошибка.

Дедлайн и приоритет по классу в срез не входят: дедлайн остаётся у клиента.

### 3.3. Политики отказоустойчивости

Все политики выключены по умолчанию; выключенная политика не меняет поведения и чисел. Параметры описаны в каталоге с единицами, начальными значениями и подсказками «?», как остальные параметры.

| Политика | Где | Чьё состояние | Эффект |
|---|---|---|---|
| Circuit breaker | `call.circuitBreaker` | вызывающего экземпляра для этой связи | открытый breaker сразу отказывает попытке |
| Бюджет повторов | `call.retryBudget` | вызывающего экземпляра для этой связи | лишний повтор не выполняется |
| Ограничение интенсивности | `service.rateLimit` | каждого экземпляра сервиса | избыток отклоняется до очереди |
| Outlier detection | `router.outlierDetection`, `call.outlierDetection` при вызове в группу | маршрутизатора, общее для всех вызывающих | экземпляр временно выводится из выбора |
| Health-check | `service.healthCheck` | каждого экземпляра, общее для всех маршрутизаторов | неготовый экземпляр выводится из выбора |

**Circuit breaker** — по образцу Resilience4j, окно по числу вызовов. Параметры: доля неуспешных попыток для размыкания, минимальное число попыток в окне, размер окна, время в открытом состоянии, число пробных попыток в полуоткрытом состоянии. Breaker оборачивает каждую попытку: повторы находятся снаружи и действуют как обычно. Открытый breaker отказывает попытке сразу — без пула, сети и работы у цели — с причиной «breaker открыт»; такие отказы в окно не засчитываются. Неуспешными считаются отказы вызываемого, таймауты попытки и отказы занятия пула.

**Бюджет повторов** — по образцу Finagle `RetryBudget`. Параметры: доля повторов от числа первых попыток за окно, минимум повторов в секунду, длина окна. Повтор, на который бюджета нет, не выполняется: вызов завершается отказом последней попытки, счётчик отклонённых повторов растёт.

**Ограничение интенсивности** — корзина токенов на экземпляр: интенсивность и размер всплеска. Запрос или попытка без токена отклоняется до очереди с причиной «ограничение интенсивности»; обработчик не занимается.

**Outlier detection** — по образцу Envoy, по подряд идущим ошибкам. Параметры: число подряд неуспешных попыток к экземпляру, базовое время вывода (умножается на номер вывода), предельная доля выведенных экземпляров. Выведенный экземпляр не выбирается, пока не истечёт время вывода. Предельная доля не даёт вывести все экземпляры. Состояние общее у маршрутизатора: это модель общего балансировщика; отдельное состояние у каждого вызывающего — точка расширения. Правило ловит отказы, а не медленность: экземпляр, который отвечает медленно, но успешно, не выводится. В сквозном кейсе медленная реплика выводится, только когда её попытки начинают отказывать — по таймауту или занятию пула.

**Health-check** — по образцу readiness-проверки Kubernetes. Параметры: интервал, таймаут, пороги неуспешных и успешных проверок, время обработки проверки. Проверка — лёгкий запрос к экземпляру: он проходит очередь и занимает обработчик на время обработки проверки, поэтому перегруженный экземпляр проваливает проверки. Неготовый экземпляр не выбирается ни одним маршрутизатором. Если готовых экземпляров не осталось, попытка получает отказ «нет готовых экземпляров» сразу. Проверки не входят в когорту измерения и учитываются отдельно. Сетевая задержка проверки не моделируется: проверяющий находится рядом с экземпляром.

Политики и отказы эксперимента сочетаются: например, «чёрная дыра» на реплике даёт таймауты, outlier detection выводит её, health-check с проверкой через обработчики выводит её, только если отказ задерживает обработку.

### 3.4. Документы и версии

- **Модель** — новая версия схемы: несколько клиентов, `client.classes`, `classes` у шагов сценария и маршрутов, параметры политик. Модель прежней версии отвергается понятной ошибкой о версии; примеры и фикстуры переписываются (правило `AGENTS.md`).
- **Эксперимент** — без изменений. Числовые параметры политик переопределяются вариантами и перебираются сеткой, как остальные.
- **Артефакт** — новая версия: результаты на входе по клиентам и классам, новые причины отказов, выходы политик (§6).

## 4. IR и компилятор

- `GraphIr` хранит список клиентов, каждый со своим входом, вместо одиночных `client` и `entry`. Обход путей, проверка достижимости и оценка стоимости идут от всех входов.
- Классы — множество идентификаторов модели; у клиента — профиль нагрузки каждого класса, у шага сценария и маршрута — множество классов или «все».
- Проверки: `TOPOLOGY_CLIENT` допускает несколько клиентов; у каждого клиента ровно одна связь `request`; новые коды для неизвестного класса, повторного класса у клиента, одновременных `load` и `classes`, класса без маршрута и параметров политик вне допустимых границ.
- Линтер проверяет дедлайн каждого клиента против его пути. Правила линтера для политик — задачи milestone «Линтер».

## 5. Движок

- **Прибытия.** Генератор прибытий на каждый класс каждого клиента, со своим потоком случайных чисел по пути клиента и идентификатору класса (ADR 0006): добавление класса или клиента не меняет прибытия остальных. Запрос несёт клиента, класс, время прибытия и дедлайн своего клиента. Дочерние вызовы наследуют клиента и класс.
- **Сценарий.** Исполнитель пропускает шаги не своего класса.
- **Попытка вызова.** Перед попыткой — бюджет повторов (для второй и следующих попыток) и breaker; после исхода — учёт в breaker, бюджете и outlier detection. Отказ breaker не занимает пул и не создаёт попытку у цели.
- **Выбор цели.** Доступные цели маршрутизатора — маршруты своего класса минус выведенные outlier detection минус неготовые по health-check минус уже опробованные (правило `retryTarget: other`); дальше — политика балансировки, как в срезе 1.
- **Сервис.** Корзина токенов перед очередью; процесс проверок health-check на каждый экземпляр.
- Состояние политик сбрасывается в начале каждого повторения; потоки случайных чисел политикам не нужны: они детерминированы.

## 6. Результаты и вывод

- **Вход.** Метрики входа — исходные запросы, успешные, неуспешные по причинам, задержки — считаются по каждому клиенту, по каждому классу и в сумме. Сумма совпадает с прежними полями верхнего уровня.
- **Новые причины отказа:** «breaker открыт», «ограничение интенсивности», «нет маршрута», «нет готовых экземпляров». Отклонённые бюджетом повторы — отдельный счётчик, а не причина отказа.
- **Выходы политик** (ADR 0011): у связи — доля времени в открытом состоянии breaker, отказы breaker, отклонённые повторы; у сервиса и экземпляра — доля отклонённых ограничением, проваленные проверки, доля времени неготовности; у маршрутизатора и экземпляра группы — число выводов и доля времени вывода.
- **Ряды** содержат те же величины по окнам, чтобы на Timeline было видно, когда breaker размыкался и когда экземпляр выводился.
- Вывод о насыщении не меняется. События политик в путях деградации — точка расширения.

## 7. API, CLI и интерфейс

API и CLI меняют содержимое по ADR 0010: каталог с новыми параметрами и выходами, документы новой версии, сводка и ряды по клиентам и классам. CLI `summary` показывает строки клиентов и классов.

Интерфейс:

- **Клиенты.** Палитра позволяет добавить несколько клиентов; полоса хода эксперимента показывает нагрузку каждого клиента.
- **Классы.** В инспекторе клиента — список классов, у каждого редактор профиля нагрузки из среза 1 (#292: таблица точек и график); полоса хода эксперимента показывает профили классов клиента друг над другом; у шага сценария и у маршрута — выбор классов; на схеме подпись маршрута показывает его классы.
- **Политики.** Разделы в инспекторе: у связи `call` — circuit breaker и бюджет повторов, у вызова в группу — outlier detection; у сервиса — ограничение интенсивности и health-check; у маршрутизатора — outlier detection. На схеме у связи и узла с включённой политикой — значок политики.
- **Результаты.** Во «Выводах» и в Map — строки по клиентам и классам; на Timeline — полосы состояния: breaker открыт, экземпляр выведен или неготов; в таблице реплик — доля времени вывода и неготовности.

## 8. Порядок работ и проверка

### 8.1. Пример

`examples/checkout-policies/` — продолжение `checkout-replicas`:

```
mobile-app ──→ api-gateway → order-service ×3 ─(пул 10)→ pgbouncer → orders-db
partner-api ─┘                     └→ payment-service → psp
```

- `mobile-app`: классы `status` (сценарий `order-service` — чтение из БД) с ровным профилем и `checkout` (чтение, оплата, запись) с пиком, как в распродажу; `partner-api`: только `status`, с всплеском нагрузки в профиле;
- эксперимент «медленная реплика»: отказ на связи реплики #2 к пулеру, как в `checkout-replicas`; варианты — без политик, outlier detection, health-check умеренный и агрессивный;
- эксперимент «отказ PSP»: «чёрная дыра» `psp`; варианты — без политик, circuit breaker на вызове оплаты, бюджет повторов;
- ограничение интенсивности на `api-gateway` — вариант эксперимента со всплеском `partner-api`;
- бюджет повторов дополнительно проверяется вариантом на `retry-storm` этапа 1;
- источники чисел и допущения — в `notes`.

### 8.2. ADR

- **ADR 0014.** Несколько клиентов и классы запросов: атрибуты запроса, когорта измерения, результаты на входе по клиентам и классам.
- **ADR 0015.** Политики отказоустойчивости: где живёт состояние каждой политики (вызывающий экземпляр, экземпляр сервиса, маршрутизатор, общая готовность) и как политики встраиваются в попытку вызова и выбор цели.

Формат, общий для нескольких задач, фиксируется в плане дорожки до выдачи задач: структура метрик входа, причины отказов, имена параметров и выходов политик.

### 8.4. Тесты

- Детерминированные сценарии на каждую политику: размыкание и замыкание breaker, полуоткрытое состояние; исчерпание бюджета повторов; корзина токенов; вывод и возврат экземпляра outlier detection, предельная доля; провал и восстановление health-check, отказ при отсутствии готовых экземпляров.
- Классы: интенсивность каждого класса по окнам сходится с его профилем в пределах статистической погрешности; шаги и маршруты своего класса.
- Несколько клиентов: добавление клиента не меняет прибытия остальных; сумма метрик входа равна прежним полям.
- Равенство чисел сводки на примерах этапа 1 и среза 1 (§2, п. 3).
- Побайтная воспроизводимость при 1, 2, 4 и 8 потоках.
- E2E: сборка примера через интерфейс, прогон, результаты по клиентам и классам, полосы состояния политик.

## 9. Точки расширения

Формат, IR и движок не должны запрещать:

- **outlier detection у каждого вызывающего** — отдельное состояние, как у Envoy в каждом sidecar; **по статистике успешности** — сравнение с остальными экземплярами; **по задержке** — балансировка с учётом наблюдаемой задержки (peak EWMA);
- **дедлайн и приоритет по классу**, сброс нагрузки по приоритету;
- **ограничение интенсивности по клиенту или классу** — квоты арендаторов;
- **адаптивное ограничение параллельности** — предел по наблюдаемой задержке;
- **breaker на каждый экземпляр цели**;
- **ключи запросов** — популярность ключей для кэша (срез 3);
- **hedged requests** — вместе с fan-out (срез 3);
- **асинхронный вызов через очередь** — срез 4;
- **события политик в путях деградации** вывода о насыщении.

## 10. Открытые вопросы

- Состояние outlier detection: общее у маршрутизатора (решение среза) или отдельное у каждого вызывающего. Общее проще и соответствует общему балансировщику; отдельное точнее для service mesh. Решение среза пересматривается, если пример покажет, что разница существенна.
- Время обработки проверки health-check по умолчанию и проходит ли проверка общую очередь или только обработчик. Решение среза — общая очередь: так перегрузка проваливает проверки, как в реальных сервисах с общим пулом потоков.
- Множитель нагрузки для перебора (#311) при нескольких клиентах и классах: общий, у каждого клиента или у каждого класса.
