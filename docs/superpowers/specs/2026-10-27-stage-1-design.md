# Этап 1 — дизайн

Дата: 2026-10-27  
Статус: согласовано  
Задача: [#5](https://github.com/ChernetsovNG/resilience-lab/issues/5)  
Связано: [продуктовое видение](../../product/2026-10-27-product-vision.md), §5.5 и §7; [целевая архитектура](../../architecture/2026-10-27-target-architecture.md) и ADR 0001–0010; [проектный дизайн MVP](2026-10-25-resilience-lab-design.md) — источник модельной семантики.

Этот документ — зонтичный дизайн этапа 1: границы, контракты между подсистемами и порядок работ. Детали реализации каждой части уточняются в планах реализации и задачах.

## 1. Цель и границы

Цель — закрыть вопрос «какие timeout и число попыток выбрать на цепочке с деградацией» уже на новой архитектуре. Основной сценарий — моделирование при заданных значениях: прогон и сравнение вариантов с таймлайном, воспроизведением на схеме и выводом. Карта по сетке параметров — дополнительный режим.

Модельная семантика MVP не меняется: блокирующие обработчики, ограниченная FIFO-очередь, timeout, retry, backoff, jitter, общий deadline, orphaned work, когорта измерения (проектный дизайн, §8–9). Меняется представление. Исключение — назначение потоков случайных чисел по путям блоков (ADR 0006): при том же seed числа будут другими.

Старый формат сценария MVP, старое API и код MVP заменены без поддержки и миграции. Новый формат документов начал нумерацию с `schemaVersion: 1`. После добавления профилей нагрузки (T2.4 этапа 2), пула соединений (T2.2) и нескольких клиентов с классами запросов (T1.1 второго среза) текущая версия модели — 6; расширенные отказы (T2.5) повысили версию эксперимента до 2, описание варианта — до 3; версия раскладки остаётся 1. Примеры и фикстуры переписаны; документ прежней версии получает ошибку `SCHEMA_VERSION` с ожидаемой версией, без миграции.

**Входит:** каталог типов этапа 1, документы модели, раскладки и эксперимента, компилятор и IR, адаптер KSL, исполнение с задачами, каталог артефакта со своими рядами, файловая рабочая область, API и CLI с одинаковыми возможностями; каркас UI, редактор, панель результатов, таймлайн, результаты на схеме, воспроизведение, вывод, линтер, карта, демо-сценарии.

**Не входит:** иерархия, составные блоки, маски и библиотека (формат к ним готов); реплики и балансировщик, БД с пулом, фазы и ресурсы, неблокирующая модель; DAG и fan-out — топология этапа 1 остаётся линейной цепочкой; частицы-запросы (#26); калибровка и импорт; проверка требований в CI (A10); SSE вместо опроса (#23); Parquet.

## 2. Критерии готовности

1. На демо retry storm пользователь, не прокручивая страницу, открывает рабочую область, меняет параметр варианта, запускает сравнение при заданных значениях и видит таймлайн, воспроизведение на схеме и вывод с причиной. Карта по сетке timeout × попытки работает как дополнительный режим той же панели.
2. CLI выполняет то же на тех же файлах; при тех же версии, документах и seed артефакты совпадают.
3. Сохранение из UI даёт документы с малошумными диффами; правку файла снаружи UI обнаруживает и предлагает перечитать.
4. Тесты доказывают, что результат не зависит от числа потоков и порядка блоков в документах.
5. CI зелёный; E2E переписаны под новый каркас.
6. Выходы типов описаны в каталоге по ADR 0011. Timeline, результаты инспектора и наложение используют эти описания; тестовый тип с дополнительным выходом получает все три представления без регистрации в коде web. Прежние метрики, подписи, единицы и значения сохраняются.

## 3. Модель и документы

### 3.1. Каталог этапа 1

| Тип | Вид | Параметры |
|---|---|---|
| `client` | блок | профиль `load` (кусочно-линейные точки), общий deadline (`1s`) |
| `service` | блок | обработчики, ёмкость очереди, время обработки (`fixed`, `exponential`, `lognormal`: среднее и разброс), доля отказов (`0.5%`) |
| `call` | связь | сетевая задержка (распределение), timeout, число попыток, backoff (`none`, `fixed`, `exponential-full-jitter`: база, максимум, множитель) |
| `request` | связь | без параметров: запрос клиента приходит на вход первого сервиса без сетевой задержки и повторов, как в MVP |

Каталог описывает блоки и связи одним контрактом параметров (ADR 0001): тип значения, физическая величина и единицы, диапазон, значение по умолчанию, описание, признак «можно перебирать в сетке». Порты: у `client` — выход; у `service` — вход и выход; `request` соединяет `client` с `service`, `call` — `service` с `service`.

В T1.4 первого среза этапа 2 каталог расширен типами `router` и `route` ([дизайн, §5.4](2026-10-30-stage-2-slice-1-design.md#54-маршрутизатор)). У `router` вход и выход, параметр `policy` со значениями `roundRobin` (по умолчанию), `random`, `leastInFlight`. Связь `call` также может вести из сервиса в маршрутизатор; связь `route` ведёт из маршрутизатора в сервис или другой маршрутизатор. `ConnectionRule.toTypes` перечисляет допустимые типы целей; текущая версия схемы каталога — 4. У `route` положительный конечный `weight`, по умолчанию 1; он влияет только на `random`. Маршрутизатор имеет ровно одну входящую связь и хотя бы один выход, не занимает обработчиков и не добавляет задержку.

Параметр `call.retryTarget` — `any` (по умолчанию) или `other`. Выход выбирается при отправке каждой попытки. При `other` на каждом маршрутизаторе сначала рассматриваются выходы, ещё не опробованные этим вызовом; после их исчерпания доступны все. История начинается заново для следующего вызова, в том числе повторного шага по той же связи. Сетевые задержки в обе стороны, таймаут и повторы относятся к входящему `call` и всему выбранному пути; `route` не задаёт дополнительных попыток. `leastInFlight` учитывает работу до окончания ответа, включая работу после таймаута вызывающего. При равенстве выбирается первый выход по пути; `roundRobin` использует тот же порядок. Для `random` используется отдельный поток роли `routing` по пути маршрутизатора. Попытки по каждому выходу записываются в строки его связи `route` существующего формата артефакта; у маршрутизатора собственной строки узла нет. Структура документов модели и эксперимента не меняется.

В T2.2 первого среза этапа 2 у `call` добавлен необязательный объект `pool`: `size` — целое не меньше 1, `acquireTimeout` — неотрицательная длительность, по умолчанию `30s`. Ноль запрещает ожидание занятого пула. Пул принадлежит вызывающему экземпляру: копии исходящей связи разных реплик имеют отдельные пулы. Перед отправкой попытка получает соединение из FIFO-очереди без предела длины; ожидание ограничено `acquireTimeout` и оставшимся общим дедлайном. Отказ получения расходует попытку и допускает повтор по политике связи. Таймаут попытки начинается после получения соединения; соединение удерживается до ответа или таймаута попытки. При совпадении освобождения с пределом ожидания приоритет у получения соединения; после достижения общего дедлайна новая отправка не начинается. Без `pool` поведение связи сохраняется. Поля рядов и итогов пула описаны в [формате артефакта](../../results-format.md).

В T2.3 добавлен блок `pooler` в режиме transaction. Параметры `maxClientConnections` и `poolSize` — целые не меньше 1, `waitTimeout` — неотрицательная длительность; все три обязательны. Собственная задержка `processing` задаётся распределением, по умолчанию `fixed` с `mean: "0ms"`. Сначала попытка занимает клиентское подключение без очереди, затем ожидает серверное соединение в FIFO-очереди не дольше `waitTimeout`, проходит собственную задержку и исходящий вызов. У пулера ровно одна исходящая связь `call` в сервис, маршрутизатор или БД; сеть, таймаут и повторы задаются на этой связи, по умолчанию одна попытка. Параметр `pool` на исходящем вызове пулера запрещён: серверные соединения ограничивает сам пулер. Ошибка `POOLER_CALL_POOL` указывает на `params.pool` исходящей связи. Серверное соединение удерживается до окончания вызова, клиентское подключение — до ответа вызывающему, включая сетевую задержку ответа. Таймаут выше по графу не отменяет принятую работу. Режим session и несколько серверных пулов не поддерживаются.

Каталог версии 4 использует списки `ConnectionRule.fromTypes` и `toTypes`. Связь `call` может исходить из сервиса и пулера; `call` и `route` могут вести в пулер. Сценарий и группы реплик применимы только к сервисам. Типы параметров модели не менялись; версия модели остаётся 5. Метрики двух наборов, ожиданий и отказов записываются в собственную строку пулера в [формате артефакта](../../results-format.md#строка-пулера).

У типа также есть `outputs`: стабильные идентификаторы выходов, названия и описания, единицы, виды величин, закрытые виды вычисления со ссылками на сырые поля и привязки итогов. Метаданные представлений задают группы Timeline, строки и мини-графики инспектора, метрики наложения. Подробнее — [ADR 0011](../../architecture/adr/0011-type-outputs.md). У `request` нет собственных рядов; его наложение использует amplification вызываемого сервиса.

В T2.1 первого среза этапа 2 добавлен блок `database`: `maxConnections` — целое число от 1, `queue` — вместимость очереди от 0 (по умолчанию 0), обязательный `processing` — распределение времени выполнения запроса с теми же полями, что у сервиса, `failureRate` — доля ошибок от 0 % до 100 % (по умолчанию 0 %). БД имеет только вход: в неё ведут `call` от сервиса и `route` от маршрутизатора. Исходящие связи, `scenario` и параметры реплик у БД запрещены. Запрос занимает соединение до завершения; при нехватке соединений ждёт в ограниченной FIFO-очереди, при полной очереди получает отказ. Таймаут вызывающего не отменяет принятую работу. В IR БД использует общую форму `ServiceNode` и набор слотов, где число обработчиков равно `maxConnections`, а обработка означает выполнение запроса. Роли потоков — `processing` и `outcome` по пути БД. Смысл полей результатов описан в [формате артефакта](../../results-format.md#окна-и-статистики). Структура документов и артефакта не меняется, их версии сохраняются.

Наложения загрузки, средней очереди и доли отказов очереди общие для сервиса и БД: их пункты сохраняют значения `utilization`, `meanQueue` и `queueRejections`. Подписи БД в инспекторе и на Timeline используют термины запросов и соединений. Меню наложений показывает только выходы типов блоков и связей, присутствующих в текущей модели; ключи различающихся выходов остаются согласованными с отрисовкой схемы.

### 3.2. Документы

Рабочая область содержит документы с суффиксами (ADR 0005):

```json
// retry-storm.model.json
{
  "schemaVersion": 6,
  "description": "Цепочка из трёх сервисов с деградацией зависимости.",
  "blocks": {
    "client": { "type": "client", "params": { "load": { "points": [{ "time": "0s", "rate": "120/s" }] }, "deadline": "1s" } },
    "gateway": { "type": "service", "params": { "handlers": 4, "queue": 16, "processing": { "kind": "fixed", "mean": "1ms" } } }
  },
  "connections": [
    { "id": "client-to-gateway", "type": "request", "from": "client", "to": "gateway" },
    { "id": "gateway-to-middle", "type": "call", "from": "gateway", "to": "middle",
      "params": { "timeout": "80ms", "attempts": 3,
                  "backoff": { "kind": "exponential-full-jitter", "base": "2ms", "max": "20ms" } } }
  ]
}
```

```json
// retry-storm.experiment.json
{
  "schemaVersion": 3,
  "modelRef": "retry-storm.model.json",
  "layoutRef": "retry-storm.layout.json",
  "execution": { "replications": 10, "warmup": "0ms", "measurement": "1s", "seed": 20261025, "window": "10ms" },
  "faults": [ { "target": "dependency", "from": "200ms", "to": "800ms", "kind": "slowdown", "multiplier": 4 } ],
  "variants": [
    { "id": "baseline" },
    { "id": "no-retries", "overrides": { "gateway-to-middle.attempts": 1 } }
  ],
  "grid": [
    { "path": "gateway-to-middle.timeout", "values": ["40ms", "80ms", "160ms"] },
    { "path": "gateway-to-middle.attempts", "values": [1, 2, 3] }
  ]
}
```

`*.layout.json` хранит координаты блоков по путям; ключи-пути позволяют позже хранить раскладку по уровням иерархии. Деградация — событие эксперимента (`faults`), а не свойство модели. `window` — длина окна рядов; по умолчанию измеряемый интервал / 100. `grid` необязателен и содержит одну или две оси. Отсутствующий `grid` и пустой список означают одну точку `p0` без координат. Ось содержит непустой список значений; повторяющиеся пути и пересечения «объект — его поле» между осями отвергаются. Переопределения варианта применяются раньше значений точки, включая вложенные поля. Диагностика пути указывает на `/grid/<i>/path`, значения — на `/grid/<i>/values/<j>`. Первая ось внешняя: сетка 2×3 даёт точки `p0`–`p5`, вторая ось меняется быстрее. Точка не входит в ключ случайного потока.

У блока `service` необязательное поле `scenario` стоит рядом с `params` и задаёт непустую последовательность шагов. Например, сервис с исходящими связями `db` и `payment` может выполнить обработку, чтение, платёж и запись:

```json
{ "scenario": [
  { "type": "process", "processing": { "kind": "fixed", "mean": "2ms" }, "failureRate": "0%" },
  { "type": "call", "connection": "db" },
  { "type": "process" },
  { "type": "call", "connection": "payment" },
  { "type": "call", "connection": "db" }
] }
```

Шаг `process` может задать `processing` в том же формате распределения, что параметры сервиса, и `failureRate` в процентах. Каждое отсутствующее значение берётся из параметров сервиса после переопределений варианта и сетки. Шаг `call` содержит `connection`: идентификатор связи типа `call`, исходящей из этого сервиса. Порядок и повторения шагов сохраняются; повторный шаг с той же связью не считается повтором неудачной попытки. Обработчик удерживается до конца сценария. Локальная ошибка или окончательная неудача вызова прерывает сценарий.

Если `scenario` отсутствует или равен `null`, сценарий по умолчанию состоит из обработки и исходящих вызовов по порядку их идентификаторов. Для нескольких исходящих вызовов поле `scenario` обязательно. Сам сценарий и параметры отдельных шагов не переопределяются в вариантах и сетке. Потоки обработки и исходов привязаны к пути сервиса, как в ADR 0006; отдельные шаги используют те же потоки. Редактор сценария относится к T4; web сохраняет это поле при редактировании параметров модели.

Параметр сервиса `replicas` задаёт целое число экземпляров от 1, по умолчанию 1; его можно переопределять в вариантах и перебирать сеткой. При одном экземпляре исходный путь сохраняется. При нескольких компилятор создаёт маршрутизатор `<сервис>#lb`, экземпляры `<сервис>#1…#N` и копии исходящих вызовов `<связь>#1…#N`. Сценарий каждой реплики ссылается на её копии вызовов. Вызов в другую группу ведёт в её маршрутизатор. Номер реплики хранится отдельным сегментом пути по ADR 0012.

Необязательное поле блока `replicaOverrides` содержит частичные параметры экземпляров, например `{"2":{"handlers":7,"processing":{"mean":"9ms"}}}`. Вложенные объекты дополняют общие параметры; номер должен быть записан без ведущих нулей и не превышать эффективное `replicas`. Менять `replicas` внутри этого поля нельзя. Диагностика указывает на группу в документе и называет номер экземпляра. Web сохраняет поле при редактировании и сохранении модели; отдельный редактор отличий реплик относится к T4.

Параметр входящего вызова `balancing` выбирает `roundRobin`, `random` или `leastInFlight`; без него используется `roundRobin`. У разных входящих вызовов одной группы могут быть свои политики; состояние маршрутизатора общее. Для цели без группы явно заданный `balancing` игнорируется с предупреждением `LINT_BALANCING_IGNORED`. Входной сервис тоже может быть группой: связь `request` использует `roundRobin` без задержки и повторов.

Целью отказа может быть `service`, `database`, `pooler` или идентификатор связи `call` либо `route`; `client`, `router` и `request` недопустимы. Цель `<сервис>` охватывает всю группу, `<сервис>#<k>` — одну реплику, идентификатор исходящего вызова — все его копии, `<связь>#<k>` — одну копию. Привязка проверяется после переопределений варианта, сетки и разворачивания групп.

Каждый отказ содержит `target`, `from`, `to` и один `kind`: `slowdown`, `errors`, `unavailable`, `blackhole` или `capacityLoss`. Параметры вида лежат в том же объекте. Интервал `[from, to)` целиком лежит между началом разогрева и концом измерения; перекрытия разрешены. Замедления перемножают множители и складывают добавочные задержки, вероятности ошибок сочетаются независимо, ограничения ёмкости выбирают минимум. На связи ошибки выбираются один раз перед отправкой запроса, а замедление — при выборке сетевой задержки отдельно в каждом направлении, включая выбранные `route`. Отказ передачи не создаёт работы у цели. Подробные параметры, приоритеты и моменты применения описаны в дизайне первого среза этапа 2, [§3.6](2026-10-30-stage-2-slice-1-design.md#36-отказы) и [§5.6](2026-10-30-stage-2-slice-1-design.md#56-отказы-и-нагрузка).

Модель версии 6 добавляет несколько клиентов и классы запросов по [ADR 0014](../../architecture/adr/0014-clients-and-request-classes.md). Клиент задаёт либо `load`, либо массив `classes` с объектами `{ id, load }`; без массива используется класс `default`. Поле `classes` у шага сценария и связи `route` ограничивает их применение указанными классами. Вариант заменяет массив клиента целиком, сеткой он не перебирается. Компилятор проверяет объявления классов и наличие маршрута для каждого класса, который может дойти до маршрутизатора. Формат, проверки, IR, линтер и оценка стоимости описаны в T1.1 [плана второго среза](../plans/2026-10-31-stage-2-slice-2-core.md). До T4 web сохраняет новые поля без отдельного редактора классов.

Движок создаёт отдельный генератор прибытий для каждого класса каждого клиента (T1.2). Добавление клиента или класса не меняет прибытия остальных; класс `default` сохраняет прежний поток клиента. Все попытки и вложенные вызовы наследуют клиента, класс, время исходного прибытия и дедлайн. Исполнитель пропускает шаги чужих классов; маршрутизатор выбирает только маршруты своего класса, в том числе при повторе с `retryTarget: other`. Если маршрута нет, попытка сразу завершается с исходом `noRoute`. Метрики входа пока суммируются для всех клиентов и классов; отдельные строки и причины отказов в артефакте относятся к T3.1.

### 3.3. Пути и величины

Идентификатор блока или связи — сегмент пути; параметр — `путь.параметр`, вложенные поля — через точку (`gateway.processing.mean`). Вложенность этапа 2 добавит `родитель/потомок` без смены формата. Величины пишутся строками с единицами (`250ms`, `2s`, `120/s`, `0.5%`); количества — целыми числами. Ядро переводит величины во внутренние единицы, UI показывает привычные.

### 3.4. Проверки и линтер

JSON-схемы генерируются из классов документов и каталога; CI проверяет, что повторная генерация не даёт диффа. Компилятор проверяет ссылки, пути переопределений и сетки, допустимость значений и топологию графа: один или несколько `client`, ровно одну связь `request` у каждого клиента, отсутствие циклов, достижимость всех сервисов хотя бы от одного входа и отсутствие вызовов во входные сервисы. Цикл диагностируется с перечислением сервисов и связей и указателем на замыкающую связь. Число входящих вызовов не ограничено; несколько исходящих вызовов разрешены с явным сценарием, без него — `SCENARIO_REQUIRED`. Пустой сценарий — `SCENARIO_EMPTY`; вызов чужой, входящей, неизвестной связи или связи `request` — `SCENARIO_CONNECTION` с указателем на `scenario/<i>/connection`. Неизвестный вид шага и поля другого вида — `SCENARIO_STEP_TYPE` и `SCENARIO_FIELD`; сценарий у блока другого типа — `SCENARIO_BLOCK`. Остальные ошибки графа используют `TOPOLOGY_GRAPH` с аргументом `reason`. Это контракты T1.1 и T1.3 [первого среза этапа 2](2026-10-30-stage-2-slice-1-design.md); поведение цепочек этапа 1 сохраняется.

Схемы `schemas/*.schema.json` проверяют структуру, обязательность параметров, единицы величин и диапазоны обычных чисел. Размерность и границы строковых величин записаны в аннотации `x-quantity` в канонических единицах каталога и пояснены в `description`; их числовую проверку выполняет ядро. Формат аннотации и команды генерации описаны в [schemas/README.md](../../../schemas/README.md).

Линтер — диагностика уровня «предупреждение», вычисляемая на IR:

- исходящая связь не используется в сценарии сервиса: `LINT_SCENARIO_UNUSED` с указателем на сценарий и идентификатором связи в аргументах;
- timeout вызова меньше расчётного бюджета следующей части цепочки более чем на допустимый запас: число попыток × timeout следующего вызова плюс сумма максимальных задержек backoff;
- произведение числа попыток по слоям больше 10;
- обработчиков сервиса меньше оценки λ·W, где λ — максимум профиля интенсивности клиента на интервале поступления запросов (консервативная оценка), а W — среднее время удержания обработчика: собственная обработка плюс ожидаемое время downstream-вызова без отказов и повторов;
- общий deadline меньше бюджета входного сервиса: его средняя собственная обработка плюс число попыток исходящего вызова × timeout и сумма максимальных задержек backoff;
- число независимых повторений меньше 5: 95 % доверительные интервалы при таком числе повторений ненадёжны.

Пороги — параметры правил, описанные в тексте диагностики.

`LINT_FEW_REPLICATIONS` сравнивает общее `execution.replications` с параметром `ModelLinter.minimumReplications`, равным 5 по умолчанию. Предупреждение советует не меньше этого числа повторений и выдаётся один раз на эксперимент независимо от вариантов и сетки: документ эксперимента, указатель `/execution/replications`, `variant = null`, без пути элемента. Оно не блокирует запуск и одинаково возвращается в API `POST /validate` и CLI `validate`. Поле `execution.replications` остаётся обязательным; скрытого значения по умолчанию в ядре и схеме нет.

`ModelLinter` проверяет IR каждой точки каждого варианта через `Lab.validate`. Диагностика содержит код, уровень `WARNING`, документ, JSON-указатель на параметр, путь элемента и необязательный идентификатор `variant`. Указатель ведёт на переопределение в эксперименте, если проблемное значение задано там, иначе на параметр модели. Без сетки одинаковое во всех вариантах предупреждение с одним местом в документе модели выдаётся один раз с `variant = null`; остальные выдаются отдельно для каждого затронутого варианта с его идентификатором. Диагностика переопределения сохраняет `variant` и при единственном варианте эксперимента. Идентификаторы вариантов в текст сообщения не добавляются. При заданном `grid` предупреждения о параметрах цепочки содержат идентификатор варианта. Одинаковые предупреждения внутри варианта объединяются; если текст или источник предупреждения отличается между точками либо предупреждение появляется не во всех точках, сообщение перечисляет точки как `points: p0, p1`. Происхождение параметров хранится отдельно для каждой скомпилированной точки, поэтому указатель на значение оси не теряется. Предупреждения не меняют `ValidationReport.valid` и не блокируют запуск. CLI `validate` печатает их в stderr с идентификатором варианта в месте диагностики и при отсутствии ошибок завершается с кодом 0.

В UI одинаковые предупреждения линтера для реплик одной группы и вариантов объединяются в строку. Совпадать должны код, элемент и структурированные аргументы расчёта; номера реплик, идентификаторы вариантов и указатели на одинаковые переопределения не мешают объединению. Разные значения бюджета, ёмкости, нагрузки или наборы точек остаются отдельными строками. Строка перечисляет реплики диапазонами и названия вариантов; счётчики проблем, значки и строка состояния считают группы. Ошибки валидации не объединяются. Исходные диагностики API сохраняются, переход из строки открывает место первого предупреждения, подсказка перечисляет исходные указатели.

Текст каждого правила объясняет проверку, риск и возможное действие. Код `LINT_*`, формула оценки и подробности расчёта доступны в подсказке «?». Числа в основном тексте показывают масштаб риска без внутренних обозначений.

В формулах линтера длительности измеряются в миллисекундах, интенсивность — в запросах за миллисекунду. Для `LINT_TIMEOUT_BUDGET` к бюджету следующего вызова добавляются среднее время собственной обработки целевого сервиса и средние сетевые задержки входящего запроса и ответа. Бюджет следующего вызова — число попыток, умноженное на timeout, плюс максимальные задержки между попытками. Для `none` задержка равна нулю, для `fixed` — меньшему из `base` и `max`, для `exponential-full-jitter` после неудачной попытки `k` — меньшему из `max` и `base × multiplier^(k − 1)`. У листового сервиса остаются собственная обработка и две сетевые задержки. Сетевые задержки следующего вызова уже входят в его timeout и повторно не прибавляются.

По умолчанию `LINT_TIMEOUT_BUDGET` допускает бюджет до `timeout × 1,05` включительно (`ModelLinter.timeoutBudgetTolerance = 0.05`). Допуск подавляет небольшой разрыв между запасами времени соседних вызовов: начальные значения каталога дают 1012 ms при timeout 1000 ms и не вызывают предупреждения. Разница больше 5% вызывает предупреждение с точными исходными числами. Это допуск статического правила, а не гарантия своевременного ответа; начальные значения каталога не меняются.

Для `LINT_HANDLERS_LITTLE` время удержания обработчика складывается из собственной обработки, обеих сетевых задержек исходящего вызова и времени удержания обработчика следующего сервиса. Это оценка предложенной нагрузки для успешного пути без очередей, отказов, повторов и обрезки таймаутами. `LINT_RETRY_AMPLIFICATION` сравнивает точное произведение числа попыток с порогом 10 по умолчанию. Средние длительности не ограничивают случайные хвосты распределений.

Интенсивность каждого клиента и класса перед оценкой спроса распределяется по применимым маршрутам. При `random` доли пропорциональны весам, нормированным после фильтрации по классу; при `roundRobin` и `leastInFlight` используются равные доли. Для `leastInFlight` это статическое допущение о равных условиях, без прогноза динамического перераспределения. Вложенные маршрутизаторы последовательно делят поток, а сходящиеся ветви его складывают; один источник по-прежнему учитывается у сервиса не больше одного раза. Максимумы профилей разных клиентов и классов складываются после распределения. Например, 900 запросов/с на три одинаковые реплики дают каждой 300 запросов/с: при удержании 35 ms расчётный спрос равен 10,5 обработчика, а не 31,5.

`LINT_DEADLINE_BUDGET` сравнивает deadline клиента с бюджетом входного сервиса: средняя собственная обработка плюс `attempts × timeout` его исходящего вызова и сумма максимальных задержек backoff между попытками. Backoff учитывается по тем же правилам, что в `LINT_TIMEOUT_BUDGET`. Если исходящего вызова нет, бюджет равен только средней собственной обработке входа. Связь `request` от клиента не добавляет ни сети, ни попыток. Сеть исходящего вызова и вложенные вызовы уже покрываются его timeout; их бюджеты проверяет `LINT_TIMEOUT_BUDGET`, повторно к deadline они не прибавляются. При равенстве deadline и бюджета предупреждения нет.

Числа в сообщениях линтера записываются без лишнего `.0` у целых значений; дробные значения сохраняют точность.

Эталон на `examples/retry-storm/` с 10 повторениями: у `baseline` одно предупреждение `LINT_TIMEOUT_BUDGET` — timeout 80 ms меньше downstream-бюджета 189 ms. Бюджет входа равен `1 + 3 × 80 + (2 + 4) = 247 ms`, что укладывается в deadline 250 ms. У `no-retries` бюджет входа 81 ms, предупреждений нет. `LINT_FEW_REPLICATIONS` не выдаётся.

В `examples/checkout/checkout.experiment.json` у `baseline` и `bigger-payment-pool` по два предупреждения `LINT_TIMEOUT_BUDGET`: timeout шлюза 5000 ms меньше бюджета 10021 ms, timeout вызова из order-service 3000 ms меньше бюджета 4036 ms. У `no-order-retries` остаётся только второе предупреждение, у `aligned-timeouts` предупреждений нет. Deadline 10000 ms покрывает бюджет входа во всех вариантах: `2 + 1 × 5000 = 5002 ms`, у `aligned-timeouts` — `2 + 1 × 8000 = 8002 ms`.

### 4.1. Пакеты

Пакеты `resiliencelab.core.scenario` и `resiliencelab.core.simulation` заменяются:

| Пакет | Ответственность |
|---|---|
| `catalog` | Описания типов блоков и связей, разбор и печать величин с единицами |
| `document` | Классы документов, кодек, детерминированный писатель, строгий загрузчик, генерация схем |
| `compiler` | Документы → переопределения варианта и точки сетки → проверка → IR; диагностика |
| `ir` | Плоский граф примитивов с типизированными параметрами и происхождением элементов |
| `engine.ksl` | Адаптер KSL, принимающий только IR |
| `execution` | Задания, задачи, планировщик, оценка стоимости |
| `experiment` | Итоги повторения, скетчи задержек, статистическая агрегация повторений, строки групп реплик |
| `results` | Ряды, их части и индекс, запись и чтение артефакта, каталог прогонов, досчёт, вывод насыщения и запас по ёмкости |
| `workspace` | Хранилище документов за абстракцией (ADR 0003): сначала файловое, с версией-хешем и проверкой при записи |
| `lab` | Фасад для сервера и CLI: проверка и запуск экспериментов рабочей области |

Диагностика — общая структура для API, CLI и UI: код, уровень, документ, указатель JSON, путь блока, текст и необязательный идентификатор `variant`. Значение `null` означает диагностику модели или общую для всех вариантов. Ошибки компилятора, указывающие на переопределение или идентификатор варианта, содержат идентификатор своего варианта.

IR ядра — `GraphIr`: список клиентов с их входами, дедлайнами и профилями классов, множество классов модели, экземпляры сервисов, рёбра вызовов, отказы и параметры прогона. Компилятор строит у каждого сервиса сценарий `process`, затем `call` по единственной исходящей связи; у конечного сервиса остаётся только `process`. Сегменты пути хранятся отдельно от его отображаемого адреса и служат ключом случайных потоков. Каждый элемент сохраняет происхождение; при перестановке массива связей JSON-указатель меняется вместе с исходной позицией, семантика IR не меняется. Порядок узлов и связей топологический от всех входов, при равенстве — по сегментам пути.

`ModelLinter` проверяет пути каждого класса каждого клиента: его дедлайн сопоставляется с его входом, а оценка ёмкости общего сервиса складывает нагрузку всех достигающих его клиентов и классов. Общие участки путей одного источника не учитываются повторно. Полная семантика ветвлений относится к дорожке линтера. `CostEstimator` использует среднюю нагрузку каждого класса, суммирует события только применимых шагов и передаёт число визитов по доступным вызовам и маршрутам в топологическом порядке. Окна и отказы учитываются один раз на задачу. Повторный шаг вызова и общая цель нескольких вызовов учитываются каждый раз. Переименование сервисов не меняет оценку. В T1.1 исправлен прежний расчёт по алфавитному порядку: он мог недооценивать число событий, когда вызываемый сервис оказывался перед вызывающим.

### 4.2. Адаптер и потоки

Адаптер принимает `GraphIr`; каждая задача создаёт свежую модель KSL. Обработчики сервиса используют общий набор слотов с ограниченной FIFO-очередью (ADR 0013). Вызов сервиса занимает обработчик один раз и удерживает его до конца сценария: шаги `process` и `call` выполняются по порядку, включая повторный вызов той же связи. Окончательная ошибка шага прерывает сценарий, обработчик освобождается в `finally`. В `process` длительность и исход выбираются до задержки. Каждая попытка `call` получает цель извне; по умолчанию это цель ребра. Таймаут, общий дедлайн, backoff и продолжение работы ниже по графу после таймаута сохраняют семантику этапа 1. Сетевые задержки и jitter принадлежат ребру и сохраняют свои потоки между шагами и повторными попытками.

Потоки случайных чисел назначаются по ADR 0006 с первого же среза: SHA-256 полного ключа (версия назначения, seed, повторение, путь экземпляра, роль) даёт номер подпотока, генератор переходит к нему штатным `advanceSubStreams`; план адресов эксперимента проверяется на коллизии до запуска. Образец реализации и тестов — прототип исследования S4 (`research/ksl-streams/`). Роли источников этапа 1: поступления у `client`; время обработки и исход обработки у `service`; сетевые задержки запроса и ответа и jitter backoff у `call`.

Адаптер не использует глобальный `KSLRandom.DefaultRNStreamProvider` и `RandomVariable`: значения берутся функциями KSL с явно переданным потоком; автоматический переход KSL на следующий подпоток и сброс потоков отключены. Одновременные события упорядочиваются детерминированно по каноническому пути, как в MVP требовал проектный дизайн, §8.5. `SeedFactory` удаляется.

### 4.3. Ряды и агрегаты

Свой сборщик (ADR 0007, 0008) пишет по каждому узлу и окну симуляционного времени достаточные статистики: поступило, принято, отклонено по переполнению, успешно, отказов, таймаутов, повторов; занятое время обработчиков; интеграл длины очереди. Сводка сохраняет семантику `MetricsAggregator`: статистики пула и по повторениям, доверительные интервалы без обрезания.

Для каждой связи `call` сборщик наблюдает отправку попыток и повторов, полученные ответы (`succeeded`, `failed`), обрывы по timeout и `orphaned` — брошенные попытки, чья работа ниже ещё не закончилась. Timeout, укороченный общим deadline, остаётся timeout. Интегралы `inFlightIntegralMs`, `orphanedIntegralMs` и `backoffIntegralMs` описывают ожидание ответа, брошенную работу до завершения вызываемого процесса вместе с обратной сетью и ожидание backoff. Обработчик вызывающего во время backoff занят. Ряды используют время события и общие границы окон узлов; у связи `request` рядов нет.

Длительность попытки от отправки до ответа сохраняется в `latency` связи с тем же профилем скетча. В неё входят только попытки с полученным ответом, включая неуспешные; timeout не даёт образца задержки. Поэтому среднее и квантили описывают эту ограниченную выборку, а не все отправленные попытки. Итоги счётчиков и задержек связей используют измеряемую когорту с run-out; интегралы охватывают фиксированный измеряемый интервал и всю присутствующую работу, включая прогрев. `AggregateMetrics.connections` содержит объединённые итоги и задержки, а также `MetricSummary` доли таймаутов среди отправленных попыток и среднего числа попыток в полёте по повторениям с 95 % CI. Поля узлов сохраняют прежний смысл.

Задержки собираются в DDSketch по итогам [исследования S5](../../research/2026-10-28-latency-sketch.md): библиотека `com.datadoghq:sketches-java:0.8.3` с обёрткой профиля `ddsketch-bitwise6-rational-v1` — отображение `BitwiseLinearlyInterpolatedMapping(6)`, представитель корзины `нижняя граница × 129/128`, отдельный точный счётчик нулей. Относительная ошибка значения не больше 0,78125 %; корзины — целые счётчики, поэтому слияние побайтно не зависит от порядка, а JVM и браузер получают одинаковые биты квантилей. Обёртка отвергает отрицательные, нечисловые и выходящие за диапазон значения; при превышении лимитов скетча (общий счётчик больше 2^53−2, диапазон индексов больше 2048) расчёт останавливается с указанием узла, окна и лимита, без огрубления. Квантили считаются прежней интерполяцией KSL по двум порядковым статистикам из корзин, а не рангом DDSketch. Среднее хранится как отдельные счётчик и сумма. Web читает и сливает корзины собственным кодом по тому же профилю.

### 4.4. Вывод v1

- Насыщение по очереди подтверждается после как минимум 100 ms подряд окон, в каждом из которых загрузка обработчиков не ниже 95 % и средняя длина очереди больше 0,5. Укороченное последнее окно учитывается по фактической длительности.
- Насыщение по переполнению подтверждается по серии подряд окон с числом отклонений больше нуля: от начала первого до начала последнего должно пройти как минимум 100 ms. Последнее окно не добавляет свою длительность, поскольку счётчик отклонений не показывает, когда внутри окна они произошли. Единичное окно с отклонениями не подтверждает насыщение при любом шаге рядов.
- Обе ветки проверяются независимо; начало насыщения — начало первого окна той из подтверждённых серий, которая началась раньше. Окно без соответствующего признака или разрыв ряда прерывает серию. Порог задан во времени и не зависит от числа окон. Шаг `execution.window` определяет усреднение и разрешение начала; крупное окно может скрывать короткие перерывы. Если весь ряд помещается в одно окно, подтвердить насыщение по переполнению нельзя.
- Первым насытившимся считается узел с самым ранним началом; порядок остальных показывает путь деградации. При одинаковом моменте первым идёт узел, стоящий дальше в топологическом порядке графа: вызываемый раньше вызывающего. Для узлов вне переданного графа порядок определяется идентификатором.
- По повторениям вывод агрегируется честно: «dependency первым в 9 из 10 повторений, медиана t = 210 ms»; если насыщения нет, вывод так и говорит.
- Поле `saturation` точки сводки хранит параметры правила (`minimumDurationMs = 100.0`, `handlerUtilizationThreshold = 0.95`, `meanQueueLengthThreshold = 0.5`, `queueRejectionsThreshold = 0`), путь каждого повторения, отдельное число повторений без насыщения и статистики первых узлов. Для каждого первого узла записаны число повторений, медиана и min/max момента начала; при чётном числе значений медиана — среднее двух центральных. Списки первых узлов упорядочены по убыванию числа повторений, затем по идентификатору.
- Вывод пересобирается из записанных оконных частей при построении сводки, в том числе при досчёте. Пороги указаны рядом с данными вывода; их текст в web относится к T4.

### 4.5. Исполнение

По ADR 0009: задание = варианты × точки сетки × повторения; общий пул с чередованием задач разных заданий; кооперативная отмена; досчёт недостающих задач при тех же версии и хешах. До запуска — оценка стоимости по формуле исследования #46. Прогресс начинается с общего числа задач эксперимента; при досчёте в завершённые сразу входят проверенные готовые задачи. Повторно вычисляемые повреждённые задачи учитываются после успешного завершения, а общий знаменатель остаётся прежним.

На текущем срезе `ExperimentExecutor` выдаёт задачи по кругу между активными заданиями, внутри задания — по вариантам, точкам сетки и повторениям. `Lab.run` принимает признак `isCancelled: () -> Boolean`; функция должна быть потокобезопасной и быстро возвращать результат. Ожидающий вызов проверяет его с интервалом 25 ms; отмена прерывает активные потоки задания, модели KSL останавливаются на границе события. Отмена и прерывание вызывающего потока завершают вызов исключением `java.util.concurrent.CancellationException`, отличимым от ошибки расчёта. Лимит реального времени на задачу сохраняется. После T1.4 при отмене остаются файлы готовых задач и уже записанные части, манифест помечает артефакт незаконченным, сводка не создаётся. Записи частей выполняются в отдельных потоках без прерывания, потому что `FileChannel.lock` прерываем; планировщик ждёт их завершения перед публикацией неполного манифеста. После последней проверки отмены окончательная запись сводки и манифеста завершается целиком, а прерывание вызывающего потока восстанавливается после записи. Сервер выполняет вызовы `Lab.run` в отдельных виртуальных потоках JDK, поэтому ожидание задания не занимает поток расчёта.

`Lab.validateResume(runDirectory)` без изменения артефакта проверяет возможность досчёта и возвращает манифест. Проверяются канонический путь каталога, версии приложения, KSL и назначения потоков, хеши документов и метаданные прогона: несовпадения дают `RUN_INCOMPATIBLE` или `RUN_DOCUMENT_CHANGED`, законченный прогон — `RUN_COMPLETE`. `Lab.resume(runDirectory, isCancelled, onProgress)` повторяет эти проверки при запуске, пересчитывает только отсутствующие или повреждённые задачи и атомарно заменяет сводку и манифест. Досчитанный артефакт побайтно равен непрерывному. Повторная отмена сохраняет неполный манифест без сводки. Параллельные вызовы `resume` для одного каталога сериализуются в JVM; вызов после публикации получает `RUN_COMPLETE`. `Lab.estimate(experimentPath, drafts, workers)` без запуска KSL возвращает `ExperimentEstimate`: число задач, ожидаемые события и строки, время при заданном числе потоков, распакованный и записанный объём, число частей и предупреждения (поля `tasks`, `expectedEvents`, `expectedRows`, `workers`, `estimatedSeconds`, `estimatedUncompressedBytes`, `estimatedArtifactBytes`, `estimatedParts`, `warnings`). Число строк учитывает клиента, экземпляры сервисов, БД и пулеров, связи `call`, выходы `route` и сводные строки групп из `ReplicaGroups.membership`, умноженные на число окон с прогревом и неполным последним окном. У `request` и самого маршрутизатора строк нет. Время использует прежние опоры S1 с настроенным числом попыток; сверх прежних событий оценка допускает по три события получения, истечения ожидания и пробуждения на каждую попытку с пулом и каждое посещение пулера. Его собственная задержка уже учтена шагом `process`; каждый развёрнутый интервал отказа добавляет два граничных события. Объём использует опоры по видам строк: 256 байт для узла, ещё 192 байта на набор слотов; 320 байт для связи и ещё 192 при наличии пула; у группы ещё 256 байт на экстремумы каждого набора. Коэффициент gzip — 0,125. Части оцениваются отдельно для `INSTANCE` и `GROUP` по бюджету 4 МиБ с запасом 512 байт на часть. Метаданные повторения и сводки оцениваются по 3072 байта на элемент плюс 4 байта на ожидаемый исходный запрос, до 2000 запросов; это опора оценки, а не ограничение данных. Для итогов каждого повторения применяется тот же коэффициент gzip 0,125; несжатая сводка учитывается один раз на пару «вариант, точка». Опоры объёма проверяются реальными артефактами `retry-storm`, `checkout` и графа с тремя репликами, пулами, пулером и БД: строки совпадают точно, объёмы до и после сжатия укладываются в ±50 %. Предупреждения `ESTIMATE_UI_CACHE` и `ESTIMATE_LONG_MODEL_TIME` передают `storageSource` и `sourceRows`: главный вклад в объём по видам строк и число его строк на повторение; названия переводятся в web на `en` и `ru`. Предупреждение `ESTIMATE_EXTRAPOLATION` выдаётся при числе сервисов больше 5000. Ускорение ограничено значением для 8 потоков (3,184): увеличение числа потоков сверх 8 не уменьшает оценку времени относительно 8 потоков, поэтому `ESTIMATE_WORKER_EXTRAPOLATION` не выдаётся. `ESTIMATE_UI_CACHE` отмечает превышение кэша UI 64 МиБ. Допуск калибровки `retry-storm` — 8× из-за переноса S1 на другое оборудование и модель меньше 50 сервисов. API и CLI вызывают эти же методы ядра.

### 4.6. Артефакт

Манифест и сводка используют текущую версию артефакта (`Versions.ARTIFACT_SCHEMA` в `RunArtifact.kt`, сейчас 17); прежние артефакты требуют нового запуска. В обоих файлах поле `grid` сохраняет оси `{ path, values }` в порядке документа, включая порядок и повторы значений; без сетки оно равно `[]`. Это позволяет UI получить оси при первой загрузке сводки независимо от сортировки ключей `coordinates`. В `series.points` манифеста находятся идентификаторы и координаты точек. У каждого варианта сводки список `points` содержит `id`, `coordinates`, `aggregate` и `saturation`; агрегата всего варианта нет. Без сетки сохраняется одна точка `p0` с пустыми координатами.

Каталог `.results/<эксперимент>/<прогон>/` (ADR 0008): `manifest.json`, `summary.json` и по каталогу на задачу `series/<вариант>/<точка>/rep-<n>/`. В каталоге задачи — итоги повторения для сводки, части рядов `part-<k>.json.gz` и индекс частей: какие узлы, связи и диапазон окон покрывает каждая часть. Части делят сетки «узел × окно» и «связь × окно» на группы элементов и диапазоны окон так, чтобы несжатая часть не превышала бюджет ответа UI (4 МиБ); поэтому любую часть можно отдать UI целиком. Манифест фиксирует версии, хеши документов, seed, окно, профиль скетча, полноту и контрольные суммы всех файлов задач. Сводка содержит метрики по вариантам и точкам сетки и данные вывода.

Версии описаны в [формате артефакта](../../results-format.md): сейчас манифест и сводка — 17, индекс и части рядов — 7. Точка без сетки — `p0`. Последовательные закрытые окна накапливаются в текущей части до лимита 4 МиБ; узлы и связи делятся на группы только для окна, которое целиком не помещается в часть. Часть рядов содержит массивы `nodes`, `connections` и `classes`, индекс перечисляет идентификаторы всех трёх видов. Лимит 4 МиБ общий для всех массивов части. При делении возможны части только со связями. Сводка пересобирается из `replication.json.gz`, `index.json` и gzip-частей в фиксированном порядке задач. `execution.window` по умолчанию равен `measurement / 100`, окна покрывают `[0, warmup + measurement)`, последнее хранит фактическую длительность. Ряды используют время событий и включают прогрев, а итоги повторений — когорту измеряемого интервала с её run-out. Скетч задержки сервиса содержит только принятые попытки; отказы очереди остаются в отдельном счётчике. Хеши документов манифеста считаются по канонической записи; версии для `If-Match` и принятого задания остаются хешами исходных байтов.

## 5. Сервер, рабочая область, CLI

### 5.1. Рабочая область

Сервер запускается с каталогом рабочей области — параметром запуска или переменной окружения; Docker Compose подключает каталог, по умолчанию `examples/`. Внешние изменения отслеживаются `WatchService`; UI получает их опросом. У документа есть версия — хеш содержимого; запись выполняется с `If-Match`, при расхождении сервер отвечает 409. Запись без `If-Match` только создаёт новый документ. `If-Match` сравнивается строго (RFC 9110): слабые теги не совпадают. Пути не выходят за рабочую область, в том числе через символьные ссылки.

`DELETE /workspace/document?path=` требует `If-Match`: без него — 428 `VERSION_REQUIRED`, при несовпадении — 409 `VERSION_CONFLICT`, отсутствующий документ — 404, успех — 204. Ядро удаляет документ под той же блокировкой рабочей области, что и запись. После удаления с проверкой версии удаляется и его пустой непосредственный каталог. Корень рабочей области, непустой каталог и каталог, достигнутый через символьную ссылку, сохраняются.

Журнал изменений ведётся в памяти процесса и хранит 1000 последних изменений документов `*.model.json`, `*.layout.json` и `*.experiment.json` вне скрытых каталогов, включая записи через API. `WatchService` дополняется полным сканированием раз в секунду, поэтому внешнее изменение попадает в журнал не позже чем через 5 секунд. Обходы пропускают скрытые каталоги целиком (`SKIP_SUBTREE`), включая `.results`; начальный снимок журнала делается при первом запросе изменений. `GET /workspace/changes?since=` возвращает непрозрачный курсор `<generation>:<sequence>`, признак `reset` и изменения `{ path, kind, version }`, где `version: null` означает удаление; без `since` — текущий курсор и пустой список. Курсор другого процесса, устаревший или больший текущего даёт `reset: true` и пустой список; некорректный курсор — 400 `CURSOR_INVALID`.

### 5.2. API

API получает базовый путь `/api/v1` и полностью заменяет нынешнее (ADR 0010).

| Ручка | Назначение |
|---|---|
| `GET /health` | Состояние сервера |
| `GET /catalog` | Каталог типов |
| `GET /workspace/documents`, `GET/PUT/DELETE /workspace/document?path=` | Документы рабочей области с версией; запись списка и ответ PUT содержат относительный `modelRef` для разбираемого эксперимента, иначе `null`; путь содержит `/`, поэтому передаётся параметром |
| `GET /workspace/changes?since=` | Внешние изменения |
| `POST /validate` | Диагностика и линтер; необязательные черновики документов позволяют проверить несохранённые правки |
| `POST /estimate` | Оценка стоимости эксперимента |
| `POST /jobs`, `GET /jobs`, `GET /jobs/{id}`, `POST /jobs/{id}/cancel` | Задания |
| `GET /runs`, `POST /runs/{id}/resume`, `GET /runs/{id}/manifest`, `GET /runs/{id}/summary`, `GET /runs/{id}/series/{variant}/{cell}/{rep}`, `GET /runs/{id}/series/{variant}/{cell}/{rep}/{part}` | Прогоны, включая незаконченные, и досчёт незаконченного — к прогону, а не к заданию: задания не переживают перезапуск сервера; для задачи — индекс частей рядов, затем сами части в gzip как есть |
| `GET /runs/obsolete`, `DELETE /runs/{id}`, `DELETE /runs?directory=…` | Список устаревших прогонов и удаление каталога прогона, включая нечитаемые артефакты |

Спецификацию генерирует springdoc в `apps/server/openapi.json`. Классы ядра сервер отдаёт через kotlinx-конвертер Spring, а springdoc строит схему по тем же классам через Jackson. Поэтому JSON API содержит все поля, отсутствующее значение пишется как `null`, а типы API не используют `@SerialName`, собственные сериализаторы и полиморфизм.

Принятое задание привязано к версиям модели и эксперимента, прочитанным при проверке. Перед расчётом ядро сверяет их с теми же загруженными документами, которые будут исполнены. Невалидные документы дают обычную диагностику проверки, а изменение версий валидных документов — `DOCUMENT_CHANGED`. В обоих случаях задание получает `FAILED`, прогон не записывается. Сервер хранит не более 100 завершённых заданий в порядке завершения (FIFO); активные задания не вытесняются.

`POST /validate` принимает `{ experiment, drafts? }`. Необязательный `drafts` — список `{ path, content }`, где `content` имеет форму `DocumentContent` и содержит ровно один документ вида, заданного суффиксом пути. Пути черновиков канонические, относительно корня рабочей области, без повторов. Черновики подменяют чтение только на время проверки, в том числе для ещё не созданных документов; файлы и их версии в хранилище не меняются. Ответ остаётся `ValidationView`. Без `drafts` проверяются сохранённые файлы. В ядре этому соответствует `Lab.validate(experimentPath, drafts: Map<String, String>)` с текстом документов.

`POST /estimate` принимает то же тело и возвращает `ExperimentEstimate` ядра; оценка не меняет документы и не создаёт `.results/`. `POST /runs/{id}/resume` сначала вызывает `Lab.validateResume`, затем создаёт задание `Lab.resume`, которое повторяет проверки при исполнении. Ответ — 202 с `JobView` и исходным `runId`. У принятого задания `totalTasks` сразу содержит полное число сочетаний варианта, точки и повторения. Первый отчёт досчёта проверяет готовые задачи и включает пригодные к повторному использованию в `completedTasks`; счётчик завершается исходным общим числом задач. Завершённый прогон даёт 409 `RUN_COMPLETE`, изменённые документы — 400 с диагностикой ядра, неизвестный — 404 `RUN_NOT_FOUND`.

`GET /runs/latest?experiment=…` возвращает не больше двух записей выбранного эксперимента: последнюю завершённую по времени публикации манифеста и последнюю незавершённую по идентификатору. Поиск использует метаданные файлов в группе эксперимента, читает только выбранные манифесты и не обходит файлы рядов. `GET /runs` перечисляет законченные и незаконченные прогоны, `RunEntry.complete` различает их состояния, `sizeBytes` содержит размер обычных файлов каталога. Сводка незаконченного прогона даёт 404 `RUN_INCOMPLETE`; манифест и готовые задачи рядов доступны. `GET /runs/obsolete` перечисляет каталоги с неподдерживаемым, повреждённым или отсутствующим манифестом: `id`, `directory`, `sizeBytes`, `experiment` или `null`. Активные прогоны в этот список не входят.

`DELETE /runs/{id}` и `DELETE /runs?directory=…` удаляют каталог прогона целиком независимо от версии манифеста. Второй вариант адресует каталог внутри `.results/`, включая прогон без манифеста. Успех — 204, отсутствующий прогон — 404 `RUN_NOT_FOUND`, недопустимый путь — 400 `RUN_PATH`. Символьные ссылки не позволяют удалить каталог за пределами `.results/`. Задание Run или Resume в очереди либо в работе блокирует удаление своего прогона и прогонов того же эксперимента с 409 `RUN_ACTIVE`; отмена снимает блокировку после завершения записи файлов. Удаление документа активного эксперимента даёт 409 `EXPERIMENT_ACTIVE`.

Ручки рядов T2.1 возвращают индекс задачи как `SeriesIndex`, а часть — исходными байтами gzip с `Content-Type: application/json` и `Content-Encoding: gzip`. Сильный `ETag` части равен её SHA-256 из индекса; `Cache-Control: max-age=31536000, public, immutable` разрешает хранить неизменяемую часть год. OpenAPI описывает распакованный `SeriesPart`. Идентификаторы проверяются до чтения: точка имеет вид `p0`, `p1` и далее, номера повторений и частей — целые от 0 до 2147483647 без ведущих нулей. Неверный формат даёт 400 `SERIES_PATH`, неизвестный объект или отсутствующий файл — 404 `SERIES_NOT_FOUND`. Часть должна быть указана в индексе; символьные ссылки в пути рядов не читаются. Ряды готовых задач доступны и у незаконченного прогона.

`POST /jobs/{id}/cancel` возвращает 202 с `JobView`. Задание в очереди сразу получает статус `CANCELLED` без создания файлов; выполняющееся получает `cancelRequested: true` и переходит в `CANCELLED`, когда ядро остановило расчёт и закончило запись артефакта. Повторная отмена возвращает текущее состояние с кодом 202. Завершённое или ошибочное задание даёт 409 `JOB_FINISHED`, неизвестное — 404 `JOB_NOT_FOUND`. Запрос во время окончательной записи готового результата не прерывает её: статус остаётся `COMPLETED`.

При остановке контекста Spring `JobService.close()` отменяет задания до закрытия вызывающего исполнителя: ожидающие задания получают `CANCELLED` сразу, выполняющиеся — `cancelRequested: true`. Новые отправки во время остановки отменяются без запуска. Затем вызывающий исполнитель ждёт остановки расчётов и завершения записей, после чего закрывается общий пул ядра.

### 5.3. CLI

Повторный SIGINT после запроса отмены принудительно завершает процесс с кодом 130. Записи при этом не дожидаются завершения; полнота артефакта и наличие манифеста не гарантируются.

Команды на тех же документах: `validate`, `estimate`, `run [--workers N]`, `resume <прогон>`, `summary [--replicas] <идентификатор-прогона>`, `catalog`, `schema`. `estimate` печатает `ExperimentEstimate` одной JSON-строкой. `run` пишет артефакт в `.results/`; `resume` принимает идентификатор прогона или путь к его каталогу внутри рабочей области и досчитывает его на месте. Для `run` и `resume` ход выполнения идёт в stderr, путь к артефакту и краткая сводка по каждой паре «вариант, точка» — в stdout. Рабочая область CLI — текущий каталог, пути к эксперименту и прогону ведут внутрь неё. `validate` пишет результат в stderr. `catalog` печатает тот же JSON, что `GET /catalog`, `schema <model|layout|experiment>` — текст соответствующего `schemas/*.schema.json` из генератора; эти две команды не открывают рабочую область. Код выхода 2 — ошибка использования или проверки, 1 — сбой расчёта, 130 — отмена.

Ctrl+C и SIGTERM передают отмену в `Lab.run` и `Lab.resume`. CLI ждёт остановки и записи незаконченного артефакта, печатает его путь в stderr и завершается с кодом 130. Если артефакт ещё не создан, CLI сообщает об этом без пути; stdout при отмене остаётся пустым. Обработчики сигналов действуют только во время команд `run` и `resume`.

`summary` читает сохранённую сводку законченного прогона через `RunCatalog`, не запускает симуляцию и не требует исходных документов. Печатает в stdout тот же путь и сводку, что `run`; неизвестный, незаконченный или нечитаемый прогон даёт код 2 и сообщение в stderr. Проверка версий артефакта остаётся в ядре.

В сводке каждой точки CLI печатает сохранённый вывод `point.saturation`. Для каждого набора слотов, который первым насытился в повторениях, указываются идентификатор элемента, имя набора, английская подпись `label.message`, число таких повторений из общего числа, медиана и диапазон начала насыщения. Далее печатается число повторений без насыщения. Строка `capacity headroom (pooled over measurement)` появляется только если насыщения не было ни в одном повторении точки; она показывает максимумы загрузки и средней очереди по объединённым данным за всё измерение. Эти правила общие для `run`, `resume` и `summary`.

В модели с группами после сводки каждой точки CLI печатает обычные сервисы, затем сервисные группы. Все строки показывают загрузку, среднюю очередь и число ошибок; строка группы дополнительно показывает p99 объединённого распределения. Худшая по загрузке реплика и её значение берутся из `totals.slotPools.handlers.replicaExtrema`. Флаг `--replicas` у `run`, `resume` и `summary` раскрывает строки экземпляров внутри группы по номеру; у `run` сочетается с `--workers N`. Для групп используются готовые `slotPoolSummaries` и `pooledLatency`; для отдельных сервисов и реплик загрузка — отношение сохранённых интегралов занятости и ёмкости, средняя очередь — отношение интеграла очереди к `measurementMs`. При нулевом знаменателе значение показывается как `n/a`. Для моделей без групп вывод `run` и `resume` остаётся прежним.

## 6. UI

### 6.1. Каркас

По §5.5 видения и ADR 0004: верхняя панель (выбор модели и её эксперимента, значок «Настройки прогона», несохранённые изменения, «Оценить», «Запустить», Cancel и Resume); слева полоса значков блоков из каталога шириной 48 px; в центре холст React Flow, связи `call` протягиваются между портами; справа инспектор с формами из каталога и вводом величин с единицами; внизу холста страницы вариантов; внизу экрана панель результатов и постоянная строка состояния во всю ширину. Страница не прокручивается.

Модель — главный объект интерфейса (§4.3 концепции). Список «Модель» содержит все `*.model.json` рабочей области. Список «Эксперимент» содержит только документы, чей `modelRef`, разрешённый относительно файла эксперимента, указывает на выбранную модель. При открытии модели выбирается её последний открытый эксперимент, иначе первый по имени файла. Последние открытые модель и эксперимент каждой модели хранятся в браузере; удалённый выбор заменяется первым доступным. Форматы документов прежние.

Значок шестерёнки с доступной подписью и подсказкой «Настройки прогона» раскрывает инспектор, снимает выделение и выводит из `Analysis`. Повторное нажатие снова показывает начало настроек и раскрывает раздел «Прогон». Кнопка нажата (`aria-pressed`), пока раскрытый инспектор показывает настройки прогона. В заголовке инспектора стоит «Настройки прогона», под ним мелко — имя файла эксперимента без каталога и суффикса `.experiment.json`; полный путь доступен в подсказке. Ниже идут сворачиваемые разделы «Прогон», «Отказы» и «Перебор». Для элемента в том же месте показаны идентификатор и тип; для варианта — название (при его отсутствии идентификатор) и подпись «Вариант».

Описание (`description`, поле на две строки) и заметки (`notes`, многострочное поле) блока и связи находятся в секции «Параметры» инспектора. Описание доступно также через «?» рядом с именем на схеме; у связи без прежней подписи появляется имя с подсказкой. Заметки видны только в инспекторе. На странице варианта оба поля элемента доступны только для чтения, как структура модели.

Пояснения модели и эксперимента находятся в сворачиваемом разделе «Описания и заметки» настроек прогона, после разделов прогона, отказов и перебора. Группы «Модель» и «Эксперимент» содержат свои поля «Описание» и «Заметки». На странице варианта пояснения модели доступны только для чтения, пояснения общего эксперимента можно менять. У варианта есть необязательное `description`: поле «Описание» в его свойствах и текст в подсказке вкладки под схемой. Формат эксперимента — `schemaVersion: 3`; версия 2 получает ошибку `SCHEMA_VERSION` до проверки структуры.

Правка пояснения сохраняется при выходе из поля одной записью Undo. Пустая строка удаляет ключ из документа; пробелы и переводы строк непустого текста сохраняются. Поля не интерпретируют Markdown или HTML.

Редактор отказов в настройках прогона общий для всех вариантов. Вид выбирается списком: смена вида сохраняет цель и интервал, заменяет параметры прежнего вида начальными значениями нового и отменяется одной записью Undo. В целях доступны сервисы, БД, пулеры, реплики `сервис#k`, связи `call` и `route`, копии исходящих связей групп. Меню перечисляет первые 100 реплик; для более длинных групп появляется поле номера, позволяющее выбрать любую реплику без создания огромного списка. Выбранная реплика также появляется в меню. Потеря ёмкости недоступна для связи без пула и для `route`; верхняя граница учитывает ёмкость цели и отличия реплик. Подписи замедления различают время обработки блока и сетевую задержку связи; формулы и пояснения полей открываются через «?». Кнопка «Добавить отказ» в инспекторе элемента создаёт отказ с выбранной целью и открывает его в настройках прогона; для группы и её исходящей связи перед созданием можно выбрать отдельную реплику или копию связи. Список параметров перебора исключает `pool` у исходящего вызова пулера, который ядро запрещает кодом `POOLER_CALL_POOL`.

Модель без экспериментов открывается с экспериментом в памяти: один вариант `baseline`, 10 повторений, разогрев 10 s и измерение 60 s. Те же начальные значения задаёт общая фабрика для «Новой модели» и «Нового эксперимента». Эксперимент в памяти записывается при первом Save или Run; проверка и оценка до записи получают его как черновик. Пока в модели нет клиента, структурные ошибки `TOPOLOGY_*` скрыты: на холсте видна подсказка «Добавьте клиента из палитры», а Run заблокирован с тем же пояснением. Ошибки параметров остаются видны. После добавления клиента показывается и диагностика топологии.

В шапке Выводов рядом с таблицей сравнения вариантов выбирается уровень доверия интервалов: 80, 90, 95 или 99 %, по умолчанию 95 %. Переключатель подписан «Интервалы», рядом стоит общий значок «?» с объяснением смысла интервала, выбранного уровня и того, что новый прогон не нужен. В меню «Вид» этого пункта нет. Выбор один на браузер и хранится в `localStorage`, отдельно от документов и истории undo/redo; если хранилище недоступно, он действует до перезагрузки страницы. Смена уровня сразу пересчитывает интервалы в Findings, инспекторе и Map без нового прогона. Web использует формулу Стьюдента `mean ± t(1 − α/2, n − 1) · stdDev / √n`, где `n` — число повторений соответствующего варианта, а `α = 1 − уровень / 100`. Если `stdDev` отсутствует или `n < 2`, интервала нет. Границы не обрезаются, подписи всех показанных интервалов называют выбранный уровень, в том числе в инспекторе и Map, где переключателя нет. Формат артефакта и API прежние: `ci95Low` и `ci95High` сохраняют границы 95 %.

На каждой странице открытого эксперимента под схемой видна полоса «Ход эксперимента». По умолчанию она свёрнута до строки высотой 32 px с нагрузкой и отказами. Развёрнутая полоса накладывается на нижнюю часть холста: размер области схемы при раскрытии не меняется, схема вписывается над полосой. Высота регулируется тем же разделителем, что у панели результатов; состояние раскрытия и желаемая высота хранятся в браузере. В небольшом окне высота ограничивается доступной областью, внутри полосы появляется прокрутка.

Ось полосы охватывает время от нуля до суммы разогрева и измерения. На ней показаны обе зоны, кусочно-линейная интенсивность каждого клиента с подписями точек и отдельная полоса для каждого отказа: цель, вид, параметры и интервал. До первой и после последней точки нагрузки удерживается ближайшее значение, на границе прогона используется интерполяция. Подписи поддерживают все виды отказов, включая замедление множителем и добавленной задержкой, ошибки, быструю недоступность, чёрную дыру и потерю ёмкости. Реплика подписывается как `order-service#2`, копия связи — как `order-service#2 → pgbouncer`.

У затронутых блоков и связей есть отдельный значок отказов с их полными описаниями в подсказке. Отказ реплики отмечает узел её группы, отказ копии связи — исходную связь. Щелчок по полосе открывает соответствующий отказ в инспекторе; значок открывает первый отказ элемента. Такой переход раскрывает свёрнутый инспектор и выводит из компоновки `Analysis`. Полоса и значки только показывают документы: перетаскивание интервалов и редактирование точек нагрузки не поддерживаются.

После прогона на странице варианта полоса делит курсор с Timeline и воспроизведением. Щелчок по оси или клавиши ←/→, Home и End выбирают окно через общий проигрыватель. При изменениях документов после прогона полоса показывает текущие условия, а управление курсором в ней отключается до нового прогона.

До первого прогона открытого эксперимента в текущей сессии панель результатов свёрнута, освободившуюся высоту занимает холст. На странице варианта результаты выбранного элемента идут первыми в инспекторе, параметры находятся под ними в сворачиваемой группе (§6.3).

Интерфейс рассчитан на настольные окна от 1280×720 до 3840×2160 и масштаб браузера 90–150 %. Шрифты и отступы заданы в `rem`. Верхняя панель при ширине окна более 1280 px остаётся в одну строку на обоих языках; при 1280 px и меньше переносится, если элементы иначе не помещаются. Название приложения, подписи кнопок и признак несохранённых изменений видны целиком. Save, Estimate и Run остаются в одной группе у правого края панели. Строка контекста и строка состояния остаются в одну строку; длинные пути экспериментов, подписи вариантов и версии backend обрезаются многоточием, полный текст доступен в подсказке. Графики Timeline занимают одну–три колонки в зависимости от ширины самой панели; при достаточной ширине минимальная ширина графика составляет 27,5 `rem`.

Ширина инспектора по умолчанию — `clamp(280px, 22vw, 480px)`. Её можно менять тем же разделителем, что высоту панели результатов: мышью, клавишами ←/→, Home и End. Ширина ограничена 280–480 px; при уменьшении окна верхняя граница уменьшается так, чтобы холсту оставалось не менее 480 px, при необходимости уменьшается и нижняя. Двойной щелчок возвращает относительный размер по умолчанию. Кнопка сворачивает инспектор до полосы и раскрывает обратно. Выбор элемента не раскрывает свёрнутый инспектор: его имя появляется на полосе. Содержимое инспектора и черновики полей сохраняются при сворачивании. Ширина и свёрнутость запоминаются в браузере вне документов и undo/redo; при увеличении окна восстанавливается желаемая ширина. Палитра остаётся полосой постоянной ширины, без изменения размера и сворачивания. Описание `Shared by all variants` показано один раз под заголовком Run settings.

Строка состояния показывает слева направо состояние задания и прогресс активного задания (`RUNNING 3/4`), запрошенную отмену, счётчики ошибок и предупреждений, признак устаревших результатов, время выбранного окна общего курсора, состояние backend с версиями приложения и KSL, масштаб холста. Щелчок по счётчикам открывает Problems и раскрывает свёрнутую панель. Строка остаётся видна при любом размере панели результатов. Статус задания и состояние backend показываются здесь; в верхней панели остаются команды Run, Cancel и Resume, в заголовке результатов статуса задания нет.

При открытии страницы UI запрашивает `GET /health` один раз. Дальше доступность сервера отслеживается существующим опросом `GET /workspace/changes` каждую секунду: ошибка сети или ответ 5xx сразу меняет статус на «Сервер недоступен» с причиной в подсказке. Save, Estimate и Run блокируются с той же причиной. Пока сервер недоступен, `/health` повторяется через 1, 2, 5 и затем каждые 10 секунд; очередная ошибка опроса изменений не сбрасывает эту паузу. Первый успешный опрос изменений во время недоступности немедленно запускает внеочередную проверку `/health`, не дожидаясь этой паузы. Для одной недоступности такая проверка выполняется не больше одного раза; если она неуспешна, повторы с нарастающей паузой продолжаются. Успешный ответ `/health` возвращает статус «Сервер работает» с версиями и снимает блокировку из-за недоступности; несохранённые правки и история undo/redo сохраняются, остальные ограничения команд продолжают действовать. В штатной работе отдельного опроса `/health` нет. Тексты состояния и причины блокировки берутся из каталогов сообщений `en` и `ru`.

Estimate получает оценку через `POST /estimate` с черновиками изменённых документов и показывает число задач, потоков, ожидаемых событий и строк, время, объём до и после сжатия, число частей и предупреждения. Кнопка Estimate открывает всплывающую панель у кнопок запуска до явного закрытия: кнопкой, щелчком вне панели или Esc. Панель не занимает высоту холста и не меняет размер результатов; закрытие во время запроса не открывает её заново при получении ответа. Оценка не сохраняет документы и не запускает расчёт. Правка или смена документов убирает прежнюю оценку; запоздалые ответы и ошибки отбрасываются. Неразбираемый ввод во время ожидания также отменяет применение ответа. Перед каждым Run запрашивается новая оценка. При Run панель открывается только для предупреждений `ESTIMATE_UI_CACHE`, `ESTIMATE_EXTRAPOLATION` или ошибки оценки и закрывается сама после получения нового задания. `ESTIMATE_UI_CACHE` требует явного подтверждения с текстом предупреждения; `ESTIMATE_EXTRAPOLATION` подтверждения не требует. При ошибке оценки запуск возможен только после явного подтверждения, что бюджет времени и размера не проверен.

После `CANCELLED` или `FAILED` кнопка Resume появляется, если доступен манифест с `complete: false`. Она вызывает `POST /runs/{id}/resume`; новое задание отслеживается и отменяется тем же способом, что обычный запуск. Результаты остаются связаны с документами исходного прогона. Несохранённые изменения блокируют Run и Resume. Resume раскрывает свёрнутую панель результатов. Отказы `RUN_COMPLETE` и диагностика изменённых документов видны на любой её вкладке с предложением начать новый прогон через Run.

На странице модели блок добавляется из палитры перетаскиванием, двойным щелчком, Enter или кнопкой «Добавить» в карточке блока. Одиночный щелчок открывает рядом с палитрой карточку с названием, описанием и ссылкой на справку по типу, не меняя модель и историю. Повторный щелчок, Esc или щелчок вне карточки закрывают её. На странице варианта и при ошибке ввода карточка и справка доступны, а добавление недоступно.

Перетаскивание ставит блок в точку броска с привязкой к выбранной сетке, если она включена. Двойной щелчок, Enter и «Добавить» ставят блок в центр видимой области холста с учётом смещения и масштаба и той же привязкой. Если холст ещё не измерен, запрос вставки ждёт первого измерения. Образец нового блока измеряется с теми же строками и кнопками, что будут у вставленного блока. Если место занято, позиция сдвигается по диагонали на два шага выбранной сетки; если блок выходит за видимую область, выбирается ближайшая свободная позиция внутри неё. Если свободного места нет, холст сдвигается к новому блоку; если блок целиком не помещается при текущем масштабе, масштаб уменьшается до его размеров. Развёрнутая полоса хода эксперимента исключается из области вставки. Новый блок выделяется; добавление любым способом использует одну команду `addBlock` в истории undo/redo.

Блок получает явные начальные значения из `ParamDescriptor.initial`. Они записываются в документ вместе с блоком; новая связь получает их так же. У всех обязательных параметров, включая вложенные поля, есть начальные значения. Для необязательного параметра без отдельного `initial` оно совпадает с `default`. Необязательный объект без значения, например `call.pool`, остаётся выключенным; при включении его поля заполняются начальными значениями. Чтение модели и компиляция используют только `default`: `initial` не меняет смысл существующего документа.

У каждого типа есть значок и доступное имя; подсказка показывает только название из локализованного каталога при наведении или фокусе с клавиатуры. После щелчка мышью она исчезает с уходом курсора. Одновременно видна не больше чем одна подсказка: наведение имеет приоритет перед фокусом с клавиатуры. Пока карточка типа открыта, подсказка его значка скрыта. Неизвестный тип получает нейтральный значок с первой буквой подписи. Раздела Connections в палитре нет: значок подсказки объясняет, что связь протягивается от выходного порта к входному, и показывает подсказку по тем же правилам. `Identifier` в инспекторе переименовывает блок или связь с обновлением ссылок во всех документах. Ctrl/Cmd+щелчок выделяет несколько элементов, Shift+перетаскивание выделяет рамкой; Delete и Backspace удаляют выделенное с каскадом, Ctrl/Cmd+C и Ctrl/Cmd+V копируют блоки и внутренние связи со сдвигом координат. После вставки выделяются копии. На страницах вариантов структура и раскладка доступны только для просмотра.

Переименование связи обновляет все ссылки `scenario[].connection` в шагах `call`. Переименование блока также меняет ID примыкающих связей, совпадающие с шаблоном `<from>-to-<to>` с необязательным положительным числовым суффиксом. Суффикс сохраняется, если ID свободен; при совпадении с ID другого блока или связи выбирается свободный ID того же шаблона. Остальные ID связей сохраняются. Вместе с ID обновляются шаги сценариев, цели отказов, включая суффиксы реплик, переопределения вариантов и оси перебора. Удаление связи, в том числе при каскадном удалении блока, удаляет ссылающиеся на неё шаги; если шагов не осталось, поле `scenario` удаляется. При вставке сценарии копий ссылаются на копии внутренних связей, а вызовы связей вне скопированного фрагмента удаляются по тому же правилу. Изменения сценариев и структуры входят в одну команду undo/redo.

При сохранении переименования блока или связи замены ID применяются также к целям отказов, переопределениям вариантов и осям перебора остальных экспериментов рабочей области, чей разрешённый `modelRef` указывает на ту же модель. Замены вычисляются между последней сохранённой моделью и текущим снимком истории по сессионной идентичности элементов: цепочка `A → B → C` даёт `A → C`, Undo до сохранения не даёт замены, а Undo после сохранения при следующем Save переносит обратную замену. Служебные сведения об идентичности не входят в JSON документов.

Перед первой записью читаются связанные эксперименты и проверяются версии всех прочитанных экспериментов модели и изменяемых открытых документов, а также состав экспериментов модели. Обнаруженный на этой проверке конфликт останавливает сохранение до любых записей и показывает имя файла. Каждая последующая запись использует прочитанную версию в `If-Match`, как другие файловые операции (§6.2). После частичной ошибки для уже записанного эксперимента сохраняются его версия и снимок модели, к которому приведены ссылки. Повтор Save или Undo с последующим Save вычисляет замену от этого снимка, сохраняя соответствие ссылок элементам при перестановке ID. Под полем `Identifier` перечислены другие эксперименты, чьи ссылки затронет переименование выбранного элемента или его автоматических связей: «Ссылки обновятся также в: checkout-grid». Если таких экспериментов нет, строка отсутствует.

Связи в инспекторе, шагах сценария, целях отказов, списке изменений варианта, Проблемах и Таймлайне показываются как `A → B (ID)`. Та же подпись используется для доступного имени связи на холсте и для связи с описанием. Для копии связи реплики суффикс добавляется к отправителю: `A#2 → B (ID#2)`. Выбор, сохранение документов и переходы по диагностике используют исходный ID.

Позиции привязываются к выбранной сетке, если привязка включена. Перемещение одного или нескольких блоков записывается в историю после завершения жеста одной командой и меняет только их позиции. Размеры узлов React Flow и выделение хранятся вне документов. На холсте есть миникарта и кнопки масштаба. Ключевые параметры — timeout и число попыток связи, обработчики, очередь и среднее время обработки сервиса — правятся прямо на схеме двойным щелчком теми же командами, что в инспекторе; на странице варианта такая правка пишет переопределение. Начальные значения нового блока видны и редактируются в инспекторе. Очистка обязательного поля даёт обычную ошибку параметра; навигация и undo остаются доступны.

Силуэт узла рисуется встроенным SVG позади HTML-полей. Модуль геометрии по фактическим ширине и высоте возвращает контур, линии деталей, прямоугольник содержимого и точки портов на видимой границе. Клиент следует эталону [Person](../../design/person.svg): голова — круг диаметром 38 % ширины, нижней третью перекрытый телом; плечи имеют радиус 25 % ширины, нижние углы — 8 px. Минимальная высота клиента включает голову, плечи, отступы и измеренную высоту HTML-содержимого. Сервис остаётся скруглённой карточкой, БД — цилиндром с крышкой высотой 16 px, пулер — двойной рамкой с отступом 6 px, маршрутизатор — вписанным кругом в узле 144 × 144 px. Группа реплик рисует две задние кромки со смещением 4 и 8 px тем же модулем и сохраняет прибавку 8 px к высоте. Превью всех фигур в трёх размерах — в [docs/design](../../design/README.md). Цвета SVG задаются через `--node-fill` и `--node-stroke`; выделение и отметки переопределений сохраняются вместе с окраской результатов. После изменения портов React Flow перечитывает их координаты.

В узле каждая пара «название: значение» занимает отдельную строку без разделителей и внутренних переносов. У сервиса это обработчики, очередь и среднее время обработки; у БД — соединения, очередь и среднее время запроса; у пулера — клиентские подключения, серверный пул и предел ожидания; у маршрутизатора — политика. Значения правятся на месте, политика выбирается из списка каталога. Клиент с одним профилем показывает интенсивность единственной точки нагрузки и дедлайн со встроенной правкой; для нескольких точек вместо интенсивности стоит «Профиль нагрузки». Правка интенсивности сохраняет время точки и записывает профиль целиком, в том числе как переопределение варианта. Клиент с видами запросов показывает суммарную интенсивность в начале прогона и число видов запросов; интенсивность правится в инспекторе. Каждая правка входит в одну запись undo/redo. Пояснения новых полей доступны за «?». Три строки параметров сервиса сохраняют одинаковую высоту узла в `en` и `ru`.

В разделе «Нагрузка» клиента переключатель «Один профиль / Несколько видов запросов» выбирает представление нагрузки. При переходе к видам запросов прежний профиль получает идентификатор `request-1`. Обратный переход складывает профили на объединении всех точек, в том числе за пределами текущего прогона, и удаляет список видов запросов. Для неверных профилей этот переход недоступен до исправления. Каждый вид запроса имеет идентификатор, таблицу точек и график; его можно добавить с профилем последнего, удалить или переставить. Идентификаторы следуют правилам блоков, уникальны у каждого клиента и общие для модели; `default` зарезервирован. Переименование обновляет объявления этого вида запроса у всех клиентов, ссылки в шагах сценария и маршрутах модели и списки в вариантах открытого эксперимента. Если в затронутом списке появится повтор идентификатора, ошибка видна у поля и переименование не записывается. Удаление и переход к одному профилю сохраняют ссылки: «Проблемы» показывают ошибки ядра для исчезнувшего вида запроса. Каждое действие отменяется одной записью Undo.

При сохранении переименование обновляет списки видов запросов в остальных экспериментах той же модели через общий механизм связанных ссылок: с проверкой версий, учётом частичных записей и обратной заменой после Undo. Под идентификатором перечислены затронутые эксперименты. Повтор идентификатора в их вариантах останавливает сохранение до первой записи и показывает имя файла.

На странице варианта список заменяется целиком; смена режима подавляет унаследованное противоположное представление, а возврат к модели снимает оба переопределения. При смене режима модели вариант с собственным профилем сохраняет его режим. Полоса хода эксперимента показывает профили видов запросов друг под другом и их сумму; для одного профиля её вид сохраняется. В интерфейсе используются термины «вид запроса» и `request type`; поле документов и API остаётся `classes`.

Силуэт задаётся типом: клиент — фигура Person нотации C4 с круглой головой над карточкой, сервис — скруглённая карточка, БД — цилиндр с эллиптической крышкой, пулер — карточка с двойной рамкой, маршрутизатор — компактный круг. Неизвестный тип получает обычную карточку. В шапке стоит тот же линейный значок, что в палитре; отдельной подписи типа под именем нет, название доступно в подсказке значка. БД и пулер также имеют значки с цветом `currentColor`. Порты остаются слева и справа, окраска по доступной метрике и отметки выделения, переопределений, отказов и насыщения относятся к телу узла. Подпись `call` с пулом дополняется размером («пул 10»), а вызова группы реплик — явно заданной политикой балансировки; подпись остаётся одной компактной плашкой.

Миникарта и кнопки масштаба находятся в правом нижнем углу поверх холста. При открытии документа схема вписывается в доступную область с учётом плашки варианта и развёрнутой полосы хода эксперимента. Для вписывания используется общий прямоугольник измеренных узлов, маршрутов связей и их подписей. Пока пользователь не взаимодействовал со схемой, вписывание повторяется при изменении размеров холста, узлов и подписей. После нажатия на холст, узел или подпись связи, ручного масштабирования, сдвига, перемещения или вставки блока, начала перетаскивания из палитры над холстом либо нажатия кнопки вписывания выбранный вид сохраняется: открытие и закрытие панелей, разделитель и переключение `Analysis` больше не вызывают вписывание. Отмена перетаскивания не возвращает автоматическое вписывание. Кнопки масштаба и миникарта располагаются над развёрнутой полосой хода эксперимента. Кнопка `Fit view` вписывает схему по явному запросу. При малой высоте холста схема вписывается слева от навигации, чтобы миникарта и кнопки не закрывали узлы и подписи. Открытие другого эксперимента снова включает автоматическое вписывание.

Связи проходят ступенчатыми линиями по свободным промежуткам между измеренными прямоугольниками узлов. Порты концов и позиции документа сохраняются; линия обходит чужие узлы, в том числе при вызове через один или несколько блоков. Измеренная подпись находится на свободном участке своей линии, как можно ближе к середине пути, вне всех узлов и других подписей. Связи обрабатываются в порядке документа; последующие линии обходят уже размещённые подписи. Если подпись не помещается на доступных участках, для неё строится горизонтальный участок в ближайшем свободном промежутке над препятствиями или под ними. Геометрия пересчитывается при перемещении или изменении размеров узлов и подписей; протягивание новых связей и выделение сохраняются. Место строк метрик узла определяется выходами типа из каталога и резервируется до прогона; до появления результатов строки пусты. Получение результатов, их отключение и переключение между `Summary` и `Time` сохраняют размеры узлов и позиции документа.

Связи с общим выходным или входным портом не делят прямые участки длиннее 12 единиц холста. При прокладке очередной связи совпадение с прямыми участками предыдущих связей этого порта запрещено, кроме первых и последних 12 единиц пути; пересечения поперёк допустимы. Подпись остаётся на своей линии и не пересекает пути других связей. Порядок документа и повторяемость результата сохраняются; формат документов не меняется.

Разделитель между схемой с вкладками вариантов и панелью анализа меняет высоту панели мышью или клавишами ↑/↓ с шагом 16 px; Home задаёт минимум, End — максимум. Двойной щелчок сбрасывает сохранённую высоту только текущей вкладки и компоновки к относительному размеру по умолчанию (§6.3). Разделитель занимает 0,5 `rem`. Самому холсту React Flow остаётся не менее 252 px при наличии полосы хода эксперимента (220 px без неё), панели результатов — 160 px. Высота сообщений, строки контекста, свёрнутой полосы и вкладок вариантов учитывается дополнительно по их фактическим размерам. В `Analysis` минимум самого холста составляет 320 px с полосой хода эксперимента (288 px без неё), чтобы оставить место под плашку варианта, подписи и навигацию. При 1280×800 высота панели результатов уменьшается до соблюдения этого минимума. Если окно меньше суммы минимумов, области схемы и результатов получают по половине доступной высоты. Прокручивается содержимое областей, страница остаётся в пределах окна.

Кнопка `Analysis` в строке контекста доступна после получения результатов на странице варианта. В этой компоновке схема со строкой контекста и вкладками вариантов занимает верхнюю часть экрана, панель анализа — нижнюю во всю ширину. При первом открытии схеме остаётся примерно 38 % доступной высоты. Палитра скрыта, справа остаётся инспектор только с результатами выбранного элемента; без выбора он предлагает выбрать узел или связь. Параметры инспектора скрыты с сохранением черновиков. Ширина и свёрнутость колонки подчиняются тем же настройкам, что в обычной компоновке. Выбор узла или связи выбирает их ряды на Timeline, параметры правятся двойным щелчком на схеме. Повторное нажатие кнопки или Esc возвращает обычную компоновку и сохраняет курсор времени. Если открыт редактор параметра или всплывающая оценка, Esc сначала закрывает его. Строка состояния видна в обеих компоновках.

У обоих видов шага сценария поле «Выполнять для» позволяет выбрать несколько видов запросов из всех клиентов модели. У связи `route` такое же поле называется «Направлять в <цель маршрута>». Пустой выбор означает все виды запросов и удаляет структурное поле `classes`; одна правка отменяется одним Undo. На странице варианта выбор доступен только для просмотра с подсказкой «структура правится на странице модели». У моделей без видов запросов новые поля не появляются; выбранный вид запроса после удаления его объявления остаётся в поле до исправления, вместе с ошибкой ядра. Указатель ошибки маршрута ведёт к соответствующему полю выбора.

Подпись маршрута показывает один или два вида запросов полностью, а для большего числа — первый и число остальных, например «status +3». Подсказка перечисляет все виды запросов маршрута. Маршрут без ограничения сохраняет прежний вид; отсутствие маршрута для вида запроса видно по диагностике у маршрутизатора.

### 6.2. Состояние и варианты

Применимость вложенного поля задаёт каталог: `ParamDescriptor.appliesWhen` содержит `field` — имя соседнего поля того же объекта — и список допустимых `values`. Отсутствующая пометка означает, что поле применимо всегда; значение управляющего поля разрешается через его значение по умолчанию. Инспектор, встроенная правка на схеме и выбор оси перебора скрывают неприменимые поля, в том числе на странице варианта. У распределений сервиса, БД, пулера, сети и собственного времени шага сценария `stdDev` действует только при `lognormal`. У backoff поля `base` и `max` действуют при `fixed` и `exponential-full-jitter`, `multiplier` — только при `exponential-full-jitter`; при `none` все три поля скрыты.

Смена вида одной командой undo/redo удаляет ставшие неприменимыми поля и заполняет вновь применимые поля из `initial` или значения по умолчанию. Для обязательного при `lognormal` поля `stdDev` без собственного `initial` берётся текущее `mean`. Если при переходе к случайному распределению среднее было нулевым, берётся положительное начальное среднее из каталога либо `1ms`; стандартное отклонение равно полученному среднему. На странице варианта изменения записываются только в эксперимент: если для очистки или заполнения зависимых полей требуется заменить объект целиком, команда сохраняет его действующие соседние поля. Для отдельной реплики обработка учитывает значения группы; неприменимое унаследованное поле подавляется значением `null` в разреженном переопределении. Undo/Redo восстанавливают смену вида вместе со всеми зависимыми значениями. Форматы документов и правила компилятора не меняются.

При смене управляющего поля (`appliesWhen.field`) на странице модели та же команда удаляет оси перебора и переопределения вариантов, которые адресуют ставшие неприменимыми поля этого элемента. Применимость переопределения проверяется с учётом значений его варианта: собственный вид, при котором поле остаётся применимым, сохраняет переопределение. Если команда удалит хотя бы одну ось или переопределение, до правки появляется подтверждение со списком осей, вариантов и полей и пояснением об отмене одной записью Undo. Без таких удалений подтверждения нет; отмена подтверждения сохраняет документы. Undo/Redo возвращают модель и эксперимент вместе. Смена вида на странице варианта очищает только редактируемый объект этого варианта и не меняет общие оси перебора.

Источник правды — загруженные документы модели, раскладки и эксперимента. Правка — команда с undo/redo; правка модели и раскладки — одна операция; воспроизведение в историю не попадает. Первая страница под схемой — страница модели: правка на ней меняет модель. Остальные страницы — варианты эксперимента, в том числе варианты без переопределений. После правок модель с задержкой проверяется через `POST /validate`; диагностика видна значками на схеме и во вкладке Problems. Состояние строится на командах поверх reducer, без новой библиотеки состояния. Переключение страницы сохраняет выбранный элемент, но меняет значения на его странице. Выбор страницы следует за идентификатором варианта при переименовании, undo и redo; удаление активного варианта возвращает страницу модели.

У полей зарезервировано место под значки ошибок и предупреждений. Полный текст и ссылки на варианты открываются наведением, фокусом с клавиатуры или щелчком по значку; Escape закрывает подсказку. Получение и снятие диагностик не меняет положение остальных полей и кнопок инспектора или верхней панели.

При добавлении варианта кнопка `+` сразу показывает «Создание варианта…» / `Creating variant…`. До появления новой страницы кнопка и переходы между страницами заблокированы. Двойной щелчок создаёт один вариант; новая страница открывается и выделяется.

Вкладка `Model` визуально отделена от группы с подписью `Variants`. Её подсказка объясняет, что здесь редактируется структура модели; подсказка варианта называет его и число записанных переопределений. На странице варианта холст обведён фиолетовой рамкой. В верхнем углу находится раскрываемая плашка с замком, именем варианта, пометкой `Structure is read-only` и числом изменений. Схема вписывается с учётом высоты плашки, в том числе при раскрытом списке. Длинное имя обрезается многоточием, полный текст доступен в подсказке.

В списке каждое записанное переопределение занимает одну строку: элемент, название параметра из каталога, значение модели и значение варианта. Для вложенного поля показаны названия его группы и самого поля; отсутствующие значения разрешаются через значения каталога по умолчанию. Числа и варианты выбора форматируются общими средствами интерфейса, величины сохраняют синтаксис полей редактирования. Без переопределений список показывает `Same as model`. Такой же список находится в свойствах варианта в инспекторе. Щелчок по строке выбирает элемент, раскрывает инспектор, возвращает обычную компоновку из `Analysis` и фокусирует соответствующее поле. Неразбираемый ввод блокирует этот переход.

Блоки и подписи связей с переопределениями отмечены янтарной рамкой и доступным значком. В показанных на схеме параметрах значение варианта соседствует с зачёркнутым значением модели; цвет результатов после прогона сохраняется. Структура и раскладка на странице варианта не меняются, курсор блока обычный. Попытка перетащить блок или протянуть связь показывает `Structure is edited on the Model page` со ссылкой на `Model`. Подписи, подсказки и список изменений переведены в каталогах `en` и `ru`.

Инспектор показывает ровно одну текущую цель, которая хранится вне документов и истории:

- щелчок по блоку или связи, переход к элементу из Problems или щелчок по группе метрик сервиса в Findings открывает свойства элемента; при мультивыделении показан последний выбранный элемент;
- щелчок по уже активной вкладке варианта открывает его идентификатор, подпись и список переопределений;
- щелчок по пустому холсту, по уже активной вкладке `Model` или значку «Настройки прогона» рядом с выбором эксперимента открывает общие настройки эксперимента: прогон, отказы и перебор.

Исчезновение цели при удалении или undo возвращает инспектор к эксперименту. При переименовании элемента или варианта цель следует за новым идентификатором, в том числе через undo/redo. Возврат удалённого объекта через undo сам по себе не выбирает его заново.

Явные команды открытия свойств варианта, «Настройки прогона», щелчок по активной вкладке `Model` и переход из Problems возвращают обычную компоновку из режима `Analysis`, чтобы инспектор и нужное поле были видны.

Действия над вариантами находятся в полосе страниц. Кнопка `+` добавляет пустой вариант и делает его активным. Контекстное меню вкладки варианта открывается правой кнопкой мыши, клавишей контекстного меню или Shift+F10 на вкладке в фокусе. `Duplicate` копирует вариант и открывает копию; `Rename` открывает свойства этого варианта в инспекторе с фокусом на подписи; `Delete` требует подтверждения. Последний вариант удалить нельзя: пункт недоступен и снабжён пояснением. У `Model` контекстного меню нет. В меню работают стрелки, Home/End, Enter и Escape; Escape возвращает фокус на вкладку. Все изменения используют общие команды с undo/redo. В инспекторе варианта остаются только его свойства; удаления там нет.

В инспекторе элемента нет свойств и действий варианта и раздела эксперимента. На странице варианта параметры блока или связи показываются с пометкой `variant overrides` и редактируются как переопределения. Описание параметра из `localizeCatalog` открывается значком «?» рядом с подписью поля или заголовком группы и связано с ним для средств доступности. Изменения идентификатора варианта проверяются на допустимость и уникальность; при очистке подписи вкладка показывает идентификатор.

Правка варианта записывает скаляр по пути `id.param`, поле объекта — по `id.param.field`. Если значение совпадает с моделью, в том числе после перевода единиц, переопределение удаляется. `Use model value` сбрасывает поле или объект целиком одной командой; сброс поля сохраняет переопределения соседних полей. Переопределённые поля выделены в инспекторе.

Сервис с `replicas > 1` показан на схеме стопкой карточек с пометкой `×N`; при одной реплике остаётся обычной карточкой. Стопка добавляет 8 px к высоте узла, тело карточки и область холста сохраняют размеры. Число реплик правится в параметрах сервиса; на странице варианта это переопределение `id.replicas`.

Раздел «Отличия реплик» содержит таблицу `replicaOverrides`: строки — номера реплик с отличиями, столбцы — переопределённые параметры. Добавление строки или параметра берёт значение из `ParamDescriptor.initial` каталога. Правка отдельного поля сохраняет наследование остальных полей от сервиса. Удаление последнего отличия убирает строку, удаление последней строки убирает `replicaOverrides`. Каждое действие — одна команда Undo. Недопустимый номер подсвечивается диагностикой `REPLICA_INDEX`; строку можно удалить, а из Problems можно перейти к полю таблицы. Неразбираемый черновик поля блокирует структурные действия до исправления. На странице варианта таблица доступна только для чтения, с подсказкой о правке структуры на странице модели. Объяснение таблицы и параметров открывается через «?».

Очистка необязательного поля варианта выбирает значение каталога по умолчанию. Если оно отличается от модели, переопределение хранит `null`: компилятор считает такое поле отсутствующим и применяет его значение по умолчанию. При разборе существующего переопределения объекта на отдельные поля так же сохраняется отсутствие его необязательных полей.

Цель «эксперимент» доступна на любой странице и содержит общие параметры прогона и отказы: число повторений, разогрев, измеряемый интервал, окно рядов, seed, лимит реального времени, цель и интервал отказа, множитель обработки и долю отказов. Единицы длительности и долей берутся из каталога. Правки меняют документ эксперимента и входят в общую историю. Пустое поле `Series window` удаляет `execution.window`; подсказка показывает текущий измеряемый интервал, делённый на 100, без записи значения по умолчанию в документ. Ошибки проверки по `/execution/window` видны у поля.

Добавленный сбой по умолчанию начинается на середине измеряемого интервала и заканчивается на трёх четвертях. К обеим границам добавляется разогрев: при разогреве 10 s и измерении 60 s сбой действует с 40 до 55 s от начала прогона. Длительности разбираются в единицах каталога; уже заданные сбои не меняются.

У правого края внутри поля `Seed` находится кнопка со значком и подсказкой `Random seed` («Случайное начальное значение генератора»). Края поля совпадают с краями остальных полей раздела «Прогон» в обоих языках. Она выбирает равномерно случайное целое число от 0 до 2⁵³−1 через `crypto.getRandomValues`. Нажатие меняет документ эксперимента одной командой undo/redo, включая замену незавершённого ввода в поле seed, отмечает несохранённые изменения и делает результаты устаревшими. Кнопка доступна везде, где редактируется поле `Seed`. Подсказка и подпись доступности берутся из каталогов `en` и `ru`.

У каждого из шести полей прогона есть общий значок «?» с описанием из каталогов `en` и `ru`, связанным с полем для экранных читалок. Подсказки объясняют независимые повторения и доверительные интервалы, исключение разогрева из результатов, измеряемый интервал, окно рядов по умолчанию `measurement / 100`, воспроизводимость по seed и ограничение реального времени одного повторения. Время отказов и окон отсчитывается от начала разогрева. Лимит реального времени служит предохранителем: превышение завершает прогон ошибкой, после которой его можно продолжить с бо́льшим лимитом; это не модельное время.

Секция «Parameter sweep» / «Перебор параметров» редактирует `grid`: до двух осей со скалярными параметрами блоков и связей из каталога. Первая строка объясняет, что эксперимент запускается для каждой комбинации значений, а результаты доступны на вкладке Map. При заданных осях строка стоимости показывает размеры осей, число точек, вариантов и повторений, например `3 × 3 = 9 points × 2 variants × 10 replications = 180 runs`. Она пересчитывается при изменении осей, вариантов и `Replications`; без осей её нет. Перебор общий для всех вариантов и перекрывает их значения этих параметров. На странице варианта у такого поля инспектора стоит пометка «Swept by the parameter grid», в том числе у вложенных и переопределённых полей. Если вложенное поле относится к незаданному необязательному объекту, пометка видна у этого объекта; значение модели и кнопка его включения сохраняются.

Заголовок оси называет параметр и элемент, например `Timeout · order-service → payment-service`. Значения редактируются компактными плашками с удалением и кнопкой добавления. Описание параметра доступно один раз за общим значком «?» в заголовке оси. Добавление и удаление осей и значений, выбор пути и правка значения входят в undo/redo.

В секции перебора диагностики, отличающиеся только вариантом, объединяются в одну строку со списком названий вариантов; без названия показывается идентификатор. Разные сообщения, аргументы, места и уровни серьёзности остаются отдельными. Значения `args.points` раскрываются через оси текущей сетки: вместо `p0, p1, p2` показано, например, `at Timeout = 1s`. Ось, перебранная целиком, опускается только для полного декартова произведения выбранных значений; отдельные сочетания не объединяются. Неизвестные идентификаторы точек и прежние сообщения без `args.points` сохраняются. Группировка меняет только строки секции: исходные диагностики, счётчики и переходы из Problems сохраняются. Диагностика `/grid/…` видна у соответствующих полей при открытых настройках эксперимента на любой странице. Переход из Problems выбирает цель и фокусирует нужное поле: общие настройки открывают эксперимент, поля варианта — вариант, параметры блока или связи — элемент. Неразбираемый ввод блокирует смену цели и страницы, команды вкладок и другие действия, которые могут потерять черновик.

История хранит последние 100 команд и сохраняется после записи документов; открытие или перечитывание эксперимента очищает её. Undo после сохранения снова делает документ изменённым. Кнопки отмены и повтора находятся в верхней панели; Ctrl/Cmd+Z отменяет команду, Ctrl/Cmd+Shift+Z и Ctrl+Y повторяют её. В полях ввода действует штатная отмена поля.

Одна кнопка сохраняет все изменённые документы в порядке: раскладка, модель, эксперимент. Каждый существующий документ записывается со своей версией `If-Match`, новый — без неё. При 409 запись останавливается: уже сохранённые документы остаются сохранёнными, UI показывает путь конфликтующего документа и блокирует повторное сохранение до перечитывания. Если `layoutRef` отсутствует, первая команда изменения раскладки в той же записи истории добавляет ссылку на `<имя эксперимента>.layout.json` рядом с экспериментом.

При несохранённых изменениях документов или изменённом вводе до выхода из поля перезагрузка, закрытие вкладки и уход по другому адресу вызывают стандартный вопрос браузера. Без правок вопроса нет. Смена модели или эксперимента, в том числе выбор «Новая модель» или «Новый эксперимент» в списке или меню «Файл», при изменённых документах предлагает «Сохранить и перейти», «Не сохранять» и «Отмена». Первый вариант сохраняет все изменённые документы и продолжает переход только после успешной записи; во время записи диалог остаётся открытым. Ошибка записи или конфликт оставляют текущий документ и правки. «Не сохранять» продолжает переход без записи, «Отмена» сохраняет текущую страницу и правки.

«Запустить» доступна при несохранённых корректных правках. Её подсказка — «Сохраняет изменения перед запуском (Ctrl/Cmd+Enter)». После оценки и необходимых подтверждений она сохраняет изменённые документы тем же механизмом и запускает эксперимент только при успешном сохранении. Ошибка записи или конфликт версий прерывает запуск; причина видна рядом с кнопкой. Неразбираемый ввод и ошибки проверки также блокируют запуск с видимым пояснением. Ctrl/Cmd+S сохраняет, Ctrl/Cmd+Enter выполняет тот же запуск. Нажатие кнопки запуска и горячие клавиши завершают ввод в однострочном поле; запуск ждёт проверки нового значения. В многострочных полях, редактируемом тексте и диалогах горячие клавиши не действуют. Сочетания указаны в подсказках кнопок.

Пока идёт оценка, отправка или расчёт нового прогона, прежние завершённые результаты остаются видны с пометкой «Результаты устарели, идёт новый прогон». Выводы, Таймлайн, наложение на холсте и результаты инспектора используют согласованный снимок прежнего прогона: его идентификатор, документы, манифест и сводку. Новый снимок заменяет прежний целиком после загрузки артефактов завершённого прогона. До первого результата Выводы и Таймлайн показывают ожидание, пока запуск идёт; приглашение запустить эксперимент в это время не показывается.

Если раскладка уже записана, а её ссылка ещё нет, перечитывание восстанавливает содержимое и версию этой раскладки. Так же обрабатывается 409 при создании файла с уже занятым именем. Само перечитывание не добавляет `layoutRef`; следующая команда изменения раскладки добавит его вместе с правкой.

Web опрашивает `GET /workspace/changes` каждые 1000 мс, пока открыта рабочая область; внешняя правка открытого документа становится видна не позднее чем через 5 секунд после записи. Курсор получают до первого чтения документов. Ответ `reset: true` заставляет перечитать список документов и сравнить версии открытых документов, а создание и удаление экспериментов обновляет список в выборе. Событие для пути с незавершённым `PUT` откладывается до ответа записи и сравнивается с возвращённой версией, поэтому собственное сохранение не создаёт баннер независимо от порядка ответов журнала и `PUT`. Сбой опроса не меняет редактор и повторяется с прежним курсором.

Внешнее изменение открытого документа показывает баннер с путём и кнопкой Reload. Если есть несохранённые правки, баннер предупреждает об их потере, а перечитывание требует подтверждения и очищает историю. Баннер сам не блокирует Save: попытка записи со старой версией по-прежнему даёт 409. Удалённый документ показывается как удалённый, без Reload и без попытки прочитать отсутствующий файл.

Проверка черновиков запускается через 500 мс после последней команды; вместе с запросом передаются все изменённые документы. Ответы, относящиеся к предыдущим состояниям, отбрасываются. Во время ожидания проверки того же эксперимента и модели сохраняются предыдущая диагностика и её счётчики; Run остаётся заблокирован до актуального ответа. При смене эксперимента или модели прежняя диагностика скрывается. Диагностика связывается с элементами по пути и с полями по JSON-указателю, включая вложенные параметры, переопределения варианта, настройки прогона и отказы. Поле `variant` определяет страницу варианта даже при указателе на модель; без него страница определяется по указателю на переопределение. На странице варианта его значки и сообщения у полей показываются как обычно; общая диагностика видна на всех страницах. На странице модели диагностика вариантов отмечается отдельным приглушённым значком у блока или связи: пунктирная рамка отличает его от значка самой модели, цвет соответствует наибольшей серьёзности, число — количеству сообщений. Подсказка перечисляет идентификаторы вариантов без повторов. Значок открывает и раскрывает Problems с записями этого элемента, сохраняя страницу модели; команда Show all problems, щелчок по вкладке Problems или счётчику в строке состояния снимает фильтр. Рядом с полем инспектора модели, включая вложенные поля, показаны короткие строки In variants с идентификатором варианта и отдельными числами ошибок и предупреждений. В подсказке у поля видны полные сообщения и ссылки на варианты. Каждая ссылка ведёт на страницу варианта, сохраняет выбранный элемент и фокусирует поле. Неразбираемый ввод блокирует эти переходы и значки, как остальную навигацию. Вкладка Problems показывает все записи, включая диагностику без элемента и диагностику ответа запуска. Одинаковая запись из проверки и запуска учитывается один раз. Диагностика ошибки запуска или возобновления относится к документам соответствующей попытки. После их изменения она исключается из текущего списка и счётчиков; новая попытка Resume может показать свою ошибку и при устаревших результатах исходного прогона. Сначала идут ошибки, затем предупреждения; внутри группы сохраняется порядок ответа. Запись начинается со значка серьёзности и готового сообщения API, затем показывает имя блока или связи и вариант, если он есть. Код и путь документа вынесены на вторую приглушённую строку; JSON-указатель виден только в подсказке. Щелчок выбирает соответствующие страницу, элемент и поле.

Новая ошибка в завершённом ответе проверки черновиков или запуска автоматически открывает Problems и раскрывает свёрнутую панель. Запрос Problems имеет приоритет над автоматическим переходом к Findings при завершении прогона. Новизна определяется по серьёзности, коду, сообщению, документу, указателю, элементу и варианту относительно предыдущего завершённого ответа того же источника. Ожидание следующей проверки сохраняет сведения о предыдущих ошибках: повтор той же ошибки не возвращает пользователя в Problems. Если ошибка исчезла из ответа и появилась снова, она считается новой. Предупреждения сами панель не открывают; их число видно в строке состояния. Значки показывают число сообщений и наибольшую серьёзность. Ошибки и предупреждения различаются цветом. На узле незавершённые соединения (нет пути от клиента, входа или выхода) показываются приглушённой подсказкой «Соедините блок со схемой». В Problems эти ошибки сохраняются и блокируют Run. Ошибки параметров, циклы и лишние соединения сохраняют красные значки. Ошибки блокируют Run, предупреждения не блокируют; ожидание проверки и ошибка связи с API также блокируют запуск с пояснением.

Разбираемые значения вне диапазона каталога входят в черновик и проверяются ядром. Неразбираемый ввод остаётся в поле и блокирует действия, которые могут его потерять.

Оценка стоимости открывается под верхней панелью в отдельной области вне холста. Её можно закрыть и открыть снова кнопкой Estimate или Run. Объёмы показываются в KiB и MiB. Перед Run запрашивается свежая оценка; предупреждение бюджета требует подтверждения. При сбое оценки видна ошибка, а запуск без проверки стоимости требует отдельного явного подтверждения. Ответ оценки, устаревший после изменения документов или полей, запуск не разрешает.

### 6.2.1. Действия с файлами

Меню «Файл» находится сразу после названия «Resilience Lab», перед списком «Модель». Последние пункты списков — «+ Новая модель…» и «+ Новый эксперимент…» — открывают те же диалоги создания с тем же подтверждением несохранённых изменений. Эти пункты не меняют выбранный документ; при отмене сохраняются текущий выбор и правки.

Имена моделей и экспериментов могут содержать кириллицу, пробелы и другие символы, допустимые для документов рабочей области. Диалог отклоняет недопустимый путь до сохранения. Каталог результатов не ограничивает имя документа: группа в `.results/` задаётся SHA-256 канонического пути эксперимента относительно рабочей области по [формату артефакта](../../results-format.md).

«Новая модель» создаёт в каталоге с указанным именем пустую модель, раскладку и эксперимент по умолчанию с 10 повторениями; открывается пустой холст с подсказкой добавить клиента. «Новый эксперимент» создаёт в каталоге текущей модели ещё один эксперимент: ссылки на её модель и раскладку, один вариант `baseline`, стандартные параметры прогона. Исходный эксперимент не меняется. «Сохранить модель как» запрашивает «Имя модели», как и «Новая модель», и копирует модель, все её эксперименты и используемые раскладки в каталог с этим именем. Несохранённые правки текущих документов входят в копию; `modelRef` и `layoutRef` переписываются на копии. Открывается копия текущего эксперимента; исходные документы не записываются.

«Импорт» принимает один или несколько файлов `*.model.json`, `*.layout.json`, `*.experiment.json` и каталог назначения. Все файлы читаются до первой записи. Ссылки на выбранные вместе модель и раскладку становятся относительными именами файлов в каталоге назначения. Для экспериментов сначала выполняется обычная проверка через `POST /validate` с черновиками; `PUT` проверяет формат каждого документа. Ошибки видны в Проблемах. При совпадении имени пользователь явно выбирает замену или отмену всего импорта. Подтверждённая замена передаёт прочитанную версию в `If-Match`; новый документ создаётся без этого заголовка. Создание и «Сохранить как» никогда не заменяют существующие документы.

«Удалить эксперимент…» удаляет файл открытого эксперимента и его прогоны. Если у модели больше нет экспериментов, она остаётся открытой с экспериментом по умолчанию в памяти (§6.1). «Удалить модель…» удаляет её файл, все эксперименты, чей разрешённый `modelRef` указывает на эту модель, их прогоны и раскладки, на которые ссылаются только эти эксперименты. Раскладка, используемая экспериментом другой модели, остаётся. Если каталог модели после удаления документов пуст, он тоже удаляется. Прогоны выбираются по полному пути `experiment` в манифесте, включая устаревшие форматы с читаемым полем: совпадение имени файла эксперимента не означает принадлежность к нему.

Подтверждение показывает число прогонов и их общий размер вместе со списком документов. Перед началом удаления UI заново проверяет задания и состав прогонов; активный Run или Resume любого удаляемого эксперимента останавливает операцию с пояснением. Сначала удаляются подтверждённые каталоги прогонов, затем документы в порядке ниже. Частичная ошибка перечисляет удалённые и оставшиеся каталоги и документы.

«Очистить устаревшие прогоны…» в меню «Файл» показывает подтверждение со списком экспериментов или каталогов без читаемого манифеста, размером каждого и общим итогом. Подтверждение удаляет перечисленные каталоги. Если устаревших прогонов нет, пункт недоступен с пояснением. Отмена диалога сохраняет файлы.

Перед удалением окно подтверждения перечисляет все удаляемые файлы и предупреждает, что Undo не восстановит их. Несохранённые изменения требуют того же подтверждения, что и смена модели. После подтверждения состав файлов модели проверяется заново; изменение списка требует нового подтверждения. Документы удаляются по одному через `DELETE /workspace/document?path=…` с прочитанной версией в `If-Match`: сначала эксперименты, затем раскладки, затем модель. Перед удалением каждой раскладки и модели проверяются оставшиеся ссылки на неё. При конфликте, появлении такой ссылки или другой ошибке операция останавливается; сообщение перечисляет уже удалённые и оставшиеся файлы по перечитанному списку документов. Если перечитать список не удалось, сообщение отдельно называет подтверждённые удаления и файлы, состояние которых нужно проверить. После полного или частичного удаления обновляются списки и открытые документы. После удаления модели открывается последняя открытая модель из оставшихся, иначе первая по имени файла. Если моделей больше нет, пустой холст предлагает создать модель через «Файл → Новая модель». Удалённые документы не входят в историю Undo.

Записи выполняются по одной, эксперимент записывается после модели и раскладки. Это не транзакция: при сбое последующей записи уже сохранённые документы остаются на сервере, а сообщение перечисляет их. После операции перечитывается список моделей и экспериментов. Смена модели или эксперимента при несохранённых правках требует подтверждения; «Сохранить модель как» переносит эти правки в копию. Создание модели, эксперимента и копирование допускают незавершённую схему: формат проверяет PUT, готовность к запуску проверяется в редакторе. Для импорта проверка через POST /validate обязательна до первой записи.

«Экспорт» скачивает документы открытого эксперимента отдельными JSON-файлами через `Blob`. Текст поступает из `GET /workspace/document/text?path=…`: сервер формирует его каноническим кодеком и отдаёт как `text/plain;charset=UTF-8` с версией исходного документа в `ETag`. Браузер не пересериализует JSON. Отсутствующая необязательная раскладка не экспортируется. При несохранённых правках предлагается сначала сохранить; отмена или ошибка сохранения прерывают экспорт. Внешнее изменение требует перечитывания перед экспортом.

Рабочая область находится на сервере. В Docker Compose по умолчанию это каталог `examples/` хоста, смонтированный в `/workspace`. Импорт переносит документы с компьютера пользователя на сервер, экспорт скачивает копии обратно; результаты прогонов и состояние браузера в эти файлы не входят.

### 6.3. Результаты

При открытии эксперимента, в том числе после перезагрузки страницы и повторного открытия модели, Web загружает его последний завершённый прогон через `GET /runs/latest?experiment=…`. Этот запрос ограничен каталогом выбранного эксперимента: завершённость кандидатов определяется меткой успешной публикации или наличием сводки, порядок — временем изменения манифеста. При выборе JSON читается только у выбранных кандидатов; содержимое сводок и рядов не читается. Принадлежность определяется полным путём `experiment`. Последним считается прогон с наибольшим `completedAt`: временем публикации завершённого `manifest.json` в миллисекундах Unix. Досчёт старого прогона обновляет это время. При равенстве времени выбирается лексикографически больший `id`, затем меньший `directory`. Порядок создания прогонов не определяет порядок завершения.

Сводка заполняется в панели результатов; на странице варианта доступны показатели схемы. Восстановление сохраняет раскрытое или свёрнутое состояние панели и не сворачивает параметры инспектора. Автоматическое раскрытие панели и приоритет результатов в инспекторе относятся к явному запуску. Исходные модель и эксперимент восстанавливаются из канонических JSON-снимков `manifest.snapshots`, покрытых хешами `manifest.documents`. Текущие документы остаются в редакторе. Если они отличаются от снимков, включая несохранённые правки, результаты получают существующую пометку о предыдущей версии документов. При отсутствии завершённых прогонов сохраняется приглашение запустить эксперимент. Последний незавершённый прогон в порядке каталога предлагается продолжить и после перезапуска сервера, когда его задания уже нет в памяти; прежние завершённые результаты при этом остаются доступны. Если `GET /jobs` возвращает уже выполняющееся задание этого прогона, Web продолжает его отслеживание вместо повторной отправки Resume. Ошибка чтения одного артефакта не скрывает успешно загруженные результаты или возможность продолжить другой прогон.

Кнопка «?» в заголовке инспектора блока или связи открывает диалог справки по типу, в том числе в компоновке «Анализ». Команды редактора не действуют внутри диалога. Он показывает описание, таблицу параметров с единицами, значениями по умолчанию и пределами, допущения и выходные метрики с объяснениями. Вложенные поля объектов и массивов идут с отступом. Источник — локализованный каталог API (`localizeCatalog`) и каталоги сообщений `en` и `ru`; отдельных страниц документации нет. Начальные значения редактора не подменяют значения по умолчанию. Для неизвестного типа справка сообщает, что описание недоступно.

Пояснения параметров инспектора находятся за значком «?» рядом с подписью поля. Строки описания под полями убраны. Общий компонент подсказки открывает окно при наведении, щелчке или нажатии Enter/Space на значке. Сам переход фокуса по Tab его не открывает; переход к соседнему полю закрывает открытое окно. Escape и щелчок вне окна также закрывают подсказку. Escape сначала закрывает подсказку внутри оценки, оставляя саму оценку открытой. Значок имеет доступное имя «Подробнее: <название поля>», текст связан с полем для экранных читалок. Окно находится в верхнем слое браузера и ограничено размером окна, поэтому прокрутка инспектора или оценки его не обрезает.

В инспекторе связи балансировка видна только при вызове группы из нескольких реплик; вариант «По умолчанию» называет действующий выбор по очереди. Пауза перед повтором видна при числе попыток больше одного. Скрытие полей сохраняет записанные значения. Подсказки распределений объясняют выбор, подсказки измерения и повторений предлагают начальные значения и условия их увеличения. Для сервиса и БД одинаковые параметры называются одинаково: «Ёмкость очереди» и «Вероятность ошибки». Узел БД, его показатели и сообщения называют соединения и очередь запросов. Структурированные сообщения ядра передают тип элемента для выбора этих терминов.

Верхняя панель переносит команды на следующую строку, чтобы на 1280×800 название приложения, статус несохранённых правок и кнопки оставались видны целиком. Выбор эксперимента показывает имя без `.experiment.json`; полный путь остаётся в подсказке. Подпись связи ставит знак умножения перед числом попыток: «× 3». Подтверждения используют диалог приложения с действиями на кнопках, например «Отменить правки» и «Остаться». Фокус сначала стоит на отмене действия; Escape сохраняет правки.

Названия вариантов берутся из документов выполненного прогона или его сводки. При отсутствии названия показывается «Базовый» или «Вариант N»; явно введённое название сохраняется дословно. Точка перебора показывается значениями осей, параметр — названием из каталога вместе с элементом. Это правило действует в Выводах, на Карте и Таймлайне, в контексте результатов и Проблемах. Текст диагностики стоит первым, технический код — отдельной строкой. «Добавить значение» для одного непрерывного значения предлагает увеличение на 50 % с учётом верхнего предела, например `300ms` становится `450ms`; для целого числа первый шаг равен единице. Дальше продолжается заданный шаг оси и выбирается ещё не использованное допустимое значение с учётом единиц и пределов; если такого значения не найдено, кнопка недоступна. Параметры отсутствующего пула связи в списке оси не предлагаются. При выборе экспоненциальной паузы редактор берёт начальные значения из каталога: база `10ms`, максимум `100ms`. Умолчания для отсутствующих в документе полей сохраняются.

Каждое из восьми полей оценки стоимости объяснено такой же подсказкой: число задач и потоков, ожидаемые события и строки, время расчёта, объём до сжатия и на диске, число частей. У счётчика активного задания подсказка показывает, сколько задач завершено, и объясняет: задача — один прогон для сочетания варианта, точки сетки и повторения. Общее число известно с момента принятия задания, а при продолжении счётчик включает ранее завершённые пригодные задачи.


В меню «Вид» выбираются шаг сетки 10, 20 или 40 единиц, привязка к сетке и её видимость. По умолчанию шаг равен 20, привязка и показ сетки включены. Шаг применяется к фону холста, перемещению блоков, добавлению из палитры и вставке из буфера; уже размещённые блоки остаются на своих местах. При выключенной привязке координаты не округляются.

Выбор значения в любом списке или переключение флажка меню «Вид» сразу применяет настройку и оставляет меню открытым. Меню закрывается по Escape, щелчку вне него или повторному нажатию кнопки «Вид»; фокус возвращается на эту кнопку. Escape при открытом меню не меняет компоновку рабочей области.

Размер текста интерфейса в том же меню принимает значения 90, 100, 110 или 125 %; по умолчанию 100 %. Настройка меняет корневой размер шрифта. Размеры узлов и подписей схемы заданы в единицах холста и меняются его собственным масштабом. Настройки хранятся в `localStorage`, вне документов и истории undo/redo, и восстанавливаются при загрузке страницы. Если хранилище недоступно, выбранные настройки действуют до перезагрузки. Все подписи доступны на английском и русском языках.

Плотность панелей подчиняется приоритету холста (§4.7 концепции интерфейса). Общие CSS-переменные в `rem` задают основной текст 13 px, подписи и вторичный текст 12 px, полужирные заголовки секций 13–14 px. Поля, списки и кнопки инспектора имеют высоту 26 px; подписи параметров прогона и отказов стоят рядом с полем. Параметры элемента, параметры прогона, отказы и сетка сворачиваются независимо, их ручное состояние хранится в браузере вне документов и undo/redo. Скрытые поля сохраняют черновики; переход из Problems раскрывает нужную секцию до фокусировки поля. Кнопки масштаба и миникарта находятся поверх холста в нижнем правом углу, отдельной полосы под схемой нет.

Timeline, секция «Результаты» инспектора и выбор метрик наложения строятся из `TypeDescriptor.outputs`. Каталог задаёт наборы, порядок, подписи и единицы; web выполняет закрытые операции над существующими полями артефакта. Переводы выходов находятся по ключам `catalog.types.<typeId>.outputs.<id>.*`. Отсутствующий источник даёт `n/a`; доверительные интервалы пересчитываются только по `mean` и `stdDev` указанного `MetricSummary` и не обрезаются. Состав нынешних представлений сохраняется; Findings, Map и правило насыщения по-прежнему имеют собственную логику.

Для группы реплик узла или скопированной связи Timeline показывает сводную линию и полосу min–max загрузки или средней очереди по репликам из записанных экстремумов окна. В выборе показателей можно добавить отдельные реплики: они используют показатели группы, а их части рядов загружаются только после выбора. Выбор реплики из инспектора открывает её линию вместе с группой. Сравнение вариантов, воспроизведение и общий курсор используют выбранные точку и повторение; выбор рядов не меняет документы и Undo.

Вкладки панели: Findings (вывод и сравнение вариантов с доверительными интервалами), Timeline (графики по выбранным узлам, связям и метрикам), Assumptions (допущения модели из каталога и условия прогона из манифеста), Problems (диагностика), Map (только при наличии сетки: линия для одной оси, тепловая карта для двух; ячейка открывает свои ряды и вывод).

Панель результатов можно свернуть или изменить её высоту разделителем. При открытии эксперимента без законченного или незаконченного прогона в текущей сессии она свёрнута. Щелчок по любой вкладке свёрнутой панели выбирает её и раскрывает панель до сохранённой для этой вкладки высоты. Повторный щелчок по активной вкладке оставляет панель раскрытой; сворачивает её только кнопка `Collapse results`. Кнопка `Restore results` возвращает сохранённую высоту; кнопки развёртывания нет, для разбора служит компоновка `Analysis` (§6.1). Ручной выбор свёрнутости сохраняется до смены эксперимента, включая завершение прогона; щелчок по вкладке, Run, Estimate, Resume, счётчик Problems и новая ошибка раскрывают панель. Высота запоминается в браузере отдельно для Findings, Timeline, Assumptions, Map и Problems в каждой из двух компоновок, вне документов и undo/redo. В обычной компоновке начальная высота Timeline составляет 55 % доступной высоты, остальных вкладок — 32 %; в `Analysis` — 62 %. Размер ограничивается минимумами областей, а сохранённая высота восстанавливается при увеличении окна. Если хранилище браузера недоступно, изменение высоты работает до закрытия страницы.

После успешного прогона открывается первая вкладка Findings. Если пользователь переключал вкладку панели после нажатия Run, в том числе во время оценки перед запуском, его выбор сохраняется. Run, Estimate и Resume раскрывают свёрнутую панель до сохранённой высоты текущей вкладки и не выключают `Analysis`; оценка показывается у кнопки Run.

Над выводом в Findings стоит одна строка условий: постоянная интенсивность клиента или её диапазон за время прогона и все отказы с интервалами. Условия берутся из документов выполненного прогона с переопределениями выбранных варианта и точки. На странице модели они соответствуют первому варианту, чей вывод показан ниже. Длинная строка обрезается многоточием, полный текст доступен в подсказке.

Вверху Findings показаны две фразы сравнения в выбранной точке: наибольшая наблюдаемая средняя доля успешных запросов и наименьший наблюдаемый средний p99. Для каждой названы варианты и значение. При единственном варианте показаны только «Доля успешных запросов: …» и «p99: …», без сравнения. Если интервалы лидера пересекаются с интервалами всех остальных вариантов, фраза начинается с «Явного лучшего нет — разница в пределах разброса», а наблюдаемый лидер и значение указаны в скобках; при нескольких равных лидерах это проверяется для каждого. При равенстве средних перечисляются все лидеры; остальные варианты сравниваются со всеми лидерами. Интервалы считаются непересекающимися только при непересечении с каждым лидером, поэтому перестановка вариантов не меняет вывод. Сравниваются интервалы выбранного уровня из `MetricSummary`, с числом наблюдений каждой метрики: строго непересекающиеся интервалы названы отдельно, пересекающиеся или соприкасающиеся получают пометку «разница в пределах разброса». Если данных для интервала нет, сравнение отмечено как недоступное; это не считается пересечением. При отсутствии метрики победитель не выбирается. Это описательное сравнение, не проверка статистической значимости и не общий рейтинг: лучший вариант по доле успешных и по p99 может различаться.

Следом показаны первые насытившиеся ресурсы по вариантам. Одинаковые наборы пар «узел, набор слотов» объединяются в одну фразу с названиями вариантов; если вывод общий для всех вариантов в этой точке, он начинается словами «Все варианты». Различающиеся наборы показаны отдельно. Подробный вывод ниже относится к варианту активной страницы: первый насытившийся ресурс, число повторений, медианное начало и диапазон, повторения без насыщения, пути деградации и правило. На странице модели показывается первый вариант по документу. При переборе и заголовок общей сводки, и заголовок подробного вывода явно называют координаты выбранной точки; без сетки подробный заголовок содержит только название варианта. Отсутствующая точка одного варианта не подменяется другой.

Одинаковые пути деградации объединяются по упорядоченному списку пар «узел, набор слотов». Для каждого пути показано число повторений, для каждого шага — время начала или его диапазон по повторениям этой группы; все повторения без насыщения образуют одну строку. Группы упорядочены по убыванию числа повторений, при равенстве сохраняют порядок первого появления. В раскрытом блоке «Пути деградации» видны три наиболее частых пути, остальные доступны под «Ещё N путей»; N — число оставшихся разных путей, не повторений.

Ниже варианты сравниваются в колонках, метрики — в строках. Первой идёт колонка варианта с ID `baseline`, а при его отсутствии — первого варианта по документу; остальные сохраняют порядок документа. Выделяется колонка активного варианта. Метрики сервисов раскрываются группами; таблица переносит текст и помещается по ширине экрана 1440 px для retry-storm.

У p95 и p99, совпадающих с таймаутом связи или дедлайном клиента, появляется пометка «совпадает с таймаутом N» или «совпадает с дедлайном N» с именем источника. Пределы берутся из модели выполненного прогона, затем применяются переопределения варианта и координаты точки. Совпадение проверяется для среднего, минимума и максимума квантиля по повторениям с относительным допуском 0,78125 % — погрешностью представления `ddsketch-bitwise6-rational-v1`. Поэтому значение около 5,03 с может быть помечено как соответствующее таймауту 5 с. Подсказка объясняет погрешность и то, что совпадение само по себе не доказывает срабатывание таймаута или дедлайна. Видимая подпись тоже сообщает о численном совпадении: таймаут внутреннего вызова не обязательно ограничивает суммарную задержку клиента. Значения и интервалы артефакта не изменяются; без документов или данных квантиля пометки нет.

Рядом с выводом называются отказы из документов выполненного прогона, в чей полуоткрытый интервал `[from, to)` попадает медианное начало первого насыщения. Подпись включает цель, вид, параметры и интервал отказа. Начало после `to` связывается с отказом только до `to + windowMs`, где `windowMs` взят из манифеста; подпись явно говорит «сразу после отказа» и ограничивает связь одним окном рядов. Более позднее или предшествующее начало не связывается с отказом. Это сопоставление во времени, а не доказательство причинности; ядро и записанное правило насыщения не пересчитываются.

Правило объясняется двумя фразами в блоке `How saturation is detected`, который по умолчанию свёрнут. Порог загрузки, порог средней очереди, число отказов в окне и минимальная длительность берутся из всех четырёх полей `saturation.rule`. Текст сохраняет различие между непрерывной длительностью насыщения очереди и интервалом от начала первого до начала последнего окна с отказами. Дополнительные записанные параметры доступны в том же блоке.

Если в выбранной точке все повторения прошли без насыщения, под выводом показана строка `Capacity headroom`: наибольшая pooled-загрузка и соответствующий ресурс, наибольшая средняя очередь и соответствующий ресурс, pooled p99 задержки на входе. Ресурсы и оба независимых максимума берутся из `headroom` сводки. Очередь указывается как среднее число запросов: сводка не содержит её ёмкости. Пометка «по объединённым данным» относится ко всей фразе и появляется один раз. p99 берётся из `aggregate.pooledLatency.all.p99Ms`, без усреднения p99 повторений. Подпись таблицы объясняет, что её p95 и p99 — средние квантилей отдельных повторений, поэтому они могут отличаться от квантилей объединённых ответов. При нулевом знаменателе или отсутствии метрики показывается `n/a`. Если хотя бы одно повторение насытилось, строка отсутствует; при отсутствии повторений запас также не выводится. Все значения берутся из сводки без загрузки рядов. Пользовательские сообщения собираются из целых фраз каталогов `en` и `ru` с именованными аргументами; формулировка первого насыщения подходит и одному пулу, и нескольким обработчикам.

Длительности, поступившие в миллисекундах и не меньшие секунды по модулю, показываются в секундах с точностью до двух знаков без незначащих нулей; короткие величины остаются в миллисекундах. Исходные числа артефакта не меняются. Горизонтальные оси Timeline используют секунды при длительности прогона от одной секунды; оси задержек также переходят на секунды, если хотя бы одно значение или порог достигает секунды. Единица явно указана у оси. Координаты графиков и вычисление курсора остаются в миллисекундах.

В модели с несколькими клиентами или видами запросов под метриками входа раскрываются группы «По клиентам» и «По видам запросов». Каждая группа появляется только при числе соответствующих объектов больше одного и изначально свёрнута. Значения берутся из `entries.clients` и `entries.classes`; интервалы и отличия от baseline показываются по тем же правилам, что у входа в целом. Фразы сравнения вариантов остаются по `entries.total`.

У входа, клиентов и видов запросов строка «Причины отказа» показывает до трёх причин по убыванию средней доли, при равенстве — по коду; раскрытие содержит все причины, встретившиеся хотя бы в одном варианте выбранной точки. Отсутствующая причина у существующей строки означает ноль, строка без отказов подписана «нет отказов». Доли берутся из `failuresByReason`, их знаменатель — исходные запросы соответствующей строки. Названия локализованы, код доступен в подсказке. «Успешные с заглушкой» (`degradedRate`) появляется у всех строк, если заглушка задана хотя бы в одном варианте или сохранённая доля ненулевая. У одного клиента без видов запросов и политик прежние строки Выводов сохраняются.

Для метрик входа в Map при нескольких клиентах или видах запросов доступен список «Вход»: «Всего», клиент или вид запроса; исходный выбор — «Всего». Выбор меняет метрику ячеек, сохраняя общие вариант и точку. Сервисные метрики от выбора входа не зависят. Отсутствующее значение популяции остаётся недоступным.

Инспектор клиента показывает долю успешных, p95, p99, причины отказа и долю успешных с заглушкой непосредственно из `entries.clients`; ниже — его явно заданные виды запросов из `entries.classes`. Показатели подписаны как итоги по повторениям и сохраняют этот смысл при движении курсора времени. Если вид отправляют несколько клиентов, подпись поясняет, что его результат общий для этих клиентов. Текущие правки модели не подменяют документы прогона при определении видов запросов.

У небазовых вариантов рядом со средним показана разность относительно базового в единицах метрики; разности долей выводятся в процентных пунктах. Пометка «Intervals do not overlap» появляется только при строго непересекающихся CI выбранного уровня с обеими границами у обоих вариантов. Для каждой метрики используется её `count` из `MetricSummary`: число повторений, по которым рассчитаны среднее и стандартное отклонение. Повторения без определённого значения метрики в это число не входят. Интервал выбранного уровня считается по `count`, а при 95 % совпадает с `ci95Low`/`ci95High` сводки; при `count < 2` интервала нет. Касание границ считается пересечением; пометка не утверждает статистическую значимость. Для pooled-загрузки busy/capacity интервал не вычисляется. При `count` метрики меньше 5 (константа web) доступные интервалы показываются приглушённо, без обрезания, с пометкой об их ненадёжности и советом увеличить `Replications`.

Выбор точки сетки сохраняется; сравнение показывает эту точку у всех вариантов, у которых она есть. Если у базового варианта точки нет, это явно указано, разности недоступны и другой вариант не становится базовым. Если документы, включая несохранённые правки, отличаются от тех, с которыми запущен прогон, Findings, Assumptions и схема помечают результаты как устаревшие. После отмены панель сообщает о незаконченном прогоне без сводки. Точка сетки, повторение и закреплённое окно хранятся в общем состоянии результатов вне документов и undo/redo.

Над схемой страницы варианта после законченного прогона показана одна компактная строка контекста результатов: название варианта активной страницы (выбирается вкладкой), выбор точки при наличии сетки, повторение с нуля, переключатель `Summary | Time`, управление временем и выбор наложения. Только эта строка содержит селекторы точки и повторения; Findings и Timeline используют общее состояние. Селектор повторения доступен и в Summary: он меняет ряды Timeline, а схема продолжает показывать сводные итоги выбранной точки. В Time выбор повторения меняет и ряды, и схему. Map меняет точку щелчком по ячейке. Сравнение `Compare variant` остаётся в Timeline и относится только к графикам. На странице модели и до законченного прогона строки нет; Findings на странице модели сохраняет выбранную точку. В конце строки находится кнопка компоновки `Analysis`.

Timeline строит на Recharts группы графиков — интенсивности, задержки, ошибки и отказы, загрузка, очередь — по выбранным узлам и метрикам; выделение элемента на холсте выбирает его ряды. Ctrl/Cmd+щелчок добавляет к выбору узлы и связи `call`. Для связи показываются собственные отправленные попытки, повторы, ответы и таймауты в секунду, средние попытки в полёте, orphaned work и backoff, средняя длительность вызова и её квантили. Метрики пула связи предлагаются, только если пул есть у активного или сравниваемого варианта в выбранной точке. Линия метрики пула строится только для варианта с пулом. Линия timeout использует параметры документов прогона с переопределениями варианта и точки. Легенда связи содержит её имя и метрику; при сравнении добавляется вариант. Длительности описывают только полученные ответы, без попыток, оборванных по timeout. Второй вариант накладывается на те же графики, повторение выбирается с нуля. Наведение показывает исходные значения окна на всех графиках, щелчок закрепляет окно курсора. Прореживание сохраняет экстремумы и границы разрывов. Разогрев берётся из манифеста, интервалы отказов — из эксперимента, с которым запущен прогон.

Результаты на схеме появляются на странице варианта после законченного прогона: у сервиса — загрузка, средняя очередь и доля отказов очереди из pooled-итогов выбранной точки, у связи — amplification вызываемого сервиса как среднее по повторениям из Findings, значок — узел `saturation.firstNodes[0]` с числом повторений. В строке контекста выбирается метрика цвета узлов: загрузка, средняя очередь или доля отказов очереди; `Off` снимает всё наложение. Легенда долей имеет шкалу 0–100 %. Для средней очереди цвет показывает заполнение `meanQueue / queueCapacity`, легенда — `Queue fill: 0–100 %`; числовая подпись узла сохраняет среднюю длину очереди. Ёмкость берётся из документов прогона с переопределениями варианта и выбранной точки сетки, поэтому правки текущего документа не меняют шкалу старых результатов. Неуказанная ёмкость равна 0 по каталогу: ожидание отключено, цвет заполнения для такого узла отсутствует. Метрика подписей связей выбирается отдельно: amplification, отправленные попытки в секунду, доля таймаутов или средняя orphaned work. Значения связей берутся из `aggregate.connections` и их собственных окон; amplification по-прежнему относится к admitted amplification вызываемого сервиса. Связь `request` собственных рядов не имеет. На странице модели наложения нет; новые элементы не получают значений из прежнего прогона.

На странице варианта после завершённого прогона инспектор выбранного элемента показывает секцию `Results` перед параметрами, если у элемента есть результаты в текущем контексте. Под ней находится группа `Parameters`, по умолчанию свёрнутая. На странице модели, до завершённого прогона и для элемента без результатов параметры по умолчанию открыты, порядок секций прежний. Сохранённый ручной выбор заменяет начальное состояние; параметры прогона, отказы и сетка изначально открыты. Переход из Problems раскрывает группу и фокусирует поле; `Use model value` возвращает фокус полю, двойной щелчок по параметру на схеме раскрывает группу и сохраняет фокус редактора на схеме. При выборе другого элемента инспектор прокручивается к началу. Секция `Results` использует общие вариант, точку, повторение и курсор. У сервиса видны загрузка, средняя очередь и её заполнение, доля отказов очереди, принятые попытки в секунду и средняя задержка. У связи `call` — отправленные попытки и повторы в секунду, доля таймаутов, число orphaned-попыток и средняя orphaned work, средние попытки в полёте и backoff, длительность вызова рядом с timeout и admitted amplification вызываемого.

В `Summary` сервисные показатели, интенсивности, длительности и средние по времени величины связи из итогов подписаны как pooled. Число orphaned-попыток показывается средним на повторение: сумма `totals.orphaned` делится на число повторений варианта, подпись — `per replication`, без вычисления доверительного интервала. В `Time` остаётся число событий выбранного окна. Доля таймаутов, средние попытки в полёте и amplification используют среднее повторений и CI выбранного уровня, если доступны данные для расчёта (§6.1); при числе повторений меньше 5 показывается то же предупреждение, что в Findings. Интервалы не обрезаются и не создаются для pooled-величин. Средняя задержка сервиса вычисляется для выбранного повторения как сумма `sumMs`, делённая на сумму `count`, по окнам измеряемого интервала и имеет отдельную подпись источника. Если окно пересекает начало измерения, его образцы нельзя разделить по границе разогрева: берутся полные измерительные окна, а рядом явно указан фактически покрытый интервал. В `Time` показаны значения выбранного окна; amplification помечен как приближение. На странице модели секции нет, отсутствующий или заменённый элемент не получает чужих значений.

Мини-графики показывают выбранное повторение: у сервиса загрузку и очередь, у связи отправленные попытки и таймауты в секунду, среднюю длительность вызова с линией timeout. На них отмечены разогрев, интервалы отказов и общий курсор. Они используют тот же ограниченный кэш декодированных частей, что Timeline и воспроизведение; одновременные обращения к одной части разделяют загрузку. `Show on Timeline` открывает Timeline с рядами выбранного элемента, допущения его типа доступны в раскрываемом блоке.

Результаты политик берутся из существующих выходов каталога с привязкой `inspector`. Выход виден, если соответствующая политика задана у элемента хотя бы в одном рассчитанном варианте или точке; для реплики учитывается её переопределение. У клиента с заглушкой выбранное окно дополнительно показывает `degradedPerSecond` по времени завершения, сохраняя итоговую долю успешных с заглушкой из сводки. В таблице реплик при соответствующих политиках появляются сортируемые столбцы доли времени вывода, доли времени неготовности и доли попыток, отклонённых ограничением интенсивности.

На Timeline рядом с клиентами доступны объявленные виды запросов. Их интенсивности исходных, успешных и неуспешных запросов, успешные с заглушкой и задержки вычисляются по выходам клиента из строк `classes`. Исходные запросы относятся ко времени прибытия, исходы и задержки — ко времени завершения. Под графиком интенсивностей полосы состояния показывают «breaker открыт» у связи, «выведен» и «не готов» у экземпляра. Насыщенность цвета соответствует доле длительности окна; время размыкания групповой связи делится также на число её копий у реплик вызывающего в выбранном варианте. Подсказка называет долю и число копий, выбор окна меняет общий курсор. Политики и виды запросов не добавляют элементов интерфейса моделям, где они не заданы.

В режиме `Time` строка контекста содержит запуск, паузу, скорости 0,25–4× при базовом темпе 10 окон в секунду независимо от длительности окна, ползунок, шаги по одному окну и время окна. Проигрыватель делит курсор с Timeline: выбор окна на графике также включает `Time`. Переключение в `Summary` снимает курсор одновременно у схемы и Timeline; Esc на холсте в обычной компоновке делает то же, кроме полей ввода. В `Analysis` Esc сначала возвращает обычную компоновку, сохраняя курсор. Отдельных кнопок `Return to summary` и `Clear time cursor` нет. С курсором схема показывает метрики окна выбранного повторения; amplification окна помечен как приближение. Ряды читаются диапазонами до 32 окон, уменьшенными по оценке 512 байт на узел и окно до целевого объёма 4 МиБ (не меньше одного окна); декодированные части Timeline и проигрыватель берут из общего LRU-кэша 64 МиБ. Пока ряды выбранного окна загружаются, часы ждут. Ручная перемотка, смена варианта, точки, повторения или скрытие наложения останавливают воспроизведение.

Map использует сетку и метрики сводки для варианта активной страницы. Порядок осей и значений, включая повторы, сохраняется: первая ось тепловой карты идёт по строкам, вторая по столбцам. Метрики — success rate, p95, p99, admitted amplification и pooled-загрузка выбранного сервиса. Линия показывает CI выбранного уровня по `count` метрики без обрезания; у pooled-загрузки busy/capacity такого интервала нет. Значение ячейки видно числом, у цветов есть шкала. Щелчок выбирает точку общего контекста результатов.

На графике задержек маркер отмечает значение исходного непустого окна. Пустые окна остаются разрывами без среднего и квантилей; пояснение рядом с графиком указывает, что значения в таких окнах отсутствуют.

Цвет узла и подпись связи соответствуют выбранным метрикам, значок отмечает первый насытившийся узел. Строка метрики на узле всегда занимает одну строку: короткая подпись из `OutputOverlay.label` и значение показываются целиком без переноса и обрезания. Общий компонент `HelpHint` за значком «?» показывает полное `overlay.title` и `overlay.description`. Название в списке «Показатели узлов» остаётся полным. У группы реплик хвост о худшей реплике сокращён до «макс. #2: 100 %», а в подсказке сохраняется полная формулировка. Политика маршрутизатора также имеет короткое значение на узле и полное название в подсказке; редактор выбора и инспектор сохраняют полные названия. На странице варианта зачёркнутое базовое значение политики расположено под текущим. Размеры узлов по типам сохраняются до и после прогона. Значки диагностик располагаются над содержимым узла и не занимают отдельной строки. У связи широкая невидимая зона выбора вдоль линии и доступная с клавиатуры подпись-плашка; выбранная связь подсвечивается вместе с концами. Кадр вычисляется только из рядов, поэтому пауза и перемотка детерминированы. В режиме времени размеры узлов и положение подписей связей сохраняются при загрузке и перемотке. Пока выбранное окно загружается, видны значения последнего загруженного окна приглушённо, с пометкой о загрузке в подсказке. До первого загруженного окна место строк метрик остаётся пустым. Ошибка загрузки сохраняет эти места и последние значения, а её текст появляется в подсказке и проигрывателе; курсор ждёт готового кадра. Смена прогона, варианта, точки или повторения очищает сохранённый кадр. Сводка не подставляется вместо окна. С началом каждого участка заранее подготавливается следующий: узлы и связи запрашиваются одновременно, рассчитанные показатели сохраняются до перехода курсора. В памяти остаются показатели только текущего и следующего участков; предыдущий удаляется при переходе. Готовность следующего участка не перерисовывает текущий кадр, а переход на готовый участок не останавливает часы. Если участок ещё не готов, часы ждут загрузки. После ошибки предзагрузки запрос повторяется, когда участок становится текущим. Предзагрузка использует существующий SeriesLoader и общий LRU-кэш рядов с прежним лимитом 64 MiB; формат запросов не меняется. Без курсора схема показывает итог измеряемого интервала из сводки — те же числа, что в Findings. Сначала грузится сводка, ряды — по выбору варианта, ячейки и повторения; распаковка и разбор идут в Web Worker.

Демо — рабочая область `examples/` с коротким retry storm и моделью оформления заказа `checkout`. Примеры открываются через список «Модель», затем выбирается её эксперимент; отдельной команды «Открыть пример» нет.

При открытии модели сначала выбирается последний открытый для неё эксперимент, если он ещё существует и ссылается на эту модель. Без сохранённого выбора предпочтителен эксперимент рядом с моделью с тем же базовым именем: для `checkout/checkout.model.json` это `checkout/checkout.experiment.json`. Если такого файла нет, выбирается первый по пути среди экспериментов этой модели; если нет ни одного — создаётся несохранённый эксперимент по умолчанию.

Если у модели или эксперимента есть описание или заметки, в левом верхнем углу холста видна компактная кнопка «О модели» со значком информации. Она расположена поверх холста, под плашкой варианта, если та есть, и не уменьшает высоту области схемы. Кнопка открывает панель поверх холста с описаниями модели и эксперимента; если у документа есть только заметки, показаны они. Длинный текст прокручивается внутри панели. Панель закрывается кнопкой ×, клавишей Esc и щелчком вне неё. Кнопка «Полные заметки» закрывает панель, раскрывает «Описания и заметки» в инспекторе и переводит фокус в заметки модели; рядом доступны заметки эксперимента.

Панель «О модели» открывается только по щелчку на кнопку, автоматического открытия нет. Пока пользователь ни разу не открывал информацию этой модели, у кнопки видна синяя точка и подсказка «Описание модели ещё не открывали». После первого ручного открытия пометка исчезает. Признак прочтения хранится в `localStorage` отдельно для каждого пути модели и сохраняется после переключения экспериментов и перезагрузки страницы. Это предпочтение браузера: оно не меняет документы и историю Undo. Если хранилище недоступно, панель остаётся доступной, но запоминание между открытиями не гарантируется.

У checkout общие модель и раскладка: `checkout.experiment.json` сравнивает четыре варианта, а `checkout-grid.experiment.json` перебирает timeout × attempts у baseline для Map. Источники чисел, типичные допущения и расчёт бюджета таймаутов записаны в `notes` документов.

### 6.4. Язык и форматирование

Web поддерживает английский (`en`) и русский (`ru`). Без явного выбора используется первый поддерживаемый язык из `navigator.languages`, включая региональные варианты `ru-*` и `en-*`; если поддерживаемых языков нет, используется английский. Явный выбор в меню «Вид» справа в верхней панели хранится в `localStorage` и имеет приоритет над языком браузера. Если хранилище недоступно, выбор действует до перезагрузки страницы. При запуске загружается только каталог выбранного языка; первый рендер ждёт его загрузки. Другой каталог загружается при переключении, а до завершения загрузки интерфейс сохраняет прежний язык. Загруженные каталоги используются повторно. После успешной загрузки последний выбранный язык обновляет интерфейс и атрибут `lang` у `<html>`, сохраняя документы, артефакты, текущие правки и историю Undo. Если новый каталог загрузить не удалось, прежний язык сохраняется.

Пользовательские строки, включая подписи доступности и тексты контролов холста, берутся функцией `t(key, params)` из `web/src/i18n/en.json` и `ru.json`. Наборы ключей и имена подстановок совпадают; это проверяют unit-тесты. Ключи сгруппированы по областям (`app`, `editor`, `results`, `status`, `common`); параметры именованные. В dev-сборке и тестах неизвестный ключ или пропущенный параметр вызывает ошибку. В production функция не бросает исключение: для неизвестного статуса задания показывает исходное значение API, например `PAUSED`, для прочих неизвестных ключей и неполных параметров — ключ сообщения. [Глоссарий](../../../web/src/i18n/README.md#глоссарий) задаёт общие переводы терминов. Обозначения p50, p95, p99, RPS и CI сохраняются. Пользовательские данные, включая названия вариантов, идентификаторы, пути и содержимое документов, не переводятся.

Подписи, описания и допущения `/catalog` локализуются в копии исходного ответа при выборе языка: сначала ищется ключ `catalog.types.<typeId>`, для параметров — `catalog.types.<typeId>.params.<dottedPath>`, затем используется исходный текст API. Поля текста обозначаются суффиксами `.title` и `.description`, допущения — `.assumptions.<index>`. Общие допущения используют `catalog.assumptions.<index>`. Оба каталога сообщений содержат эти тексты; unit-тест проверяет покрытие всех типов, вложенных параметров и допущений полного снимка `/catalog`. Идентификаторы, значения и исходный ответ сохраняются.

Диагностика `Diagnostic`, ошибки запросов `ApiProblem` и предупреждения оценки `EstimateWarning` содержат стабильный `code` и необязательный `args`: словарь со строками и числами. У ошибки задания рядом с прежним `error` находятся необязательные `errorCode` и `errorArgs` того же формата. Числа передаются исходными значениями; единица задаётся текстом перевода. Произведение попыток больше `9007199254740991` передаётся строкой десятичных цифр: web форматирует её как `BigInt`, сохраняя точность за пределами безопасного целого JavaScript. `message` и `error` сохраняют прежний английский текст для CLI и старых клиентов.

Web переводит эти сообщения при отображении по ключу `messages.<CODE>`. Если у одного кода несколько причин, `args.reason` выбирает ключ `messages.<CODE>.<reason>`; остальные аргументы подставляются по имени, числа проходят общее форматирование. `args.points` сохраняет список точек сетки в локализованном суффиксе предупреждения линтера. Отсутствующее `args`, неизвестный код или причина, отсутствующий ключ либо обязательный аргумент возвращают исходный `message` или `error`, в том числе в dev-сборке и тестах. Подробности стороннего парсера или ввода-вывода в `detail` сохраняются в исходном виде. Это правило действует в списке Проблем, подсказках значков на схеме, сообщениях у полей, оценке и ошибках запросов и заданий.

Известная причина сбоя задания передаётся кодом и аргументами сообщения ядра, а также диагностикой. Интерфейс переводит её при показе и сохраняет вариант, точку и номер повторения. Это включает превышение лимита реального времени, незавершённую работу, выход времени за числовой диапазон и превышение размера части рядов. Непредвиденное исключение возвращает общий `EXPERIMENT_EXECUTION_FAILED`; подробности записываются только в журнал сервера.

Контракты сообщений заданы в `CoreMessage` и `ServerMessage`, которые используют места выдачи сообщений. Проверки собирают список кодов, причин и параметров из этих исходников и сверяют его со всеми языковыми каталогами web; отдельный ручной список кодов не поддерживается.

Отображаемые числа форматирует `web/src/i18n/format.ts` через `Intl.NumberFormat` с текущим языком. Максимальная точность: числа, RPS и множители — два знака, проценты и миллисекунды — один, секунды и размеры — два; лишние нули не выводятся. В русском интерфейсе используются десятичная запятая и локализованные единицы: `65,7 %`, `80 мс`, `800 КиБ`. Размеры используют KiB/КиБ до 1 MiB и MiB/МиБ начиная с этой границы. Отсутствующие значения показываются как `n/a` или его перевод; доверительные границы не обрезаются. Синтаксис величин в документах и редактируемые значения (`600ms`, `10s`) не меняются. Unit-тест на TypeScript AST запрещает пользовательские литералы в JSX.

## 7. Порядок работ

### 7.1. Сквозной срез

Срез заменяет MVP целиком; старый код и API удаляются.

- **Ядро:** каталог и документы; компилятор с проверкой цепочки и переопределениями вариантов; IR; адаптер KSL с потоками по путям блоков (ADR 0006) и проверкой плана адресов; задачи и пул без отмены и досчёта; артефакт с манифестом и сводкой без рядов.
- **Сервер и CLI:** файловая рабочая область без отслеживания изменений; ручки каталога, документов, `validate`, `jobs`, сводки прогона; генерация OpenAPI и TS-типов; CLI `validate` и `run`.
- **Web:** каркас, холст, инспектор из каталога с сохранением, правка модели на странице модели, страницы вариантов только для просмотра, запуск задания, вкладка Summary.
- **Примеры:** `examples/retry-storm/` в новом формате.
- **E2E:** открыть пример → изменить параметр → сохранить → запустить → увидеть сводку по вариантам.
- **Удаление MVP:** после перехода web — ручки MVP, пакет `scenario`, `ExperimentRunner`, `SweepExpander`, `SeedFactory` и адаптер старых сценариев; смысловые тесты MVP переносятся на IR, пакет `simulation` становится `engine.ksl`. Раньше удалить нельзя: ручки MVP нужны нынешнему web и обязательной проверке `e2e`.

Срез выполняется четырьмя планами: ядро, сервер и CLI, web, удаление MVP. Ядро добавляет фундамент рядом со старым кодом, сервер открывает новое API рядом с ручками MVP.

Пока идут дорожки, часть возможностей MVP — серии на графике, импорт и экспорт — недоступна.

## 8. Тестирование

- **Ядро:** разбор величин с единицами; эталонные файлы детерминированной записи; отсутствие диффа при повторной генерации схем; диагностика компилятора с местом в документе; перенесённые смысловые тесты MVP (M/M/1, повторы, orphaned work, когорта); одинаковый результат при разном числе потоков и перестановке блоков; правило вывода на синтетических рядах; полнота артефакта и досчёт.
- **Сервер:** тесты API, включая конфликт `If-Match` и отсутствие диффа OpenAPI.
- **Web:** unit-тесты команд, undo, переопределений и единиц; E2E по критериям готовности в реальном Chromium с настоящим backend, без mock API.
- JaCoCo формирует отчёты покрытия для CI; порогов в сборке нет: прежние были выбраны наугад, покрытие оценивается по отчётам.
