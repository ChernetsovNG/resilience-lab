# Этап 1 — дизайн

Дата: 2026-10-27  
Статус: согласовано  
Задача: [#5](https://github.com/ChernetsovNG/resilience-lab/issues/5)  
Связано: [продуктовое видение](../../product/2026-10-27-product-vision.md), §5.5 и §7; [целевая архитектура](../../architecture/2026-10-27-target-architecture.md) и ADR 0001–0010; [проектный дизайн MVP](2026-10-25-resilience-lab-design.md) — источник модельной семантики.

Этот документ — зонтичный дизайн этапа 1: границы, контракты между подсистемами и порядок работ. Детали реализации каждой части уточняются в планах реализации и задачах.

## 1. Цель и границы

Цель — закрыть вопрос «какие timeout и число попыток выбрать на цепочке с деградацией» уже на новой архитектуре. Основной сценарий — моделирование при заданных значениях: прогон и сравнение вариантов с таймлайном, воспроизведением на схеме и выводом. Карта по сетке параметров — дополнительный режим.

Модельная семантика MVP не меняется: блокирующие обработчики, ограниченная FIFO-очередь, timeout, retry, backoff, jitter, общий deadline, orphaned work, когорта измерения (проектный дизайн, §8–9). Меняется представление. Исключение — назначение потоков случайных чисел по путям блоков (ADR 0006): при том же seed числа будут другими.

Старый формат сценария MVP, старое API и код MVP заменены без поддержки и миграции. Новый формат документов начал нумерацию с `schemaVersion: 1`. После добавления сценария сервиса (T1.3 этапа 2) текущая версия модели — 2; версии эксперимента и раскладки остаются 1. Примеры и фикстуры переписаны; модель версии 1 получает ошибку `SCHEMA_VERSION` с ожидаемой версией, без миграции.

**Входит:** каталог типов этапа 1, документы модели, раскладки и эксперимента, компилятор и IR, адаптер KSL, исполнение с задачами, каталог артефакта со своими рядами, файловая рабочая область, API и CLI с одинаковыми возможностями; каркас UI, редактор, панель результатов, таймлайн, результаты на схеме, воспроизведение, вывод, линтер, карта, демо-сценарии.

**Не входит:** иерархия, составные блоки, маски и библиотека (формат к ним готов); реплики и балансировщик, БД с пулом, фазы и ресурсы, неблокирующая модель; DAG и fan-out — топология этапа 1 остаётся линейной цепочкой; частицы-запросы (#26); калибровка и импорт; проверка требований в CI (A10); SSE вместо опроса (#23); Parquet.

## 2. Критерии готовности

1. На демо retry storm пользователь, не прокручивая страницу, открывает рабочую область, меняет параметр варианта, запускает сравнение при заданных значениях и видит таймлайн, воспроизведение на схеме и вывод с причиной. Карта по сетке timeout × попытки работает как дополнительный режим той же панели.
2. CLI выполняет то же на тех же файлах; при тех же версии, документах и seed артефакты совпадают.
3. Сохранение из UI даёт документы с малошумными диффами; правку файла снаружи UI обнаруживает и предлагает перечитать.
4. Тесты доказывают, что результат не зависит от числа потоков и порядка блоков в документах.
5. CI зелёный; E2E переписаны под новый каркас.
6. Выходы типов описаны в каталоге по ADR 0011. Timeline, результаты инспектора и наложение используют эти описания; тестовый тип с дополнительным выходом получает все три представления без регистрации в коде web. Прежние метрики, подписи, единицы и значения сохраняются.

## 3. Модель и документы

### 3.1. Каталог этапа 1

| Тип | Вид | Параметры |
|---|---|---|
| `client` | блок | интенсивность (`120/s`), общий deadline (`1s`) |
| `service` | блок | обработчики, ёмкость очереди, время обработки (`fixed`, `exponential`, `lognormal`: среднее и разброс), доля отказов (`0.5%`) |
| `call` | связь | сетевая задержка (распределение), timeout, число попыток, backoff (`none`, `fixed`, `exponential-full-jitter`: база, максимум, множитель) |
| `request` | связь | без параметров: запрос клиента приходит на вход первого сервиса без сетевой задержки и повторов, как в MVP |

Каталог описывает блоки и связи одним контрактом параметров (ADR 0001): тип значения, физическая величина и единицы, диапазон, значение по умолчанию, описание, признак «можно перебирать в сетке». Порты: у `client` — выход; у `service` — вход и выход; `request` соединяет `client` с `service`, `call` — `service` с `service`.

В T1.4 первого среза этапа 2 каталог расширен типами `router` и `route` ([дизайн, §5.4](2026-10-30-stage-2-slice-1-design.md#54-маршрутизатор)). У `router` вход и выход, параметр `policy` со значениями `roundRobin` (по умолчанию), `random`, `leastInFlight`. Связь `call` также может вести из сервиса в маршрутизатор; связь `route` ведёт из маршрутизатора в сервис или другой маршрутизатор. `ConnectionRule.toTypes` перечисляет допустимые типы целей; версия схемы каталога — 2. У `route` положительный конечный `weight`, по умолчанию 1; он влияет только на `random`. Маршрутизатор имеет ровно одну входящую связь и хотя бы один выход, не занимает обработчиков и не добавляет задержку.

Параметр `call.retryTarget` — `any` (по умолчанию) или `other`. Выход выбирается при отправке каждой попытки. При `other` на каждом маршрутизаторе сначала рассматриваются выходы, ещё не опробованные этим вызовом; после их исчерпания доступны все. История начинается заново для следующего вызова, в том числе повторного шага по той же связи. Сетевые задержки в обе стороны, таймаут и повторы относятся к входящему `call` и всему выбранному пути; `route` не задаёт дополнительных попыток. `leastInFlight` учитывает работу до окончания ответа, включая работу после таймаута вызывающего. При равенстве выбирается первый выход по пути; `roundRobin` использует тот же порядок. Для `random` используется отдельный поток роли `routing` по пути маршрутизатора. Попытки по каждому выходу записываются в строки его связи `route` существующего формата артефакта; у маршрутизатора собственной строки узла нет. Структура документов модели и эксперимента не меняется.

У типа также есть `outputs`: стабильные идентификаторы выходов, названия и описания, единицы, виды величин, закрытые виды вычисления со ссылками на сырые поля и привязки итогов. Метаданные представлений задают группы Timeline, строки и мини-графики инспектора, метрики наложения. Подробнее — [ADR 0011](../../architecture/adr/0011-type-outputs.md). У `request` нет собственных рядов; его наложение использует amplification вызываемого сервиса.

### 3.2. Документы

Рабочая область содержит документы с суффиксами (ADR 0005):

```json
// retry-storm.model.json
{
  "schemaVersion": 2,
  "description": "Цепочка из трёх сервисов с деградацией зависимости.",
  "blocks": {
    "client": { "type": "client", "params": { "rate": "120/s", "deadline": "1s" } },
    "gateway": { "type": "service", "params": { "handlers": 4, "queue": 16, "processing": { "kind": "fixed", "mean": "1ms" } } }
  },
  "connections": [
    { "id": "client-to-gateway", "type": "request", "from": "client", "to": "gateway" },
    { "id": "gateway-to-middle", "type": "call", "from": "gateway", "to": "middle",
      "params": { "timeout": "80ms", "attempts": 3,
                  "backoff": { "kind": "exponential-full-jitter", "base": "2ms", "max": "20ms" } } }
  ]
}
```

```json
// retry-storm.experiment.json
{
  "schemaVersion": 1,
  "modelRef": "retry-storm.model.json",
  "layoutRef": "retry-storm.layout.json",
  "execution": { "replications": 10, "warmup": "0ms", "measurement": "1s", "seed": 20261025, "window": "10ms" },
  "faults": [ { "target": "dependency", "from": "200ms", "to": "800ms", "processingMultiplier": 4 } ],
  "variants": [
    { "id": "baseline" },
    { "id": "no-retries", "overrides": { "gateway-to-middle.attempts": 1 } }
  ],
  "grid": [
    { "path": "gateway-to-middle.timeout", "values": ["40ms", "80ms", "160ms"] },
    { "path": "gateway-to-middle.attempts", "values": [1, 2, 3] }
  ]
}
```

`*.layout.json` хранит координаты блоков по путям; ключи-пути позволяют позже хранить раскладку по уровням иерархии. Деградация — событие эксперимента (`faults`), а не свойство модели. `window` — длина окна рядов; по умолчанию измеряемый интервал / 100. `grid` необязателен и содержит одну или две оси. Отсутствующий `grid` и пустой список означают одну точку `p0` без координат. Ось содержит непустой список значений; повторяющиеся пути и пересечения «объект — его поле» между осями отвергаются. Переопределения варианта применяются раньше значений точки, включая вложенные поля. Диагностика пути указывает на `/grid/<i>/path`, значения — на `/grid/<i>/values/<j>`. Первая ось внешняя: сетка 2×3 даёт точки `p0`–`p5`, вторая ось меняется быстрее. Точка не входит в ключ случайного потока.

У блока `service` необязательное поле `scenario` стоит рядом с `params` и задаёт непустую последовательность шагов. Например, сервис с исходящими связями `db` и `payment` может выполнить обработку, чтение, платёж и запись:

```json
{ "scenario": [
  { "type": "process", "processing": { "kind": "fixed", "mean": "2ms" }, "failureRate": "0%" },
  { "type": "call", "connection": "db" },
  { "type": "process" },
  { "type": "call", "connection": "payment" },
  { "type": "call", "connection": "db" }
] }
```

Шаг `process` может задать `processing` в том же формате распределения, что параметры сервиса, и `failureRate` в процентах. Каждое отсутствующее значение берётся из параметров сервиса после переопределений варианта и сетки. Шаг `call` содержит `connection`: идентификатор связи типа `call`, исходящей из этого сервиса. Порядок и повторения шагов сохраняются; повторный шаг с той же связью не считается повтором неудачной попытки. Обработчик удерживается до конца сценария. Локальная ошибка или окончательная неудача вызова прерывает сценарий.

Если `scenario` отсутствует или равен `null`, сценарий по умолчанию состоит из обработки и исходящих вызовов по порядку их идентификаторов. Для нескольких исходящих вызовов поле `scenario` обязательно. Сам сценарий и параметры отдельных шагов не переопределяются в вариантах и сетке. Потоки обработки и исходов привязаны к пути сервиса, как в ADR 0006; отдельные шаги используют те же потоки. Редактор сценария относится к T4; web сохраняет это поле при редактировании параметров модели.

### 3.3. Пути и величины

Идентификатор блока или связи — сегмент пути; параметр — `путь.параметр`, вложенные поля — через точку (`gateway.processing.mean`). Вложенность этапа 2 добавит `родитель/потомок` без смены формата. Величины пишутся строками с единицами (`250ms`, `2s`, `120/s`, `0.5%`); количества — целыми числами. Ядро переводит величины во внутренние единицы, UI показывает привычные.

### 3.4. Проверки и линтер

JSON-схемы генерируются из классов документов и каталога; CI проверяет, что повторная генерация не даёт диффа. Компилятор проверяет ссылки, пути переопределений и сетки, допустимость значений и топологию графа: ровно один `client` с одной связью `request`, отсутствие циклов, достижимость всех сервисов от клиента и отсутствие вызовов во входной сервис. Цикл диагностируется с перечислением сервисов и связей и указателем на замыкающую связь. Число входящих вызовов не ограничено; несколько исходящих вызовов разрешены с явным сценарием, без него — `SCENARIO_REQUIRED`. Пустой сценарий — `SCENARIO_EMPTY`; вызов чужой, входящей, неизвестной связи или связи `request` — `SCENARIO_CONNECTION` с указателем на `scenario/<i>/connection`. Неизвестный вид шага и поля другого вида — `SCENARIO_STEP_TYPE` и `SCENARIO_FIELD`; сценарий у блока другого типа — `SCENARIO_BLOCK`. Остальные ошибки графа используют `TOPOLOGY_GRAPH` с аргументом `reason`. Это контракты T1.1 и T1.3 [первого среза этапа 2](2026-10-30-stage-2-slice-1-design.md); поведение цепочек этапа 1 сохраняется.

Схемы `schemas/*.schema.json` проверяют структуру, обязательность параметров, единицы величин и диапазоны обычных чисел. Размерность и границы строковых величин записаны в аннотации `x-quantity` в канонических единицах каталога и пояснены в `description`; их числовую проверку выполняет ядро. Формат аннотации и команды генерации описаны в [schemas/README.md](../../../schemas/README.md).

Линтер — диагностика уровня «предупреждение», вычисляемая на IR:

- исходящая связь не используется в сценарии сервиса: `LINT_SCENARIO_UNUSED` с указателем на сценарий и идентификатором связи в аргументах;
- timeout вызова меньше, чем нужно downstream-части цепочки: число попыток × timeout следующего вызова плюс сумма максимальных задержек backoff;
- произведение числа попыток по слоям больше 10;
- обработчиков сервиса меньше оценки λ·W, где λ — интенсивность клиента, а W — среднее время удержания обработчика: собственная обработка плюс ожидаемое время downstream-вызова без отказов и повторов;
- общий deadline меньше бюджета входного сервиса: его средняя собственная обработка плюс число попыток исходящего вызова × timeout и сумма максимальных задержек backoff;
- число независимых повторений меньше 5: 95 % доверительные интервалы при таком числе повторений ненадёжны.

Пороги — параметры правил, описанные в тексте диагностики.

`LINT_FEW_REPLICATIONS` сравнивает общее `execution.replications` с параметром `ModelLinter.minimumReplications`, равным 5 по умолчанию. Предупреждение советует не меньше этого числа повторений и выдаётся один раз на эксперимент независимо от вариантов и сетки: документ эксперимента, указатель `/execution/replications`, `variant = null`, без пути элемента. Оно не блокирует запуск и одинаково возвращается в API `POST /validate` и CLI `validate`. Поле `execution.replications` остаётся обязательным; скрытого значения по умолчанию в ядре и схеме нет.

`ModelLinter` проверяет IR каждой точки каждого варианта через `Lab.validate`. Диагностика содержит код, уровень `WARNING`, документ, JSON-указатель на параметр, путь элемента и необязательный идентификатор `variant`. Указатель ведёт на переопределение в эксперименте, если проблемное значение задано там, иначе на параметр модели. Без сетки одинаковое во всех вариантах предупреждение с одним местом в документе модели выдаётся один раз с `variant = null`; остальные выдаются отдельно для каждого затронутого варианта с его идентификатором. Диагностика переопределения сохраняет `variant` и при единственном варианте эксперимента. Идентификаторы вариантов в текст сообщения не добавляются. При заданном `grid` предупреждения о параметрах цепочки содержат идентификатор варианта. Одинаковые предупреждения внутри варианта объединяются; если текст или источник предупреждения отличается между точками либо предупреждение появляется не во всех точках, сообщение перечисляет точки как `points: p0, p1`. Происхождение параметров хранится отдельно для каждой скомпилированной точки, поэтому указатель на значение оси не теряется. Предупреждения не меняют `ValidationReport.valid` и не блокируют запуск. CLI `validate` печатает их в stderr с идентификатором варианта в месте диагностики и при отсутствии ошибок завершается с кодом 0.

В формулах линтера длительности измеряются в миллисекундах, интенсивность — в запросах за миллисекунду. Для `LINT_TIMEOUT_BUDGET` к бюджету следующего вызова добавляются среднее время собственной обработки целевого сервиса и средние сетевые задержки входящего запроса и ответа. Бюджет следующего вызова — число попыток, умноженное на timeout, плюс максимальные задержки между попытками. Для `none` задержка равна нулю, для `fixed` — меньшему из `base` и `max`, для `exponential-full-jitter` после неудачной попытки `k` — меньшему из `max` и `base × multiplier^(k − 1)`. У листового сервиса остаются собственная обработка и две сетевые задержки. Сетевые задержки следующего вызова уже входят в его timeout и повторно не прибавляются.

Для `LINT_HANDLERS_LITTLE` время удержания обработчика складывается из собственной обработки, обеих сетевых задержек исходящего вызова и времени удержания обработчика следующего сервиса. Это оценка предложенной нагрузки для успешного пути без очередей, отказов, повторов и обрезки таймаутами. `LINT_RETRY_AMPLIFICATION` сравнивает точное произведение числа попыток с порогом 10 по умолчанию. Средние длительности не ограничивают случайные хвосты распределений.

`LINT_DEADLINE_BUDGET` сравнивает deadline клиента с бюджетом входного сервиса: средняя собственная обработка плюс `attempts × timeout` его исходящего вызова и сумма максимальных задержек backoff между попытками. Backoff учитывается по тем же правилам, что в `LINT_TIMEOUT_BUDGET`. Если исходящего вызова нет, бюджет равен только средней собственной обработке входа. Связь `request` от клиента не добавляет ни сети, ни попыток. Сеть исходящего вызова и вложенные вызовы уже покрываются его timeout; их бюджеты проверяет `LINT_TIMEOUT_BUDGET`, повторно к deadline они не прибавляются. При равенстве deadline и бюджета предупреждения нет.

Числа в сообщениях линтера записываются без лишнего `.0` у целых значений; дробные значения сохраняют точность.

Эталон на `examples/retry-storm/` с 10 повторениями: у `baseline` одно предупреждение `LINT_TIMEOUT_BUDGET` — timeout 80 ms меньше downstream-бюджета 189 ms. Бюджет входа равен `1 + 3 × 80 + (2 + 4) = 247 ms`, что укладывается в deadline 250 ms. У `no-retries` бюджет входа 81 ms, предупреждений нет. `LINT_FEW_REPLICATIONS` не выдаётся.

В `examples/checkout/checkout.experiment.json` у `baseline` и `bigger-payment-pool` по два предупреждения `LINT_TIMEOUT_BUDGET`: timeout шлюза 5000 ms меньше бюджета 10021 ms, timeout вызова из order-service 3000 ms меньше бюджета 4036 ms. У `no-order-retries` остаётся только второе предупреждение, у `aligned-timeouts` предупреждений нет. Deadline 10000 ms покрывает бюджет входа во всех вариантах: `2 + 1 × 5000 = 5002 ms`, у `aligned-timeouts` — `2 + 1 × 8000 = 8002 ms`.

## 4. Ядро

### 4.1. Пакеты

Пакеты `resiliencelab.core.scenario` и `resiliencelab.core.simulation` заменяются:

| Пакет | Ответственность |
|---|---|
| `catalog` | Описания типов блоков и связей, разбор и печать величин с единицами |
| `document` | Классы документов, кодек, детерминированный писатель, строгий загрузчик, генерация схем |
| `compiler` | Документы → переопределения варианта и точки сетки → проверка → IR; диагностика |
| `ir` | Плоский граф примитивов с типизированными параметрами и происхождением элементов |
| `engine.ksl` | Адаптер KSL, принимающий только IR |
| `execution` | Задания, задачи, планировщик, оценка стоимости |
| `results` | Сборщик рядов, агрегаты, вывод v1, запись артефакта |
| `workspace` | Хранилище документов за абстракцией (ADR 0003): сначала файловое, с версией-хешем и проверкой при записи |
| `lab` | Фасад для сервера и CLI: проверка и запуск экспериментов рабочей области |

Диагностика — общая структура для API, CLI и UI: код, уровень, документ, указатель JSON, путь блока, текст и необязательный идентификатор `variant`. Значение `null` означает диагностику модели или общую для всех вариантов. Ошибки компилятора, указывающие на переопределение или идентификатор варианта, содержат идентификатор своего варианта.

IR ядра — `GraphIr`: клиент, входной сервис, экземпляры сервисов, рёбра вызовов, отказы и параметры прогона. Компилятор строит у каждого сервиса сценарий `process`, затем `call` по единственной исходящей связи; у конечного сервиса остаётся только `process`. Сегменты пути хранятся отдельно от его отображаемого адреса и служат ключом случайных потоков. Каждый элемент сохраняет происхождение; при перестановке массива связей JSON-указатель меняется вместе с исходной позицией, семантика IR не меняется. Порядок узлов и связей топологический от клиента, при равенстве — по сегментам пути.

`ModelLinter` применяет правила этапа 1 отдельно вдоль путей от клиента; полная семантика ветвлений относится к дорожке линтера. `CostEstimator` суммирует события по шагам сценария и передаёт число визитов по вызовам в топологическом порядке. Повторный шаг вызова и общая цель нескольких вызовов учитываются каждый раз. Переименование сервисов не меняет оценку. В T1.1 исправлен прежний расчёт по алфавитному порядку: он мог недооценивать число событий, когда вызываемый сервис оказывался перед вызывающим.

### 4.2. Адаптер и потоки

Адаптер принимает `GraphIr`; каждая задача создаёт свежую модель KSL. Обработчики сервиса используют общий набор слотов с ограниченной FIFO-очередью (ADR 0013). Вызов сервиса занимает обработчик один раз и удерживает его до конца сценария: шаги `process` и `call` выполняются по порядку, включая повторный вызов той же связи. Окончательная ошибка шага прерывает сценарий, обработчик освобождается в `finally`. В `process` длительность и исход выбираются до задержки. Каждая попытка `call` получает цель извне; по умолчанию это цель ребра. Таймаут, общий дедлайн, backoff и продолжение работы ниже по графу после таймаута сохраняют семантику этапа 1. Сетевые задержки и jitter принадлежат ребру и сохраняют свои потоки между шагами и повторными попытками.

Потоки случайных чисел назначаются по ADR 0006 с первого же среза: SHA-256 полного ключа (версия назначения, seed, повторение, путь экземпляра, роль) даёт номер подпотока, генератор переходит к нему штатным `advanceSubStreams`; план адресов эксперимента проверяется на коллизии до запуска. Образец реализации и тестов — прототип исследования S4 (`research/ksl-streams/`). Роли источников этапа 1: поступления у `client`; время обработки и исход обработки у `service`; сетевые задержки запроса и ответа и jitter backoff у `call`.

Адаптер не использует глобальный `KSLRandom.DefaultRNStreamProvider` и `RandomVariable`: значения берутся функциями KSL с явно переданным потоком; автоматический переход KSL на следующий подпоток и сброс потоков отключены. Одновременные события упорядочиваются детерминированно по каноническому пути, как в MVP требовал проектный дизайн, §8.5. `SeedFactory` удаляется.

### 4.3. Ряды и агрегаты

Свой сборщик (ADR 0007, 0008) пишет по каждому узлу и окну симуляционного времени достаточные статистики: поступило, принято, отклонено по переполнению, успешно, отказов, таймаутов, повторов; занятое время обработчиков; интеграл длины очереди. Сводка сохраняет семантику `MetricsAggregator`: статистики пула и по повторениям, доверительные интервалы без обрезания.

Для каждой связи `call` сборщик наблюдает отправку попыток и повторов, полученные ответы (`succeeded`, `failed`), обрывы по timeout и `orphaned` — брошенные попытки, чья работа ниже ещё не закончилась. Timeout, укороченный общим deadline, остаётся timeout. Интегралы `inFlightIntegralMs`, `orphanedIntegralMs` и `backoffIntegralMs` описывают ожидание ответа, брошенную работу до завершения вызываемого процесса вместе с обратной сетью и ожидание backoff. Обработчик вызывающего во время backoff занят. Ряды используют время события и общие границы окон узлов; у связи `request` рядов нет.

Длительность попытки от отправки до ответа сохраняется в `latency` связи с тем же профилем скетча. В неё входят только попытки с полученным ответом, включая неуспешные; timeout не даёт образца задержки. Поэтому среднее и квантили описывают эту ограниченную выборку, а не все отправленные попытки. Итоги счётчиков и задержек связей используют измеряемую когорту с run-out; интегралы охватывают фиксированный измеряемый интервал и всю присутствующую работу, включая прогрев. `AggregateMetrics.connections` содержит объединённые итоги и задержки, а также `MetricSummary` доли таймаутов среди отправленных попыток и среднего числа попыток в полёте по повторениям с 95 % CI. Поля узлов сохраняют прежний смысл.

Задержки собираются в DDSketch по итогам [исследования S5](../../research/2026-10-28-latency-sketch.md): библиотека `com.datadoghq:sketches-java:0.8.3` с обёрткой профиля `ddsketch-bitwise6-rational-v1` — отображение `BitwiseLinearlyInterpolatedMapping(6)`, представитель корзины `нижняя граница × 129/128`, отдельный точный счётчик нулей. Относительная ошибка значения не больше 0,78125 %; корзины — целые счётчики, поэтому слияние побайтно не зависит от порядка, а JVM и браузер получают одинаковые биты квантилей. Обёртка отвергает отрицательные, нечисловые и выходящие за диапазон значения; при превышении лимитов скетча (общий счётчик больше 2^53−2, диапазон индексов больше 2048) расчёт останавливается с указанием узла, окна и лимита, без огрубления. Квантили считаются прежней интерполяцией KSL по двум порядковым статистикам из корзин, а не рангом DDSketch. Среднее хранится как отдельные счётчик и сумма. Web читает и сливает корзины собственным кодом по тому же профилю.

### 4.4. Вывод v1

- Насыщение по очереди подтверждается после как минимум 100 ms подряд окон, в каждом из которых загрузка обработчиков не ниже 95 % и средняя длина очереди больше 0,5. Укороченное последнее окно учитывается по фактической длительности.
- Насыщение по переполнению подтверждается по серии подряд окон с числом отклонений больше нуля: от начала первого до начала последнего должно пройти как минимум 100 ms. Последнее окно не добавляет свою длительность, поскольку счётчик отклонений не показывает, когда внутри окна они произошли. Единичное окно с отклонениями не подтверждает насыщение при любом шаге рядов.
- Обе ветки проверяются независимо; начало насыщения — начало первого окна той из подтверждённых серий, которая началась раньше. Окно без соответствующего признака или разрыв ряда прерывает серию. Порог задан во времени и не зависит от числа окон. Шаг `execution.window` определяет усреднение и разрешение начала; крупное окно может скрывать короткие перерывы. Если весь ряд помещается в одно окно, подтвердить насыщение по переполнению нельзя.
- Первым насытившимся считается узел с самым ранним началом; порядок остальных показывает путь деградации. При одинаковом моменте первым идёт узел, стоящий дальше в топологическом порядке графа: вызываемый раньше вызывающего. Для узлов вне переданного графа порядок определяется идентификатором.
- По повторениям вывод агрегируется честно: «dependency первым в 9 из 10 повторений, медиана t = 210 ms»; если насыщения нет, вывод так и говорит.
- Поле `saturation` точки сводки хранит параметры правила (`minimumDurationMs = 100.0`, `handlerUtilizationThreshold = 0.95`, `meanQueueLengthThreshold = 0.5`, `queueRejectionsThreshold = 0`), путь каждого повторения, отдельное число повторений без насыщения и статистики первых узлов. Для каждого первого узла записаны число повторений, медиана и min/max момента начала; при чётном числе значений медиана — среднее двух центральных. Списки первых узлов упорядочены по убыванию числа повторений, затем по идентификатору.
- Вывод пересобирается из записанных оконных частей при построении сводки, в том числе при досчёте. Пороги указаны рядом с данными вывода; их текст в web относится к T4.

### 4.5. Исполнение

По ADR 0009: задание = варианты × точки сетки × повторения; общий пул с чередованием задач разных заданий; кооперативная отмена; досчёт недостающих задач при тех же версии и хешах. До запуска — оценка стоимости по формуле исследования #46.

На текущем срезе `ExperimentExecutor` выдаёт задачи по кругу между активными заданиями, внутри задания — по вариантам, точкам сетки и повторениям. `Lab.run` принимает признак `isCancelled: () -> Boolean`; функция должна быть потокобезопасной и быстро возвращать результат. Ожидающий вызов проверяет его с интервалом 25 ms; отмена прерывает активные потоки задания, модели KSL останавливаются на границе события. Отмена и прерывание вызывающего потока завершают вызов исключением `java.util.concurrent.CancellationException`, отличимым от ошибки расчёта. Лимит реального времени на задачу сохраняется. После T1.4 при отмене остаются файлы готовых задач и уже записанные части, манифест помечает артефакт незаконченным, сводка не создаётся. Записи частей выполняются в отдельных потоках без прерывания, потому что `FileChannel.lock` прерываем; планировщик ждёт их завершения перед публикацией неполного манифеста. После последней проверки отмены окончательная запись сводки и манифеста завершается целиком, а прерывание вызывающего потока восстанавливается после записи. Сервер выполняет вызовы `Lab.run` в отдельных виртуальных потоках JDK, поэтому ожидание задания не занимает поток расчёта.

`Lab.validateResume(runDirectory)` без изменения артефакта проверяет возможность досчёта и возвращает манифест. Проверяются канонический путь каталога, версии приложения, KSL и назначения потоков, хеши документов и метаданные прогона: несовпадения дают `RUN_INCOMPATIBLE` или `RUN_DOCUMENT_CHANGED`, законченный прогон — `RUN_COMPLETE`. `Lab.resume(runDirectory, isCancelled, onProgress)` повторяет эти проверки при запуске, пересчитывает только отсутствующие или повреждённые задачи и атомарно заменяет сводку и манифест. Досчитанный артефакт побайтно равен непрерывному. Повторная отмена сохраняет неполный манифест без сводки. Параллельные вызовы `resume` для одного каталога сериализуются в JVM; вызов после публикации получает `RUN_COMPLETE`. `Lab.estimate(experimentPath, drafts, workers)` без запуска KSL возвращает `ExperimentEstimate`: число задач, ожидаемые события и строки, время при заданном числе потоков, распакованный и записанный объём, число частей и предупреждения (поля `tasks`, `expectedEvents`, `expectedRows`, `workers`, `estimatedSeconds`, `estimatedUncompressedBytes`, `estimatedArtifactBytes`, `estimatedParts`, `warnings`). Время использует S1 с настроенным числом попыток, объём — 512 байт на узел и окно и коэффициент gzip 0,25 по S3/S5. Предупреждение `ESTIMATE_EXTRAPOLATION` выдаётся при числе сервисов больше 5000. Ускорение ограничено значением для 8 потоков (3,184): увеличение числа потоков сверх 8 не уменьшает оценку времени относительно 8 потоков, поэтому `ESTIMATE_WORKER_EXTRAPOLATION` не выдаётся. `ESTIMATE_UI_CACHE` отмечает превышение кэша UI 64 МиБ. Допуск калибровки `retry-storm` — 8× из-за переноса S1 на другое оборудование и модель меньше 50 сервисов. API и CLI вызывают эти же методы ядра.

### 4.6. Артефакт

Манифест и сводка используют версию 7; прежние артефакты требуют нового запуска. В обоих файлах поле `grid` сохраняет оси `{ path, values }` в порядке документа, включая порядок и повторы значений; без сетки оно равно `[]`. Это позволяет UI получить оси при первой загрузке сводки независимо от сортировки ключей `coordinates`. В `series.points` манифеста находятся идентификаторы и координаты точек. У каждого варианта сводки список `points` содержит `id`, `coordinates`, `aggregate` и `saturation`; агрегата всего варианта нет. Без сетки сохраняется одна точка `p0` с пустыми координатами.

Каталог `.results/<эксперимент>/<прогон>/` (ADR 0008): `manifest.json`, `summary.json` и по каталогу на задачу `series/<вариант>/<точка>/rep-<n>/`. В каталоге задачи — итоги повторения для сводки, части рядов `part-<k>.json.gz` и индекс частей: какие узлы, связи и диапазон окон покрывает каждая часть. Части делят сетки «узел × окно» и «связь × окно» на группы элементов и диапазоны окон так, чтобы несжатая часть не превышала бюджет ответа UI (4 МиБ); поэтому любую часть можно отдать UI целиком. Манифест фиксирует версии, хеши документов, seed, окно, профиль скетча, полноту и контрольные суммы всех файлов задач. Сводка содержит метрики по вариантам и точкам сетки и данные вывода.

T1.4–T1.6 реализуют [формат артефакта](../../results-format.md) версии 7 для манифеста и сводки. Точка без сетки — `p0`. Последовательные закрытые окна накапливаются в текущей части до лимита 4 МиБ; узлы и связи делятся на группы только для окна, которое целиком не помещается в часть. Индекс и части рядов имеют версию 2; часть содержит массивы `nodes` и `connections`, индекс перечисляет идентификаторы обоих видов. Лимит 4 МиБ общий для обоих массивов. При делении возможны части только со связями. Сводка пересобирается из `replication.json`, `index.json` и gzip-частей в фиксированном порядке задач. `execution.window` по умолчанию равен `measurement / 100`, окна покрывают `[0, warmup + measurement)`, последнее хранит фактическую длительность. Ряды используют время событий и включают прогрев, а итоги повторений — когорту измеряемого интервала с её run-out. Скетч задержки сервиса содержит только принятые попытки; отказы очереди остаются в отдельном счётчике. Хеши документов манифеста считаются по канонической записи; версии для `If-Match` и принятого задания остаются хешами исходных байтов.

## 5. Сервер, рабочая область, CLI

### 5.1. Рабочая область

Сервер запускается с каталогом рабочей области — параметром запуска или переменной окружения; Docker Compose подключает каталог, по умолчанию `examples/`. Внешние изменения отслеживаются `WatchService`; UI получает их опросом. У документа есть версия — хеш содержимого; запись выполняется с `If-Match`, при расхождении сервер отвечает 409. Запись без `If-Match` только создаёт новый документ. `If-Match` сравнивается строго (RFC 9110): слабые теги не совпадают. Пути не выходят за рабочую область, в том числе через символьные ссылки.

`DELETE /workspace/document?path=` требует `If-Match`: без него — 428 `VERSION_REQUIRED`, при несовпадении — 409 `VERSION_CONFLICT`, отсутствующий документ — 404, успех — 204. Ядро удаляет документ под той же блокировкой рабочей области, что и запись.

Журнал изменений ведётся в памяти процесса и хранит 1000 последних изменений документов `*.model.json`, `*.layout.json` и `*.experiment.json` вне скрытых каталогов, включая записи через API. `WatchService` дополняется полным сканированием раз в секунду, поэтому внешнее изменение попадает в журнал не позже чем через 5 секунд. Обходы пропускают скрытые каталоги целиком (`SKIP_SUBTREE`), включая `.results`; начальный снимок журнала делается при первом запросе изменений. `GET /workspace/changes?since=` возвращает непрозрачный курсор `<generation>:<sequence>`, признак `reset` и изменения `{ path, kind, version }`, где `version: null` означает удаление; без `since` — текущий курсор и пустой список. Курсор другого процесса, устаревший или больший текущего даёт `reset: true` и пустой список; некорректный курсор — 400 `CURSOR_INVALID`.

### 5.2. API

API получает базовый путь `/api/v1` и полностью заменяет нынешнее (ADR 0010).

| Ручка | Назначение |
|---|---|
| `GET /health` | Состояние сервера |
| `GET /catalog` | Каталог типов |
| `GET /workspace/documents`, `GET/PUT/DELETE /workspace/document?path=` | Документы рабочей области с версией; путь содержит `/`, поэтому передаётся параметром |
| `GET /workspace/changes?since=` | Внешние изменения |
| `POST /validate` | Диагностика и линтер; необязательные черновики документов позволяют проверить несохранённые правки |
| `POST /estimate` | Оценка стоимости эксперимента |
| `POST /jobs`, `GET /jobs`, `GET /jobs/{id}`, `POST /jobs/{id}/cancel` | Задания |
| `GET /runs`, `POST /runs/{id}/resume`, `GET /runs/{id}/manifest`, `GET /runs/{id}/summary`, `GET /runs/{id}/series/{variant}/{cell}/{rep}`, `GET /runs/{id}/series/{variant}/{cell}/{rep}/{part}` | Прогоны, включая незаконченные, и досчёт незаконченного — к прогону, а не к заданию: задания не переживают перезапуск сервера; для задачи — индекс частей рядов, затем сами части в gzip как есть |

Спецификацию генерирует springdoc в `apps/server/openapi.json`. Классы ядра сервер отдаёт через kotlinx-конвертер Spring, а springdoc строит схему по тем же классам через Jackson. Поэтому JSON API содержит все поля, отсутствующее значение пишется как `null`, а типы API не используют `@SerialName`, собственные сериализаторы и полиморфизм.

Принятое задание привязано к версиям модели и эксперимента, прочитанным при проверке. Перед расчётом ядро сверяет их с теми же загруженными документами, которые будут исполнены. Невалидные документы дают обычную диагностику проверки, а изменение версий валидных документов — `DOCUMENT_CHANGED`. В обоих случаях задание получает `FAILED`, прогон не записывается. Сервер хранит не более 100 завершённых заданий в порядке завершения (FIFO); активные задания не вытесняются.

`POST /validate` принимает `{ experiment, drafts? }`. Необязательный `drafts` — список `{ path, content }`, где `content` имеет форму `DocumentContent` и содержит ровно один документ вида, заданного суффиксом пути. Пути черновиков канонические, относительно корня рабочей области, без повторов. Черновики подменяют чтение только на время проверки, в том числе для ещё не созданных документов; файлы и их версии в хранилище не меняются. Ответ остаётся `ValidationView`. Без `drafts` проверяются сохранённые файлы. В ядре этому соответствует `Lab.validate(experimentPath, drafts: Map<String, String>)` с текстом документов.

`POST /estimate` принимает то же тело и возвращает `ExperimentEstimate` ядра; оценка не меняет документы и не создаёт `.results/`. `POST /runs/{id}/resume` сначала вызывает `Lab.validateResume`, затем создаёт задание `Lab.resume`, которое повторяет проверки при исполнении. Ответ — 202 с `JobView` и исходным `runId`. Завершённый прогон даёт 409 `RUN_COMPLETE`, изменённые документы — 400 с диагностикой ядра, неизвестный — 404 `RUN_NOT_FOUND`.

`GET /runs` перечисляет законченные и незаконченные прогоны, `RunEntry.complete` различает их состояния. Сводка незаконченного прогона даёт 404 `RUN_INCOMPLETE`; манифест и готовые задачи рядов доступны.

Ручки рядов T2.1 возвращают индекс задачи как `SeriesIndex`, а часть — исходными байтами gzip с `Content-Type: application/json` и `Content-Encoding: gzip`. Сильный `ETag` части равен её SHA-256 из индекса; `Cache-Control: max-age=31536000, public, immutable` разрешает хранить неизменяемую часть год. OpenAPI описывает распакованный `SeriesPart`. Идентификаторы проверяются до чтения: точка имеет вид `p0`, `p1` и далее, номера повторений и частей — целые от 0 до 2147483647 без ведущих нулей. Неверный формат даёт 400 `SERIES_PATH`, неизвестный объект или отсутствующий файл — 404 `SERIES_NOT_FOUND`. Часть должна быть указана в индексе; символьные ссылки в пути рядов не читаются. Ряды готовых задач доступны и у незаконченного прогона.

`POST /jobs/{id}/cancel` возвращает 202 с `JobView`. Задание в очереди сразу получает статус `CANCELLED` без создания файлов; выполняющееся получает `cancelRequested: true` и переходит в `CANCELLED`, когда ядро остановило расчёт и закончило запись артефакта. Повторная отмена возвращает текущее состояние с кодом 202. Завершённое или ошибочное задание даёт 409 `JOB_FINISHED`, неизвестное — 404 `JOB_NOT_FOUND`. Запрос во время окончательной записи готового результата не прерывает её: статус остаётся `COMPLETED`.

При остановке контекста Spring `JobService.close()` отменяет задания до закрытия вызывающего исполнителя: ожидающие задания получают `CANCELLED` сразу, выполняющиеся — `cancelRequested: true`. Новые отправки во время остановки отменяются без запуска. Затем вызывающий исполнитель ждёт остановки расчётов и завершения записей, после чего закрывается общий пул ядра.

### 5.3. CLI

Повторный SIGINT после запроса отмены принудительно завершает процесс с кодом 130. Записи при этом не дожидаются завершения; полнота артефакта и наличие манифеста не гарантируются.

Команды на тех же документах: `validate`, `estimate`, `run [--workers N]`, `resume <прогон>`, `catalog`, `schema`. `estimate` печатает `ExperimentEstimate` одной JSON-строкой. `run` пишет артефакт в `.results/`; `resume` принимает идентификатор прогона или путь к его каталогу внутри рабочей области и досчитывает его на месте. Для `run` и `resume` ход выполнения идёт в stderr, путь к артефакту и краткая сводка по каждой паре «вариант, точка» — в stdout. Рабочая область CLI — текущий каталог, пути к эксперименту и прогону ведут внутрь неё. `validate` пишет результат в stderr. `catalog` печатает тот же JSON, что `GET /catalog`, `schema <model|layout|experiment>` — текст соответствующего `schemas/*.schema.json` из генератора; эти две команды не открывают рабочую область. Код выхода 2 — ошибка использования или проверки, 1 — сбой расчёта, 130 — отмена.

Ctrl+C и SIGTERM передают отмену в `Lab.run` и `Lab.resume`. CLI ждёт остановки и записи незаконченного артефакта, печатает его путь в stderr и завершается с кодом 130. Если артефакт ещё не создан, CLI сообщает об этом без пути; stdout при отмене остаётся пустым. Обработчики сигналов действуют только во время команд `run` и `resume`.

## 6. UI

### 6.1. Каркас

По §5.5 видения и ADR 0004: верхняя панель (выбор эксперимента, пункт `Experiment`, несохранённые изменения, «Оценить», «Запустить», Cancel и Resume); слева полоса значков блоков из каталога шириной 48 px; в центре холст React Flow, связи `call` протягиваются между портами; справа инспектор с формами из каталога и вводом величин с единицами; внизу холста страницы вариантов; внизу экрана панель результатов и постоянная строка состояния во всю ширину. Страница не прокручивается.

До первого прогона открытого эксперимента в текущей сессии панель результатов свёрнута, освободившуюся высоту занимает холст. На странице варианта результаты выбранного элемента идут первыми в инспекторе, параметры находятся под ними в сворачиваемой группе (§6.3).

Интерфейс рассчитан на настольные окна от 1280×720 до 3840×2160 и масштаб браузера 90–150 %. Шрифты и отступы заданы в `rem`. Верхняя панель, строка контекста и строка состояния остаются в одну строку; длинные пути экспериментов, подписи вариантов и версии backend обрезаются многоточием, полный текст доступен в подсказке. Графики Timeline занимают одну–три колонки в зависимости от ширины самой панели; при достаточной ширине минимальная ширина графика составляет 27,5 `rem`.

Ширина инспектора по умолчанию — `clamp(280px, 22vw, 480px)`. Её можно менять тем же разделителем, что высоту панели результатов: мышью, клавишами ←/→, Home и End. Ширина ограничена 280–480 px; при уменьшении окна верхняя граница уменьшается так, чтобы холсту оставалось не менее 480 px, при необходимости уменьшается и нижняя. Двойной щелчок возвращает относительный размер по умолчанию. Кнопка сворачивает инспектор до полосы и раскрывает обратно. Выбор элемента не раскрывает свёрнутый инспектор: его имя появляется на полосе. Содержимое инспектора и черновики полей сохраняются при сворачивании. Ширина и свёрнутость запоминаются в браузере вне документов и undo/redo; при увеличении окна восстанавливается желаемая ширина. Палитра остаётся полосой постоянной ширины, без изменения размера и сворачивания. Описание `Shared by all variants` показано один раз под заголовком Run settings.

Строка состояния показывает слева направо состояние задания и прогресс активного задания (`RUNNING 3/4`), запрошенную отмену, счётчики ошибок и предупреждений, признак устаревших результатов, время выбранного окна общего курсора, состояние backend с версиями приложения и KSL, масштаб холста. Щелчок по счётчикам открывает Problems и раскрывает свёрнутую панель. Строка остаётся видна при любом размере панели результатов. Статус задания и состояние backend показываются здесь; в верхней панели остаются команды Run, Cancel и Resume, в заголовке результатов статуса задания нет.

Estimate получает оценку через `POST /estimate` с черновиками изменённых документов и показывает число задач, потоков, ожидаемых событий и строк, время, объём до и после сжатия, число частей и предупреждения. Кнопка Estimate открывает всплывающую панель у кнопок запуска до явного закрытия: кнопкой, щелчком вне панели или Esc. Панель не занимает высоту холста и не меняет размер результатов; закрытие во время запроса не открывает её заново при получении ответа. Оценка не сохраняет документы и не запускает расчёт. Правка или смена документов убирает прежнюю оценку; запоздалые ответы и ошибки отбрасываются. Неразбираемый ввод во время ожидания также отменяет применение ответа. Перед каждым Run запрашивается новая оценка. При Run панель открывается только для предупреждений `ESTIMATE_UI_CACHE`, `ESTIMATE_EXTRAPOLATION` или ошибки оценки и закрывается сама после получения нового задания. `ESTIMATE_UI_CACHE` требует явного подтверждения с текстом предупреждения; `ESTIMATE_EXTRAPOLATION` подтверждения не требует. При ошибке оценки запуск возможен только после явного подтверждения, что бюджет времени и размера не проверен.

После `CANCELLED` или `FAILED` кнопка Resume появляется, если доступен манифест с `complete: false`. Она вызывает `POST /runs/{id}/resume`; новое задание отслеживается и отменяется тем же способом, что обычный запуск. Результаты остаются связаны с документами исходного прогона. Несохранённые изменения блокируют Run и Resume. Resume раскрывает свёрнутую панель результатов. Отказы `RUN_COMPLETE` и диагностика изменённых документов видны на любой её вкладке с предложением начать новый прогон через Run.

На странице модели блок добавляется из палитры перетаскиванием, щелчком или Enter без заполнения параметров по умолчанию. Щелчок и Enter ставят блок в центр видимой области холста с учётом смещения и масштаба, с привязкой к сетке 20 единиц. Если место занято, позиция сдвигается по диагонали шагами 40 единиц до свободного места с учётом размеров узлов. Новый блок выделяется; добавление любым способом использует одну команду `addBlock` в истории undo/redo. У каждого типа есть значок и доступное имя; подпись и описание из локализованного каталога показываются при наведении и фокусе. Неизвестный тип получает нейтральный значок с первой буквой подписи. Раздела Connections в палитре нет: значок подсказки объясняет, что связь протягивается от выходного порта к входному. На странице варианта кнопки добавления недоступны. `Identifier` в инспекторе переименовывает блок или связь с обновлением ссылок во всех документах. Ctrl/Cmd+щелчок выделяет несколько элементов, Shift+перетаскивание выделяет рамкой; Delete и Backspace удаляют выделенное с каскадом, Ctrl/Cmd+C и Ctrl/Cmd+V копируют блоки и внутренние связи со сдвигом координат. После вставки выделяются копии. На страницах вариантов структура и раскладка доступны только для просмотра.

Позиции привязываются к сетке 20 единиц. Перемещение одного или нескольких блоков записывается в историю после завершения жеста одной командой и меняет только их позиции. Размеры узлов React Flow и выделение хранятся вне документов. На холсте есть миникарта и кнопки масштаба. Ключевые параметры — timeout и число попыток связи, обработчики, очередь и среднее время обработки сервиса — правятся прямо на схеме двойным щелчком теми же командами, что в инспекторе; на странице варианта такая правка пишет переопределение. У нового блока незаполненные обязательные поля видны в инспекторе и не блокируют навигацию или undo.

Миникарта и кнопки масштаба находятся в отдельной полосе под схемой. При изменении размеров холста или узлов схема автоматически вписывается в доступную область, в том числе при перетаскивании разделителя панели анализа и переключении компоновки `Analysis`.

Разделитель между схемой с вкладками вариантов и панелью анализа меняет высоту панели мышью или клавишами ↑/↓ с шагом 16 px; Home задаёт минимум, End — максимум. Двойной щелчок сбрасывает сохранённую высоту только текущей вкладки и компоновки к относительному размеру по умолчанию (§6.3). Разделитель занимает 0,5 `rem`. Схеме вместе со строкой контекста, навигацией и вкладками остаётся не менее 220 px, панели — 160 px; если окно меньше суммы минимумов, они уменьшаются до половины доступной высоты. Прокручивается содержимое областей, страница остаётся в пределах окна.

Кнопка `Analysis` в строке контекста доступна после получения результатов на странице варианта. В этой компоновке схема со строкой контекста и вкладками вариантов занимает верхнюю часть экрана, панель анализа — нижнюю во всю ширину. При первом открытии схеме остаётся примерно 38 % доступной высоты. Палитра скрыта, справа остаётся инспектор только с результатами выбранного элемента; без выбора он предлагает выбрать узел или связь. Параметры инспектора скрыты с сохранением черновиков. Ширина и свёрнутость колонки подчиняются тем же настройкам, что в обычной компоновке. Выбор узла или связи выбирает их ряды на Timeline, параметры правятся двойным щелчком на схеме. Повторное нажатие кнопки или Esc возвращает обычную компоновку и сохраняет курсор времени. Если открыт редактор параметра или всплывающая оценка, Esc сначала закрывает его. Строка состояния видна в обеих компоновках.

### 6.2. Состояние и варианты

Источник правды — загруженные документы модели, раскладки и эксперимента. Правка — команда с undo/redo; правка модели и раскладки — одна операция; воспроизведение в историю не попадает. Первая страница под схемой — страница модели: правка на ней меняет модель. Остальные страницы — варианты эксперимента, в том числе варианты без переопределений. После правок модель с задержкой проверяется через `POST /validate`; диагностика видна значками на схеме и во вкладке Problems. Состояние строится на командах поверх reducer, без новой библиотеки состояния. Переключение страницы сохраняет выбранный элемент, но меняет значения на его странице. Выбор страницы следует за идентификатором варианта при переименовании, undo и redo; удаление активного варианта возвращает страницу модели.

Инспектор показывает ровно одну текущую цель, которая хранится вне документов и истории:

- щелчок по блоку или связи, переход к элементу из Problems или щелчок по группе метрик сервиса в Answer открывает свойства элемента; при мультивыделении показан последний выбранный элемент;
- щелчок по уже активной вкладке варианта открывает его идентификатор и подпись;
- щелчок по пустому холсту, по уже активной вкладке `Model` или пункту `Experiment` рядом с выбором эксперимента открывает общие настройки эксперимента: прогон, отказы и сетку, без свёрнутого раздела.

Исчезновение цели при удалении или undo возвращает инспектор к эксперименту. При переименовании элемента или варианта цель следует за новым идентификатором, в том числе через undo/redo. Возврат удалённого объекта через undo сам по себе не выбирает его заново.

Явные команды открытия свойств варианта, `Experiment`, щелчок по активной вкладке `Model` и переход из Problems возвращают обычную компоновку из режима `Analysis`, чтобы инспектор и нужное поле были видны.

Действия над вариантами находятся в полосе страниц. Кнопка `+` добавляет пустой вариант и делает его активным. Контекстное меню вкладки варианта открывается правой кнопкой мыши, клавишей контекстного меню или Shift+F10 на вкладке в фокусе. `Duplicate` копирует вариант и открывает копию; `Rename` открывает свойства этого варианта в инспекторе с фокусом на подписи; `Delete` требует подтверждения. Последний вариант удалить нельзя: пункт недоступен и снабжён пояснением. У `Model` контекстного меню нет. В меню работают стрелки, Home/End, Enter и Escape; Escape возвращает фокус на вкладку. Все изменения используют общие команды с undo/redo. В инспекторе варианта остаются только его свойства; удаления там нет.

В инспекторе элемента нет свойств и действий варианта и раздела эксперимента. На странице варианта параметры блока или связи показываются с пометкой `variant overrides` и редактируются как переопределения. Описание параметра из `localizeCatalog` видно текстом под полем или заголовком группы и связано с ним для средств доступности. Изменения идентификатора варианта проверяются на допустимость и уникальность; при очистке подписи вкладка показывает идентификатор.

Правка варианта записывает скаляр по пути `id.param`, поле объекта — по `id.param.field`. Если значение совпадает с моделью, в том числе после перевода единиц, переопределение удаляется. `Use model value` сбрасывает поле или объект целиком одной командой; сброс поля сохраняет переопределения соседних полей. Переопределения отмечены в инспекторе и значком на блоке или связи.

Очистка необязательного поля варианта выбирает значение каталога по умолчанию. Если оно отличается от модели, переопределение хранит `null`: компилятор считает такое поле отсутствующим и применяет его значение по умолчанию. При разборе существующего переопределения объекта на отдельные поля так же сохраняется отсутствие его необязательных полей.

Цель «эксперимент» доступна на любой странице и содержит общие параметры прогона и отказы: число повторений, разогрев, измеряемый интервал, окно рядов, seed, лимит реального времени, цель и интервал отказа, множитель обработки и долю отказов. Единицы длительности и долей берутся из каталога. Правки меняют документ эксперимента и входят в общую историю. Пустое поле `Series window` удаляет `execution.window`; подсказка показывает текущий измеряемый интервал, делённый на 100, без записи значения по умолчанию в документ. Ошибки проверки по `/execution/window` видны у поля.

Здесь же редактируется `grid`: до двух осей с путями перебираемых скалярных параметров блоков и связей из каталога и списками значений в их единицах. Добавление и удаление осей и значений, выбор пути и правка значения входят в undo/redo. Диагностика `/grid/…` видна у соответствующих полей при открытых настройках эксперимента на любой странице. Переход из Problems выбирает цель и фокусирует нужное поле: общие настройки открывают эксперимент, поля варианта — вариант, параметры блока или связи — элемент. Неразбираемый ввод блокирует смену цели и страницы, команды вкладок и другие действия, которые могут потерять черновик.

История хранит последние 100 команд и сохраняется после записи документов; открытие или перечитывание эксперимента очищает её. Undo после сохранения снова делает документ изменённым. Кнопки отмены и повтора находятся в верхней панели; Ctrl/Cmd+Z отменяет команду, Ctrl/Cmd+Shift+Z и Ctrl+Y повторяют её. В полях ввода действует штатная отмена поля.

Одна кнопка сохраняет все изменённые документы в порядке: раскладка, модель, эксперимент. Каждый существующий документ записывается со своей версией `If-Match`, новый — без неё. При 409 запись останавливается: уже сохранённые документы остаются сохранёнными, UI показывает путь конфликтующего документа и блокирует повторное сохранение до перечитывания. Если `layoutRef` отсутствует, первая команда изменения раскладки в той же записи истории добавляет ссылку на `<имя эксперимента>.layout.json` рядом с экспериментом.

Если раскладка уже записана, а её ссылка ещё нет, перечитывание восстанавливает содержимое и версию этой раскладки. Так же обрабатывается 409 при создании файла с уже занятым именем. Само перечитывание не добавляет `layoutRef`; следующая команда изменения раскладки добавит его вместе с правкой.

Web опрашивает `GET /workspace/changes` каждые 1000 мс, пока открыта рабочая область; внешняя правка открытого документа становится видна не позднее чем через 5 секунд после записи. Курсор получают до первого чтения документов. Ответ `reset: true` заставляет перечитать список документов и сравнить версии открытых документов, а создание и удаление экспериментов обновляет список в выборе. Событие для пути с незавершённым `PUT` откладывается до ответа записи и сравнивается с возвращённой версией, поэтому собственное сохранение не создаёт баннер независимо от порядка ответов журнала и `PUT`. Сбой опроса не меняет редактор и повторяется с прежним курсором.

Внешнее изменение открытого документа показывает баннер с путём и кнопкой Reload. Если есть несохранённые правки, баннер предупреждает об их потере, а перечитывание требует подтверждения и очищает историю. Баннер сам не блокирует Save: попытка записи со старой версией по-прежнему даёт 409. Удалённый документ показывается как удалённый, без Reload и без попытки прочитать отсутствующий файл.

Проверка черновиков запускается через 500 мс после последней команды; вместе с запросом передаются все изменённые документы. Ответы, относящиеся к предыдущим состояниям, отбрасываются. Диагностика связывается с элементами по пути и с полями по JSON-указателю, включая вложенные параметры, переопределения варианта, настройки прогона и отказы. Поле `variant` определяет страницу варианта даже при указателе на модель; без него страница определяется по указателю на переопределение. На странице варианта его значки и сообщения у полей показываются как обычно; общая диагностика видна на всех страницах. На странице модели диагностика вариантов отмечается отдельным приглушённым значком у блока или связи: пунктирная рамка отличает его от значка самой модели, цвет соответствует наибольшей серьёзности, число — количеству сообщений. Подсказка перечисляет идентификаторы вариантов без повторов. Значок открывает и раскрывает Problems с записями этого элемента, сохраняя страницу модели; команда Show all problems, щелчок по вкладке Problems или счётчику в строке состояния снимает фильтр. Рядом с полем инспектора модели, включая вложенные поля, показаны короткие строки In variants с идентификатором варианта и отдельными числами ошибок и предупреждений. Каждая строка ведёт на страницу этого варианта, сохраняет выбранный элемент и фокусирует поле; полные сообщения остаются на странице варианта. Неразбираемый ввод блокирует эти переходы и значки, как остальную навигацию. Вкладка Problems показывает все записи, включая диагностику без элемента и диагностику ответа запуска. Одинаковая запись из проверки и запуска учитывается один раз. Диагностика ошибки запуска или возобновления относится к документам соответствующей попытки. После их изменения она исключается из текущего списка и счётчиков; новая попытка Resume может показать свою ошибку и при устаревших результатах исходного прогона. Сначала идут ошибки, затем предупреждения; внутри группы сохраняется порядок ответа. Запись начинается со значка серьёзности и готового сообщения API, затем показывает имя блока или связи и вариант, если он есть. Код и путь документа вынесены на вторую приглушённую строку; JSON-указатель виден только в подсказке. Щелчок выбирает соответствующие страницу, элемент и поле.

Новая ошибка в завершённом ответе проверки черновиков или запуска автоматически открывает Problems и раскрывает свёрнутую панель. Запрос Problems имеет приоритет над автоматическим переходом к Answer при завершении прогона. Новизна определяется по серьёзности, коду, сообщению, документу, указателю, элементу и варианту относительно предыдущего завершённого ответа того же источника. Ожидание следующей проверки сохраняет сведения о предыдущих ошибках: повтор той же ошибки не возвращает пользователя в Problems. Если ошибка исчезла из ответа и появилась снова, она считается новой. Предупреждения сами панель не открывают; их число видно в строке состояния. Значки показывают число сообщений и наибольшую серьёзность. Ошибки и предупреждения различаются цветом. Ошибки блокируют Run, предупреждения не блокируют; ожидание проверки и ошибка связи с API также блокируют запуск с пояснением.

Разбираемые значения вне диапазона каталога входят в черновик и проверяются ядром. Неразбираемый ввод остаётся в поле и блокирует действия, которые могут его потерять.

Оценка стоимости открывается под верхней панелью в отдельной области вне холста. Её можно закрыть и открыть снова кнопкой Estimate или Run. Объёмы показываются в KiB и MiB. Перед Run запрашивается свежая оценка; предупреждение бюджета требует подтверждения. При сбое оценки видна ошибка, а запуск без проверки стоимости требует отдельного явного подтверждения. Ответ оценки, устаревший после изменения документов или полей, запуск не разрешает.

### 6.3. Результаты

Timeline, секция «Результаты» инспектора и выбор метрик наложения строятся из `TypeDescriptor.outputs`. Каталог задаёт наборы, порядок, подписи и единицы; web выполняет закрытые операции над существующими полями артефакта. Переводы выходов находятся по ключам `catalog.types.<typeId>.outputs.<id>.*`. Отсутствующий источник даёт `n/a`; доверительные интервалы берутся только из указанного `MetricSummary` и не обрезаются. Состав нынешних представлений сохраняется; Answer, Map и правило насыщения по-прежнему имеют собственную логику.

Вкладки панели: Answer (вывод и сравнение вариантов с доверительными интервалами), Timeline (графики по выбранным узлам, связям и метрикам), Assumptions (допущения модели из каталога и условия прогона из манифеста), Problems (диагностика), Map (только при наличии сетки: линия для одной оси, тепловая карта для двух; ячейка открывает свои ряды и вывод).

Панель результатов можно свернуть или изменить её высоту разделителем. При открытии эксперимента без законченного или незаконченного прогона в текущей сессии она свёрнута. Щелчок по любой вкладке свёрнутой панели выбирает её и раскрывает панель до сохранённой для этой вкладки высоты. Повторный щелчок по активной вкладке оставляет панель раскрытой; сворачивает её только кнопка `Collapse results`. Кнопка `Restore results` возвращает сохранённую высоту; кнопки развёртывания нет, для разбора служит компоновка `Analysis` (§6.1). Ручной выбор свёрнутости сохраняется до смены эксперимента, включая завершение прогона; щелчок по вкладке, Run, Estimate, Resume, счётчик Problems и новая ошибка раскрывают панель. Высота запоминается в браузере отдельно для Answer, Timeline, Assumptions, Map и Problems в каждой из двух компоновок, вне документов и undo/redo. В обычной компоновке начальная высота Timeline составляет 55 % доступной высоты, остальных вкладок — 32 %; в `Analysis` — 62 %. Размер ограничивается минимумами областей, а сохранённая высота восстанавливается при увеличении окна. Если хранилище браузера недоступно, изменение высоты работает до закрытия страницы.

После успешного прогона открывается первая вкладка Answer. Если пользователь переключал вкладку панели после нажатия Run, в том числе во время оценки перед запуском, его выбор сохраняется. Run, Estimate и Resume раскрывают свёрнутую панель до сохранённой высоты текущей вкладки и не выключают `Analysis`; оценка показывается у кнопки Run.

Вверху Answer стоит вывод для варианта активной страницы и выбранной точки: первый насытившийся узел, число повторений, медианное начало и диапазон, повторения без насыщения, пути деградации и правило. На странице модели показывается первый вариант по документу с его названием. Без сетки заголовок содержит только название варианта; с сеткой к нему добавляются координаты выбранной точки вместо её идентификатора. Ниже варианты сравниваются в колонках, метрики — в строках. Первой идёт колонка варианта с ID `baseline`, а при его отсутствии — первого варианта по документу; остальные сохраняют порядок документа. Выделяется колонка активного варианта. Метрики сервисов раскрываются группами; таблица переносит текст и помещается по ширине экрана 1440 px для retry-storm.

Правило объясняется двумя фразами в блоке `How saturation is detected`, который по умолчанию свёрнут. Порог загрузки, порог средней очереди, число отказов в окне и минимальная длительность берутся из всех четырёх полей `saturation.rule`. Текст сохраняет различие между непрерывной длительностью насыщения очереди и интервалом от начала первого до начала последнего окна с отказами. Дополнительные записанные параметры доступны в том же блоке.

Если в выбранной точке все повторения прошли без насыщения, под выводом показана строка `Capacity headroom`: наибольшая pooled-загрузка обработчиков и соответствующий сервис, наибольшая средняя очередь и соответствующий сервис, pooled p99 задержки на входе. Загрузка вычисляется как `busyHandlerTimeMs / handlerCapacityTimeMs`, средняя очередь — как `queueLengthIntegralMs / measurementMs`; максимумы выбираются среди сервисов независимо. Очередь указывается в запросах: сводка не содержит её ёмкости. p99 берётся из `aggregate.pooledLatency.all.p99Ms`, без усреднения p99 повторений. При нулевом знаменателе или отсутствии метрики показывается `n/a`. Если хотя бы одно повторение насытилось, строка отсутствует; при отсутствии повторений запас также не выводится. Все значения берутся из сводки без загрузки рядов.

У небазовых вариантов рядом со средним показана разность относительно базового в единицах метрики; разности долей выводятся в процентных пунктах. Пометка «Intervals do not overlap» появляется только при строго непересекающихся 95 % CI с обеими границами у обоих вариантов. Касание границ считается пересечением; пометка не утверждает статистическую значимость. Для pooled-загрузки busy/capacity интервал не вычисляется. При числе повторений меньше 5 (константа web) интервалы показываются приглушённо, без скрытия и обрезания, с пометкой об их ненадёжности и советом увеличить `Replications`.

Выбор точки сетки сохраняется; сравнение показывает эту точку у всех вариантов, у которых она есть. Если у базового варианта точки нет, это явно указано, разности недоступны и другой вариант не становится базовым. Если документы, включая несохранённые правки, отличаются от тех, с которыми запущен прогон, Answer, Assumptions и схема помечают результаты как устаревшие. После отмены панель сообщает о незаконченном прогоне без сводки. Точка сетки, повторение и закреплённое окно хранятся в общем состоянии результатов вне документов и undo/redo.

Над схемой страницы варианта после законченного прогона показана одна компактная строка контекста результатов: название варианта активной страницы (выбирается вкладкой), выбор точки при наличии сетки, повторение с нуля, переключатель `Summary | Time`, управление временем и выбор наложения. Только эта строка содержит селекторы точки и повторения; Answer и Timeline используют общее состояние. Селектор повторения доступен и в Summary: он меняет ряды Timeline, а схема продолжает показывать сводные итоги выбранной точки. В Time выбор повторения меняет и ряды, и схему. Map меняет точку щелчком по ячейке. Сравнение `Compare variant` остаётся в Timeline и относится только к графикам. На странице модели и до законченного прогона строки нет; Answer на странице модели сохраняет выбранную точку. В конце строки находится кнопка компоновки `Analysis`.

Timeline строит на Recharts группы графиков — интенсивности, задержки, ошибки и отказы, загрузка, очередь — по выбранным узлам и метрикам; выделение элемента на холсте выбирает его ряды. Ctrl/Cmd+щелчок добавляет к выбору узлы и связи `call`. Для связи показываются собственные отправленные попытки, повторы, ответы и таймауты в секунду, средние попытки в полёте, orphaned work и backoff, средняя длительность вызова и её квантили. Линия timeout использует параметры документов прогона с переопределениями варианта и точки. Легенда связи содержит её имя и метрику; при сравнении добавляется вариант. Длительности описывают только полученные ответы, без попыток, оборванных по timeout. Второй вариант накладывается на те же графики, повторение выбирается с нуля. Наведение показывает исходные значения окна на всех графиках, щелчок закрепляет окно курсора. Прореживание сохраняет экстремумы и границы разрывов. Разогрев берётся из манифеста, интервалы отказов — из эксперимента, с которым запущен прогон.

Результаты на схеме появляются на странице варианта после законченного прогона: у сервиса — загрузка, средняя очередь и доля отказов очереди из pooled-итогов выбранной точки, у связи — amplification вызываемого сервиса как среднее по повторениям из Answer, значок — узел `saturation.firstNodes[0]` с числом повторений. В строке контекста выбирается метрика цвета узлов: загрузка, средняя очередь или доля отказов очереди; `Off` снимает всё наложение. Легенда долей имеет шкалу 0–100 %. Для средней очереди цвет показывает заполнение `meanQueue / queueCapacity`, легенда — `Queue fill: 0–100 %`; числовая подпись узла сохраняет среднюю длину очереди. Ёмкость берётся из документов прогона с переопределениями варианта и выбранной точки сетки, поэтому правки текущего документа не меняют шкалу старых результатов. Неуказанная ёмкость равна 0 по каталогу: ожидание отключено, цвет заполнения для такого узла отсутствует. Метрика подписей связей выбирается отдельно: amplification, отправленные попытки в секунду, доля таймаутов или средняя orphaned work. Значения связей берутся из `aggregate.connections` и их собственных окон; amplification по-прежнему относится к admitted amplification вызываемого сервиса. Связь `request` собственных рядов не имеет. На странице модели наложения нет; новые элементы не получают значений из прежнего прогона.

На странице варианта после завершённого прогона инспектор выбранного элемента показывает секцию `Results` перед параметрами, если у элемента есть результаты в текущем контексте. Под ней находится группа `Parameters`, изначально свёрнутая; её состояние сохраняется в браузере вне документов и undo/redo. Переход из Problems раскрывает группу и фокусирует поле; `Use model value` возвращает фокус полю, двойной щелчок по параметру на схеме раскрывает группу и сохраняет фокус редактора на схеме. На странице модели, до завершённого прогона и для элемента без результатов параметры открыты, порядок секций прежний. При выборе другого элемента инспектор прокручивается к началу. Секция `Results` использует общие вариант, точку, повторение и курсор. У сервиса видны загрузка, средняя очередь и её заполнение, доля отказов очереди, принятые попытки в секунду и средняя задержка. У связи `call` — отправленные попытки и повторы в секунду, доля таймаутов, число orphaned-попыток и средняя orphaned work, средние попытки в полёте и backoff, длительность вызова рядом с timeout и admitted amplification вызываемого.

В `Summary` сервисные показатели, интенсивности, длительности и средние по времени величины связи из итогов подписаны как pooled. Число orphaned-попыток показывается средним на повторение: сумма `totals.orphaned` делится на число повторений варианта, подпись — `per replication`, без вычисления доверительного интервала. В `Time` остаётся число событий выбранного окна. Доля таймаутов, средние попытки в полёте и amplification используют среднее повторений и 95 % CI, если сводка его содержит; при числе повторений меньше 5 показывается то же предупреждение, что в Answer. Интервалы не обрезаются и не создаются для pooled-величин. Средняя задержка сервиса вычисляется для выбранного повторения как сумма `sumMs`, делённая на сумму `count`, по окнам измеряемого интервала и имеет отдельную подпись источника. Если окно пересекает начало измерения, его образцы нельзя разделить по границе разогрева: берутся полные измерительные окна, а рядом явно указан фактически покрытый интервал. В `Time` показаны значения выбранного окна; amplification помечен как приближение. На странице модели секции нет, отсутствующий или заменённый элемент не получает чужих значений.

Мини-графики показывают выбранное повторение: у сервиса загрузку и очередь, у связи отправленные попытки и таймауты в секунду, среднюю длительность вызова с линией timeout. На них отмечены разогрев, интервалы отказов и общий курсор. Они используют тот же ограниченный кэш декодированных частей, что Timeline и воспроизведение; одновременные обращения к одной части разделяют загрузку. `Show on Timeline` открывает Timeline с рядами выбранного элемента, допущения его типа доступны в раскрываемом блоке.

В режиме `Time` строка контекста содержит запуск, паузу, скорости 0,25–4× при базовом темпе 10 окон в секунду независимо от длительности окна, ползунок, шаги по одному окну и время окна. Проигрыватель делит курсор с Timeline: выбор окна на графике также включает `Time`. Переключение в `Summary` снимает курсор одновременно у схемы и Timeline; Esc на холсте в обычной компоновке делает то же, кроме полей ввода. В `Analysis` Esc сначала возвращает обычную компоновку, сохраняя курсор. Отдельных кнопок `Return to summary` и `Clear time cursor` нет. С курсором схема показывает метрики окна выбранного повторения; amplification окна помечен как приближение. Ряды читаются диапазонами до 32 окон, уменьшенными по оценке 512 байт на узел и окно до целевого объёма 4 МиБ (не меньше одного окна); декодированные части Timeline и проигрыватель берут из общего LRU-кэша 64 МиБ. Пока ряды загружаются, часы ждут. Ручная перемотка, смена варианта, точки, повторения или скрытие наложения останавливают воспроизведение.

Map использует сетку и метрики сводки для варианта активной страницы. Порядок осей и значений, включая повторы, сохраняется: первая ось тепловой карты идёт по строкам, вторая по столбцам. Метрики — success rate, p95, p99, admitted amplification и pooled-загрузка выбранного сервиса. Линия показывает 95 % CI из сводки без обрезания; у pooled-загрузки busy/capacity такого интервала нет. Значение ячейки видно числом, у цветов есть шкала. Щелчок выбирает точку общего контекста результатов.

На графике задержек маркер отмечает значение исходного непустого окна. Пустые окна остаются разрывами без среднего и квантилей; пояснение рядом с графиком указывает, что значения в таких окнах отсутствуют.

Цвет узла и подпись связи соответствуют выбранным метрикам, значок отмечает первый насытившийся узел. У связи широкая невидимая зона выбора вдоль линии и доступная с клавиатуры подпись-плашка; выбранная связь подсвечивается вместе с концами. Кадр вычисляется только из рядов, поэтому пауза и перемотка детерминированы. В режиме времени размеры узлов и положение подписей связей сохраняются при загрузке и перемотке. Пока выбранное окно загружается, видны значения последнего загруженного окна приглушённо, с пометкой о загрузке в подсказке. До первого загруженного окна место строк метрик остаётся пустым. Ошибка загрузки сохраняет эти места и последние значения, а её текст появляется в подсказке и проигрывателе; курсор ждёт готового кадра. Смена прогона, варианта, точки или повторения очищает сохранённый кадр. Сводка не подставляется вместо окна. В последних восьми окнах текущего участка (или во всём участке, если он короче) заранее загружается следующий участок узлов и связей. Предзагрузка использует существующий SeriesLoader и общий LRU-кэш рядов с прежним лимитом 64 MiB; отдельный кэш не создаётся, формат запросов не меняется. Без курсора схема показывает итог измеряемого интервала из сводки — те же числа, что в Answer. Сначала грузится сводка, ряды — по выбору варианта, ячейки и повторения; распаковка и разбор идут в Web Worker.

Демо — рабочая область `examples/` с коротким retry storm и моделью оформления заказа `checkout`. Примеры видны в списке выбора эксперимента рабочей области; отдельной команды «Открыть пример» нет. У checkout общие модель и раскладка: `checkout.experiment.json` сравнивает четыре варианта, а `checkout-grid.experiment.json` перебирает timeout × attempts у baseline для Map. Источники чисел, типичные допущения и расчёт бюджета таймаутов записаны в `notes` документов.

### 6.4. Язык и форматирование

Web поддерживает английский (`en`) и русский (`ru`). Без явного выбора используется первый поддерживаемый язык из `navigator.languages`, включая региональные варианты `ru-*` и `en-*`; если поддерживаемых языков нет, используется английский. Явный выбор в меню «Вид» справа в верхней панели хранится в `localStorage` и имеет приоритет над языком браузера. Если хранилище недоступно, выбор действует до перезагрузки страницы. Переключение сразу обновляет интерфейс и атрибут `lang` у `<html>`, сохраняя документы, артефакты, текущие правки и историю Undo.

Пользовательские строки, включая подписи доступности и тексты контролов холста, берутся функцией `t(key, params)` из `web/src/i18n/en.json` и `ru.json`. Наборы ключей и имена подстановок совпадают; это проверяют unit-тесты. Ключи сгруппированы по областям (`app`, `editor`, `results`, `status`, `common`); параметры именованные. В dev-сборке и тестах неизвестный ключ или пропущенный параметр вызывает ошибку. В production функция не бросает исключение: для неизвестного статуса задания показывает исходное значение API, например `PAUSED`, для прочих неизвестных ключей и неполных параметров — ключ сообщения. [Глоссарий](../../../web/src/i18n/README.md#глоссарий) задаёт общие переводы терминов. Обозначения p50, p95, p99, RPS и CI сохраняются. Пользовательские данные, включая названия вариантов, идентификаторы, пути и содержимое документов, не переводятся.

Подписи, описания и допущения `/catalog` локализуются в копии исходного ответа при выборе языка: сначала ищется ключ `catalog.types.<typeId>`, для параметров — `catalog.types.<typeId>.params.<dottedPath>`, затем используется исходный текст API. Поля текста обозначаются суффиксами `.title` и `.description`, допущения — `.assumptions.<index>`. Общие допущения используют `catalog.assumptions.<index>`. Оба каталога сообщений содержат эти тексты; unit-тест проверяет покрытие всех типов, вложенных параметров и допущений полного снимка `/catalog`. Идентификаторы, значения и исходный ответ сохраняются.

Диагностика `Diagnostic`, ошибки запросов `ApiProblem` и предупреждения оценки `EstimateWarning` содержат стабильный `code` и необязательный `args`: словарь со строками и числами. У ошибки задания рядом с прежним `error` находятся необязательные `errorCode` и `errorArgs` того же формата. Числа передаются исходными значениями; единица задаётся текстом перевода. Произведение попыток больше `9007199254740991` передаётся строкой десятичных цифр: web форматирует её как `BigInt`, сохраняя точность за пределами безопасного целого JavaScript. `message` и `error` сохраняют прежний английский текст для CLI и старых клиентов.

Web переводит эти сообщения при отображении по ключу `messages.<CODE>`. Если у одного кода несколько причин, `args.reason` выбирает ключ `messages.<CODE>.<reason>`; остальные аргументы подставляются по имени, числа проходят общее форматирование. `args.points` сохраняет список точек сетки в локализованном суффиксе предупреждения линтера. Отсутствующее `args`, неизвестный код или причина, отсутствующий ключ либо обязательный аргумент возвращают исходный `message` или `error`, в том числе в dev-сборке и тестах. Подробности стороннего парсера или ввода-вывода в `detail` сохраняются в исходном виде. Это правило действует в списке Проблем, подсказках значков на схеме, сообщениях у полей, оценке и ошибках запросов и заданий.

Контракты сообщений заданы в `CoreMessage` и `ServerMessage`, которые используют места выдачи сообщений. Проверки собирают список кодов, причин и параметров из этих исходников и сверяют его со всеми языковыми каталогами web; отдельный ручной список кодов не поддерживается.

Отображаемые числа форматирует `web/src/i18n/format.ts` через `Intl.NumberFormat` с текущим языком. Максимальная точность: числа, RPS и множители — два знака, проценты и миллисекунды — один, секунды и размеры — три; лишние нули не выводятся. В русском интерфейсе используются десятичная запятая и локализованные единицы: `65,7 %`, `80 мс`, `800 КиБ`. Размеры используют KiB/КиБ до 1 MiB и MiB/МиБ начиная с этой границы. Отсутствующие значения показываются как `n/a` или его перевод; доверительные границы не обрезаются. Синтаксис величин в документах и редактируемые значения (`600ms`, `10s`) не меняются. Unit-тест на TypeScript AST запрещает пользовательские литералы в JSX.

## 7. Порядок работ

### 7.1. Сквозной срез

Срез заменяет MVP целиком; старый код и API удаляются.

- **Ядро:** каталог и документы; компилятор с проверкой цепочки и переопределениями вариантов; IR; адаптер KSL с потоками по путям блоков (ADR 0006) и проверкой плана адресов; задачи и пул без отмены и досчёта; артефакт с манифестом и сводкой без рядов.
- **Сервер и CLI:** файловая рабочая область без отслеживания изменений; ручки каталога, документов, `validate`, `jobs`, сводки прогона; генерация OpenAPI и TS-типов; CLI `validate` и `run`.
- **Web:** каркас, холст, инспектор из каталога с сохранением, правка модели на странице модели, страницы вариантов только для просмотра, запуск задания, вкладка Summary.
- **Примеры:** `examples/retry-storm/` в новом формате.
- **E2E:** открыть пример → изменить параметр → сохранить → запустить → увидеть сводку по вариантам.
- **Удаление MVP:** после перехода web — ручки MVP, пакет `scenario`, `ExperimentRunner`, `SweepExpander`, `SeedFactory` и адаптер старых сценариев; смысловые тесты MVP переносятся на IR, пакет `simulation` становится `engine.ksl`. Раньше удалить нельзя: ручки MVP нужны нынешнему web и обязательной проверке `e2e`.

Срез выполняется четырьмя планами: ядро, сервер и CLI, web, удаление MVP. Ядро добавляет фундамент рядом со старым кодом, сервер открывает новое API рядом с ручками MVP.

Пока идут дорожки, часть возможностей MVP — серии на графике, импорт и экспорт — недоступна.

## 8. Тестирование

- **Ядро:** разбор величин с единицами; эталонные файлы детерминированной записи; отсутствие диффа при повторной генерации схем; диагностика компилятора с местом в документе; перенесённые смысловые тесты MVP (M/M/1, повторы, orphaned work, когорта); одинаковый результат при разном числе потоков и перестановке блоков; правило вывода на синтетических рядах; полнота артефакта и досчёт.
- **Сервер:** тесты API, включая конфликт `If-Match` и отсутствие диффа OpenAPI.
- **Web:** unit-тесты команд, undo, переопределений и единиц; E2E по критериям готовности в реальном Chromium с настоящим backend, без mock API.
- JaCoCo формирует отчёты покрытия для CI; порогов в сборке нет: прежние были выбраны наугад, покрытие оценивается по отчётам.
