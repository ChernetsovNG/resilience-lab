# Объём и формат результатов прогона

Дата: 2026-10-27. Исследование [#48](https://github.com/ChernetsovNG/resilience-lab/issues/48). Статус: рекомендация для A7; архитектурное решение ещё не принято.

## Вывод

Рекомендуется сохранить A7: каталог артефакта с небольшими JSON-манифестом и сводкой, отдельными временными рядами и выборочной трассой. Для объёмных таблиц основной кандидат — **Parquet со Snappy**, с загрузкой выбранных колонок и диапазонов. JSON + gzip остаётся простым форматом небольших фрагментов и экспорта. Arrow IPC Stream полезен для последовательной передачи, если она понадобится; хранить одновременно все представления одного результата не требуется.

На синтетическом прогоне из 5000 листьев и 600 окон Parquet занял **54,14 MB**, JSON + gzip — **52,80 MB**. Медианы записи JVM: **2,30 с** и **7,63 с**; декодирования с проверкой значений в Chromium: **517 мс** и **1109 мс**. Arrow записался за **0,46 с** и прочитан за **282 мс**, но занял **268,75 MB**. Это сравнение конкретных схем, кодеков и реализаций, а не универсальный рейтинг форматов.

Без подгрузки по частям A7 не решает проблему: сетка 5×5 с десятью повторениями для 5000 листьев содержит **7,5 млрд значений**, то есть **60 GB** только десяти колонок float64. Полные большие сетки здесь не записывались; ниже их оценки явно отделены от физических файлов.

## Расчёт объёма

Обозначения: `B` — листья, `W=600` — окна, `M=10` — метрики, `R=10` — повторения, `G=25` — точки сетки. Одна строка — один узел в одном окне, повторении и точке.

```text
rows       = B × W × R × G
values     = rows × M
metricBytes = values × 8
tableBytes  = rows × (10 × 8 + 2 × 4)
```

В прототипе два ключа `node` и `window` имеют тип int32. Точка и повторение задаются разделом артефакта, поэтому не дублируются в каждой строке. MB/GB здесь десятичные; MiB/GiB — двоичные.

| Листья | Строки, один прогон | float64, один прогон | Строки, вся сетка | Только метрики, вся сетка | Метрики и два ключа, вся сетка |
|---|---:|---:|---:|---:|---:|
| 50 | 30 000 | 2,4 MB | 7 500 000 | 0,6 GB / 0,559 GiB | 0,66 GB |
| 500 | 300 000 | 24 MB | 75 000 000 | 6 GB / 5,588 GiB | 6,6 GB |
| 5000 | 3 000 000 | 240 MB | 750 000 000 | 60 GB / 55,879 GiB | 66 GB |

Это несжатое содержимое колонок, а не размер готового файла или требуемая память браузера. Не учтены метаданные, validity buffers, составные блоки и порты, распределения задержек, служебные индексы и трасса. Десять отображаемых скаляров также не заменяют достаточные статистики для точной агрегации.

## Методика и воспроизведение

Окружение: macOS 26.6.2 arm64, Apple M4 Pro, 14 логических CPU, 48 GiB RAM; Microsoft OpenJDK 25.0.3+9-LTS; Node.js 26.12.1; Playwright 1.64.1, Chromium 156.0.8078.4. Gradle Wrapper 9.8.2. Arrow Java 19.0.0, Arrow JS 21.2.0, Parquet Java 1.18.1, Hadoop Common 3.4.3, hyparquet 1.31.5. Команды и параметры приведены в [README прототипа](../../research/results-volume/README.md); точные байты, все три наблюдения и хеши — в [results.json](../../research/results-volume/results.json).

Набор `series` имеет десять числовых метрик: интенсивность, доли успехов, ошибок и таймаутов, среднюю и p99 задержку, загрузку, длину очереди, попытки на запрос и долю отклонений. Есть различия между узлами, временной профиль, деградация части узлов и шум seed. Все значения заранее округлены до 0,001 одинаково для всех форматов; это условие синтетики. JSON использует список названий и массивы строк, без повторения имён полей в каждой строке. CSV содержит только числовые поля, поэтому его reader не является универсальным CSV-парсером.

Физически записаны:

- по три полных прогона для 50, 500 и 5000 листьев в каждом формате;
- вся сетка для 50 листьев: 25 сочетаний множителей интенсивности и задержки от 1 до 2 с шагом 0,25, десять разных seed на сочетание; всего 250 файлов на формат;
- отдельная трасса и контрольный набор с полноточным шумом.

Всего проверены размеры и SHA-256 **1315 файлов общим объёмом 4 856 446 264 байта**. Chromium полностью декодировал и сверил канонический SHA-256 40 файлов: основные наборы, трассу, шум и три из 250 разделов сетки каждого формата. Для остальных разделов сетки проверены физические файлы и хеши исходного канонического потока; независимое декодирование всех 1250 файлов не выполнялось. Перечень разделов с размерами и хешами: [grid-sizes.csv](../../research/results-volume/grid-sizes.csv).

JVM-таймер включает генератор, контрольную сумму, запись и закрытие writer; отдельный проход SHA-256 исключён. Три измерения выполнялись в свежих JVM после одного прогрева на 5000 строк. Это практическая оценка, без доказанного steady state JIT. В длинной серии сетки JVM постепенно прогревается, поэтому её сумму времени нельзя напрямую сопоставлять с одиночными процессами. `fsync` не выполнялся.

В Chromium отдельно измерены загрузка и декодирование с валидацией и обходом **каждого значения**. Медианы рассчитаны по трём попыткам после двух прогревов; первая попытка сохранена отдельно. Для SHA-256 выполняется дополнительный проход вне таймера. Arrow читается через типизированные массивы, Parquet через колонки без построения объектов на каждую строку. Проверяются имена, физические типы бинарных колонок, отсутствие null и число значений.

HTTP-кэш отключён; кэш файловой системы не очищался. Загрузка шла через loopback, без конкурирующего JVM benchmark. В таблицах нет времени загрузки библиотек, отрисовки и подготовки React-состояния. Пиковая память не измерялась. Проверочный буфер SHA-256 в Chromium достигает 288 MB и не описывает память будущего интерфейса.

|---|---:|---:|
| JSON + gzip | 0.529 | 2.770 |
| CSV | 2.092 | 5.647 |

Преимущество JSON + gzip по размеру исчезает на полноточном шуме. Сжатие зависит от точности, повторяемости и распределения данных. Нельзя переносить коэффициент сжатия синтетики на результаты реальной модели без контрольного прогона.

### Поток и типичный срез UI

Arrow IPC Stream прочитан непосредственно из `response.body`, без предварительного `arrayBuffer()`: для 5000 листьев **367 пакетов**, первая полностью обработанная порция за **4.1 мс**, весь поток за **309.5 мс**. Это одиночное дополнительное измерение на прогретой странице. Отдельный повторный поток сверил полный SHA-256. Время создания представления не подменяет обход данных.

Из Parquet на 5000 листьев реально запрошены первые 50 узлов × 600 окон и четыре колонки: `node`, `window`, `utilization`, `queueLength`. Получено **3 503 466 байт** за **4 HTTP-запроса с ответом 206**, чтение заняло **9.4 мс**. Срез отдельно проверен по SHA-256 против полностью прочитанной таблицы. Полная передача файла требовала бы 54 135 746 байт. Запрос захватывает служебные данные и страницы соседних строк: указание `rowEnd` не гарантирует передачу ровно выбранных значений. Для маленького файла Range может передать даже больше его размера из-за пересекающихся запросов.

Файлы имеют row group 16 MiB и page 64 KiB; Arrow batch — 8192 строки. Такой порядок строк удобен для непрерывного диапазона узлов. Разрозненные узлы, произвольные временные интервалы, задержки реальной сети, Web Worker и отрисовка здесь не измерены.

## Выборочная трасса 1%

Объём трассы определяется нагрузкой и фактически пройденными путями, а не одним числом листьев:

```text
expectedRoots  = samplingProbability × requestRate × duration × R × G
expectedEvents = expectedRoots × (rootEvents + visitedNodes × attemptsPerNode × eventsPerAttempt)
traceBytes     = events × measuredBytesPerEvent
```

Если интенсивность и пути различаются между точками, нужно суммировать по точкам и повторениям. `attemptsPerNode` — фактическая средняя кратность, включая вложенные повторы; она не равна одному настроенному `maxAttempts`.

Параметры отдельного опыта: 1000 запросов/с, 600 секунд, 600 000 исходных запросов, десять посещённых узлов, около 1,2 попытки на узел, четыре события на попытку, без дополнительных корневых событий. Seeded hash выбирает весь запрос; его вызовы и попытки сохраняются целиком. Это ожидаемые 1%, не ровно один из ста последовательных запросов.

При seed 42 выбрано **5891 запросов (0,982%)**, записано **70 751 попытка и 283 004 события**. Ожидание по формуле — 288 000 событий. Одна строка содержит шесть int32 и время float64, то есть 32 байта числовой нагрузки; фактически 9 056 128 байт до служебных структур.

| Формат | Файл, MB | JVM, медиана, мс | Chromium, медиана, мс |
|---|---:|---:|---:|
| JSON + gzip | 2.250 | 260.7 | 49.6 |
| CSV | 11.313 | 44.0 | 110.1 |
| Arrow IPC Stream | 9.319 | 36.0 | 16.1 |
| Parquet + Snappy | 2.702 | 208.3 | 24.5 |
| JSON без сжатия | 11.879 | 43.0 | 37.1 |

Для 250 прогонов с теми же параметрами ожидается 72 млн событий и 2,304 GB числовой нагрузки. Простое умножение фактического файла даёт 0,563 GB для JSON + gzip и 0,676 GB для Parquet; эти 250 трасс не генерировались. При неизменных интенсивности и длине пути оценка одинакова для моделей из 50, 500 и 5000 листьев.

Чувствительность: если принять длину пути равной числу листьев, остальные параметры оставить прежними, несжатые 32-байтовые события займут **11,52 / 115,2 / 1152 GB** на сетку соответственно. Это сценарий оценки, не верхняя граница. Дополнительные события, fan-out, большие идентификаторы, атрибуты и более частые повторы увеличат объём. 32-байтовая строка прототипа не является утверждённым контрактом трассы продукта.

Реальная выборка должна определяться по корневому запросу независимо от RNG симуляции и сохранять всех потомков до drain, включая orphaned work. Нужны стабильный порядок событий с одинаковым временем, связи parent/attempt, различие timeout вызывающей стороны и завершения downstream. Для перемотки нужны начальное состояние либо checkpoint и события после него. Выборка 1% предназначена для объяснения отдельных путей; точные метрики и редкие отказы по ней восстанавливать нельзя.

## Свойства форматов и библиотеки

| Формат | Частичное чтение и передача | Отладка и ограничения |
|---|---|---|
| JSON + gzip | Отдельные законченные фрагменты; gzip распаковывается потоком, стандартный JSON parser ждёт целый документ | Читаемый после распаковки; минимум зависимостей. Нет произвольного доступа внутри обычного gzip-потока |
| CSV | Последовательный разбор строк; для выборки нужен индекс или отдельные файлы | Удобен для выгрузки, но типы, единицы и null policy вынесены в схему. Общий CSV требует полноценного parser |
| Arrow IPC Stream | Пакеты можно читать до окончания потока | Типизированные колонки и быстрый обход; несжатые данные занимают больше места. Бинарный файл требует reader |
| Parquet | Footer, затем нужные column chunks/row groups; HTTP Range | Сжатие и проекция колонок, но чтение незаконченного файла не эквивалентно Arrow Stream. Reader и кодек сложнее JSON |

Основания: [Arrow IPC](https://arrow.apache.org/docs/format/Columnar.html#ipc-streaming-format), [Parquet file layout](https://parquet.apache.org/docs/file-format/), [hyparquet API](https://github.com/hyparam/hyparquet/tree/v1.31.5), [gzip RFC 1952](https://www.rfc-editor.org/rfc/rfc1952), [CSV RFC 4180](https://www.rfc-editor.org/rfc/rfc4180).

Arrow IPC File имеет footer для произвольного доступа, однако стандартный [JS reader 21.2.0](https://github.com/apache/arrow-js/blob/v21.2.0/src/ipc/reader.ts) при чтении File через fetch загружает поток целиком. В опыте использован Stream. Встроенная [compressionRegistry](https://github.com/apache/arrow-js/blob/v21.2.0/src/ipc/compression/registry.ts) изначально пуста: сжатый IPC возможен после регистрации codec, но здесь не исследован. Внешний gzip для Arrow и CSV, Parquet с другими кодеками и WASM-reader не измерялись. Дополнительный формат не включён: четырёх требуемых достаточно для решения A7, а сравнение ещё одной библиотеки не устраняет необходимость порционной загрузки.

JVM-прототип использует `ExampleParquetWriter`, `LocalOutputFile` и `PlainParquetConfiguration`; это пример API для исследования. Стандартная [CodecFactory](https://github.com/apache/parquet-java/blob/apache-parquet-1.18.1/parquet-hadoop/src/main/java/org/apache/parquet/hadoop/CodecFactory.java) всё равно требует Hadoop Common. MapReduce для записи не понадобился. Arrow/Netty на JDK 25 потребовал явного доступа к `java.nio` и разрешения Unsafe; Snappy — native access. Флаги зафиксированы в отдельной сборке прототипа и не добавлены приложению.

## Стратегия больших моделей

**Разделение артефакта.** Манифест и общая сводка должны оставаться небольшими. Сводка для карты 5×5 содержит 25 результатов и статистику повторений; не следует помещать в неё подробные данные всех листьев. Таблицы разделяются по варианту, точке и повторению, затем по группам узлов и времени. Не создавать файл на каждый узел: для 5000 листьев и 250 прогонов это уже 1,25 млн файлов. Индексы разделов можно хранить рядом с ними, не перечисляя каждую строку в корневом манифесте.

**Семантика агрегации.** Составной блок показывает результаты на своих портах. Сумма leaf attempts повторно считает внутренние вызовы; сумма задержек неверна при перекрывающихся ожиданиях и fan-out. Доли объединяются через числитель и знаменатель; загрузка совместимых ресурсов — через busy-time/capacity-time; окна очередей — через интеграл и длительность. p99 нельзя усреднить: нужны исходные наблюдения либо сливаемое распределение с указанной погрешностью. Для анализа насыщения сохраняются экстремумы и сведения о конкретном ресурсе.

**Повторения и границы времени.** Сохранять различие pooled-распределения и статистики метрик независимых повторений, уже принятое в [MetricsAggregator.kt](../../core/src/main/kotlin/resiliencelab/core/experiment/MetricsAggregator.kt). Доверительные границы не обрезаются до физического диапазона. Событийные ряды по времени возникновения и метрики когорты по времени поступления имеют разные границы: run-out входит в исходы когорты, но не в временное среднее загрузки исходного интервала. Схема должна фиксировать это явно.

**Подгрузка и воспроизведение.** UI сначала получает общую сводку, затем выбранные узлы текущего уровня, метрики и диапазон времени. Результаты остальных повторений и ячеек не загружаются автоматически. Декодирование больших фрагментов следует вынести в Worker. Для масштаба экрана нужны агрегаты с сохранением min/max и границ переходов; простое «каждое десятое окно» может скрыть короткое насыщение. Исходные результаты остаются источником аналитических выводов. Ряды всех уровней не следует дублировать заранее: при неограниченной глубине это добавит множитель глубины; агрегаты можно материализовывать по мере запроса.

**Бюджеты вместо предела числа блоков.** Предлагаемые стартовые ориентиры для следующего дизайна: закрытые файлы до 64 MiB, row groups до 16 MiB, целевой ответ UI до 4 MiB и кэш декодированных данных порядка 64 MiB. Это параметры для последующей проверки интерфейса, не измеренные пределы и не запрет модели из большего числа блоков. Прототип не доказывает работу UI в таком бюджете памяти. Перед запуском показывать оценку строк, места и числа событий; уточнять коэффициент сжатия по первым завершённым разделам. При нехватке диска или превышении бюджета трассы — явная остановка либо согласованное сокращение детализации, с отметкой неполноты; молча усекать данные нельзя.

D3 сохраняется как переносимые файлы с относительными путями. Возможность удобного хранения всех крупных результатов обычным Git требует отдельного решения: [GitHub запрещает файлы больше 100 MiB](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github), а история многих гигабайт остаётся дорогой и при мелких файлах. Предложение: манифест, сводка и небольшие контрольные результаты в Git; крупные артефакты — отдельное файловое хранение либо явно выбранный Git LFS. Автоматически менять политику репозитория этим исследованием не предлагается.

## Рекомендация по A7

Принять структуру каталога; в ADR уточнить контракт:

```text
run/
  manifest.json
  summary.json
  series/cell-000/rep-000/part-000.parquet
  traces/cell-000/rep-000/part-000.parquet
  indexes/...
```

В манифесте нужны версия схемы, версии приложения и движка, модель и эксперимент либо их устойчивые хеши, seed/stream каждого повторения, координаты сетки, единицы и семантика метрик, интервалы, sampling и фактическая полнота, относительные пути и контрольные суммы завершённых разделов. Незавершённый артефакт не должен выглядеть готовым. Наличие этих полей здесь — рекомендация, не новая реализация API.

Parquet выбран за сочетание размера, стоимости записи и проверенного выборочного чтения в Chromium. JSON + gzip предпочтителен для небольшого читаемого экспорта; CSV — для внешнего анализа. Arrow не требуется добавлять в первый этап только ради хранения: его преимущество проявится при последовательной передаче и массовой обработке колонок, если последующий профиль UI подтвердит такую потребность.

Перед реализацией остаётся согласовать семантику окон, достаточные статистики для иерархии и квантилей, точный состав событий replay и политику хранения больших файлов. Полные сетки на 500/5000 листьев, реальная нагрузка KSL, удалённая сеть, случайный доступ по времени, память и отзывчивость готового UI остаются вне проверенного результата.
