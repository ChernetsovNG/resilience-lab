# S5: сливаемые скетчи задержек для рядов и сводки

Дата: 2026-10-28. Задача: [#67](https://github.com/ChernetsovNG/resilience-lab/issues/67). Статус: исследование и рекомендация для дорожки T1; код приложения не изменён.

## Рекомендация

Использовать `com.datadoghq:sketches-java:0.8.3` в ядре: отображение `BitwiseLinearlyInterpolatedMapping(6)` и небольшую обёртку с проверками. Для отдельных окон рекомендован штатный `SparseStore`, для pooled-сводок и слияния — `UnboundedSizeDenseStore`. Формат и точность у них одинаковы; скетчи разных хранилищ можно сливать. Для web достаточно собственного TypeScript-кода чтения и слияния целочисленных корзин. Готовый прототип находится в [research/latency-sketch](../../research/latency-sketch/).

Профиль `ddsketch-bitwise6-rational-v1` фиксирует шесть бит мантиссы, представителя корзины `lowerBound * 129/128`, отдельный точный ноль и интерполяцию квантилей KSL. Теоретическая относительная погрешность представителя не превышает `1/128 = 0,78125 %` с точностью округления binary64. Это оставляет запас до требуемого 1 %. Коэффициент намеренно задан точной двоичной дробью: штатный коэффициент DataDog вычисляется через `Math.exp`, для которого Java не обещает совпадение битов на всех JVM.

Канонические скетчи содержат только целые счётчики. Их слияние ассоциативно и коммутативно в указанном ниже диапазоне; порядок добавления, группировка по окнам, повторениям и узлам не меняют байты. Значения квантилей восстанавливаются одинаковыми двоичными операциями в JVM и Chromium. Внутренние массивы DataDog, суммы `Double` и формат Protobuf частью этого контракта не являются.

Основания и границы задачи: [дизайн этапа 1, §4.3](../superpowers/specs/2026-10-27-stage-1-design.md), [ADR 0008](../architecture/adr/0008-run-results.md), [D2 и D6](../architecture/2026-10-27-target-architecture.md), [ADR 0006](../architecture/adr/0006-random-streams-by-block-path.md). Предлагается выбор реализации скетча; семантика окон и разбиение частей ещё должны быть описаны в контракте T1.

### Почему не готовая пара Java/JS

В Java логарифмическое отображение использует `floor`-подобную индексацию и `log/exp`; JS 2.1.1 использует `ceil`, `log2/pow` и иначе вычисляет gamma. Поэтому совпадение точности не означает совпадение корзин и битов квантиля. Это видно непосредственно в [Java LogLikeIndexMapping](https://github.com/DataDog/sketches-java/blob/v0.8.3/src/main/java/com/datadoghq/sketch/ddsketch/mapping/LogLikeIndexMapping.java#L113-L125), [Java LogarithmicMapping](https://github.com/DataDog/sketches-java/blob/v0.8.3/src/main/java/com/datadoghq/sketch/ddsketch/mapping/LogarithmicMapping.java#L28-L35) и [JS mapping](https://github.com/DataDog/sketches-js/blob/v2.1.1/src/ddsketch/mapping/KeyMapping.ts#L50-L78).

Предлагаемый TS-код не зависит от DataDog JS и не вызывает трансцендентных функций для отображения. В JVM индекс и границы берутся из [bitwise-реализации 0.8.3](https://github.com/DataDog/sketches-java/blob/v0.8.3/src/main/java/com/datadoghq/sketch/ddsketch/mapping/BitwiseLinearlyInterpolatedMapping.java); представитель переопределён. В JS те же биты строятся через `DataView`. Применимость доказательства не зависит от совпадения реализаций [`Math.exp`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Math.html).

## Контракт профиля

### Отображение и точность

Для положительного нормализованного binary64 `x = 2^e * (1 + m)` берутся первые шесть бит мантиссы: `r = floor(64*m)`. Индекс `i = 64*e + r`; нижняя граница `L = 2^e * (1+r/64)`, представитель `v = L * 129/128`. При обратном преобразовании отрицательного индекса требуется `floor(i/64)`, а не деление с усечением к нулю.

Границы представлены точно. Отношение верхней границы к нижней не больше `65/64`. На нижнем краю ошибка представителя равна `1/128`; на верхнем она по модулю не больше `1/130`. Следовательно, во всей корзине ошибка не больше 0,78125 %, кроме обычного округления binary64. Представители возрастают с индексом. Нулевые значения имеют собственный счётчик и возвращают ровно `0`.

Поддерживаются `0` и положительные значения в диапазоне `[2^-1021, 2^1023)` во внутренних единицах задержки. Диапазон намного шире проверяемых `0,001–60 000 ms`. Отрицательные значения, `NaN`, бесконечности и положительные значения вне диапазона явно отклоняются. Это необходимо: штатный Java `accept` превращает слишком малые значения и даже `NaN` в нулевую корзину. [Проверяемый исходник](https://github.com/DataDog/sketches-java/blob/v0.8.3/src/main/java/com/datadoghq/sketch/ddsketch/DDSketch.java#L218-L259).

### Ограничения и слияние

- Общий count, включая нули, не больше `2^53−2 = 9 007 199 254 740 990`. Все веса — положительные целые. Верхняя граница оставляет точно представимым также `n+1` для интерполяции.
- Непустые положительные корзины имеют индексы от `−65344` до `65471`. Длина занятого диапазона `maxIndex−minIndex+1` не больше 2048; это ограничение диапазона, а не только количества непустых корзин.
- До добавления и слияния проверяются будущие count и диапазон. Ошибка оставляет принимающий скетч неизменным. Схлопывания, удаления хвоста и автоматического изменения точности нет.
- Сливаются только скетчи одного профиля и одной единицы измерения. Складываются счётчики одинаковых индексов и нулей; сериализация сортирует индексы и пропускает пустые корзины.

При этих условиях каждое сложение целых счётчиков точно и в `Long`, и в JavaScript `Number`, и в `double` хранилища DataDog. Все промежуточные суммы не больше итоговой. Поэтому любое дерево слияния допустимого набора даёт те же корзины, а их каноническая запись — те же байты. Перестановка наблюдений при сборе имеет то же свойство. Это доказательство относится к скетчу; временные замеры и сторонние поля артефакта в него не входят.

`UnboundedSizeDenseStore` округляет размер массива; при диапазоне 2048 его capacity может достигать 2112 `double`, то есть 16 896 байт только для положительного массива. Объекты и пустое отрицательное хранилище добавляются отдельно. [Правило роста DenseStore](https://github.com/DataDog/sketches-java/blob/v0.8.3/src/main/java/com/datadoghq/sketch/ddsketch/store/DenseStore.java#L219-L222). Штатные [collapsing stores](https://github.com/DataDog/sketches-java/blob/v0.8.3/src/main/java/com/datadoghq/sketch/ddsketch/store/CollapsingLowestDenseStore.java#L38-L81) переносят значения в крайнюю корзину и для этой гарантии не подходят.

2048 адресов покрывают примерно 32 двоичных порядка. При чрезмерном разбросе задержек T1 должен завершить расчёт с диагностикой, указывающей узел, окно и лимит, либо заранее выбрать другой версионированный профиль. Нельзя молча переключить точность в середине части. Разбиение файла не исправляет превышение диапазона у агрегата: после слияния ограничение проверяется снова.

### JSON

Профиль указывается один раз на часть. Каждое окно — плоский массив `[zeroCount,index,count,...]`, например:

```json
{"profile":"ddsketch-bitwise6-rational-v1","nodes":[{"id":"service-a","windows":[[2,0,3,64,5],[0]]}]}
```

В первом окне 2 нуля, 3 наблюдения в корзине 0 и 5 в корзине 64. `[0]` означает пустое распределение. Это сокращённый пример формы, а не измеренная часть. Полная часть стенда содержит 600 окон каждого узла. Путь: `series/<вариант>/<точка>/rep-<n>.json.gz`; границы окон, единицы и метод назначения наблюдений должны быть в манифесте. Вариант с индексами и counts в параллельных массивах не уменьшает число чисел; плоская запись убирает объект и имена полей на каждую корзину.

Читатель проверяет профиль, допустимость индексов, строгий порядок без повторов, целые counts и оба лимита. Канонический писатель использует десятичные целые без экспоненты и пробелов; `[0]` не заменяется на `null`. Пустой результат запроса квантиля — `null`, нулевая задержка — `0`.

Сливать можно непересекающиеся наборы наблюдений. Объединение задержек разных узлов даёт распределение посещений этих узлов, а не end-to-end latency клиента; нельзя одновременно включать агрегат родителя и его листья. Аналогично, `all` уже включает `successful` и `failed`.

## Сохранение семантики сводки

Текущий [MetricsAggregator](../../core/src/main/kotlin/resiliencelab/core/experiment/MetricsAggregator.kt) использует KSL `Statistic.percentile`: `pos=p*(n+1)`, крайние позиции ограничиваются min/max, остальные интерполируются между соседними порядковыми статистиками. DataDog использует ранг `p*(n−1)` и выбирает одну корзину. Ошибка между этими определениями может быть сколь угодно большой и не является погрешностью DDSketch.

Контрпример: 19 значений `1` и одно `1000`. KSL даёт p95 `950,05`, p99 `1000`. Штатный ранг DDSketch выбирает значение около `1` для обоих. Поэтому прототип извлекает из корзин две нужные порядковые статистики и применяет прежнее выражение KSL `a + fraction*(b−a)`. В вещественной арифметике выпуклая комбинация неотрицательных значений сохраняет относительную границу ошибки обоих представителей. В диапазоне задачи `0,001–60 000 ms`, включая точные нули, округление binary64 не исчерпывает запас до 1 %. Допустимы конечные `0<p<1`; пустой скетч возвращает `null`.

Расширенный диапазон принимаемых binary64-значений не означает относительной гарантии для subnormal-результата интерполяции. Например, `[0, 5.562684646268003e-308]` при `p=0.3333333333333334` даёт `1.5e-323` вместо `1e-323` в выражении KSL над исходными значениями. Это потеря относительной точности при округлении крайне малого результата, за пределами диапазона задержек задачи. Если T1 разрешит такие значения и потребует гарантии также для них, потребуется явный отказ при underflow либо более узкий диапазон входа; молча обещать 1 % для них нельзя.

Для T1 предлагается заменить списки задержек в [MetricsCollector](../../core/src/main/kotlin/resiliencelab/core/engine/ksl/MetricsCollector.kt) скетчами соответствующих популяций. `LatencySummary` сохраняет `all/successful/failed`; pooled p95/p99 вычисляются после слияния скетчей. `MetricsAggregator` по-прежнему отдельно строит `MetricSummary` по p95/p99 независимых повторений, с теми же формулами Стьюдента и без обрезания доверительных границ. Усреднять p99 для получения pooled p99 нельзя.

Среднее `meanMs` нельзя получать из представителей корзин без изменения его смысла. Count и сумма наблюдений должны храниться отдельно. Обычные суммы `Double` зависят от порядка: для них T1 должен закрепить порядок редукции частей либо отдельно реализовать точное суммирование. Побитовая коммутативность скетча не доказывает коммутативность floating-point sums. Статистическая неопределённость между повторениями также не исчезает: 0,78125 % — ошибка представления квантиля, а не доверительный интервал.

## Измерения

Измерения выполнены на Apple M4 Pro, 14 ядер, 48 GiB RAM, macOS 26.6.2 arm64, Microsoft OpenJDK 25.0.3, Kotlin 2.4.21, Gradle 9.8.2. Измеренный срез core — `7a469cdc770b901a99ea5c66669134b4909919ff`; конкретные исходники стенда и JAR зафиксированы хешами. Chromium 156.0.8078.4 запущен через Playwright 1.64.1, Node 26.12.1. JVM: `-Xms512m -Xmx4g -XX:+UseG1GC`; фоновые процессы не изолировались. Время зависит от машины, JIT и GC: воспроизводятся проверки и хеши содержимого, а не наносекунды.

Сохранены [исходные измерения](../../research/latency-sketch/results/2026-10-28/), включая все trials, окружение, хеши исходников и JAR. Большие части, трасса и входные fixtures в git не добавляются: команды создают их заново в `build/`.

### Точность и воспроизводимость

Проверены 28 сочетаний данных и реализации, по 1007 вероятностей в каждом: нули, singleton, фиксированная задержка, разрыв распределения, смесь `0,001–60 000 ms` и значения непосредственно до/на/после двоичных границ корзин. Максимальная наблюдаемая ошибка portable-профиля — 0,7812500000000134 %, логарифмических вариантов — 1,0000000000000009 %; последние цифры отражают округление binary64. Проверка допускает только `1e-12` абсолютного запаса к относительной границе 0,01.

120 000 значений разделены на 600 окон; сравниваются прямой сбор, обратный порядок наблюдений, 14 порядков слияния и два дерева группировки, включая узлы и повторения. Окна чередуют SparseStore и DenseStore. Канонический JSON совпал. Проверки также подтвердили атомарный отказ при неверных значениях, превышении диапазона корзин и count, несовместимом отображении. Повторный запуск той же JVM-программы дал одинаковые байты `selected-ui.json`, gzip, отчёта точности и проверок.

Chromium заново собирает скетчи из тех же исходных значений: совпали канонические массивы и все 64 бита квантилей в 26 случаях, включая 18 распределений настоящего `retry-storm`. Прямое, обратное, случайное и сбалансированное слияние 600 окон проверяется в каждом измерении. Это измеренная межплатформенная проверка на указанной JVM/Chromium; доказательство переносимости опирается на целые counts, фиксированные биты границ и одинаковые binary64-операции.

| kotlin-log | 111.85 | 81.85–1111.83 | 897 | 71864 |

`java-portable` использует DenseStore; `java-portable-sparse` — SparseStore с тем же отображением; `java-log` — штатный логарифмический DDSketch; `kotlin-log` — собственный логарифмический вариант с TreeMap. Это сравнение конкретных реализаций, не верхняя оценка скорости всех возможных Kotlin-реализаций.

JOL 0.17 оценивает размер достижимого графа объектов через layout JVM. Dynamic Attach и Serviceability Agent отключены, поскольку на этой macOS подключение зависало. Числа включают контейнеры и массивы, но не являются peak heap/RSS и не учитывают последующую работу GC. Для рядов JOL измеряет первые пять узлов в лексикографическом порядке с их 600 слотами; общие объекты внутри выборки учитываются один раз.

### Реальная нагрузка S1

Стенд исполняет неизменённую модель [S1](2026-10-27-ksl-capabilities.md) при 50, 500 и 5000 ресурсах, 60 000 и 400 000 исходных запросах. Включена полная трасса, из пар `queue/acquire/release` извлекается фактическая задержка посещения `release−queue`, в условных единицах времени S1. На запрос приходится шесть посещений пяти ресурсов: worker вызывающей стороны занимается дважды. Проверены завершение модели, соответствие событий и ровно `6*N` наблюдений.

В этом наборе окно определяется когортой исходного запроса: `floor(requestOrdinal*600/N)`. Все посещения из run-out сохраняются. Это способ разбить данные для сравнения скетчей; он не утверждает будущую семантику временных окон T1 и не заменяет временные средние TimeSeriesResponse. В S1 было 100 окон средних; здесь требуемые issue 600 окон задержек.

Генерация и разбор трассы исключены из таймера записи. Записанные наблюдения проигрываются в оконные скетчи: два прогрева, пять измерений; один узел из 600 слотов одновременно. Таймер включает создание коллектора, выбор окна и добавление, исключает хеширование, сериализацию и JOL. Поэтому это стоимость оконного сбора на реальных данных S1, а не измеренный процент замедления движка при подключении сборщика.

| Ресурсов | Запросов | Наблюдений | Пустых окон | Dense, ns/набл. | Sparse, ns/набл. | Свой log, ns/набл. |
|---:|---:|---:|---:|---:|---:|---:|
| 50 | 60000 | 360000 | 0 | 38.52 | 37.51 | 58.03 |
| 50 | 400000 | 2400000 | 0 | 10.37 | 59.94 | 75.89 |
| 500 | 60000 | 360000 | 0 | 66.97 | 38.48 | 26.50 |
| 500 | 400000 | 2400000 | 0 | 25.59 | 35.39 | 41.23 |
| 5000 | 60000 | 360000 | 2700000 | 62.82 | 40.94 | 27.60 |
| 5000 | 400000 | 2400000 | 1000000 | 55.67 | 38.84 | 27.07 |

Средний размер графа объектов на слот «узел × окно», включая пустые слоты:

| Ресурсов | Запросов | Dense, байт/слот | Sparse, байт/слот | Свой log, байт/слот |
|---:|---:|---:|---:|---:|
| 50 | 60000 | 1168.03 | 966.71 | 518.97 |
| 50 | 400000 | 1212.06 | 3637.50 | 1671.42 |
| 500 | 60000 | 715.76 | 301.17 | 140.80 |
| 500 | 400000 | 1103.17 | 730.23 | 388.95 |
| 5000 | 60000 | 75.19 | 34.49 | 18.41 |
| 5000 | 400000 | 478.13 | 202.50 | 95.52 |

Для одного узла со всеми 600 окнами соответствующее значение умножается на 600. Например, при 5000 ресурсах/400 000 запросов это около 280 KiB для Dense и 119 KiB для Sparse. Разреженные окна поддерживают выбор SparseStore; плотные окна на 50 ресурсах выгоднее хранить в DenseStore. Собственный log-код ещё компактнее на малых выборках, но не решает задачу побитового межплатформенного отображения через `log/exp`. Выбор библиотеки опирается на готовые проверенные хранилища и bitwise-отображение, а не на обещание минимальной памяти во всех режимах.

Границы памяти должны учитывать число одновременно незавершённых окон. Хранить 5000 × 600 JVM-скетчей до конца расчёта не рекомендуется: даже Sparse в измеренном случае даёт порядок 580 MiB только по экстраполяции пяти узлов. Это не измеренный heap всей модели. Окна нужно выгружать после закрытия согласно будущей семантике T1; число ещё открытых окон и общий бюджет проверяются отдельно. Лимит 2048 адресов ограничивает один скетч, но не сумму всех скетчей.

### Размер частей и бюджеты

Ниже фактически записанные части **только скетчей задержки**; счётчики остальных метрик, манифест и индексы добавят объём. 1 MiB = 1 048 576 байт. В каждой части 600 окон на узел, включая `[0]`; JSON записывается потоком, затем gzip.

| Ресурсов | Запросов S1 | JSON, MiB | gzip, MiB | JSON, байт/узел/окно |
|---:|---:|---:|---:|---:|
| 50 | 60000 | 1.969 | 0.407 | 68.82 |
| 50 | 400000 | 8.538 | 1.609 | 298.42 |
| 500 | 60000 | 3.150 | 0.540 | 11.01 |
| 500 | 400000 | 13.835 | 2.930 | 48.36 |
| 5000 | 60000 | 13.593 | 0.725 | 4.75 |
| 5000 | 400000 | 24.871 | 4.201 | 8.69 |

Отдельный стресс-набор заполняет каждое окно 16 корзинами с различающимися индексами и counts, диапазон охватывает около 24 двоичных порядков. Это синтетический JSON-тест бюджета, а не ещё один запуск S1:

| Узлов × 600 окон | JSON, MiB | gzip, MiB | JSON, байт/окно |
|---:|---:|---:|---:|
| 50 | 3.778 | 1.512 | 132.06 |
| 500 | 37.785 | 15.104 | 132.07 |
| 5000 | 377.851 | 151.030 | 132.07 |

Все части S1 укладываются в 64 MiB и до, и после gzip. Однако при 5000 ресурсах/400 000 запросов уже gzip занимает 4,201 MiB и превышает ответ UI 4 MiB. Стресс-набор на 5000 узлах занимает 151,030 MiB gzip, поэтому превышает также бюджет части 64 MiB. Размер нельзя оценивать только числом узлов: важны заполненность, разброс и counts. Один полный файл повторения нельзя всегда отправлять UI целиком.

ADR 0008 не уточняет, относится ли бюджет к сжатому представлению. Поэтому показаны оба размера. Рекомендация для T1: ограничивать распакованную часть 64 MiB и ответ UI 4 MiB до сжатия, отдельно учитывать передаваемые байты; это более строгая трактовка до уточнения контракта. Делить по группам узлов и диапазонам окон, считать фактические байты при записи, останавливать расчёт явно, если не помещается даже минимальная часть. Простое уменьшение числа корзин уничтожило бы гарантию точности.

Кэш браузера 64 MiB требует отдельного учёта декодированных объектов: размер gzip не равен памяти Map/массивов. Полный UI, Web Worker и eviction-кэш этим прототипом не измерены; полученные размеры и времена задают входные данные для их реализации.

### Chromium: 600 окон

Набор для UI содержит 120 000 наблюдений широкого диапазона, 600 окон: 667 237 байт JSON и 202 862 байта gzip. Данные загружены до таймеров, затем выполнены два прогрева и семь измерений. Loopback-сервер включает COOP/COEP для точного `performance.now`; headless Chromium исполняет настоящий TypeScript, скомпилированный в JavaScript.

| Фаза | Медиана, ms | Min–max, ms |
|---|---:|---:|
| JSON.parse | 0.635 | 0.595–0.720 |
| Проверка и декодирование 600 скетчей | 2.720 | 2.630–3.290 |
| Слияние 600 окон | 2.215 | 2.105–2.295 |
| Восемь квантилей | 0.940 | 0.815–1.510 |
| Слияние и восемь квантилей | 3.160 | 3.045–3.700 |
| gzip и декодирование UTF-8 | 1.680 | 1.525–2.030 |

Сериализация результата и сравнение с JVM находятся вне таймеров. Распаковка использует штатный `DecompressionStream('gzip')`; её фаза включает создание Blob и чтение UTF-8. Таблица не является измерением HTTP, отрисовки графика или работы Web Worker.

### Настоящий retry-storm

Пример загружен через `DocumentCodec`, скомпилирован `ModelCompiler` и выполнен `ExperimentExecutor` с исходными seed, вариантами и двумя повторениями. Списки задержек получены непосредственно из результатов core; `examples/` не менялся. Проверены all/successful/failed каждого повторения и pooled-распределения, всего 18 распределений.

| Вариант / повторение | Точный p95, ms | Скетч p95, ms | Точный p99, ms | Скетч p99, ms |
|---|---:|---:|---:|---:|
| baseline / 1 | 250.000000 | 251.953125 | 250.000000 | 251.953125 |
| baseline / 2 | 250.000000 | 251.953125 | 250.000000 | 251.953125 |
| no-retries / 1 | 233.311775 | 234.014062 | 250.000000 | 251.953125 |
| no-retries / 2 | 130.206002 | 131.015625 | 157.562707 | 158.468438 |

Максимальная ошибка сохраняющего KSL-интерполяцию профиля на этих распределениях — 0,78125 %. Штатный DDSketch-ранг у `no-retries`, повторение 2, даёт p99 `149,15625 ms` вместо `157,562707 ms`: отличие 5,3353 %. Таким образом, сохранять соглашение о квантиле нужно даже на текущем примере.

Межповторительный `MetricSummary` меняется вслед за приближёнными p95/p99. Например, средний p95 `no-retries` меняется с `181,758888` на `182,514844 ms`; его 95 % интервал — с `[-473,282642; 836,800419]` на `[-471,844773; 836,874461] ms`. Формула и отсутствие обрезания сохранены; большой интервал связан с двумя независимыми повторениями. Полные signed deltas, pooled и outcome-разделения лежат в `retry-storm.json`. Оценка 0,78125 % относится к самим квантилям, не к относительному изменению границ доверительного интервала.

## Воспроизведение

Нужны JDK 25, Python 3 и Node из `web/.nvmrc` (в измерении 26.12.1). Из корня репозитория:

```bash
./gradlew -p research/latency-sketch installDist
cd research/latency-sketch/browser
fnm exec --using 26.12.1 npm ci
fnm exec --using 26.12.1 npm test
fnm exec --using 26.12.1 npx playwright install chromium
cd ../../..
fnm exec --using 26.12.1 python3 research/latency-sketch/run.py --output research/latency-sketch/build/reproduced
./gradlew clean build
```

Вместо `fnm exec` можно заранее выбрать ту же версию Node через nvm; сами команды npm/node/python остаются обычными. При уже установленном соответствующем Chromium установка не нужна. Каталог `--output` должен быть новым. Проверки завершаются ненулевым кодом при расхождении; только после всей матрицы появляется `verification.txt` с PASS.

Полная матрица последовательно запускает отдельные JVM для точности, retry-storm, трёх микроизмерений, шести конфигураций S1 и размеров, затем Chromium. Heap ограничен 4 GiB; полная трасса 400 000 запросов содержит 8,4 млн записей и нужна только при подготовке данных. Gzip стресс-набора на 5000 узлах занимает около 151 MiB на диске. Времена, порядок измерений и область каждого таймера зафиксированы в JSON; stdout/stderr сохраняются в log рядом с ним.

Для повторной побайтовой проверки небольшого набора:

```bash
research/latency-sketch/build/install/latency-sketch/bin/latency-sketch verify research/latency-sketch/build/repeat
cmp research/latency-sketch/build/reproduced/selected-ui.json research/latency-sketch/build/repeat/selected-ui.json
cmp research/latency-sketch/build/reproduced/selected-ui.json.gz research/latency-sketch/build/repeat/selected-ui.json.gz
```

Основная сборка, TypeScript и проверки прототипа выполнены успешно. Исследование не меняет `core/`, `apps/`, `web/`, основной Gradle-конфиг, ADR или дизайн. Автоматическая интеграция скетча, API рядов, закрытие окон и ограничение полного артефакта остаются работой T1 по этой рекомендации.
