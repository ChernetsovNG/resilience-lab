# KSL: возможности и стоимость расчёта целевой модели

Дата: 2026-10-27. Исследование [S1, issue #46](https://github.com/ChernetsovNG/resilience-lab/issues/46). Статус: рекомендация для A4, архитектурное решение ещё не принято.

## Рекомендация

**KSL остаётся с оговорками.** `KSLCore:R1.8.1` позволяет выразить фазовое удержание ресурсов, блокирующее и неблокирующее исполнение, параллельные обращения с общим таймаутом и продолжением downstream-работы, оконные ряды и выборочную трассу. Прототип и проверки находятся в [research/ksl-capabilities](../../research/ksl-capabilities/).

На измеренной машине модель из 5000 листовых ресурсов выполнила 7,2 млн событий за 7,269 с внутри симуляции; полное измеренное выполнение заняло 7,308 с. Восемь независимых повторений на восьми потоках ускорились в 3,184 раза относительно одного потока. Эти результаты позволяют продолжить работу с KSL; оснований менять движок в S1 не обнаружено.

Оговорки относятся к предметному адаптеру и масштабу измерений: прекращение ожидания должно сохранять downstream-процессы; случайные потоки принадлежат отдельной модели; оконные ряды занимают память пропорционально числу узлов и окон; штатный формат трассы требует преобразования для браузера. Производительность произвольных графов, насыщенных очередей и retry storm этим стендом не определена.

## Возможности и идиомы

### Фазы и ресурсы

В `Entity.process {}` allocation живёт до явного `release`, в том числе во время `delay`, ожидания другого ресурса или сигнала. Для блокирующей модели caller захватывает worker перед первой фазой и освобождает после последней. Для неблокирующей освобождает worker перед I/O и снова получает его для завершающей вычислительной фазы:

```kotlin
val worker = seize(workers)
delay(preCompute)
release(worker)
val connection = seize(connections)
delay(databaseTime)
release(connection)
val continuationWorker = seize(workers)
delay(postCompute)
release(continuationWorker)
```

Это фрагмент процесса; полный выполняемый вариант находится в `CapabilityModel.Request.run`. Используются симуляционные `delay` и `schedule` KSL. Обычный coroutine `withTimeout` отсчитывает реальное время и здесь не подходит. [Контракт операций с ресурсами](https://github.com/rossetti/KSL/blob/928d324c498b25102be3b718af4b1d83c7ad72e8/KSLCore/src/main/kotlin/ksl/modeling/entity/KSLProcess.kt#L712).

В детерминированной проверке занятость worker составляет 8 единиц времени для блокирующего caller и 2 для неблокирующего; локальное соединение в обоих случаях занято с `t=1` до `t=5`. Два одновременных запроса с одним worker завершаются к `t=16` и `t=12` соответственно. Dependency B в прототипе намеренно удерживает свой worker во время собственного I/O: внутри одной модели смешиваются обе схемы исполнения.

### Fan-out и timeout

Обычное ожидание всех ответов:

```kotlin
activate(a.run)
activate(b.run)
blockUntilAllCompleted(setOf(a.run, b.run))
```

Операция `blockUntilAllCompleted` требует заранее активировать детей и не принимает timeout. Для ограниченного ожидания прототип использует один `Signal` на модель, счётчик оставшихся ответов и флаг закрытия на запрос:

```kotlin
fun finishJoin(timeout: Boolean) {
    if (closed) return
    closed = true
    timedOut[ordinal] = timeout
    joinSignal.signal(this)
}
```

Последний ответ вызывает `finishJoin(false)`, событие общего таймаута вызывает `finishJoin(true)`. Флаг меняется до сигнала, поскольку `signal` планирует отдельное событие возобновления. Таймер имеет `KSLEvent.LOW_PRIORITY`: завершение обоих детей ровно на deadline успевает раньше таймаута. Отдельный тест подтверждает один исход и одно возобновление.

Дети продолжают работу и освобождают свои allocation после таймаута. В одном тесте клиент заканчивает при `t=8`, поздний ребёнок при `t=9`. В другом timeout равен нулю: все три клиента заканчивают при `t=0`, принятые дети остаются в очередях и полностью завершаются к `t=12`. Проверка окончания требует всех клиентов, обоих детей каждого запроса, пустых очередей и свободных ресурсов.

Для этой семантики нельзя заменять таймаут завершением связанного процесса: KSL умеет каскадно завершать вызванные процессы и ожидающие completion listeners. [Fan-in](https://github.com/rossetti/KSL/blob/928d324c498b25102be3b718af4b1d83c7ad72e8/KSLCore/src/main/kotlin/ksl/modeling/entity/ProcessModel.kt#L2123), [Signal](https://github.com/rossetti/KSL/blob/928d324c498b25102be3b718af4b1d83c7ad72e8/KSLCore/src/main/kotlin/ksl/modeling/entity/Signal.kt#L38), [ветка завершения процесса](https://github.com/rossetti/KSL/blob/928d324c498b25102be3b718af4b1d83c7ad72e8/KSLCore/src/main/kotlin/ksl/modeling/entity/ProcessModel.kt#L3296).

### Оконные ряды и трасса

Прототип использует штатный сборщик:

```kotlin
TimeSeriesResponse(
    this,
    periodLength = observationEnd / windows,
    numPeriods = windows,
    responses = resources.flatMap { listOf(it.numBusyUnits, it.waitingQ.numInQ) }.toSet(),
)
```

Для `TWResponse` значение окна равно интегралу по времени, делённому на длительность окна. Для `Response` это среднее наблюдений, для `Counter` приращение счётчика. Для пустого окна `Response` может вернуть `null`. `defaultStartTime` позволяет начать после warm-up; незавершённое окно не попадает в результат. [Реализация TimeSeriesResponse](https://github.com/rossetti/KSL/blob/928d324c498b25102be3b718af4b1d83c7ad72e8/KSLCore/src/main/kotlin/ksl/modeling/variable/TimeSeriesResponse.kt#L247).

В измерениях собираются 100 окон на интервале поступления запросов, по два ряда на ресурс. Последующая доработка уже принятой работы входит во время симуляции, исходы и трассу, но находится за пределами этих окон. При 5000 ресурсах получается 1 000 000 записей окон на повторение. Штатный сборщик сохраняет их в памяти; формат потоковой выгрузки и агрегация по уровням остаются задачей A7/S3.

Трасса прототипа записывает прибытие исходного запроса, вход в очередь, захват и освобождение ресурса, результат ожидания и завершение клиента. Детерминированное смешивание request ID выбирает около 1% запросов вместе со всеми их детьми. Выборка не обращается к RNG симуляции и не совпадает по периоду с round-robin распределением запросов между подсистемами. Поля CSV: `request,node,action,time`. Записи сначала собираются в памяти, затем экспортируются; streaming backpressure здесь не измерен. В точках изменения состояния вызывается небольшой предметный сборщик:

```kotlin
if (sampled.isNotEmpty() && sampled[request]) {
    trace.add(TraceRow(request, node, action, time))
}
```

В R1.8.1 уже есть `AnimationCapture.toFile`, `CaptureSpec` и выбор элементов модели, повторений и окна времени. Отдельный тест записывает штатную трассу и проверяет события процессов и ресурсов:

```kotlin
AnimationCapture.toFile(model, tracePath).use { model.simulate() }
```

Для выборки связанных запросов штатного фильтра по элементам недостаточно. Кроме того, в проверенном коротком native trace 39 из 210 строк содержали `NaN` или `Infinity`: сериализатор KSL разрешает специальные значения с плавающей точкой. Такой поток нельзя напрямую передать в браузерный `JSON.parse`; необходима нормализация нечисловых значений или предметный формат. Источник: `ksl/animation/AnimationEvent.kt:1041–1055` и `ResponseAnimationEmitter.kt:67–78` в указанном source JAR. Библиотека в исследовании не исправлялась.

## Методика измерений

Стенд — отдельный Gradle-проект, не включённый в `settings.gradle.kts` основной сборки. В каждом повторении создаётся свежая модель. Шаблон подсистемы содержит пять листьев: пул caller workers, локальный пул соединений, workers зависимостей A и B, пул соединений B. Разворачивание 10/100/1000 экземпляров даёт 50/500/5000 ресурсов. Все участвуют в обработке. Лист здесь означает примитив ресурса; составной сервис может содержать несколько таких листьев.

Поступление открытое и детерминированное: запросы назначаются подсистемам по кругу, каждая получает запрос раз в пять единиц симуляционного времени. Вместимость каждого ресурса — 4. Базовые длительности фаз: caller compute 0,25; caller DB 0,75; A 1; B compute 0,5; B DB 2; caller postcompute 0,25. Каждая длительность независимо умножается на равномерную величину из `[0,5; 1,5)`. Timeout fan-out — 1,5. Это малоконфликтная синтетическая нагрузка; очередь и насыщение отдельно проверены только семантическими тестами.

На один запрос в baseline приходится 18 выполненных событий KSL: arrival, три активации процессов, шесть seize-yield, шесть delay, timer и возобновление join. Guarded timer исполняется и после успешного join. Для 60 000 / 400 000 запросов получаются 1,08 / 7,2 млн событий. Один общий `TimeSeriesResponse` добавляет 101 событие независимо от числа рядов. Пропускная способность ниже рассчитана по фактически выполненным `Executive.numEventsExecuted`, не по числу запланированных событий.

Матрица содержит 17 конфигураций, каждую в трёх свежих JVM с циклическим сдвигом порядка. Перед измерением выполняются два прогрева по 50 000 запросов с тем же размером модели и режимом записи, включая экспорт и хеширование. Затем вызывается `System.gc()` вне измеряемого интервала. Всего измерены 51 запуск JVM и 135 повторений; прогрев в эти числа повторений не включён. Калибровочная точка 500 блоков / 200 000 запросов не используется для подбора коэффициентов.

| Окружение | Значение |
|---|---|
| CPU | Apple M4 Pro, 14 физических/логических ядер |
| RAM | 48 GiB |
| ОС | macOS 26.6.2, arm64 |
| JDK | Microsoft OpenJDK 25.0.3+9-LTS |
| Kotlin / KSL / Gradle | 2.4.21 / R1.8.1 / Wrapper 9.8.2 |
| JVM | `-Xms512m -Xmx2g -XX:+UseG1GC` |
| Питание | AC; фоновые процессы и температура не изолировались |

`simulation_ms` измеряет `Model.simulate()`. `batch_ms` включает создание моделей, расчёт, проверку окончания, сбор результатов, экспорт, проверку SHA-256 и работу пула потоков. JVM startup и прогрев исключены из обоих времён. В CSV отдельно сохранены build, collection, write и file-hash timings; суммы фаз могут немного отличаться от batch из-за служебной работы.

Пиковая используемая heap измеряется через `MemoryMXBean` каждые 10 мс: короткий пик может быть пропущен. Peak RSS берётся из `/usr/bin/time -l` вокруг отдельного JVM-процесса и включает startup и прогрев; на данной macOS единица исходного значения — байт. Пики разных memory pools не складываются. Значения GC count/time также сохранены. [Семантика heap usage](https://docs.oracle.com/en/java/javase/25/docs/api/java.management/java/lang/management/MemoryUsage.html), [измерение elapsed time](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html#nanoTime()), [обоснование отдельных JVM forks](https://github.com/openjdk/jmh/blob/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_12_Forking.java).

Выборка сохранила 13 188 событий трассы для 60 000 запросов и 86 121 для 400 000.

### Параллельные повторения

Во всех строках одинаковый объём: восемь независимых повторений по 500 листьев и 60 000 запросов, всего 8,64 млн событий. `workers` ограничивает число одновременно выполняемых моделей. События внутри одной модели исполняются последовательно.

| Потоков | Полное время batch, с | Диапазон трёх JVM, с | Ускорение | Эффективность | Peak RSS, MiB |
|---:|---:|---:|---:|---:|---:|
| 1 | 3,596 | 3,349–3,778 | 1,000× | 100,0% | 498 |
| 2 | 2,141 | 1,983–2,296 | 1,679× | 84,0% | 503 |
| 4 | 1,400 | 1,378–1,515 | 2,569× | 64,2% | 651 |
| 8 | 1,129 | 0,966–1,161 | 3,184× | 39,8% | 837 |

Каждому повторению заранее назначен logical replication ID. Свежая `Model` получает seed `[12345,12345,12345,12345,12345,12345]`; все streams создаются до `simulate`, затем `numberOfStreamAdvancesPriorToRunning = replication - 1` выбирает независимый substream. Номер потока в seed не входит. Использованы отдельные JVM RNG providers модели, без изменения `KSLRandom.DefaultRNStreamProvider`.

SHA-256 включает биты времени окончания каждого клиента, каждого из двух детей и исход timeout; сравнивается отдельно по replication ID. Все совпадения между worker counts, повторными JVM и режимами записи проверены автоматически. Для больших batch проверен baseline; равенство всех рядов и событий трассы на 1/2/4/8 потоках проверено отдельным тестом на восьми повторениях по 500 запросов. Глобальные QObject IDs KSL в экспорт не попадают: при параллельном исполнении они зависят от порядка выдачи. Нельзя переносить полученную воспроизводимость на совместное использование одной модели или одного RNG несколькими потоками.

## Оценка стоимости для интерфейса

Для этой малоконфликтной модели baseline число событий точно `E = 18N`. По двум измеренным размерам нагрузки построена линейная оценка полного времени одного повторения:

`T_one(B, E) = a_B + b_B × (E / 10⁶)`, время в секундах.

| 500 | 0,012782 | 0,408272 |
| 5000 | 0,080353 | 1,003791 |

Коэффициенты включают измеренные накладные расходы harness, поэтому `a_B` не следует трактовать как чистую стоимость построения графа. В отложенной точке 500 листьев / 200 000 запросов прогноз равен 1,483 с, измеренная медиана 1,544 с: ошибка −4,0%. Диапазон измерений этой точки — 1,424–1,682 с.

Для нового сценария оценивать события следует по параметрам нагрузки и маршрутам:

```text
N ≈ суммарная интенсивность входов × (warmup + измеряемая длительность)
E ≈ N × Σ(ожидаемые посещения примитива на исходный запрос × события на посещение)
    + события таймеров, повторов, пробуждения очередей и наблюдателей
T_experiment ≈ (число вариантов × число повторений / S(workers))
               × [T_one(B, E) + стоимость выбранного режима записи]
```

Ожидаемые посещения включают fan-out, retry amplification и всю принятую orphaned work, в том числе после конца подачи нагрузки. Число 18 относится только к данному шаблону. Для произвольного графа эти коэффициенты нужно получить коротким пробным запуском, который одновременно оценивает число событий, живую очередь и объём данных. Ряды растут как `число метрик × B × число окон`, трасса как `доля выбранных запросов × N × событий трассы на запрос`; запись на диск добавляется к сбору. В текущих anchors поправки полного времени для рядов/трассы/обоих режимов равны соответственно 0,180 / 0,017 / 0,446 с при 500 листьях и 0,497 / 0,014 / 0,508 с при 5000. Значения для трассы находятся на уровне шума.

`S(1/2/4/8) = 1 / 1,679 / 2,569 / 3,184` измерено только для batch из восьми повторений по 500 листьев / 60 000 запросов. Перенос на иное число повторений, размеры графа и запись больших рядов требует повторной калибровки. При числе задач меньше workers лишние потоки не дают полезной работы.

Для предупреждения UI можно начать с диапазона ±25% вокруг оценки на этой машине и в измеренном диапазоне baseline: он покрывает эти наблюдения, включая выброс около +20%. Это инженерный запас, не доверительный интервал и не гарантия. Для другого оборудования, насыщения, больших календарей событий, глубоких маршрутов и объёма данных за пределами измерений нужен новый pilot. Экстраполяция за 5000 листьев без замера не обоснована.

## Воспроизведение и проверки

Нужны JDK 25, Python 3, `/usr/bin/time` и зависимости Gradle из Maven Central. Команды из корня репозитория:

```bash
./gradlew -p research/ksl-capabilities test installDist
python3 research/ksl-capabilities/run_benchmarks.py --output research/ksl-capabilities/build/reproduced
./gradlew clean build
```

Каталог `--output` должен быть новым: команда не перезаписывает предыдущие измерения. Полная матрица использует до восьми потоков в одной JVM с heap до 2 GiB; JVM-конфигурации запускаются последовательно. После успешного окончания появляются `measurements.csv`, `replications.csv`, `medians.csv`, `environment.json` и `verification.txt`. В подкаталогах остаются сырые `/usr/bin/time`, JVM metadata, stdout и экспортированные ряды/трассы. Прерывание или несовпадение хешей завершает команду с ошибкой; частичные CSV не считаются полным результатом.

Для одиночной конфигурации после `installDist`:

```bash
java -Xms512m -Xmx2g -XX:+UseG1GC \
  -cp 'research/ksl-capabilities/build/install/ksl-capabilities/lib/*' \
  resiliencelab.research.ksl.BenchmarkKt 5000 60000 both 1 1 2 \
  research/ksl-capabilities/build/single
```

Аргументы: листья, запросы, `none|series|trace|both`, workers, повторения, прогревы, каталог результата. Один simulation ограничен десятью минутами реального времени; проверка полного завершения обнаружит незаконченный расчёт.

В сохранённых результатах приведены строки всех запусков и повторений, медианы и окружение. `source-sha256.txt` и `jars-sha256.txt` фиксируют измеренный прототип и JAR-файлы: base revision относится к основной сборке до добавления spike и сам по себе не идентифицирует исследовательский код. Из сведений о питании для публикации оставлен только источник AC.

Проверки прототипа: 9 тестов, 0 ошибок. Они покрывают фазовое удержание, обычный fan-in, одновременные ответы на deadline, нулевой timeout с ожидающими детьми, отличие блокирующего и неблокирующего caller, неизменность исходов при наблюдении, распределение выборки между подсистемами, точную воспроизводимость и native capture. Основная `./gradlew clean build` прошла; основной JVM-код и build-файлы этим исследованием не меняются.

Для A4 достаточно сохранить KSL и отдельно спроектировать предметный адаптер взаимодействий, стабильные идентификаторы результатов и ограничение объёма рядов. Переход на другой движок потребовал бы новых доказательств преимуществ на целевом сценарии; S1 такого основания не дал. Утверждение A4 и merge PR остаются за автором проекта.
