# AGENTS.md

## Текущее состояние

Текущий срез включает модули `core`, `apps:cli`, `apps:server` и `web`:

- `core` — фундамент этапа 1: каталог типов, документы рабочей области и их JSON-схемы, компилятор в IR, линтер схемы, KSL-симуляция с потоками по путям блоков, сетку параметров по одной или двум осям, исполнение задач с чередованием заданий и отменой, оконные ряды со скетчами задержек, артефакты прогонов и фасад `Lab`.
- `apps:cli` — команды `validate`, `run [--workers N]`, `catalog` и `schema <model|layout|experiment>`, собираемые с помощью Gradle `application`.
- `apps:server` — Spring Boot API этапа 1 (каталог, документы рабочей области, проверка, задания, прогоны) со спецификацией `apps/server/openapi.json`; задания хранятся process-local.
- `web` — Vite/React SPA этапа 1: экран без прокрутки, редактор структуры и раскладки на React Flow (палитра, порты по каталогу, каскадные удаление и переименование, копирование, мультивыделение, миникарта и сетка), правка ключевых параметров узлов и связей на схеме, инспектор параметров из каталога с командами и undo/redo, сохранение изменённых документов модели, раскладки и эксперимента с `If-Match`, правка переопределений и управление вариантами, общие настройки прогона и отказов, проверка черновиков с диагностикой на схеме, у полей и в Problems, запуск задания и сводка; типы API генерируются из `apps/server/openapi.json`.

Сквозной срез этапа 1: реальный Chromium-сценарий открывает пример рабочей области, меняет параметр, сохраняет модель, запускает эксперимент и видит сводку без mock API.

## Стандартные команды сборки и проверки

Gradle-команды выполняются из корня репозитория, команды web — из каталога `web`; для всех JVM-модулей требуется JDK 25 (`jvmToolchain(25)`), для web — версия Node.js из `web/.nvmrc` и npm из её комплекта.

В каталоге `web/` выполните `nvm install && nvm use` или `fnm install && fnm use`: версия будет взята из `.nvmrc`.

- `./gradlew test` — все JVM-тесты.
- `./gradlew clean build` — чистая полная сборка и все доступные JVM-проверки.
- `./gradlew :core:test` — тесты модуля `core`.
- `UPDATE_SCHEMAS=1 ./gradlew :core:test --tests 'resiliencelab.core.document.DocumentSchemasTest' --rerun` — пересоздать `schemas/*.schema.json` из классов документов и каталога; без переменной тест проверяет актуальность файлов. Схемы проверяют структуру, единицы и диапазоны обычных чисел; границы строковых величин записаны в `x-quantity` в канонических единицах и проверяются ядром. Формат аннотации описан в [schemas/README.md](schemas/README.md).
- `./gradlew :apps:cli:test` — тесты модуля `apps:cli`, включая проверку установленного launcher.
- `./gradlew :apps:server:test` — тесты модуля `apps:server`.
- `UPDATE_OPENAPI=1 ./gradlew :apps:server:test --tests 'resiliencelab.server.lab.OpenApiSpecTest' --rerun` — пересоздать `apps/server/openapi.json` после изменения API; без переменной тест проверяет, что файл совпадает с кодом.
- `./gradlew ktlintCheck` — проверка KtLint для всех JVM-модулей.
- `./gradlew jacocoTestReport` — отчёты покрытия JaCoCo для всех JVM-модулей; пороги покрытия сборка не проверяет.
- `npm ci` — воспроизводимая установка frontend-зависимостей из `package-lock.json`.
- `npm test -- --run` — web unit-тесты.
- `npm run test:coverage` — web unit-тесты с V8-покрытием без порогов; HTML и LCOV сохраняются в `web/coverage/`.
- `npm run build` — type-check и production-сборка web в `web/dist/`.
- `npm run lint` — ESLint для web.
- `npm run api:types` — пересоздать `web/src/api/schema.d.ts` из `apps/server/openapi.json`; `npm run api:check` проверяет, что файл актуален.
- `npm run dev` — Vite dev server с proxy `/api` на `http://127.0.0.1:8080`.
- `npx playwright install chromium` — локальная установка Chromium; в CI браузеры и системные зависимости уже установлены в официальном Docker-образе Playwright.
- `npm run test:e2e` — Playwright запускает изолированные `./gradlew :apps:server:bootRunE2e` из корня (сервер на свежей копии `examples/` в `apps/server/build/e2e-workspace/`, поэтому E2E не меняют файлы репозитория) и Vite в режиме `e2e` с `--strictPort` из `web`, ждёт сообщения об успешном запуске от каждого своего процесса, затем проверяет HTTP health backend, корень web и health через proxy `/api` в `web/playwright.global-setup.ts`, не использует уже запущенные серверы и останавливает browser/server processes после прогона. Trace и screenshot при ошибках сохраняются в `web/test-results/`; CI также загружает `web/playwright-report/`, если он сформирован.

E2E принимает `E2E_BACKEND_PORT` (по умолчанию `8080`) и `E2E_WEB_PORT` (по умолчанию `5173`). Порты должны быть разными целыми числами от 1 до 65535. До запуска серверов Playwright проверяет оба TCP-порта на `127.0.0.1`: если порт недоступен, прогон завершается до тестов с номером порта и именем переменной для его замены. Vite запускается с `--strictPort`, поэтому не переходит на соседний порт. Порт backend передаётся в `bootRunE2e`, proxy `/api` в режиме Vite `e2e` и адрес проверки health; порт web — в Vite, `baseURL` и проверки web. Готовность определяется по stdout запущенных процессов, поэтому чужой HTTP-ответ после предварительной проверки порта не разрешает начало тестов. Обычные `npm run dev` и `bootRun` сохраняют порты `5173` и `8080`, в том числе при заданных переменных E2E.

Пример запуска из `web` на других портах: `E2E_BACKEND_PORT=18080 E2E_WEB_PORT=15173 npm run test:e2e`. Для одновременных прогонов используйте отдельные worktree и разные пары портов: временные рабочие области и отчёты каждого прогона остаются внутри своего worktree.

Проект использует Gradle Wrapper 9.8.2. Workflow `.github/workflows/ci.yml` запускается на `push` только в ветку `main`, на `pull_request` и вручную через `workflow_dispatch`. В нём настроены две независимые job с лимитом 20 минут каждая. `build` на обычном Ubuntu-раннере выполняет `./gradlew --no-daemon clean build`, `npm ci`, lint, проверку сгенерированных типов API (`npm run api:check`), `npm run test:coverage` и production build. `e2e` запускает `npm ci` и `npm run test:e2e -- --reporter=line,html` внутри официального образа `mcr.microsoft.com/playwright:v1.64.1-noble` с готовыми браузерами и системными зависимостями; установки браузеров и apt-пакетов в workflow нет. Обе job используют JDK 25 и Node.js из `web/.nvmrc`, кэши Gradle и npm. При запуске E2E `GRADLE_USER_HOME="$HOME/.gradle"` направляет Gradle в каталог, который кэширует `actions/setup-java` внутри контейнера.

Перед E2E проверяется совпадение версии образа с `@playwright/test` из `web/package-lock.json`; при обновлении Playwright нужно также обновить `jobs.e2e.container.image`, иначе проверка завершится с понятной ошибкой. YAML anchor связывает образ контейнера и значение для проверки. HTML/XML-отчёты JaCoCo `core/build/reports/jacoco/test`, `apps/cli/build/reports/jacoco/test`, `apps/server/build/reports/jacoco/test` и V8-отчёт `web/coverage/` (артефакт `frontend-coverage`) сохраняет job `build`, а `web/test-results/` и `web/playwright-report/` — job `e2e`, в обоих случаях и при ошибке предыдущих шагов, если файлы сформированы. HTML-отчёт Playwright формируется и при успешном прогоне.

### Обновление зависимостей и Docker-образов

Dependabot еженедельно проверяет npm, Gradle, GitHub Actions и Dockerfile в `apps/server` и `web`. Обновления minor/patch объединяются по экосистеме; major приходят отдельными PR. Для `@playwright/test` выделена группа `playwright` для всех типов обновлений.

- В `web/package.json` `@typescript/native` (`npm:typescript@7.0.2`) предоставляет `tsc` для сборки и проверки типов. Alias `typescript` (`npm:@typescript/typescript6@6.0.2`) предоставляет `tsc6` и API TypeScript 6 для инструментов, включая `typescript-eslint`. Фактический компилятор TypeScript 6 точно закреплён отдельно в `overrides["@typescript/old"]` (`npm:typescript@6.0.2`). TypeScript обновляется вручную: `@typescript/native`, alias `typescript`, `overrides["@typescript/old"]` и `web/package-lock.json` меняются в одном PR; версия override совпадает с версией alias.
- При обновлении Node.js меняй `web/.nvmrc` и `FROM node:<версия>-alpine` в `web/Dockerfile` в одном PR, в том числе в PR Dependabot. CI проверяет точное совпадение перед сборкой. Если меняется major, согласуй также `web/package.json` (`engines.node`).
- При обновлении `@playwright/test` обновляй `web/package.json`, `web/package-lock.json` и `jobs.e2e.container.image` в `.github/workflows/ci.yml` в одном PR. Образ должен иметь вид `mcr.microsoft.com/playwright:v<версия @playwright/test>-noble`; существующая CI-проверка блокирует рассинхрон. В PR группы `playwright` образ меняется вручную: [Dependabot для GitHub Actions](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories#github-actions) обновляет ссылки `uses:`, а не `container.image`.
- Плавающий `nginx:alpine` получает новое содержимое при загрузке образа. Без версии или digest Dependabot не создаёт PR на изменение содержимого этого тега.

Параметры `directories`, `groups` и `exclude-patterns` сверены с [документацией Dependabot](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference).

### Локальный Docker Compose

- `docker compose up --build -d` — собрать production-like образы и запустить backend и frontend из корня репозитория.
- Frontend: `http://127.0.0.1:5173`; backend health: `http://127.0.0.1:8080/api/v1/health`. Оба host-порта опубликованы только на loopback (`127.0.0.1`), без configurable LAN access.
- `docker compose down` — остановить и удалить только контейнеры этого Compose-проекта; bind mount, образы и исходники не удаляются.
- Браузер обращается к same-origin `/api`, Nginx передаёт запросы сервису `backend:8080`. Контейнеры работают от non-root пользователей; секреты и named volumes не используются.
- Задания хранятся в памяти процесса: перезапуск backend удаляет их.
- Compose монтирует `${RESILIENCE_LAB_WORKSPACE:-./examples}` в `/workspace` на запись. Документы, `.workspace.lock` и `.results/` сохраняются на хосте; внешние правки видны через `GET /api/v1/workspace/changes`.
- Backend получает UID/GID из `RESILIENCE_LAB_UID` и `RESILIENCE_LAB_GID`, по умолчанию `1000:1000`. На Linux задайте вывод `id -u` и `id -g`, если идентификаторы пользователя отличаются; Docker Desktop на Windows и macOS сопоставляет запись с пользователем хоста сам.
- На Docker Desktop и Colima `.workspace.lock` связывает процессы внутри Linux VM, но не связывает процессы хоста и контейнера. Пока работает Compose, не запускайте на хосте CLI или `./gradlew :apps:server:bootRun` с той же рабочей областью. На native Linux блокировка между хостом и контейнером действует.

### Backend API

Backend использует Spring Boot 4.1.2 и JDK 25. `./gradlew :apps:server:bootRun` запускает локальный API с базовым URL `http://127.0.0.1:8080/api/v1` и рабочей областью `examples/`; другой каталог задаётся переменной `RESILIENCE_LAB_WORKSPACE` или аргументом `--args='--resilience-lab.workspace=<каталог>'`. Прогоны записываются в `<рабочая область>/.results/`, этот каталог не попадает в git. Спецификацию `apps/server/openapi.json` генерирует springdoc. `./gradlew :apps:server:test` запускает тесты backend. Задания хранятся только в памяти процесса (process-local) и не сохраняются между перезапусками; хранятся не более 100 завершённых заданий в порядке завершения FIFO, активные задания никогда не вытесняются. Результаты прогонов этапа 1 остаются в `.results/`.

`DELETE /api/v1/workspace/document?path=` требует `If-Match`: без него возвращает 428 `VERSION_REQUIRED`, при несовпадении — 409 `VERSION_CONFLICT`, для отсутствующего документа — 404, при успехе — 204. `GET /api/v1/workspace/changes?since=` возвращает непрозрачный строковый курсор `<generation>:<sequence>`, признак `reset` и изменения `{ path, kind, version }`; `version: null` означает удаление. Без `since` ответ содержит текущий курсор и пустой список. Process-local журнал хранит 1000 последних изменений документов `*.model.json`, `*.layout.json` и `*.experiment.json` вне скрытых каталогов; записи API попадают туда же. `FileWorkspace` использует `WatchService` с запасным полным сканированием каждую секунду, поэтому внешние изменения видны не позже чем через 5 секунд. `list()` и обходы журнала используют `walkFileTree` с `SKIP_SUBTREE` для скрытых каталогов, включая `.results`; начальный снимок журнала откладывается до первого `changes`. Курсор другого процесса, устаревший или больший текущего даёт `reset: true` и пустой список: клиент перечитывает документы. Некорректные generation и sequence дают 400 `CURSOR_INVALID`.

При принятии задания фиксируются версии модели и эксперимента. Если к началу расчёта документы изменились, задание завершается с `FAILED`; для валидных изменённых документов возвращается диагностика `DOCUMENT_CHANGED`. Результаты не записываются.

`POST /api/v1/validate` принимает необязательный список `drafts` из `{ path, content }`, где `content` имеет форму `DocumentContent`. Черновики подменяют чтение документов только для этой проверки, включая ещё не созданные документы; файлы и версии хранилища не меняются. Пути черновиков канонические, относительно корня рабочей области, без повторов; вид содержимого должен совпадать с суффиксом пути. В ядре этому соответствует `Lab.validate(experimentPath, drafts: Map<String, String>)` с текстом документов. Без черновиков проверка работает по сохранённым файлам.

Web запускает проверку через 500 мс после последней команды; устаревшие ответы отбрасываются. Ошибки блокируют Run, предупреждения не блокируют; ожидание проверки и ошибка связи с API также блокируют запуск с пояснением. Разбираемые значения вне диапазона каталога передаются в черновик для проверки ядром; неразбираемый ввод остаётся в поле под прежней защитой от потери правки.

`Diagnostic.variant` — необязательный идентификатор варианта; `null` означает диагностику модели или общую для всех вариантов. Без сетки одинаковые предупреждения линтера с одним местом в документе модели выдаются один раз с `variant = null`; остальные — отдельно для каждого затронутого варианта. Указатель ведёт на переопределение в эксперименте, если проблемное значение задано там, иначе на параметр модели. Диагностика переопределения сохраняет `variant` и при единственном варианте эксперимента. Ошибки компилятора в переопределениях также содержат `variant`. В экспериментах с сеткой все предупреждения линтера содержат `variant`; одинаковые предупреждения внутри варианта объединяются. Если предупреждение отличается между точками или появляется не во всех точках, текст перечисляет соответствующие идентификаторы `p0`, `p1` и далее. Указатели на переопределения сохраняются отдельно для каждой точки. Web учитывает это поле при показе значков и сообщений у полей; Problems показывает все записи с идентификатором варианта и открывает его страницу по щелчку.

Все вызовы одного `ExperimentExecutor` используют общий пул: задачи активных заданий выдаются по кругу, внутри задания — по вариантам, точкам сетки и повторениям. `Lab.run` принимает необязательный признак `isCancelled: () -> Boolean`; функция должна быть потокобезопасной и быстро возвращать результат. Ожидающий вызов проверяет отмену с интервалом 25 ms. После обнаружения отмены новые задачи задания не запускаются, активные потоки прерываются, модели KSL останавливаются на границе события. Исполнитель ждёт завершения начатых записей: готовые каталоги задач и части сохраняются, манифест получает `complete: false`, сводка не создаётся. Вызов завершается `java.util.concurrent.CancellationException`; лимит `maxRealTimeSeconds` сохраняется. Уже отменённый вызов не создаёт файлов. После последней проверки отмены окончательная запись сводки и манифеста завершается целиком, а прерывание вызывающего потока восстанавливается после записи. Запись частей защищена от прерывания отдельным потоком, поскольку `FileChannel.lock` прерываем.

`Lab.validateResume(runDirectory)` выполняет без изменения артефакта те же проверки, что досчёт, и возвращает манифест. `Lab.resume(runDirectory, isCancelled, onProgress)` повторяет их при запуске и досчитывает незаконченный артефакт на месте: канонический путь, версии приложения/KSL/потоков, хеши документов и метаданные; несовпадения дают `RUN_INCOMPATIBLE` или `RUN_DOCUMENT_CHANGED`, завершённый прогон — `RUN_COMPLETE`. Задача сохраняется только при корректных форматах и SHA-256 всех её файлов в манифесте и индексе. Отсутствующие, лишние и повреждённые файлы задачи удаляются, задача пересчитывается с исходным номером повторения. Сводка пересобирается из итогов, манифест заменяется атомарно; досчитанный артефакт побайтно равен непрерывному. Повторная отмена оставляет `complete: false` без сводки. Параллельные вызовы `resume` для одного `runDirectory` сериализуются в JVM; вызов после публикации получает `RUN_COMPLETE`.

`POST /api/v1/estimate` принимает тело как `POST /validate` и возвращает `ExperimentEstimate` ядра. `POST /api/v1/runs/{id}/resume` создаёт задание досчёта и возвращает 202 с `JobView`; завершённый прогон даёт 409 `RUN_COMPLETE`, изменённые документы — 400 с диагностикой ядра, неизвестный — 404 `RUN_NOT_FOUND`. `GET /api/v1/runs` перечисляет законченные и незаконченные прогоны с полем `complete`. Сводка незаконченного прогона даёт 404 `RUN_INCOMPLETE`; манифест и ряды готовых задач доступны.

`Lab.estimate(experimentPath, drafts, workers)` возвращает `ExperimentEstimate` с полями `tasks`, `expectedEvents`, `expectedRows`, `workers`, `estimatedSeconds`, `estimatedUncompressedBytes`, `estimatedArtifactBytes`, `estimatedParts` и `warnings`, не запуская KSL и не создавая `.results/`. События и время оцениваются по IR и формуле S1 с настроенным числом попыток; объём — 512 байт на узел и окно до сжатия, коэффициент gzip 0,25 и части до 4 МиБ. Экстраполяция S1 отмечается только при числе сервисов больше 5000: ускорение ограничено значением для 8 потоков (3,184), поэтому увеличение числа потоков сверх 8 не уменьшает оценку времени относительно 8 потоков и не вызывает калибровочного предупреждения. Бюджет ADR 0008 отмечается при превышении кэша UI 64 МиБ. Приёмочный допуск для `retry-storm` — 8× от фактического времени из-за переноса коэффициентов на другое оборудование и модель меньше 50 сервисов.

Сервер запускает каждый вызов `Lab.run` в отдельном виртуальном потоке JDK; расчётные потоки остаются в общем пуле ядра. `POST /api/v1/jobs/{id}/cancel` возвращает 202 с `JobView`: задание в очереди сразу получает `CANCELLED`, выполняющееся — `cancelRequested: true` и статус `CANCELLED` после остановки ядра и окончания записей. Повторная отмена возвращает текущее состояние с кодом 202; для завершённого или ошибочного задания — 409 `JOB_FINISHED`, для неизвестного — 404 `JOB_NOT_FOUND`. Отмена до начала расчёта не создаёт файлов. Если запрос пришёл во время окончательной записи уже готового результата, прогон завершается целиком со статусом `COMPLETED`.

`execution.window` — длительность с единицами, по умолчанию `measurement / 100`. Ряды покрывают `[0, warmup + measurement)` по времени событий, включая прогрев и исключая run-out. Итоги повторений используют когорту измеряемого интервала с её run-out. Файлы задач лежат в `series/<вариант>/<точка>/rep-<n>/`: `replication.json`, индекс и gzip-части не больше 4 МиБ до сжатия. Сводка строится только из записанных итогов повторений. Формат манифеста и сводки — версия 4; неподдерживаемые версии требуют нового запуска. Подробности: [формат артефакта](docs/results-format.md).

Необязательный `grid` эксперимента содержит до двух осей `{ path, values }` с непустыми списками значений в единицах документа. Отсутствующий `grid` и пустой список означают одну точку `p0` без координат. Значения точки применяются поверх переопределений варианта; пути осей не должны совпадать или пересекаться как объект и его поле. Первая ось внешняя, идентификаторы точек — `p0`, `p1` и далее. Потоки случайных чисел общие для одинаковых путей блоков во всех точках. Манифест и сводка сохраняют оси в верхнеуровневом поле `grid`: порядок осей и значений совпадает с документом, включая повторы; без сетки записывается `[]`. Манифест хранит координаты в `series.points`; сводка варианта содержит список `points` с координатами и метриками вместо общего `aggregate`. Summary в web показывает строку на каждую пару «вариант, точка»; вкладка Map относится к T4.

В web поле `Series window` в `Experiment settings (shared)` задаёт `execution.window` в единицах из каталога. Очистка удаляет поле из документа; подсказка пересчитывает `measurement / 100` без записи значения по умолчанию. Правка входит в undo/redo, диагностика `/execution/window` видна у поля.

`GET /api/v1/runs/{id}/series/{variant}/{cell}/{rep}` возвращает типизированный `SeriesIndex` готовой задачи любого прогона, включая незаконченный; `cell` имеет вид `p0`, `p1` и далее. `GET /api/v1/runs/{id}/series/{variant}/{cell}/{rep}/{part}` отдаёт исходные байты `part-<part>.json.gz`: `Content-Type: application/json`, `Content-Encoding: gzip`, сильный `ETag` из SHA-256 части в индексе и `Cache-Control: max-age=31536000, public, immutable`. Браузер распаковывает тело сам; схема ответа в OpenAPI описывает распакованный `SeriesPart`. Номера повторений и частей — целые от 0 до 2147483647 без ведущих нулей. Неверный формат параметров даёт 400 `SERIES_PATH`, неизвестный объект или отсутствующий файл — 404 `SERIES_NOT_FOUND`. Читаются только обычные файлы внутри каталога прогона; часть должна быть перечислена в индексе. Формат содержимого описан в [docs/results-format.md](docs/results-format.md).

При остановке контекста Spring сначала вызывает `JobService.close()`: задания в очереди сразу получают `CANCELLED`, выполняющиеся — `cancelRequested: true`. Новые отправки после начала остановки тоже получают `CANCELLED` без запуска. Затем закрывается `labJobExecutor`, ожидая остановки расчётов и завершения записей, и только после него — общий пул ядра.

### CLI

Повторный SIGINT после запроса отмены принудительно завершает CLI с кодом 130, не дожидаясь записей. Полнота артефакта и наличие манифеста в этом случае не гарантируются.

- `./gradlew :apps:cli:run --args="validate examples/retry-storm/retry-storm.experiment.json"` — проверить пример эксперимента.
- `./gradlew :apps:cli:run --args="estimate examples/retry-storm/retry-storm.experiment.json"` — напечатать оценку стоимости в JSON.
- `./gradlew :apps:cli:run --args="run examples/retry-storm/retry-storm.experiment.json"` — выполнить пример; `--workers N` перед путём ограничивает число потоков расчёта.
- `./gradlew :apps:cli:run --args="resume <прогон>"` — досчитать незаконченный прогон по идентификатору или пути к его каталогу.
- `./gradlew :apps:cli:run --args="catalog"` — напечатать каталог типов.
- `./gradlew :apps:cli:run --args="schema model"` — напечатать JSON-схему модели; также доступны `layout` и `experiment`.
- `./gradlew :apps:cli:installDist` — собрать установленный launcher в `apps/cli/build/install/cli/bin/` (`cli` для Linux/macOS, `cli.bat` для Windows).

Рабочая область CLI — текущий каталог; путь к эксперименту или каталогу прогона должен вести внутрь неё. `run` записывает артефакт в `.results/<эксперимент>/<прогон>/`; `resume` досчитывает существующий на месте. Обе команды печатают в stdout каталог прогона и по строке сводки на пару «вариант, точка» с координатами, а ход выполнения — в stderr. `estimate` печатает `ExperimentEstimate` одной JSON-строкой в stdout, `validate` печатает результат в stderr. `catalog` печатает в stdout тот же JSON, что `GET /api/v1/catalog`; `schema <model|layout|experiment>` — текст соответствующего `schemas/*.schema.json` из генератора. Эти две команды не открывают рабочую область. Код выхода 2 означает ошибку использования или проверки, 1 — сбой расчёта, 130 — отмену. Ctrl+C и SIGTERM передают отмену в `Lab.run` и `Lab.resume`; CLI ждёт остановки и записи незаконченного артефакта, затем печатает его путь в stderr. Если отмена произошла до создания артефакта, CLI сообщает об этом без пути. Запуск через Gradle добавляет в вывод служебные сообщения; для разбора stdout запускайте установленный launcher.

`Lab.validate`, `POST /validate` и CLI `validate` возвращают предупреждения линтера: `LINT_TIMEOUT_BUDGET`, `LINT_RETRY_AMPLIFICATION`, `LINT_HANDLERS_LITTLE`, `LINT_DEADLINE_BUDGET`. Предупреждения не блокируют запуск; CLI `validate` при отсутствии ошибок завершается с кодом 0. На `examples/retry-storm/` у `baseline` два предупреждения: timeout 80 ms меньше downstream-бюджета 189 ms, deadline 250 ms меньше суммы timeout 420 ms. У `no-retries` предупреждений нет.

## Устойчивые решения

- Все JVM-модули используют JDK 25.
- Ядро на Kotlin/JVM с использованием KSL/KSLCore.
- Backend на Spring Boot 4.1.2, без добавления второго web-фреймворка.
- Приложение распространяется под GPLv3.
- Браузерный UI отделён от вычислительного ядра; симуляция запускается и без UI.
- Собственный универсальный дискретно-событийный движок не разрабатывается.
- Модели MiSim используются как справочная семантика блоков, отображаемая на KSL, а не как переносимый DESMO-J код или готовый тестовый оракул.
- Эксперименты воспроизводятся по конфигурации и случайным seed/stream; независимые повторения обязательны.
- В `MetricSummary` поля `mean`, `min` и `max` описывают наблюдаемые значения метрики; доверительные границы Стьюдента `ci95Low`/`ci95High` не обрезаются до физического диапазона и могут выходить за `[0,1]`, в том числе для `successRate`.
- Квантили задержек используют профиль `ddsketch-bitwise6-rational-v1` библиотеки `sketches-java:0.8.3`, сохраняют интерполяцию KSL и допускают ошибку представления до 0,78125 % в проверенном диапазоне `0.001–60000 ms` с учётом округления binary64. Среднее считается из отдельных counts и сумм. Погрешность скетча не заменяет доверительный интервал между повторениями.
- В репозиторий не помещаются секреты, производственные адреса, клиентские идентификаторы или реальные конфиденциальные данные.

## Границы MVP

Первая версия моделирует линейную цепочку синхронных вызовов с ограниченными обработчиками и очередями, timeout, retry, backoff, jitter и общим deadline. Первый законченный эксперимент исследует деградацию сервиса и retry amplification.

Не расширять MVP до произвольных графов, брокеров, баз данных или автоматической калибровки без отдельного согласования. Точная семантика попыток, orphaned work, измерений и метрик определяется проектным дизайном.

## Обязательное развитие после MVP

Предметная модель должна развиваться до асинхронных взаимодействий, gRPC, RabbitMQ/Kafka, баз данных, Redis и других компонентов реальных программных архитектур. После MVP также обязателен универсальный Graph UI для рисования архитектурных схем реальных систем с произвольными топологиями и новыми типами узлов и связей. Порядок и глубина моделирования согласовываются отдельными этапами. Ограничения MVP не должны становиться архитектурным запретом на такие расширения.

## Соглашения по коду

- Kotlin-код размещать в пакете `resiliencelab` и его подпакетах.
- В тестах использовать AssertJ для утверждений.
- Публичные API и нетривиальные контракты документировать с помощью KDoc.
- Типы API сервера — `@Serializable` data-классы и enum без `@SerialName`, `@Transient`, собственных сериализаторов и полиморфизма; ответы содержат все поля, отсутствующее значение — `null`; имена методов контроллеров уникальны. Схему OpenAPI springdoc строит по свойствам Kotlin, JSON пишет kotlinx, и тест `OpenApiConformance` сверяет ответы со схемой.

## Правила работы

- Сначала проверять проектный дизайн и фактические manifest/build-файлы.
- Не добавлять зависимости по предположению о доступности; использовать совместимые версии и идиомы выбранного toolchain.
- Сохранять сценарии версионируемыми и воспроизводимыми.
- При изменении поведения обновлять проектный дизайн, устаревшие комментарии и этот файл, если затронуты записанные здесь правила.

## Работа по issue

`AGENTS.md` — единственный источник правил для агентов. В шаблонах и других файлах ссылайся на него, не копируй правила.

Репозиторий публичный. Не включай в файлы, сообщения коммитов и PR секреты, производственные данные, реальные клиентские идентификаторы, внутренние названия компаний и систем. Для примеров используй вымышленные данные.

1. Прочитай issue целиком, комментарии, этот файл и связанные документы. Сверь постановку с проектным дизайном и продуктовым видением по ссылкам выше; уточняй только то, чего эти источники не объясняют.
2. Проверь `git status`; не перезаписывай чужие незакоммиченные изменения. Выполни `git fetch origin` и создай отдельную ветку от актуального `main`: `git switch -c <имя-ветки> origin/main`. Не работай в `main` или ветке другой задачи.
3. Меняй только то, что нужно для issue. Сторонние ошибки и технический долг перечисли в PR; не исправляй их в той же задаче.
4. Проверь изменения по затронутым областям, как указано ниже. Создавай коммиты в стиле Conventional Commits на английском, например `docs: add agent task templates`.
   В коммитах с участием Codex сохраняй автора-человека и добавляй трейлер `Co-authored-by: Codex <codex@openai.com>`. При squash сохраняй этот трейлер в итоговом сообщении коммита.
5. Перед PR снова выполни `git fetch origin` и `git rebase origin/main`, сохранив актуальные изменения `main`. Если после rebase изменился результат работы или были конфликты, повтори соответствующие проверки.
6. Отправь ветку командой `git push -u origin HEAD` и открой PR в `main`: `gh pr create --base main`. В описании укажи `Closes #N`, заменив `N` номером issue. Самостоятельно не мержи PR.

Перед PR проверь конечное состояние ветки:

- Всегда: `git diff --check origin/main` и просмотр diff относительно `origin/main`, чтобы исключить посторонние изменения.
- JVM-код, зависимости или сборка JVM-модулей: `./gradlew clean build` из корня. Команда включает тесты, KtLint и отчёты покрытия.
- Web-код, зависимости или сборка web: из `web` выполни `npm ci`, `npm run lint`, `npm test -- --run` и `npm run build`.
- Взаимодействие UI и API, пользовательские сценарии, E2E-тесты или их запуск: из `web` выполни `npm run test:e2e`. Подготовка окружения и установка Chromium описаны в разделе стандартных команд выше.
- Только документация или шаблоны: проверь ссылки, Markdown и YAML-заголовок шаблона issue. Сборка приложения для таких изменений не требуется.

В описании PR объясни, что изменено и зачем; перечисли команды проверок и их результаты, а также то, что проверить не удалось, с причиной. Отдельно укажи найденное попутно или напиши, что таких находок нет. Не называй проверку пройденной, если её результат неизвестен.
