# AGENTS.md

Правила работы агентов в репозитории Resilience Lab: что за проект, какие команды запускать, какие границы соблюдать и как оформлять работу. Поведение продукта здесь не описывается — оно в документах из раздела «Где что описано».

Правила для отдельных частей лежат рядом с кодом и дополняют этот файл: [web/AGENTS.md](web/AGENTS.md) — frontend, E2E и зависимости web; [apps/server/AGENTS.md](apps/server/AGENTS.md) — backend и контракт API. При работе в этих каталогах читай и их.

## Проект

Лаборатория отказоустойчивости: моделирует цепочки синхронных вызовов сервисов и показывает, как timeout, retry и deadline влияют на деградацию. Модули Gradle:

- `core` — Kotlin/JVM на KSL: каталог типов, документы рабочей области, компилятор, симуляция, исполнение, артефакты прогонов, фасад `Lab`;
- `apps:cli` — CLI поверх `Lab`;
- `apps:server` — Spring Boot API поверх `Lab`;
- `web` — React/Vite SPA, клиент API.

Пример рабочей области — `examples/retry-storm/`.

## Команды

Gradle — из корня репозитория, JDK 25 (`jvmToolchain(25)`), Gradle Wrapper 9.8.2. Команды web — в [web/AGENTS.md](web/AGENTS.md).

- `./gradlew clean build` — полная сборка: все JVM-тесты, KtLint, отчёты JaCoCo.
- `./gradlew test`, `./gradlew :core:test`, `./gradlew :apps:cli:test`, `./gradlew :apps:server:test` — тесты всех или одного модуля.
- `./gradlew ktlintCheck` — KtLint; `./gradlew jacocoTestReport` — отчёты покрытия без порогов.
- `UPDATE_SCHEMAS=1 ./gradlew :core:test --tests 'resiliencelab.core.document.DocumentSchemasTest' --rerun` — пересоздать `schemas/*.schema.json`; без переменной тест проверяет актуальность. Формат аннотаций — [schemas/README.md](schemas/README.md).
- `UPDATE_OPENAPI=1 ./gradlew :apps:server:test --tests 'resiliencelab.server.lab.OpenApiSpecTest' --rerun` — пересоздать `apps/server/openapi.json` после изменения API.
- `UPDATE_SERIES_GOLDEN=1 ./gradlew :core:test --tests 'resiliencelab.core.results.WebSeriesGoldenTest' --rerun` — пересоздать эталон рядов web `web/src/results/series/fixtures/retry-storm-baseline-rep-0.json`. Без переменной тест не запускает пример, а проверяет закоммиченную часть и биты квантилей: суммы `sumMs` между платформами расходятся в последних битах.
- `./gradlew :apps:server:bootRun` — локальный API на `http://127.0.0.1:8080/api/v1`, рабочая область `examples/`; другой каталог — `RESILIENCE_LAB_WORKSPACE=<каталог>`. Прогоны пишутся в `<рабочая область>/.results/`, он в `.gitignore`.
- `./gradlew :apps:cli:installDist` — установленный CLI в `apps/cli/build/install/cli/bin/`; рабочая область CLI — текущий каталог. Для разбора stdout запускай установленный launcher, а не `:apps:cli:run`: Gradle добавляет в вывод служебные сообщения.
- `docker compose up --build -d` / `docker compose down` — production-like запуск, подробности в README. На Docker Desktop и Colima `.workspace.lock` не связывает процессы хоста и контейнера: пока работает Compose, не запускай на хосте CLI или `bootRun` с той же рабочей областью.

CI (`.github/workflows/ci.yml`) запускается на push в `main`, на pull request и вручную. Job `build` выполняет `./gradlew --no-daemon clean build`, lint, `npm run api:check`, `npm run test:coverage` и production build web; job `e2e` — `npm run test:e2e` в образе Playwright. Отчёты сохраняются артефактами и при падении. Pull request, который меняет только `docs/` и файлы `*.md`, пропускает `build` и `e2e`: это решает job `changes`, а пропущенный job засчитывается обязательной проверкой. Push в `main` и ручной запуск проверяют всё.

## Устойчивые решения

- JDK 25 для всех JVM-модулей; ядро на Kotlin/JVM с KSL/KSLCore; собственный дискретно-событийный движок не пишется.
- Backend на Spring Boot 4.1.2, без второго web-фреймворка. Браузерный UI отделён от ядра: симуляция запускается и без UI.
- Лицензия GPLv3.
- Модели MiSim — справочная семантика блоков на KSL, а не переносимый код DESMO-J и не тестовый оракул.
- Эксперименты воспроизводятся по конфигурации и seed; независимые повторения обязательны. На одной платформе артефакт побайтно повторяется при любом числе потоков.
- Доверительные границы Стьюдента `ci95Low`/`ci95High` не обрезаются до физического диапазона. Квантили задержек — профиль скетча `ddsketch-bitwise6-rational-v1`; p99 не усредняется.
- До появления внешних пользователей обратная совместимость форматов не поддерживается. Смена формата документа или артефакта повышает его `schemaVersion`, переписывает `examples/**` и тестовые фикстуры под новую версию; миграций и совместимости с прежними версиями нет. Документ или прогон прежней версии получает понятную ошибку о версии, а не непонятный отказ (решение 2026-10-30).

## Границы

- Модель этапа 1 — линейная цепочка синхронных вызовов с ограниченными обработчиками и очередями, timeout, retry, backoff, jitter и общим deadline. Произвольные графы, брокеры, базы данных и автоматическая калибровка — только по отдельному согласованию.
- Развитие до асинхронных взаимодействий, gRPC, RabbitMQ/Kafka, баз данных, Redis и универсального Graph UI обязательно на следующих этапах. Ограничения этапа 1 не должны становиться архитектурным запретом на такие расширения.
- Новый код следует принятым ADR; расхождение с ADR или дизайном обсуждается в issue до реализации.
- Новые зависимости — только с обоснованием в issue, без предположений о доступности; версии и идиомы — совместимые с выбранным toolchain.
- Репозиторий публичный. В файлы, коммиты и PR не попадают секреты, производственные адреса и данные, реальные клиентские идентификаторы, внутренние названия компаний и систем. Для примеров — вымышленные данные.
- Сценарии и документы остаются версионируемыми и воспроизводимыми.

## Соглашения по коду

- Kotlin — в пакете `resiliencelab` и его подпакетах.
- В тестах — AssertJ.
- Публичные API и нетривиальные контракты документируются KDoc.

## Где документировать изменения

- Поведение и контракты продукта — в дизайне этапа 1 и формате артефакта; модельная семантика — в проектном дизайне MVP; решения — новым ADR; пользовательский запуск — в README. Обновляй их и устаревшие комментарии в коде вместе с изменением поведения.
- `AGENTS.md` (корневой и вложенные) меняется только вместе с командами, toolchain, CI или правилами работы. Возможности и поведение продукта сюда не записываются.
- `AGENTS.md` — единственный источник правил для агентов. В шаблонах и других файлах ссылайся на него, не копируй правила.

## Работа по issue

1. Прочитай issue целиком, комментарии, этот файл, вложенный `AGENTS.md` затронутой части и связанные документы. Сверь постановку с дизайном этапа 1 и продуктовым видением; уточняй только то, чего эти источники не объясняют.
2. Проверь `git status`; не перезаписывай чужие незакоммиченные изменения. Выполни `git fetch origin` и создай отдельную ветку от актуального `main`: `git switch -c <имя-ветки> origin/main`. Не работай в `main` или ветке другой задачи.
3. Меняй только то, что нужно для issue. Сторонние ошибки и технический долг перечисли в PR; не исправляй их в той же задаче. Свои рабочие планы и заметки к задаче не коммить: `docs/superpowers/plans/` — только для планов-контрактов дорожек, которые выдаются в issues. Если инструмент сохраняет план в этот каталог, исключи файл из коммита.
4. Проверь изменения по затронутым областям, как указано ниже. Создавай коммиты в стиле Conventional Commits на английском, например `docs: add agent task templates`.
   В коммитах с участием Codex сохраняй автора-человека и добавляй трейлер `Co-authored-by: Codex <codex@openai.com>`. При squash сохраняй этот трейлер в итоговом сообщении коммита.
5. Перед PR снова выполни `git fetch origin` и `git rebase origin/main`, сохранив актуальные изменения `main`. Если после rebase изменился результат работы или были конфликты, повтори соответствующие проверки.
6. Отправь ветку командой `git push -u origin HEAD` и открой PR в `main`. Описание запиши в файл и передай `gh pr create --base main --body-file <файл>`: в строке оболочки обратные кавычки выполняются как команды и портят текст. В описании укажи `Closes #N`, заменив `N` номером issue. Самостоятельно не мержи PR.

Перед PR проверь конечное состояние ветки:

- Всегда: `git diff --check origin/main` и просмотр diff относительно `origin/main`, чтобы исключить посторонние изменения.
- JVM-код, зависимости или сборка JVM-модулей: `./gradlew clean build` из корня.
- Web-код, зависимости или сборка web: проверки из [web/AGENTS.md](web/AGENTS.md).
- Взаимодействие UI и API, пользовательские сценарии, E2E-тесты или их запуск: затронутые сценарии E2E из `web` по правилу [web/AGENTS.md](web/AGENTS.md#e2e); полный набор выполняет CI.
- Только документация или шаблоны: проверь ссылки, Markdown и YAML-заголовок шаблона issue. Сборка приложения не требуется.

В описании PR объясни, что изменено и зачем; перечисли команды проверок и их результаты, а также то, что проверить не удалось, с причиной. Отдельно укажи найденное попутно или напиши, что таких находок нет. Не называй проверку пройденной, если её результат неизвестен.

Скриншоты и другие иллюстрации к PR не коммить в ветку задачи и в `main`. Клади их в служебную ветку `pr-assets`, у которой нет общей истории с `main`, в каталог `issue-<N>/`, и ссылайся на них из описания PR: `https://raw.githubusercontent.com/ChernetsovNG/resilience-lab/pr-assets/issue-<N>/<файл>.png`. Ветку `pr-assets` не мержи. Если её ещё нет, создай в отдельном worktree командой `git switch --orphan pr-assets`.
