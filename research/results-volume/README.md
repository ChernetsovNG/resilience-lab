# Прототип исследования объёма результатов

Этот каталог относится к [issue #48](https://github.com/ChernetsovNG/resilience-lab/issues/48). Он не входит в основную сборку и не меняет симуляцию. Правила работы с репозиторием: [AGENTS.md](../../AGENTS.md). Итоги и ограничения: [исследование](../../docs/research/2026-10-27-results-volume.md).

## Воспроизведение

Нужны JDK 25, Python 3.11 или новее и Node.js из `web/.nvmrc`. Команды из корня репозитория:

```sh
./gradlew -p research/results-volume installDist --no-daemon
cd research/results-volume
fnm exec --using "$(cat ../../web/.nvmrc)" npm ci
fnm exec --using "$(cat ../../web/.nvmrc)" npx playwright install chromium
python3 measure.py all
fnm exec --using "$(cat ../../web/.nvmrc)" node browser.mjs build/browser-input.json build/browser-results.json
python3 summarize.py
```

Если Node.js уже выбран через `nvm use` или `fnm use`, префикс `fnm exec` не нужен. Chromium должен запускаться на машине; контейнеру могут понадобиться системные зависимости Playwright.

Все данные и промежуточные результаты находятся в игнорируемом `build/`. Запуск записывает примерно 5 GB файлов; предусмотрите запас свободного места. Повторный запуск заменяет только файлы с теми же именами внутри выходных каталогов прототипа. `summarize.py` проверяет фактические размеры, хеши и набор измерений, затем обновляет небольшие публикуемые `results.json` и `grid-sizes.csv`.

Отдельные фазы: `python3 measure.py single`, `grid`, `noise`. Сначала нужны `single`; после последней фазы пересоздаётся `build/browser-input.json`. Для собственного набора:

```sh
build/install/results-volume/bin/results-volume build/custom series parquet 5000 600 42
```

Аргументы: каталог, `series|series-noise|trace`, `json|json-gzip|csv|arrow|parquet`, число блоков, число окон, seed, необязательное число файлов. Аргумент числа файлов увеличивает seed; stdout содержит JSONL. Режим `250 grid` добавляет два параметра сетки: множители интенсивности и задержки от 1 до 2 с шагом 0,25; на ячейку приходится десять seed. Длительность и интенсивность синтетической трассы фиксированы в коде, аргумент окон не меняет их.

## Данные и проверки

`series`: одна строка на узел и окно, два `int32` и десять `float64`. Порядок: узел, затем окно. Есть различия между узлами, временной профиль, интервал деградации и псевдослучайная составляющая. Значения заранее округлены до 0,001 во всех форматах; это свойство синтетического набора, а не потеря точности при сериализации. `series-noise` сохраняет ту же схему, но использует независимые полноточные числа без физического смысла, чтобы проверить влияние энтропии на сжатие. Ни один набор не является результатом KSL.

`trace`: 600 000 исходных запросов за 600 секунд при 1000 запросах/с. Seeded hash выбирает ожидаемо 1% корневых запросов; фактическое число записывается. На запрос приходится до десяти узлов, одна либо две попытки на узел и четыре события на попытку. Идентификаторы и последовательность сохраняются. Это числовая нагрузка для сериализации, не корректная модель выполнения синхронных вызовов. Реальная трасса потребует собственного согласованного контракта.

Все поля канонического потока представлены как little-endian `float64`, включая целочисленные ключи, в порядке строк и колонок. JVM считает SHA-256 отдельным проходом вне таймера записи. Chromium независимо читает файл, проверяет имена колонок, число строк и значений, затем считает тот же SHA-256 вне таймера чтения. Потоковый путь Arrow и срез Parquet проверяются отдельным повторным чтением с SHA-256 вне публикуемого таймера. Для канонической проверки Chromium временно выделяет дополнительный буфер до 288 MB; это не оценка памяти будущего UI. Контрольная сумма внутри таймера зависит от каждого значения и препятствует измерению только метаданных ленивого reader. Null, NaN, Infinity и отрицательный ноль в набор не входят.

## Что измеряется

- JVM: генерация, подсчёт контрольной суммы, кодирование и закрытие writer. Один прогрев на 5000 строк на процесс, три процесса для каждого основного набора. Порядок форматов между раундами меняется. Канонический SHA-256 и SHA-256 файла не входят в `writeMs`. `fsync` не выполняется, поэтому результат не характеризует запись с гарантией сохранности после отключения питания.
- Chromium: загрузка с loopback, затем декодирование и полный обход значений. Первая загрузка страницы записывается отдельно; после двух прогревов следуют три измерения. JSON/gzip распаковывается явно через `DecompressionStream`: HTTP не выставляет `Content-Encoding`. Arrow обходится через типизированные массивы; Parquet — по колонкам через `onChunk`, без транспонирования всех строк в объекты.
- Все HTTP-ответы имеют `Cache-Control: no-store`. Файловый кэш ОС не очищается; loopback не заменяет измерения удалённой сети. Загрузка библиотек, построение графика и отрисовка UI в таймер не входят. Пиковая память не измеряется.
- Дополнительно: Arrow читается непосредственно из `response.body` пакетами. Parquet читает первые 30 000 строк и четыре колонки через реальные ответы `206`; количество запросов и переданных байтов сохраняется.
- Полная сетка для 50 блоков: 25 сочетаний двух множителей × 10 повторений с различными seed; каждый файл содержит 30 000 строк. Для 500/5000 блоков целые сетки не генерируются. Их объём в отчёте — экстраполяция, а не замер.
- CSV reader намеренно рассчитан только на числовые строки этого набора. Это не реализация общего RFC 4180.

Прототип запускает JVM с `-Xmx1g`; Arrow allocator ограничен 256 MiB, batch — 8192 строки. Parquet: Snappy, row group 16 MiB, page 64 KiB. Для Arrow/Netty и Snappy на этом JDK указаны `--add-opens=java.base/java.nio=ALL-UNNAMED`, `--sun-misc-unsafe-memory-access=allow` и `--enable-native-access=ALL-UNNAMED`. Эти параметры относятся к отдельному прототипу.
